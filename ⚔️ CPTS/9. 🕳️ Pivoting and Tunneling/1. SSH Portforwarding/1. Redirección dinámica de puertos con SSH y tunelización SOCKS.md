
## 1. Conceptos fundamentales

El **port forwarding** permite redirigir conexiones de un puerto a otro. Combinado con SSH o SOCKS, permite acceder a servicios de otras redes a través de un host intermedio.

El **pivoting** consiste en utilizar un equipo al que tenemos acceso para alcanzar otros sistemas o redes que no son accesibles directamente desde nuestra máquina.

### Tipos de redirección SSH

|Tipo|Opción SSH|Función|
|---|---|---|
|Redirección local|`-L`|Expone localmente un servicio accesible desde el servidor SSH.|
|Redirección dinámica|`-D`|Crea un proxy SOCKS local para alcanzar distintos destinos a través del servidor SSH.|
|Redirección remota|`-R`|Expone en el servidor SSH un puerto que redirige conexiones hacia un servicio accesible desde el cliente.|

En esta sección nos centramos en la **redirección local (**`**-L**`**) y dinámica (**`**-D**`**)**.

## 2. Redirección local de puertos con SSH

### 2.1. Escenario

Tenemos una máquina atacante y un servidor Ubuntu comprometido al que podemos conectarnos mediante SSH.

El servidor Ubuntu tiene dos interfaces de red:

- `ens192`: conectada a la red accesible desde la máquina atacante.
    
- `ens224`: conectada a una red interna.
    

Queremos acceder a un servicio MySQL que escucha en el puerto `3306` del propio servidor Ubuntu, pero no podemos acceder directamente a ese puerto desde nuestra máquina.

### 2.2. Enumerar los puertos del servidor

```
nmap -sT -p22,3306 <IP_SERVIDOR>
```

Ejemplo:

```
nmap -sT -p22,3306 10.129.202.64
```

Resultado del laboratorio:

```
PORT     STATE  SERVICE
22/tcp   open   ssh
3306/tcp closed mysql
```

El puerto SSH está abierto, pero MySQL no es accesible directamente desde la máquina atacante.

### 2.3. Crear una redirección local

```
ssh -L 1234:localhost:3306 ubuntu@<IP_SERVIDOR>
```

Ejemplo:

```
ssh -L 1234:localhost:3306 ubuntu@10.129.202.64
```

**Sintaxis:**

```
-L <PUERTO_LOCAL>:<DESTINO>:<PUERTO_DESTINO>
```

En este caso:

- `1234`: puerto que escucha localmente en la máquina atacante.
    
- `localhost`: destino interpretado desde el servidor SSH.
    
- `3306`: puerto MySQL del servidor Ubuntu.
    

Una vez establecida la conexión SSH, podemos acceder al servicio MySQL mediante el puerto local `1234`.

### 2.4. Verificar la redirección

**Con Netstat:**

```
netstat -antp | grep 1234
```

Esperamos encontrar un socket escuchando en el puerto local:

```
127.0.0.1:1234    LISTEN    ssh
```

**Con Nmap:**

```
nmap -v -sV -p1234 localhost
```

Si la redirección funciona, Nmap podrá identificar el servicio MySQL a través del puerto local.

### 2.5. Redirigir varios puertos

Podemos crear varias redirecciones locales en una misma conexión SSH:

```
ssh -L 1234:localhost:3306 -L 8080:localhost:80 ubuntu@<IP_SERVIDOR>
```

Esto permite acceder a:

|Puerto local|Destino desde el servidor SSH|
|---|---|
|`1234`|`localhost:3306` — MySQL|
|`8080`|`localhost:80` — servidor web|

**Idea clave:** con `-L`, los servicios se consumen desde nuestra máquina a través de puertos locales, aunque el servicio de destino no sea accesible directamente desde ella.

## 3. Identificar redes internas para pivotar

Una vez dentro del servidor comprometido, debemos identificar las interfaces de red y las subredes a las que tiene acceso.

### 3.1. Enumerar las interfaces

```
ifconfig
```

También podemos utilizar:

```
ip addr
```

En el escenario del módulo encontramos:

|Interfaz|Dirección IP|Función|
|---|---|---|
|`ens192`|`10.129.202.64`|Conexión con la red accesible desde el atacante.|
|`ens224`|`172.16.5.129`|Conexión con la red interna.|
|`lo`|`127.0.0.1`|Interfaz de loopback.|

La interfaz `ens224` revela que el servidor Ubuntu también está conectado a la red interna `172.16.5.0/23`.

La máquina atacante no tiene una ruta directa hacia esa subred. Por tanto, necesitamos utilizar el servidor Ubuntu como pivote.

## 4. Redirección dinámica de puertos con SSH

### 4.1. ¿Qué es un proxy SOCKS?

Un proxy SOCKS permite que una aplicación envíe conexiones a través de un intermediario que alcanza los destinos en su nombre.

En este escenario, SSH crea un proxy SOCKS local y transporta las conexiones a través del servidor Ubuntu, que puede acceder a la red interna.

Esto permite utilizar herramientas locales para conectarnos a servicios de otros sistemas sin disponer de conectividad directa hacia ellos.

### 4.2. SOCKS4 frente a SOCKS5

|Característica|SOCKS4|SOCKS5|
|---|---|---|
|Autenticación del proxy|No la proporciona|Puede admitir autenticación|
|Tráfico TCP|Sí|Sí|
|Tráfico UDP|No|Sí|

### 4.3. Crear el túnel SOCKS con SSH

```
ssh -D 9050 ubuntu@<IP_SERVIDOR>
```

Ejemplo:

```
ssh -D 9050 ubuntu@10.129.202.64
```

El argumento `-D` crea un proxy dinámico local en el puerto `9050`.

El flujo de tráfico es:

1. Una herramienta de la máquina atacante inicia una conexión.
    
2. La herramienta envía el tráfico al proxy SOCKS local.
    
3. El cliente SSH transporta ese tráfico a través de la conexión SSH.
    
4. El servidor Ubuntu establece la conexión hacia el destino interno.
    
5. Las respuestas regresan por el túnel SSH.
    

**Importante:** `-D` crea un proxy SOCKS; no crea automáticamente una ruta de red convencional hacia toda la subred interna.

## 5. Configurar Proxychains

`Proxychains` permite dirigir las conexiones TCP de determinadas aplicaciones a través de un proxy, como el SOCKS creado mediante SSH.

### 5.1. Editar la configuración

El archivo utilizado en el módulo es:

```
/etc/proxychains.conf
```

Añadimos o verificamos una entrada como esta al final del archivo:

```
socks4 127.0.0.1 9050
```

Esta configuración corresponde al ejemplo del módulo, que utiliza SOCKS4 sobre el puerto local `9050`.

Si el proxy configurado es SOCKS5, debe utilizarse el tipo `socks5` correspondiente.

### 5.2. Ejecutar Nmap a través del proxy

Para realizar un descubrimiento de hosts en un rango interno:

```
proxychains nmap -v -sn 172.16.5.1-200
```

Para examinar un host concreto:

```
proxychains nmap -v -Pn -sT 172.16.5.19
```

Parámetros importantes:

- `proxychains`: dirige las conexiones compatibles a través del proxy configurado.
    
- `-v`: muestra información detallada.
    
- `-sn`: realiza descubrimiento de hosts sin escanear puertos.
    
- `-Pn`: omite el descubrimiento previo de hosts.
    
- `-sT`: realiza un escaneo mediante conexiones TCP completas.
    

El ejemplo del módulo identifica varios puertos abiertos en `172.16.5.19`:

|Puerto|Servicio habitual|
|---|---|
|`135/tcp`|Microsoft RPC|
|`139/tcp`|NetBIOS-SSN|
|`445/tcp`|SMB|
|`3389/tcp`|RDP|

### 5.3. Limitaciones de Nmap con Proxychains

**No todos los tipos de escaneo funcionan correctamente a través de Proxychains.**

- Utiliza `-sT` para realizar conexiones TCP completas.
    
- No confíes en escaneos SYN (`-sS`) a través de este tipo de proxy.
    
- Los escaneos pueden ser lentos debido a los tiempos de espera y a la latencia del túnel.
    
- El descubrimiento de hosts mediante ICMP puede no funcionar como se espera.
    
- Algunos equipos Windows bloquean solicitudes ICMP mediante el firewall.
    

Para obtener resultados más fiables, conviene centrarse en hosts conocidos o rangos pequeños y utilizar `-Pn` cuando el descubrimiento inicial no sea fiable.

## 6. Utilizar Metasploit a través del túnel SOCKS

También podemos iniciar Metasploit mediante Proxychains:

```
proxychains msfconsole
```

De esta forma, las conexiones compatibles de Metasploit pueden pasar por el proxy configurado.

### 6.1. Buscar el módulo de detección RDP

Desde la consola de Metasploit:

```
search rdp_scanner
```

Seleccionamos el módulo:

```
use auxiliary/scanner/rdp/rdp_scanner
```

Configuramos el objetivo:

```
set RHOSTS 172.16.5.19
```

Ejecutamos el escaneo:

```
run
```

El módulo puede identificar si el objetivo ofrece RDP y mostrar información como el nombre del host, la versión del sistema operativo y si requiere Network Level Authentication (NLA).

En el ejemplo de HTB, el resultado indica que el puerto RDP está abierto y que el servidor no requiere NLA.

## 7. Conectarse por RDP a través de Proxychains

Si disponemos de credenciales válidas y autorización para acceder al equipo, podemos establecer una sesión RDP a través del túnel.

```
proxychains xfreerdp /v:<IP_INTERNA> /u:<USUARIO> /p:'<CONTRASEÑA>'
```

Ejemplo con los valores del laboratorio:

```
proxychains xfreerdp /v:172.16.5.19 /u:victor /p:'pass@123'
```

Si el servidor presenta un certificado que requiere confirmación, puede ser necesario aceptarlo para completar la conexión.

El flujo es:

1. `xfreerdp` inicia la conexión RDP.
    
2. Proxychains dirige la conexión al proxy SOCKS local.
    
3. SSH transporta el tráfico hasta el servidor Ubuntu.
    
4. Ubuntu conecta con el servidor RDP interno.
    
5. Se establece la sesión remota si las credenciales y las condiciones de acceso son válidas.
    

Las credenciales del ejemplo pertenecen al laboratorio y no deben asumirse válidas para otros objetivos.

## 8. Flujo de trabajo para HTB

### Escenario A: acceder a un servicio concreto

Si conocemos el puerto de destino, utilizamos una redirección local.

```
ssh -L 1234:localhost:3306 ubuntu@<IP_PIVOTE>
```

Después comprobamos el puerto local:

```
nmap -sV -p1234 localhost
```

### Escenario B: explorar una red interna

Si el servidor pivote tiene acceso a una subred que nuestra máquina no puede alcanzar directamente:

**1. Identificar las interfaces del pivote:**

```
ip addr
```

**2. Crear el proxy SOCKS:**

```
ssh -D 9050 ubuntu@<IP_PIVOTE>
```

**3. Configurar Proxychains:**

```
socks4 127.0.0.1 9050
```

**4. Buscar hosts activos:**

```
proxychains nmap -sn <SUBRED>
```

**5. Examinar un host concreto:**

```
proxychains nmap -Pn -sT <IP_INTERNA>
```

**6. Utilizar otras herramientas compatibles a través del proxy:**

```
proxychains msfconsole
```

**7. Acceder a un servicio interno**, si se dispone de las credenciales y permisos necesarios:

```
proxychains xfreerdp /v:<IP_INTERNA> /u:<USUARIO> /p:'<CONTRASEÑA>'
```

## 10. Lo que debes recordar

- `**ssh -L**`**:** permite acceder localmente a un servicio remoto concreto.
    
- `**ssh -D**`**:** crea un proxy SOCKS local para acceder a distintos destinos mediante el servidor SSH.
    
- **Proxychains:** permite dirigir las conexiones TCP compatibles de herramientas como Nmap o Metasploit a través del proxy.
    
- **Pivoting:** utiliza un host con acceso a varias redes para alcanzar sistemas que no son directamente accesibles desde el atacante.
    
- `**-sT**`**:** es el tipo de escaneo TCP que debemos utilizar con Proxychains en este escenario.
    
- `**-Pn**`**:** resulta útil cuando el descubrimiento de hosts no funciona correctamente.
    
- **Interfaces de red:** pueden revelar redes internas accesibles desde el pivote.
    

**Diferencia esencial:** una redirección local proporciona acceso a un servicio concreto; un túnel SOCKS permite encaminar conexiones hacia múltiples destinos accesibles desde el host pivote.
