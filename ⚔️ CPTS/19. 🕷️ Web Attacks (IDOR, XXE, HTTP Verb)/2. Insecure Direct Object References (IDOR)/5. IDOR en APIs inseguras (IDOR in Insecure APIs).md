
## 1. Tipos de vulnerabilidades IDOR en APIs

Las vulnerabilidades IDOR no se limitan a acceder a archivos. También pueden permitir ejecutar funciones de una API en nombre de otros usuarios.

Existen dos categorías principales:

|Tipo|Impacto|
|---|---|
|**IDOR Information Disclosure**|Leer información privada de otros usuarios.|
|**IDOR Insecure Function Calls**|Ejecutar acciones sobre otros usuarios o modificar recursos sin autorización.|

Las llamadas a funciones inseguras pueden permitir:

- Modificar información de otros usuarios.
    
- Restablecer contraseñas ajenas.
    
- Crear o eliminar usuarios.
    
- Cambiar roles y privilegios.
    
- Realizar compras utilizando información de pago de otros usuarios.
    

Una vulnerabilidad de divulgación de información puede proporcionar datos útiles para explotar posteriormente una llamada a función insegura.

## 2. Identificar una API vulnerable

En el laboratorio Employee Manager, accedemos a la página de edición del perfil:

```
http://SERVER_IP:PORT/profile/index.php
```

Al modificar el perfil e interceptar la petición con Burp Suite, encontramos una petición `PUT` a:

```
PUT /profile/api.php/profile/1 HTTP/1.1
```

El cuerpo JSON contiene:

```
{
    "uid": 1,
    "uuid": "40f5888b67c748df7efba008e7c2f9d2",
    "role": "employee",
    "full_name": "Amy Lindon",
    "email": "a_lindon@employees.htb",
    "about": "A Release is like a boat. 80% of the holes plugged is not good enough."
}
```

### Parámetros importantes

|Parámetro|Función|
|---|---|
|`uid`|Identificador del usuario.|
|`uuid`|Identificador adicional asociado al usuario.|
|`role`|Rol o nivel de privilegios.|
|`full_name`|Nombre completo.|
|`email`|Correo electrónico.|
|`about`|Información del perfil.|

Los campos `uid`, `uuid` y `role` son especialmente interesantes porque no aparecen como campos editables normales en el formulario.

**Importante:** que un parámetro esté oculto en el frontend no significa que sea seguro. Debemos comprobar si el backend valida los valores y aplica los permisos correctamente.

---

## 3. Comprender los métodos HTTP

Las APIs suelen utilizar diferentes métodos HTTP para realizar operaciones sobre los recursos.

|Método|Uso habitual|
|---|---|
|`GET`|Consultar información.|
|`POST`|Crear recursos o enviar datos para su procesamiento.|
|`PUT`|Actualizar o sustituir un recurso.|
|`DELETE`|Eliminar un recurso.|

En una API vulnerable, la autorización podría estar implementada de manera incorrecta en uno o varios de estos métodos.

Por ello, debemos comprobar tanto las operaciones de lectura como las de modificación.

## 4. Probar llamadas a funciones inseguras

Utilizaremos Burp Suite para interceptar las peticiones y modificar los parámetros.

### 4.1. Modificar el UID

Intentamos cambiar:

```
{
    "uid": 1
}
```

por:

```
{
    "uid": 2
}
```

La aplicación devuelve:

```
uid mismatch
```

Esto indica que el backend comprueba la coherencia entre el UID del JSON y el identificador del recurso solicitado en la URL.

### 4.2. Modificar el endpoint y el UID

Probamos la ruta:

```
PUT /profile/api.php/profile/2 HTTP/1.1
```

Y enviamos:

```
{
    "uid": 2,
    "uuid": "40f5888b67c748df7efba008e7c2f9d2",
    "role": "employee",
    "full_name": "Test",
    "email": "test@example.com",
    "about": "Test"
}
```

La aplicación responde:

```
uuid mismatch
```

El backend también parece comprobar que el UUID proporcionado corresponde al usuario solicitado.

**Conclusión:** estas comprobaciones impiden que las modificaciones probadas se realicen utilizando simplemente nuestro UID y UUID.

### 4.3. Intentar crear usuarios

Probamos el método `POST` contra el endpoint de la API, utilizando un nuevo identificador.

La aplicación responde:

```
Creating new employees is for admins only
```

### 4.4. Intentar eliminar usuarios

Al probar el método `DELETE`, recibimos:

```
Deleting employees is for admins only
```

Estos mensajes indican que la aplicación restringe las operaciones de creación y eliminación a los administradores.

### 4.5. Modificar el rol

En el JSON encontramos:

```
{
    "role": "employee"
}
```

Probamos a cambiarlo por un rol más privilegiado, como `admin` o `administrator`.

La aplicación devuelve:

```
Invalid role
```

El rol enviado no se acepta como válido y no conseguimos elevar nuestros privilegios.

La cookie también contiene información relacionada con el rol:

```
Cookie: role=employee
```

Esto merece investigación, pero no demuestra por sí solo que modificar la cookie permita obtener privilegios. Es necesario comprobar si el backend confía indebidamente en ella.

## 5. Comprobar la divulgación de información mediante GET

Aunque los intentos de modificar usuarios y roles hayan fallado, **todavía no podemos concluir que la API sea segura frente a IDOR**.

Hasta ahora hemos probado principalmente llamadas a funciones mediante `PUT`, `POST` y `DELETE`.

Nos falta comprobar si es posible consultar información de otros usuarios mediante `GET`.

### Procedimiento

1. Interceptar una petición válida de consulta con Burp Suite.
    
2. Identificar el endpoint y el UID del usuario.
    
3. Enviar la petición a Repeater.
    
4. Cambiar el identificador del recurso, manteniendo el resto de la petición.
    
5. Comparar las respuestas para determinar si se devuelve información de otro usuario.
    
6. Comprobar si el backend verifica los permisos de acceso.
    

Si la API permite leer los datos de otros empleados sin autorización, tendríamos una posible vulnerabilidad de **IDOR Information Disclosure**.

La información obtenida podría ayudar a investigar otras operaciones de la API, por ejemplo, proporcionando identificadores que necesitamos para probar llamadas a funciones.

> El contenido de esta sección no especifica el resultado final de las pruebas GET. Debemos realizar el ejercicio para confirmar si la API es vulnerable.

## 6. Metodología para HTB

Cuando encuentres una API que gestione perfiles o usuarios:

1. **Intercepta una petición legítima:** identifica la ruta, el método HTTP, las cookies y el cuerpo de la petición.
    
2. **Inspecciona el JSON:** busca campos como `uid`, `uuid` y `role`.
    
3. **Prueba cambios controlados:** modifica identificadores y parámetros.
    
4. **Analiza los errores:** mensajes como `uid mismatch`, `uuid mismatch` o `Invalid role` aportan información sobre las validaciones.
    
5. **Prueba los distintos métodos:** comprueba las operaciones permitidas y sus controles de autorización.
    
6. **Investiga las peticiones GET:** determina si puedes leer datos de otros usuarios.
    
7. **Comprueba la autorización del backend:** no des por segura una operación únicamente porque el frontend la limite.
    

## Chuleta rápida

|Prueba|Qué comprobar|
|---|---|
|Cambiar `uid` en JSON|Si el backend verifica el identificador.|
|Cambiar el UID del endpoint|Si se puede acceder a otro perfil.|
|Modificar `uuid`|Si existe una comprobación de correspondencia.|
|Cambiar `role`|Si el backend acepta roles arbitrarios.|
|Probar `POST`|Si permite crear usuarios sin autorización.|
|Probar `DELETE`|Si permite eliminar usuarios sin autorización.|
|Probar `GET`|Si expone información privada de otros usuarios.|
|Modificar la cookie `role`|Si el servidor confía indebidamente en un valor controlado por el cliente.|

### Concepto clave para el examen

**Que una API bloquee las modificaciones no significa que también proteja correctamente la lectura de datos.**

Hay que probar por separado las vulnerabilidades de divulgación de información y las llamadas a funciones inseguras, verificando siempre si el backend aplica la autorización correspondiente.
