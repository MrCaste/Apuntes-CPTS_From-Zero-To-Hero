
## 1. ¿Qué es una vulnerabilidad IDOR?

Una vulnerabilidad **IDOR (Insecure Direct Object Reference)** ocurre cuando una aplicación web permite acceder o modificar recursos internos mediante referencias directas controladas por el usuario, **sin comprobar correctamente los permisos de acceso en el backend**.

Estas referencias pueden ser:

- Identificadores de archivos.
    
- ID de usuarios.
    
- Identificadores de registros de una base de datos.
    
- Parámetros de URL.
    
- Referencias utilizadas por una API.
    

### Ejemplo básico

Una aplicación permite descargar un archivo mediante:

```
GET /download.php?file_id=123 HTTP/1.1
Host: example.com
```

Podemos probar a cambiar el identificador:

```
GET /download.php?file_id=124 HTTP/1.1
Host: example.com
```

Si la aplicación devuelve un archivo perteneciente a otro usuario sin comprobar los permisos, existe una posible vulnerabilidad IDOR.

**Importante:** modificar un identificador no constituye por sí solo una vulnerabilidad. El problema aparece cuando el backend no verifica si el usuario tiene autorización para acceder al recurso solicitado.

---

## 2. Causa principal

Las vulnerabilidades IDOR suelen producirse por la ausencia de un control de acceso adecuado en el backend.

Una aplicación puede ocultar archivos, enlaces o funcionalidades en el frontend para que los usuarios solo vean sus propios recursos. Sin embargo, si el backend no comprueba los permisos, un usuario podría manipular manualmente las peticiones HTTP para acceder a información ajena.

### Flujo vulnerable

1. El usuario inicia sesión.
    
2. La aplicación proporciona una referencia directa a un recurso.
    
3. El usuario modifica el identificador de la petición.
    
4. El backend recupera el recurso sin verificar los permisos.
    
5. El usuario obtiene acceso a información o funcionalidades que no le corresponden.
    

### Control de acceso adecuado

El backend debe comprobar que el usuario autenticado tiene permiso para acceder al recurso solicitado.

Por ejemplo, no basta con comprobar que el usuario está autenticado: también debe verificarse que puede acceder al archivo concreto que solicita.

Un mecanismo posible es el **RBAC (Role-Based Access Control)**, que gestiona los permisos según los roles de los usuarios.

---

## 3. Impacto de las vulnerabilidades IDOR

### A. Divulgación de información

Permite acceder a información privada de otros usuarios.

Ejemplos:

- Archivos personales.
    
- Documentos privados.
    
- Datos confidenciales.
    
- Información de tarjetas de crédito.
    

Se conoce como **IDOR Information Disclosure**.

### B. Modificación o eliminación de datos

Si la aplicación permite modificar o eliminar recursos mediante referencias directas, un atacante podría manipular datos de otros usuarios o borrar sus archivos.

### C. Toma de control de cuentas

En determinados casos, acceder o modificar recursos sensibles puede facilitar una **Account Takeover (ATO)**, es decir, la toma de control de una cuenta.

### D. Elevación de privilegios

Una vulnerabilidad IDOR también puede permitir que un usuario estándar acceda a funcionalidades administrativas.

Por ejemplo, una aplicación podría exponer una API para cambiar contraseñas o asignar roles, pero confiar únicamente en las restricciones del frontend.

Si el backend no comprueba los permisos, un usuario estándar podría invocar directamente esa funcionalidad.

Este tipo de problema se conoce como **IDOR Insecure Function Calls** y puede conducir a una elevación de privilegios.

---

## 4. Metodología de enumeración para HTB

Cuando investiguemos una posible vulnerabilidad IDOR:

1. **Identificar referencias directas:** revisar parámetros como `id`, `user_id`, `file_id` o identificadores similares.
    
2. **Capturar las peticiones HTTP:** utilizar Burp Suite para observar las solicitudes y respuestas.
    
3. **Modificar los identificadores:** probar otros valores en los parámetros que controlan el recurso solicitado.
    
4. **Comparar las respuestas:** comprobar si cambian los datos, los archivos devueltos o los permisos observados.
    
5. **Verificar la autorización:** determinar si el recurso pertenece a otro usuario o requiere privilegios adicionales.
    
6. **Buscar otras referencias:** revisar parámetros de URL, peticiones POST y llamadas a APIs.
    
7. **Evaluar el impacto:** comprobar si el acceso no autorizado permite leer, modificar o eliminar recursos, o ejecutar funcionalidades privilegiadas.
    

Realiza estas pruebas únicamente en laboratorios autorizados y evita modificar o eliminar datos ajenos fuera del entorno de pruebas.

---

## 5. Checklist rápido

|Elemento|Qué comprobar|
|---|---|
|Parámetros de URL|`id`, `user_id`, `file_id` y referencias similares.|
|Peticiones HTTP|Si es posible modificar los identificadores mediante Burp Suite.|
|Control de acceso|Si el backend verifica los permisos sobre cada recurso.|
|Información expuesta|Si aparecen datos pertenecientes a otros usuarios.|
|Modificación de recursos|Si pueden modificarse o eliminarse datos sin autorización.|
|Funciones administrativas|Si un usuario estándar puede invocar operaciones restringidas.|

### Concepto clave para el examen

**IDOR no consiste simplemente en adivinar o modificar un ID, sino en acceder a un objeto o ejecutar una función sin la autorización correspondiente.**

La causa principal es un control de acceso insuficiente en el backend, y sus consecuencias pueden incluir divulgación de información, modificación de datos, elevación de privilegios y toma de control de cuentas.
