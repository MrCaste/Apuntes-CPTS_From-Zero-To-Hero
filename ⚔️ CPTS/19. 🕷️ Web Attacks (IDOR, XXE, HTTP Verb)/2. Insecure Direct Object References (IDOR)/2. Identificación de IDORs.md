
## 1. Parámetros de URL y API

El primer paso para identificar una vulnerabilidad **IDOR (Insecure Direct Object Reference)** es localizar las referencias directas a objetos que controla el usuario.

Debemos revisar las peticiones HTTP y buscar identificadores en:

- Parámetros de URL: `?uid=1`, `?file_id=123`.
    
- Nombres de archivos: `?filename=file_1.pdf`.
    
- Parámetros enviados a las API.
    
- Cabeceras HTTP y cookies.
    

### Ejemplo práctico

Petición original:

```
GET /download.php?file_id=123 HTTP/1.1
Host: example.com
```

Modificar el identificador:

```
GET /download.php?file_id=124 HTTP/1.1
Host: example.com
```

Si conseguimos acceder a un archivo de otro usuario sin autorización, habremos identificado una posible IDOR.

**Metodología:**

1. Identificar los parámetros que hacen referencia a objetos.
    
2. Modificar sus valores manualmente.
    
3. Comparar las respuestas del servidor.
    
4. Comprobar si podemos acceder a recursos que no nos pertenecen.
    
5. Si es necesario, utilizar herramientas de fuzzing para probar múltiples identificadores.

## 2. Identificar llamadas AJAX

Las aplicaciones web pueden contener funciones JavaScript que realizan llamadas AJAX a endpoints o API.

Estas funciones pueden existir en el código del frontend aunque no aparezcan durante la navegación habitual, por ejemplo, porque están destinadas a usuarios administradores.

### Ejemplo

```
function changeUserPassword() {
    $.ajax({
        url: "change_password.php",
        type: "post",
        dataType: "json",
        data: {
            uid: user.uid,
            password: user.password,
            is_admin: is_admin
        },
        success: function(result) {
            //
        }
    });
}
```

En este ejemplo encontramos:

- Endpoint: `change_password.php`.
    
- Método HTTP: `POST`.
    
- Referencia al usuario: `uid`.
    
- Parámetro relacionado con privilegios: `is_admin`.
    

### Procedimiento

1. Inspeccionar el código JavaScript del frontend.
    
2. Buscar llamadas AJAX y endpoints.
    
3. Identificar parámetros que hagan referencia a usuarios u objetos.
    
4. Comprobar si existen funciones que no aparecen en la interfaz habitual.
    
5. Reproducir las peticiones mediante Burp Suite.
    
6. Verificar si el backend comprueba los permisos del usuario autenticado.
    

**Importante:** encontrar un endpoint o un parámetro administrativo no demuestra que exista una vulnerabilidad. Debemos comprobar si permite realizar operaciones sin la autorización necesaria.

## 3. Analizar referencias codificadas o con hash

Las referencias a objetos no siempre aparecen como números secuenciales o nombres de archivo legibles. Algunas aplicaciones utilizan codificación o hashes.

### A. Referencias codificadas en Base64

Ejemplo:

```
ZmlsZV8xMjMucGRm
```

Podemos decodificar el valor con:

```
echo -n 'ZmlsZV8xMjMucGRm' | base64 -d
```

Resultado:

```
file_123.pdf
```

Si la aplicación utiliza este mecanismo, podemos comprobar si la referencia se construye codificando el nombre del archivo.

Por ejemplo, para generar la referencia de `file_124.pdf`:

```
echo -n 'file_124.pdf' | base64
```

Resultado:

```
ZmlsZV8xMjQucGRm
```

Podemos probar la nueva referencia para comprobar si permite acceder a otro archivo.

**Concepto clave:** Base64 es una codificación, no un mecanismo de control de acceso. Ocultar el nombre de un recurso mediante codificación no impide acceder a él si el backend no verifica los permisos.

### B. Referencias basadas en hashes

Ejemplo de petición:

```
GET /download.php?filename=c81e728d9d4c2f636f067f89cc14862c HTTP/1.1
Host: example.com
```

El valor podría corresponder al hash MD5 de un nombre de archivo.

Para investigarlo, podemos inspeccionar el código JavaScript:

```
$.ajax({
    url: "download.php",
    type: "post",
    dataType: "json",
    data: {
        filename: CryptoJS.MD5('file_1.pdf').toString()
    },
    success: function(result) {
        //
    }
});
```

Aquí vemos que el nombre del archivo se transforma mediante `CryptoJS.MD5`.

Si identificamos el algoritmo y cómo se genera el valor, podemos calcular referencias para otros nombres de archivo.

**Procedimiento:**

1. Identificar el parámetro que contiene el hash.
    
2. Inspeccionar el código frontend para determinar qué dato se transforma.
    
3. Identificar el algoritmo utilizado.
    
4. Calcular el hash de otra referencia candidata.
    
5. Probarla y verificar si permite acceder a un recurso no autorizado.
    

Un hash no garantiza que exista un control de acceso adecuado. Sin embargo, tampoco implica que podamos recuperar cualquier recurso: debemos comprobar cómo valida el backend cada solicitud.

## 4. Comparar diferentes usuarios y roles

Una técnica útil consiste en comparar las peticiones HTTP realizadas por dos cuentas diferentes.

Esto permite identificar cómo se construyen las referencias y comprobar si el backend verifica los permisos de cada usuario.

### Ejemplo de respuesta de una API

```
{
  "attributes": {
    "type": "salary",
    "url": "/services/data/salaries/users/1"
  },
  "Id": "1",
  "Name": "User1"
}
```

La respuesta muestra una referencia a los datos salariales del usuario con identificador `1`.

### Procedimiento

1. Iniciar sesión con el primer usuario y capturar sus peticiones.
    
2. Identificar los endpoints y las referencias a objetos.
    
3. Iniciar sesión con un segundo usuario.
    
4. Repetir la petición utilizando la sesión del segundo usuario.
    
5. Comprobar si puede acceder a los datos del primero.
    
6. Determinar si el backend comprueba la autorización sobre el recurso solicitado.
    

Si el segundo usuario puede consultar los datos del primero sin disponer de los permisos necesarios, existe una posible vulnerabilidad IDOR.

Este procedimiento también puede ayudar a descubrir fallos de control de acceso aunque todavía no conozcamos cómo generar referencias válidas para otros usuarios.

## 5. Checklist de enumeración para HTB

|Elemento|Qué buscar|
|---|---|
|Parámetros URL|`id`, `uid`, `user_id`, `file_id`, `filename`.|
|Cookies y cabeceras|Identificadores que puedan controlar el recurso solicitado.|
|Llamadas AJAX|Endpoints y funciones que no aparecen en la interfaz habitual.|
|Referencias Base64|Valores codificados que puedan revelar nombres de archivos o identificadores.|
|Hashes|Algoritmos y datos originales utilizados para generar las referencias.|
|Diferentes usuarios|Diferencias entre las peticiones de cuentas con distintos permisos.|
|Respuestas del servidor|Acceso a información o funcionalidades que no corresponden al usuario.|

## Conceptos clave para el examen

- **Referencias directas:** pueden aparecer en URL, API, cookies, cabeceras o código JavaScript.
    
- **Fuzzing:** permite probar múltiples valores para identificar referencias válidas.
    
- **AJAX:** puede revelar endpoints y funciones que no son visibles durante el uso normal de la aplicación.
    
- **Base64:** permite recuperar el contenido original de referencias codificadas cuando se conoce el formato.
    
- **Hashes:** pueden ser reproducibles si identificamos el algoritmo y el dato original.
    
- **Comparación de roles:** ayuda a detectar fallos de autorización entre usuarios.
    
- **Causa fundamental de IDOR:** ausencia de comprobaciones de autorización adecuadas en el backend.
    

**Regla de oro:** identificar o modificar una referencia no basta. Para confirmar una IDOR, debemos demostrar que la aplicación permite acceder o realizar operaciones sobre un recurso sin los permisos correspondientes.
