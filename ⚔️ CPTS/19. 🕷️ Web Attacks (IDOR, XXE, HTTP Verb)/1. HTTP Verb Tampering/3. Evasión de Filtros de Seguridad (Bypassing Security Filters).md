
## 1. ¿En qué consiste?

La manipulación de verbos HTTP también puede permitir evadir filtros de seguridad debido a errores de programación.

Por ejemplo, si una aplicación solo comprueba las inyecciones en los parámetros `POST`, podríamos cambiar el método HTTP a `GET` para intentar evitar el filtro.

**Causa principal:** la aplicación no aplica las mismas validaciones a todos los métodos HTTP.

## 2. Identificar el filtro de seguridad

En el laboratorio utilizamos una aplicación web de administración de archivos (_File Manager_).

Al intentar crear un archivo con caracteres especiales en el nombre, por ejemplo:

```
test;
```

La aplicación devuelve:

```
Malicious Request Denied!
```

Esto indica que existe un filtro de seguridad que detecta y bloquea determinadas entradas potencialmente maliciosas.

## 3. Explotación mediante HTTP Verb Tampering

### Paso 1: Interceptar la petición

Utilizamos Burp Suite para interceptar la petición HTTP que envía el nombre del archivo.

### Paso 2: Cambiar el método HTTP

En Burp Suite, hacemos clic derecho sobre la petición y seleccionamos:

**Change Request Method**

Cambiamos el método HTTP y reenviamos la petición.

En el laboratorio, la solicitud modificada consigue crear el archivo sin mostrar el mensaje `Malicious Request Denied!`.

Esto indica que el filtro podría estar asociado al método HTTP original y no aplicarse correctamente al método alternativo.

### Paso 3: Confirmar la vulnerabilidad

Para comprobar si realmente hemos evadido el filtro, intentamos verificar una posible inyección de comandos.

Utilizamos el siguiente nombre de archivo:

```
file1; touch file2;
```

El objetivo es crear dos archivos:

- `file1`: archivo solicitado por la aplicación.
    
- `file2`: archivo cuya creación demostraría que se ha ejecutado el comando `touch file2`.
    

Enviamos la petición con el método HTTP alternativo y comprobamos el resultado.

En el laboratorio aparecen ambos archivos, lo que confirma que:

1. El filtro de seguridad ha sido evadido.
    
2. La aplicación ha interpretado parte de la entrada como un comando.
    
3. Se ha conseguido explotar una vulnerabilidad de **Command Injection**.
    

## 4. Flujo de trabajo para HTB

1. Introducir una entrada que active el filtro.
    
2. Identificar el mensaje de bloqueo: `Malicious Request Denied!`.
    
3. Interceptar la petición con Burp Suite.
    
4. Cambiar el método HTTP mediante `Change Request Method`.
    
5. Reenviar la petición y comprobar si desaparece el bloqueo.
    
6. Utilizar una prueba controlada para verificar si la entrada se interpreta como un comando.
    
7. Confirmar el resultado observando los archivos creados.
    

## 5. Conceptos clave

|Concepto|Explicación|
|---|---|
|HTTP Verb Tampering|Manipular el método HTTP para intentar evadir controles de seguridad.|
|Filtro de seguridad|Mecanismo que detecta y bloquea entradas potencialmente maliciosas.|
|Validación inconsistente|La aplicación aplica filtros diferentes según el método HTTP.|
|Command Injection|Vulnerabilidad que permite ejecutar comandos del sistema mediante entradas controladas por el usuario.|
|Confirmación de explotación|Verificar que el comando se ejecutó realmente, en lugar de basarse únicamente en la ausencia del mensaje de bloqueo.|

**Conclusión:** una aplicación puede disponer de un filtro que bloquee correctamente las peticiones originales y seguir siendo vulnerable si no aplica las mismas comprobaciones a otros métodos HTTP. La solución consiste en validar de forma coherente todas las entradas, independientemente del método utilizado.
