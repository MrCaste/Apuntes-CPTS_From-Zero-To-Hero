
## 1. Objetivo

Aprovechar una configuración insegura del servidor web para **evadir la autenticación HTTP Basic modificando el método HTTP de la petición**.

El servidor puede exigir autenticación para determinados métodos, como `GET` y `POST`, pero permitir otros, como `HEAD`, sin aplicar el mismo control de acceso.

## 2. Identificar el recurso protegido

En el laboratorio encontramos una aplicación web de administración de archivos.

Al pulsar el botón `Reset`, se accede a:

```
/admin/reset.php
```

La página solicita credenciales y devuelve:

```
401 Unauthorized
```

Para determinar el alcance de la restricción, también probamos a acceder al directorio `/admin`. Si solicita autenticación, podemos sospechar que todo el directorio está protegido.

## 3. Probar diferentes métodos HTTP

### Paso 1: Identificar el método original

Interceptamos la petición con Burp Suite y comprobamos que utiliza `GET`.

```
GET /admin/reset.php HTTP/1.1
Host: SERVER_IP:PORT
```

### Paso 2: Probar POST

En Burp Suite, hacemos clic derecho sobre la petición y seleccionamos:

**Change Request Method**

La petición se transforma en:

```
POST /admin/reset.php HTTP/1.1
Host: SERVER_IP:PORT
```

Reenviamos la petición. Si seguimos recibiendo `401 Unauthorized`, significa que este método también está sujeto a la autenticación.

### Paso 3: Consultar los métodos aceptados

Podemos utilizar `OPTIONS` para consultar los métodos HTTP que anuncia el servidor:

```
curl -i -X OPTIONS http://SERVER_IP:PORT/
```

Ejemplo de respuesta:

```
HTTP/1.1 200 OK
Server: Apache/2.4.41 (Ubuntu)
Allow: POST,OPTIONS,HEAD,GET
```

La cabecera `Allow` indica que el servidor anuncia los métodos `POST`, `OPTIONS`, `HEAD` y `GET`.

**Importante:** que un método aparezca en `Allow` no demuestra que permita eludir la autenticación. Hay que probarlo contra el recurso protegido.

## 4. Explotar la vulnerabilidad con HEAD

El método `HEAD` es similar a `GET`, pero la respuesta no contiene el cuerpo.

Probamos a cambiar la petición a:

```
HEAD /admin/reset.php HTTP/1.1
Host: SERVER_IP:PORT
```

Reenviamos la petición desde Burp Suite y comprobamos la respuesta.

En el laboratorio, la petición `HEAD` no muestra el formulario de autenticación ni devuelve el error `401 Unauthorized`. Aunque la respuesta está vacía, la funcionalidad de reinicio se ejecuta.

Al regresar al administrador de archivos, comprobamos que todos los archivos han sido eliminados.

**Resultado:** se ha conseguido ejecutar una funcionalidad protegida sin disponer de credenciales administrativas.

## 5. Flujo de trabajo para HTB

1. Identificar la página o funcionalidad protegida.
    
2. Comprobar qué método HTTP utiliza la aplicación.
    
3. Interceptar la petición con Burp Suite.
    
4. Probar `POST` y verificar si sigue solicitando autenticación.
    
5. Consultar los métodos anunciados mediante `OPTIONS`.
    
6. Probar `HEAD` contra el recurso protegido.
    
7. Comprobar si se ejecuta la funcionalidad, aunque la respuesta esté vacía.
    
8. Verificar el resultado en la aplicación.
    

### Chuleta rápida

|Método|Prueba|Objetivo|
|---|---|---|
|`GET`|Petición original|Identificar el comportamiento normal.|
|`POST`|Cambiar el método en Burp|Comprobar si también exige autenticación.|
|`OPTIONS`|`curl -i -X OPTIONS URL`|Consultar los métodos anunciados por el servidor.|
|`HEAD`|Cambiar el método en Burp|Comprobar si permite ejecutar la funcionalidad sin autenticación.|

### Concepto clave

**La vulnerabilidad aparece cuando el control de autenticación no se aplica de forma coherente a todos los métodos HTTP.** No basta con recibir una respuesta vacía: hay que comprobar si la operación protegida se ha ejecutado realmente.
