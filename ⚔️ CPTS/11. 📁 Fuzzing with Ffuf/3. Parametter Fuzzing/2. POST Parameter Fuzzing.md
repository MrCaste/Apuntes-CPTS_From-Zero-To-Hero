
## 1. Diferencias entre GET y POST

- **GET:** los parámetros se envían en la URL, después de `?`.
    
- **POST:** los parámetros se envían en el cuerpo (_body_) de la petición HTTP, no directamente en la URL.
    

Ejemplo GET:

```
GET /admin/admin.php?id=key HTTP/1.1
Host: admin.academy.htb
```

Ejemplo POST:

```
POST /admin/admin.php HTTP/1.1
Host: admin.academy.htb
Content-Type: application/x-www-form-urlencoded

id=key
```

## 2. Fuzzing de parámetros POST con ffuf

Para enumerar parámetros POST utilizamos:

- `-X POST`: especifica el método HTTP.
    
- `-d`: establece los datos que se envían en el cuerpo de la petición.
    
- `-H`: añade una cabecera HTTP.
    
- `FUZZ`: representa el nombre del parámetro que queremos descubrir.
    

### Comando

```
ffuf -w /opt/useful/seclists/Discovery/Web-Content/burp-parameter-names.txt:FUZZ \
-u http://admin.academy.htb:PORT/admin/admin.php \
-X POST \
-d 'FUZZ=key' \
-H 'Content-Type: application/x-www-form-urlencoded' \
-fs TAMAÑO
```

En Kali, la wordlist también puede encontrarse en:

```
/usr/share/seclists/Discovery/Web-Content/burp-parameter-names.txt
```

**Importante:** sustituye `PORT` por el puerto del laboratorio y `TAMAÑO` por el tamaño de las respuestas que quieras excluir.

### Explicación de los parámetros

|Parámetro|Función|
|---|---|
|`-w`|Define la wordlist.|
|`-u`|Especifica la URL objetivo.|
|`-X POST`|Envía peticiones POST.|
|`-d 'FUZZ=key'`|Prueba distintos nombres de parámetros con el valor `key`.|
|`-H`|Añade una cabecera HTTP.|
|`Content-Type: application/x-www-form-urlencoded`|Indica el formato de los datos enviados.|
|`-fs`|Filtra respuestas por tamaño.|

## 3. Analizar los resultados

En el laboratorio aparecen parámetros como `id`, además del parámetro encontrado durante el fuzzing GET.

Un resultado relevante es:

```
id    [Status: xxx, Size: xxx, Words: xxx, Lines: xxx]
```

Esto indica que la petición con el parámetro `id` produce una respuesta que merece ser investigada.

**Encontrar un parámetro no significa que funcione correctamente:** debemos probarlo y observar cómo responde la aplicación.

## 4. Comprobar el parámetro con curl

Podemos enviar manualmente una petición POST con el parámetro `id`:

```
curl -X POST \
  'http://admin.academy.htb:PORT/admin/admin.php' \
  -d 'id=key' \
  -H 'Content-Type: application/x-www-form-urlencoded'
```

La respuesta del laboratorio es:

```
<div class='center'><p>Invalid id!</p></div>
```

El mensaje `Invalid id!` confirma que la aplicación está procesando el parámetro `id`, pero el valor `key` no es válido.

Esto nos permite distinguir entre un parámetro que simplemente se ha descubierto y uno que la aplicación reconoce y procesa.

## 5. Flujo de trabajo

1. Identificar una página que pueda aceptar parámetros.
    
2. Seleccionar una wordlist de nombres de parámetros.
    
3. Colocar `FUZZ` en el cuerpo de la petición POST.
    
4. Ejecutar `ffuf` con `-X POST` y `-d`.
    
5. Añadir la cabecera `Content-Type` adecuada.
    
6. Filtrar respuestas repetitivas con `-fs`.
    
7. Probar los parámetros interesantes con `curl`.
    
8. Analizar los mensajes devueltos por la aplicación.
    

## 6. Resumen para el examen

- **GET:** parámetros en la URL.
    
- **POST:** parámetros en el cuerpo de la petición.
    
- `**-X POST**`**:** selecciona el método POST.
    
- `**-d**`**:** define los datos enviados en el cuerpo.
    
- `**-H**`**:** permite establecer `Content-Type`.
    
- **Wordlist:** `burp-parameter-names.txt`.
    
- `**-fs**`**:** filtra respuestas según su tamaño.
    
- `**Invalid id!**`**:** indica que la aplicación ha procesado el parámetro, pero el valor enviado no es válido.
    
- Después del fuzzing, verifica manualmente los parámetros encontrados para comprender su comportamiento.
