
## 1. ¿Qué son los URI bien conocidos?

El estándar `.well-known`, definido en la **RFC 8615**, establece una ubicación común dentro de un dominio para publicar metadatos, archivos de configuración e información relacionada con servicios y mecanismos de seguridad.

La ruta habitual es:

```
https://<DOMINIO>/.well-known/
```

Permite que navegadores, aplicaciones y herramientas de seguridad localicen automáticamente recursos específicos mediante URL estandarizadas.

## 2. URI `.well-known` importantes

|URI|Función|Referencia|
|---|---|---|
|`/.well-known/security.txt`|Proporciona información de contacto para comunicar vulnerabilidades de seguridad.|RFC 9116|
|`/.well-known/change-password`|Ofrece una URL estandarizada para acceder a la página de cambio de contraseña.|Estándar provisional|
|`/.well-known/openid-configuration`|Publica la configuración de un proveedor OpenID Connect.|OpenID Connect Discovery|
|`/.well-known/assetlinks.json`|Permite verificar asociaciones entre un dominio y activos digitales, como aplicaciones.|Digital Asset Links|
|`/.well-known/mta-sts.txt`|Publica la política MTA-STS para mejorar la seguridad del correo electrónico.|RFC 8461|

**Para el reconocimiento web**, interesa comprobar estos recursos porque pueden revelar información sobre la configuración y los servicios del objetivo.

## 3. Consultar URI `.well-known`

Puedes consultar directamente las rutas desde el navegador o mediante `curl`.

### Consultar `security.txt`

```
curl -s https://<DOMINIO>/.well-known/security.txt
```

Busca información de contacto y posibles instrucciones para comunicar vulnerabilidades.

### Consultar la configuración de OpenID Connect

```
curl -s https://<DOMINIO>/.well-known/openid-configuration
```

Este endpoint puede devolver un documento JSON con información sobre los endpoints y las capacidades de autenticación del proveedor.

Para visualizar el JSON de forma legible:

```
curl -s https://<DOMINIO>/.well-known/openid-configuration | jq .
```

## 4. OpenID Connect Discovery

OpenID Connect es una capa de identidad construida sobre OAuth 2.0. Su endpoint `openid-configuration` proporciona metadatos que permiten descubrir cómo está configurado el proveedor de identidad.

Ejemplo de respuesta:

```
{
  "issuer": "https://example.com",
  "authorization_endpoint": "https://example.com/oauth2/authorize",
  "token_endpoint": "https://example.com/oauth2/token",
  "userinfo_endpoint": "https://example.com/oauth2/userinfo",
  "jwks_uri": "https://example.com/oauth2/jwks",
  "response_types_supported": ["code", "token", "id_token"],
  "subject_types_supported": ["public"],
  "id_token_signing_alg_values_supported": ["RS256"],
  "scopes_supported": ["openid", "profile", "email"]
}
```

### Campos importantes

|Campo|Información que proporciona|
|---|---|
|`issuer`|Identificador del proveedor de identidad.|
|`authorization_endpoint`|Endpoint utilizado para las solicitudes de autorización.|
|`token_endpoint`|Endpoint utilizado para emitir tokens.|
|`userinfo_endpoint`|Endpoint que proporciona información del usuario.|
|`jwks_uri`|Ubicación del conjunto de claves públicas JWKS.|
|`response_types_supported`|Tipos de respuesta compatibles.|
|`subject_types_supported`|Tipos de identificadores de usuario admitidos.|
|`id_token_signing_alg_values_supported`|Algoritmos de firma admitidos para los ID tokens.|
|`scopes_supported`|Scopes que el proveedor declara compatibles.|

## 5. Valor para el reconocimiento web

Consultar estos endpoints puede ayudar a:

- **Descubrir endpoints:** localizar las rutas de autorización, emisión de tokens e información del usuario.
    
- **Identificar servicios:** conocer qué mecanismos de identidad utiliza la aplicación.
    
- **Analizar capacidades:** identificar scopes, tipos de respuesta y algoritmos de firma declarados.
    
- **Conocer claves públicas:** localizar el JWKS utilizado para publicar las claves criptográficas correspondientes.
    

Estos datos permiten comprender mejor la superficie de ataque y seleccionar qué endpoints investigar durante una auditoría autorizada. La información publicada no demuestra por sí sola que exista una vulnerabilidad.

## 6. Metodología práctica

1. Comprueba si existen URI `.well-known` relevantes.
    
2. Consulta `security.txt` para identificar los canales de contacto de seguridad.
    
3. Consulta `openid-configuration` si el objetivo utiliza OpenID Connect.
    
4. Examina el JSON e identifica los endpoints, scopes y algoritmos declarados.
    
5. Investiga los endpoints descubiertos dentro del alcance autorizado de la prueba.
    

## Cheat Sheet

|Objetivo|Comando|
|---|---|
|Consultar `security.txt`|`curl -s https://<DOMINIO>/.well-known/security.txt`|
|Obtener configuración OpenID Connect|`curl -s https://<DOMINIO>/.well-known/openid-configuration`|
|Formatear la respuesta JSON|`curl -s https://<DOMINIO>/.well-known/openid-configuration \| jq .`|
|Consultar la política MTA-STS|`curl -s https://<DOMINIO>/.well-known/mta-sts.txt`|
|Consultar asociaciones digitales|`curl -s https://<DOMINIO>/.well-known/assetlinks.json`|

### Conceptos clave para el examen

- `.well-known` estandariza la ubicación de metadatos y archivos de configuración.
    
- La ruta habitual comienza por `/.well-known/`.
    
- `security.txt` facilita la comunicación de vulnerabilidades.
    
- `openid-configuration` permite descubrir la configuración de OpenID Connect.
    
- `jwks_uri` identifica dónde se publica el conjunto de claves JWKS.
    
- Los endpoints, scopes y algoritmos declarados ayudan a comprender la superficie de ataque.
    

**Idea clave:** durante el reconocimiento web, consulta los URI `.well-known` para descubrir metadatos, endpoints y configuraciones que puedan orientar la investigación posterior.
