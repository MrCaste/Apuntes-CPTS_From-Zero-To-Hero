
## 1. ¿Qué es una transferencia de zona DNS?

Una **transferencia de zona DNS** es un mecanismo que permite copiar los registros DNS de una zona desde un servidor DNS a otro, normalmente para mantener sincronizados los servidores primarios y secundarios.

Una zona puede contener información sobre:

- Subdominios.
    
- Direcciones IP.
    
- Servidores de nombres.
    
- Servidores de correo.
    
- Otros registros DNS.
    

El problema aparece cuando un servidor permite que terceros no autorizados descarguen todos los registros de la zona.

## 2. ¿Cómo funciona una transferencia de zona?

El proceso habitual es el siguiente:

1. **Solicitud AXFR:** el servidor secundario solicita una transferencia completa al servidor primario.
    
2. **Respuesta SOA:** el servidor proporciona información administrativa de la zona, incluido su número de serie.
    
3. **Transferencia de registros:** se envían los registros DNS de la zona.
    
4. **Finalización:** el servidor indica que se han transmitido todos los registros.
    
5. **Confirmación:** el servidor secundario procesa la información recibida y completa la sincronización.
    

### Conceptos clave

|Concepto|Descripción|
|---|---|
|AXFR|Tipo de consulta utilizado para solicitar una transferencia completa de zona.|
|SOA|Registro que contiene información administrativa de la zona.|
|Servidor primario|Servidor de referencia para los datos de la zona.|
|Servidor secundario|Servidor que obtiene una copia de los datos para mantenerlos sincronizados.|

---

## 3. ¿Por qué puede ser una vulnerabilidad?

Si un servidor DNS permite transferencias de zona sin restringir quién puede solicitarlas, un usuario no autorizado podría obtener una copia de los registros DNS.

Esto puede revelar:

- **Subdominios ocultos:** nombres que no aparecen enlazados desde la web principal.
    
- **Direcciones IP:** posibles objetivos para investigar.
    
- **Servidores de nombres:** información sobre la infraestructura DNS.
    
- **Servicios internos o poco visibles:** nombres relacionados con entornos de desarrollo, administración o pruebas.
    

Una transferencia de zona expuesta puede facilitar el reconocimiento porque proporciona numerosos registros de una sola vez, en lugar de tener que descubrirlos individualmente mediante fuerza bruta.

**Importante:** una transferencia de zona permitida no implica por sí sola que los servicios descubiertos sean vulnerables; el riesgo principal es la divulgación no autorizada de información DNS.

## 4. Cómo comprobar una transferencia de zona con `dig`

### Sintaxis

```
dig axfr @SERVIDOR_DNS dominio.com
```

|Parámetro|Función|
|---|---|
|`dig`|Herramienta para realizar consultas DNS.|
|`axfr`|Solicita una transferencia completa de zona.|
|`@SERVIDOR_DNS`|Especifica el servidor DNS al que se envía la solicitud.|
|`dominio.com`|Zona que se intenta transferir.|

### Ejemplo del módulo

```
dig axfr @nsztm1.digi.ninja zonetransfer.me
```

Este ejemplo consulta al servidor `nsztm1.digi.ninja` para intentar obtener la zona `zonetransfer.me`.

El dominio del ejemplo está configurado específicamente para demostrar los riesgos de las transferencias de zona DNS.

### Ejemplo de una transferencia exitosa

```
zonetransfer.me.       IN SOA    nsztm1.digi.ninja. robin.digi.ninja. ...
zonetransfer.me.       IN MX     0 ASPMX.L.GOOGLE.COM.
zonetransfer.me.       IN A      5.196.105.14
zonetransfer.me.       IN NS     nsztm1.digi.ninja.
zonetransfer.me.       IN NS     nsztm2.digi.ninja.
canberra-office.zonetransfer.me. IN A 202.14.81.230
```

En este resultado se observan registros de distintos tipos:

- `SOA`: información administrativa.
    
- `MX`: servidores de correo.
    
- `A`: direcciones IPv4.
    
- `NS`: servidores de nombres.
    
- Otros nombres de host, como `canberra-office.zonetransfer.me`.
    

### ¿Cómo saber si ha funcionado?

Una transferencia exitosa devuelve numerosos registros de la zona. En la salida de `dig` puede aparecer una línea como:

```
;; XFR size: 50 records
```

Esto indica que se han transferido 50 registros en el ejemplo.

Si la transferencia falla, el servidor puede rechazar la solicitud o no proporcionar los datos. Un intento fallido no demuestra que la zona carezca de subdominios.

## 5. Metodología de reconocimiento

### Paso 1. Identificar los servidores DNS

Consulta los registros NS del dominio:

```
dig dominio.com NS
```

### Paso 2. Intentar una transferencia de zona autorizada

```
dig axfr @ns1.dominio.com dominio.com
```

Sustituye `ns1.dominio.com` por el servidor DNS identificado y utiliza únicamente objetivos para los que tengas autorización.

### Paso 3. Analizar los registros obtenidos

Si la transferencia funciona, busca:

- Nombres de subdominios.
    
- Direcciones IPv4 e IPv6.
    
- Servidores de correo.
    
- Alias CNAME.
    
- Otros registros que revelen servicios o infraestructura.
    

### Paso 4. Continuar el reconocimiento

Documenta los nombres y direcciones encontrados para investigar los servicios correspondientes.

---

## 6. Remediación

Para evitar la divulgación no autorizada de información DNS:

- Restringir las transferencias de zona a servidores secundarios autorizados.
    
- Configurar correctamente los controles de acceso.
    
- Revisar periódicamente la configuración de los servidores DNS.
    
- Supervisar solicitudes de transferencia de zona inesperadas.
    

Las transferencias de zona siguen siendo necesarias para la administración legítima del DNS; el objetivo no es eliminarlas, sino limitar quién puede realizarlas.

## 7. Chuleta para el examen

|Objetivo|Comando o concepto|
|---|---|
|Consultar servidores DNS|`dig dominio.com NS`|
|Solicitar transferencia completa|`dig axfr @SERVIDOR_DNS dominio.com`|
|Tipo de transferencia completa|`AXFR`|
|Registro administrativo|`SOA`|
|Riesgo principal|Divulgación de todos los registros de una zona.|
|Información obtenida|Subdominios, IP, servidores de correo y otros registros.|
|Causa de la vulnerabilidad|Permitir transferencias a clientes no autorizados.|
|Medida correctiva|Restringir las transferencias a servidores de confianza.|

**Idea clave:** una transferencia de zona DNS mal configurada puede revelar de una sola vez gran parte de la infraestructura DNS de un dominio. Por eso, comprobar AXFR es una técnica importante durante el reconocimiento autorizado.
