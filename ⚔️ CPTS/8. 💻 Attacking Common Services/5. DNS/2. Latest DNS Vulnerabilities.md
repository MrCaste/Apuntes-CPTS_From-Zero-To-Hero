
## 1. Subdomain Takeover

El **Subdomain Takeover** o secuestro de subdominios se produce cuando un subdominio de una organización apunta a un servicio externo que ya no está activo o cuyo recurso puede ser registrado por otra persona.

Es habitual que las empresas utilicen proveedores externos como AWS, GitHub u otros servicios para alojar contenido. Cuando dejan de utilizar estos servicios, pueden olvidarse de eliminar los registros DNS asociados.

Esto puede dejar subdominios apuntando a recursos inexistentes que un atacante podría llegar a reclamar.

### ¿Por qué ocurre?

Una organización puede tener un registro DNS como el siguiente:

```
customer-drive.inlanefreight.com CNAME inlanefreight.s3.amazonaws.com
```

Si el recurso de destino deja de existir, pero el registro `CNAME` permanece, puede existir una oportunidad de secuestro.

El problema aparece cuando el proveedor permite registrar o reclamar el recurso de destino y el atacante consigue vincularlo a su propia infraestructura.

**Importante:** un `CNAME` que apunta a un recurso inexistente no demuestra por sí solo que el subdominio sea vulnerable. Es necesario verificar que el recurso pueda reclamarse y que el proveedor permita asociarlo al subdominio.

---

## 2. Concepto del ataque

El riesgo principal es que el atacante puede llegar a controlar contenido accesible desde un subdominio legítimo de la organización.

Por ejemplo, un cliente visita:

```
customer-drive.inlanefreight.com
```

El usuario puede confiar en el enlace porque pertenece aparentemente al dominio oficial de la empresa. Sin embargo, si el subdominio está secuestrado, el contenido podría estar controlado por un atacante.

Esto puede utilizarse para alojar páginas fraudulentas y realizar campañas de phishing.

### Condiciones que pueden indicar una vulnerabilidad

Durante la enumeración, conviene buscar:

- Registros `CNAME` que apuntan a servicios de terceros.
    
- Recursos externos que ya no existen.
    
- Errores HTTP `404` u otros mensajes que indiquen un recurso ausente.
    
- Servicios que permiten registrar un recurso con el nombre necesario para asociarlo al subdominio.
    

Un error HTTP `404` es solamente un indicio: no confirma que el recurso pueda reclamarse.

---

## 3. Funcionamiento del Subdomain Takeover

El proceso descrito en el módulo puede dividirse en dos fases.

### Fase 1. Reclamar el recurso externo

1. **Origen:** se identifica un subdominio que la empresa ya no utiliza.
    
2. **Proceso:** se comprueba si el recurso externo al que apunta puede registrarse o reclamarse.
    
3. **Privilegios:** el propietario del dominio principal mantiene el control de los registros DNS, mientras que el proveedor externo gestiona su propio servicio.
    
4. **Destino:** si el recurso puede reclamarse y se configura correctamente, el atacante consigue controlar el contenido servido desde ese recurso.
    

### Fase 2. Acceso de los visitantes al recurso controlado

5. **Origen:** un usuario visita el subdominio legítimo.
    
6. **Proceso:** la resolución DNS sigue el registro `CNAME` existente hacia el servicio externo.
    
7. **Privilegios:** el servidor DNS continúa utilizando el registro configurado por la organización; el atacante no necesita modificar directamente la zona DNS si consigue reclamar el recurso externo.
    
8. **Destino:** el visitante puede terminar accediendo al contenido controlado por el atacante a través del subdominio original.
    

**Idea clave:** el atacante aprovecha un registro DNS obsoleto y la posibilidad de reclamar el recurso externo al que apunta.

---

## 4. Impacto y posibles ataques

Un subdominio secuestrado puede utilizarse para distintos ataques:

|Ataque|Posible impacto|
|---|---|
|Phishing|Alojar páginas fraudulentas que aparenten pertenecer a la organización.|
|Robo de cookies|Intentar obtener cookies cuando las condiciones del dominio, sus atributos y el contexto de la aplicación lo permitan.|
|CSRF|Intentar explotar la confianza del navegador en determinadas solicitudes entre sitios.|
|Abuso de CORS|Aprovechar políticas de intercambio de recursos entre orígenes mal configuradas.|
|Evasión de CSP|Intentar aprovechar políticas de seguridad de contenido que confíen en el subdominio comprometido.|

Estos impactos no son automáticos: dependen de la configuración del navegador, las políticas de seguridad, el alcance de las cookies y la arquitectura de la aplicación.

## 5. Procedimiento de enumeración

### Paso 1. Descubrir subdominios

Utilizar herramientas como Subfinder:

```
subfinder -d <DOMAIN> -v
```

### Paso 2. Identificar registros CNAME

Consultar un subdominio:

```
host <SUBDOMAIN>
```

Ejemplo:

```
host customer-drive.inlanefreight.com
```

También puede utilizarse:

```
nslookup <SUBDOMAIN>
```

### Paso 3. Investigar el destino

Si el resultado apunta a un proveedor externo, comprobar si el recurso sigue existiendo y si está correctamente asociado al servicio.

### Paso 4. Validar la posible vulnerabilidad

Verificar si el proveedor permite reclamar el recurso y si es posible asociarlo al subdominio afectado.

No debemos considerar confirmado un Subdomain Takeover únicamente porque exista un registro `CNAME` o aparezca un error al visitar el sitio.

---

## 6. Prevención

Para reducir el riesgo de secuestro de subdominios, las organizaciones deberían:

- Eliminar los registros DNS que apunten a servicios externos que ya no utilizan.
    
- Mantener un inventario actualizado de subdominios y proveedores externos.
    
- Revisar periódicamente los registros `CNAME`.
    
- Desvincular los recursos externos antes de cancelar un servicio.
    
- Supervisar los subdominios que apuntan a plataformas de terceros.

## 7. Resumen para el examen

|Concepto|Descripción|
|---|---|
|Vulnerabilidad|Subdomain Takeover|
|Causa habitual|Registro DNS obsoleto que apunta a un recurso externo reclamable.|
|Registro relevante|`CNAME`|
|Servicios implicados|Proveedores externos de alojamiento y otros servicios.|
|Indicadores|Recurso inexistente, errores de servicio o configuración DNS obsoleta.|
|Condición fundamental|Que el recurso de destino pueda reclamarse y asociarse al subdominio.|
|Impacto|Phishing y posibles ataques contra aplicaciones que confían en el subdominio.|
|Prevención|Eliminar registros DNS obsoletos y revisar los recursos externos asociados.|

### Idea clave

**Un Subdomain Takeover aprovecha un registro DNS que sigue apuntando a un recurso externo abandonado o reclamable.** Si un atacante consigue controlar ese recurso, puede llegar a servir contenido bajo un subdominio legítimo de la organización, lo que puede facilitar ataques de phishing y otros abusos dependiendo de la configuración de la aplicación.
