
## 1. Sesiones en Metasploit

Las **sesiones** permiten gestionar los canales de comunicación establecidos con los sistemas objetivo mediante exploits y otros módulos.

Permiten:

- Mantener conexiones con los objetivos mientras trabajamos con otros módulos.
    
- Cambiar entre distintas sesiones activas.
    
- Ejecutar módulos de post-explotación sobre sistemas comprometidos.
    
- Mantener conexiones en segundo plano sin perder el acceso al objetivo.
    

Una sesión en segundo plano continúa ejecutándose y mantiene la conexión con el objetivo, siempre que el payload y el canal de comunicación sigan funcionando correctamente.

## 2. Poner una sesión en segundo plano

Cuando un exploit establece una sesión, podemos volver al prompt de `msfconsole` sin cerrar necesariamente la conexión.

Hay dos formas de hacerlo:

**Opción 1: combinación de teclas**

```
CTRL + Z
```

Se solicitará confirmación para poner la sesión en segundo plano.

**Opción 2: comando** `**background**`

Desde una sesión Meterpreter:

```
background
```

Volveremos al prompt de Metasploit y podremos ejecutar otros módulos mientras la sesión permanece activa.

## 3. Listar las sesiones activas

Para mostrar las sesiones existentes:

```
sessions
```

La salida permite consultar información como:

- ID de la sesión.
    
- Tipo de sesión.
    
- Sistema y usuario comprometidos.
    
- Información de la conexión.
    

Ejemplo:

```
Active sessions
===============

Id  Name  Type                     Information
--  ----  ----                     -----------
1         meterpreter x86/windows  NT AUTHORITY\SYSTEM @ MS01
```

El identificador permite seleccionar la sesión con la que queremos trabajar.

## 4. Interactuar con una sesión

Para entrar en una sesión específica:

```
sessions -i 1
```

Donde `1` es el ID de la sesión.

Una vez conectados, podremos ejecutar los comandos disponibles en esa sesión, por ejemplo:

```
meterpreter >
```

### Flujo de trabajo: ejecutar un módulo sobre una sesión existente

1. Poner la sesión actual en segundo plano.
    
2. Seleccionar el módulo que queremos ejecutar.
    
3. Consultar sus opciones:
    

```
show options
```

4. Si el módulo lo permite, establecer el ID de la sesión:
    

```
set SESSION 1
```

5. Ejecutar el módulo:
    

```
run
```

Los módulos de post-explotación (`post`) son especialmente útiles para trabajar sobre sistemas ya comprometidos.

Entre sus funciones habituales se encuentran:

- Recopilación de credenciales.
    
- Comprobaciones relacionadas con posibles exploits locales.
    
- Escaneo de redes internas.
    

**Importante:** El nombre exacto de la opción para seleccionar una sesión depende del módulo. Compruébalo con `show options`.

## 5. Jobs: tareas en segundo plano

Los **jobs** permiten ejecutar tareas de Metasploit en segundo plano.

Son especialmente útiles cuando un módulo necesita mantener un puerto ocupado, como ocurre con un handler que escucha conexiones entrantes.

Si detenemos una tarea de forma incorrecta o dejamos un handler ejecutándose, podemos tener problemas al intentar utilizar el mismo puerto con otro módulo.

Los jobs permiten identificar esas tareas y detenerlas cuando sea necesario.

## 6. Ejecutar un exploit como job

Podemos ejecutar un exploit como tarea en segundo plano añadiendo `-j`:

```
exploit -j
```

También puede utilizarse:

```
run -j
```

La opción `-j` ejecuta el módulo en el contexto de un job, permitiéndonos continuar trabajando desde `msfconsole`.

Ejemplo:

```
msf6 exploit(multi/handler) > exploit -j
```

Posible salida:

```
[*] Exploit running as background job 0.
[*] Exploit completed, but no session was created.
[*] Started reverse TCP handler on 10.10.14.34:4444
```

**Importante:** Que el job se haya iniciado no significa que se haya creado una sesión. El handler puede estar esperando una conexión entrante.

## 7. Gestionar los jobs

### Consultar la ayuda

```
jobs -h
```

### Listar los jobs activos

```
jobs -l
```

Ejemplo:

```
Jobs
====

Id  Name                    Payload                    Payload opts
--  ----                    -------                    ------------
0   Exploit: multi/handler  generic/shell_reverse_tcp  tcp://10.10.14.34:4444
```

El ID identifica cada job.

### Consultar información detallada

```
jobs -i 0
```

Muestra información sobre el job indicado.

### Detener un job específico

Según la ayuda del material, puede utilizarse:

```
jobs -k 0
```

Donde `0` es el ID del job.

### Detener todos los jobs

```
jobs -K
```

### Ayuda rápida de las opciones

|Opción|Función|
|---|---|
|`-l`|Listar los jobs activos.|
|`-i <ID>`|Mostrar información detallada de un job.|
|`-k <ID>`|Detener uno o varios jobs.|
|`-K`|Detener todos los jobs.|
|`-v`|Mostrar información más detallada junto con `-i` o `-l`.|
|`-h`|Mostrar la ayuda.|
|`-p <ID>`|Añadir persistencia a un job.|
|`-P`|Hacer persistentes todos los jobs al reiniciar.|

## 8. Diferencias entre Sessions y Jobs

|Característica|Sessions|Jobs|
|---|---|---|
|Función|Gestionar canales de comunicación con objetivos.|Gestionar tareas ejecutadas en segundo plano.|
|Comando principal|`sessions`|`jobs`|
|Listar elementos|`sessions`|`jobs -l`|
|Interactuar|`sessions -i <ID>`|`jobs -i <ID>` para consultar información detallada.|
|Poner en segundo plano|`background` o `CTRL + Z`|`exploit -j` para iniciar un exploit como job.|
|Detener|Depende del tipo de sesión y del método utilizado.|`jobs -k <ID>`|

### Conceptos clave para el examen

- **Session:** representa un canal de comunicación con un sistema objetivo.
    
- `**background**`**:** devuelve el control a Metasploit sin cerrar necesariamente la sesión.
    
- `**sessions -i <ID>**`**:** permite interactuar con una sesión concreta.
    
- **Job:** representa una tarea ejecutada en segundo plano.
    
- `**exploit -j**`**:** inicia un exploit en el contexto de un job.
    
- `**jobs -l**`**:** muestra los jobs activos.
    
- `**jobs -k <ID>**`**:** detiene un job específico.
    
- `**jobs -K**`**:** detiene todos los jobs.
    

**Idea clave:** Las sesiones permiten conservar e interactuar con conexiones establecidas con los objetivos; los jobs permiten controlar tareas que se ejecutan en segundo plano. Ambos mecanismos facilitan trabajar con varios módulos sin tener que interrumpir constantemente las operaciones.
