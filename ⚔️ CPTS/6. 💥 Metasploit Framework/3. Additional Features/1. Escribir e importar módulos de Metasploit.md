
## 1. Buscar módulos existentes

Si un exploit no está disponible en nuestra versión de Metasploit, podemos buscarlo en **ExploitDB** y descargar el módulo individualmente, sin necesidad de actualizar todo el framework.

- **ExploitDB:** permite filtrar exploits por plataforma, tipo y etiqueta.
    
- **Etiqueta MSF:** muestra exploits disponibles en formato de módulo de Metasploit.
    
- **SearchSploit:** herramienta de terminal para buscar exploits en la base de datos local.
    

### Comandos de búsqueda

```
# Buscar exploits relacionados con Nagios3
searchsploit nagios3

# Buscar por título y excluir archivos Python
searchsploit -t Nagios3 --exclude=".py"
```

Los archivos `.rb` están escritos en Ruby, pero **no todos los scripts Ruby son módulos compatibles con Metasploit**.

También podemos buscar directamente desde `msfconsole`:

```
msf6 > search nagios
```

Si el módulo aparece en ExploitDB o SearchSploit, pero no en Metasploit, podemos descargarlo e instalarlo manualmente.

## 2. Directorios de Metasploit

Los directorios principales son:

```
# Directorio principal del framework
/usr/share/metasploit-framework/

# Directorio personal de configuración y módulos
~/.msf4/
```

Los módulos personalizados suelen guardarse dentro de `~/.msf4/modules/` o en la estructura correspondiente de `/usr/share/metasploit-framework/modules/`.

### Estructura de los módulos

La ruta debe coincidir con el tipo de módulo y la plataforma correspondiente. Por ejemplo:

```
modules/
└── exploits/
    └── unix/
        └── webapp/
            └── nagios3_command_injection.rb
```

Si las carpetas necesarias no existen, hay que crearlas.

### Convenciones de nombres

Utiliza nombres descriptivos en formato `snake_case`:

```
nagios3_command_injection.rb
our_module_here.rb
```

Evita los guiones y utiliza caracteres alfanuméricos y guiones bajos.

## 3. Importar un módulo personalizado

Ejemplo del módulo de Nagios3 mostrado en el curso:

```
# Copiar el módulo descargado a la carpeta correspondiente
sudo cp ~/Downloads/9861.rb \
/usr/share/metasploit-framework/modules/exploits/unix/webapp/nagios3_command_injection.rb
```

### Cargar los módulos

Podemos cargar módulos desde una ruta específica al iniciar Metasploit:

```
msfconsole -m /usr/share/metasploit-framework/modules/
```

O, desde una sesión abierta de `msfconsole`:

```
msf6 > loadpath /usr/share/metasploit-framework/modules/
```

También podemos recargar los módulos:

```
msf6 > reload_all
```

### Comprobar que el módulo funciona

```
msf6 > search nagios3_command_injection
msf6 > use exploit/unix/webapp/nagios3_command_injection
msf6 exploit(unix/webapp/nagios3_command_injection) > show options
```

Antes de ejecutarlo, revisa sus opciones y configura los parámetros necesarios para el objetivo.

**Importante:** si el módulo no aparece, comprueba la ruta, el nombre del archivo, la estructura de directorios y si el script realmente es compatible con Metasploit.

## 4. Adaptar scripts a módulos de Metasploit

Si encontramos un exploit personalizado escrito en Python, PHP u otro lenguaje, podemos adaptarlo a Metasploit mediante Ruby.

Para hacerlo, necesitamos conocer la estructura de los módulos del framework y los métodos, clases y mixins que utiliza.

En lugar de empezar desde cero, podemos utilizar un módulo existente de la misma categoría como plantilla.

### Ejemplo: adaptar un exploit de Bludit

El curso utiliza el exploit de Bludit 3.9.2 para ilustrar la adaptación de un script que permite comprobar contraseñas aprovechando una vulnerabilidad en el mecanismo de protección contra intentos repetidos de autenticación.

Primero, buscamos módulos de Bludit existentes:

```
ls /usr/share/metasploit-framework/modules/exploits/linux/http/ | grep bludit
```

Después, copiamos el script descargado a esa carpeta con un nombre descriptivo:

```
sudo cp ~/Downloads/48746.rb \
/usr/share/metasploit-framework/modules/exploits/linux/http/bludit_auth_bruteforce_mitigation_bypass.rb
```

El archivo debe adaptarse para utilizar correctamente la estructura y las funcionalidades de Metasploit. Copiarlo y cambiarle el nombre no garantiza que funcione.

## 5. Estructura de un módulo Ruby

Un módulo de Metasploit utiliza una clase principal y puede incorporar mixins mediante sentencias `include`.

Ejemplo del curso:

```
class MetasploitModule < Msf::Exploit::Remote
  Rank = ExcellentRanking

  include Msf::Exploit::Remote::HttpClient
  include Msf::Exploit::PhpEXE
  include Msf::Exploit::FileDropper
  include Msf::Auxiliary::Report
end
```

### Función de los mixins

|Mixin|Función|
|---|---|
|`Msf::Exploit::Remote::HttpClient`|Proporciona métodos para interactuar con servidores HTTP.|
|`Msf::Exploit::PhpEXE`|Permite generar un payload PHP de primera etapa.|
|`Msf::Exploit::FileDropper`|Ayuda a gestionar la limpieza de archivos después de establecer una sesión.|
|`Msf::Auxiliary::Report`|Proporciona métodos para registrar información en la base de datos de Metasploit.|

Debemos incluir únicamente las funcionalidades que necesita nuestro módulo.

Para consultar los métodos, clases y mixins disponibles, utiliza la documentación oficial de Metasploit.

## 6. Definir la información del módulo

La función `initialize` establece los metadatos que aparecerán al consultar la información del módulo.

Ejemplo simplificado:

```
def initialize(info = {})
  super(update_info(info,
    'Name'           => 'Nombre del módulo',
    'Description'    => %q{
      Descripción de la vulnerabilidad y su funcionamiento.
    },
    'License'        => MSF_LICENSE,
    'Author'         => ['Autor original', 'Autor del módulo'],
    'References'     => [
      ['CVE', 'XXXX-XXXXX'],
      ['URL', 'https://example.com']
    ],
    'Platform'       => 'php',
    'Arch'           => ARCH_PHP,
    'Targets'        => [
      ['Versión vulnerable', {}]
    ],
    'Privileged'     => false,
    'DefaultTarget'  => 0
  ))
end
```

Los campos principales son:

|Campo|Propósito|
|---|---|
|`Name`|Nombre del módulo.|
|`Description`|Descripción de la vulnerabilidad.|
|`License`|Licencia del módulo.|
|`Author`|Autores del descubrimiento y del módulo.|
|`References`|Referencias a CVE, publicaciones y parches.|
|`Platform`|Plataforma objetivo.|
|`Arch`|Arquitectura o tipo de payload.|
|`Targets`|Versiones o configuraciones objetivo.|
|`Privileged`|Indica si el módulo requiere o utiliza privilegios.|
|`DisclosureDate`|Fecha de divulgación de la vulnerabilidad.|
|`DefaultTarget`|Objetivo seleccionado por defecto.|

El módulo también puede incluir `Notes` para describir efectos secundarios, fiabilidad y estabilidad.

## 7. Definir las opciones del módulo

Las opciones se registran mediante `register_options`. En el ejemplo original de Bludit, se definen la ruta base, el usuario y la contraseña:

```
register_options(
  [
    OptString.new('TARGETURI', [true, 'The base path for Bludit', '/']),
    OptString.new('BLUDITUSER', [true, 'The username for Bludit']),
    OptString.new('BLUDITPASS', [true, 'The password for Bludit'])
  ]
)
```

En la adaptación del curso, se sustituye la contraseña individual por una ruta a una lista de contraseñas:

```
OptPath.new('PASSWORDS', [
  true,
  'The list of passwords',
  File.join(Msf::Config.data_directory, 'wordlists', 'passwords.txt')
])
```

De esta forma, el módulo puede recibir una wordlist mediante la opción `PASSWORDS`.

### Tipos utilizados en el ejemplo

- `OptString`: define una opción de tipo texto.
    
- `OptPath`: define una opción que representa una ruta de archivo.
    

El primer parámetro del array indica si la opción es obligatoria; los demás describen la opción y su valor predeterminado cuando corresponde.

## 8. Adaptar la lógica del exploit

Después de definir los metadatos y las opciones, hay que adaptar la lógica del script original para utilizar los métodos y las convenciones del framework.

En el ejemplo de Bludit, el código trabaja con elementos como:

- Obtención del token CSRF.
    
- Preparación de las peticiones HTTP.
    
- Envío de los datos de autenticación.
    
- Lectura de una wordlist.
    
- Comprobación de si la autenticación ha tenido éxito.
    

No basta con cambiar el nombre del archivo ni con añadir los metadatos: el código debe integrarse correctamente con las clases y métodos de Metasploit.

Para resolver dudas sobre los métodos disponibles, consulta la documentación oficial del framework.

## 9. Flujo de trabajo para el examen

```
1. Buscar el exploit
   ├── msfconsole: search <término>
   └── Terminal: searchsploit <término>

2. Comprobar si está disponible como módulo de Metasploit
   └── Identificar el archivo y su formato

3. Descargar el módulo
   └── Obtener el archivo desde una fuente apropiada

4. Instalarlo
   ├── Elegir la categoría correcta
   ├── Crear los directorios necesarios
   └── Copiar el archivo con un nombre válido

5. Cargar o recargar los módulos
   ├── loadpath <ruta>
   └── reload_all

6. Verificar que Metasploit lo reconoce
   ├── search <nombre>
   ├── use <ruta_del_módulo>
   └── show options

7. Si el script no es compatible
   ├── Elegir un módulo existente como plantilla
   ├── Adaptar los mixins
   ├── Definir metadatos y opciones
   └── Adaptar la lógica del exploit
```

### Puntos clave

- **ExploitDB y SearchSploit** permiten localizar exploits que no están disponibles en la instalación actual.
    
- Los archivos `.rb` no son necesariamente módulos compatibles con Metasploit.
    
- La ubicación, la estructura de directorios y el nombre del archivo importan.
    
- `loadpath` y `reload_all` permiten cargar módulos adicionales sin realizar necesariamente una actualización completa.
    
- Los módulos de Metasploit están escritos en Ruby y utilizan clases, métodos y mixins.
    
- Para adaptar un exploit, es recomendable partir de un módulo existente y consultar la documentación oficial.
    
- Un módulo personalizado debe definir sus metadatos, opciones y lógica de explotación antes de poder utilizarse correctamente.
