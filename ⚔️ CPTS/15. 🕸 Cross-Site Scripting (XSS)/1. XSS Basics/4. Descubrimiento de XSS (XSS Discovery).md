
## 🔎 1. Descubrimiento automatizado

Existen herramientas que permiten detectar posibles vulnerabilidades XSS mediante el análisis del código y el envío de payloads.

### Escáneres de vulnerabilidades

|Herramienta|Características|
|---|---|
|**Burp Suite Professional**|Permite realizar análisis activos y pasivos de aplicaciones web.|
|**OWASP ZAP**|Escáner de aplicaciones web con capacidades de detección de XSS.|
|**Nessus**|Escáner de vulnerabilidades que incluye comprobaciones de seguridad web.|

Los escáneres pueden utilizar dos tipos de análisis:

- **Passive Scan:** analiza el contenido y el código del lado del cliente para identificar posibles vulnerabilidades, incluidas algunas relacionadas con DOM XSS.
    
- **Active Scan:** envía payloads para intentar provocar vulnerabilidades y comprobar cómo responde la aplicación.
    

### Herramientas de código abierto

Algunas herramientas habituales para detectar XSS son:

- **XSStrike**
    
- **Brute XSS**
    
- **XSSer**
    

Estas herramientas suelen identificar entradas, enviar diferentes payloads y analizar cómo se reflejan en las respuestas.

**Importante:** encontrar un payload en el HTML no demuestra necesariamente que se haya ejecutado JavaScript. Siempre hay que verificar manualmente los resultados.

## 🛠️ 2. Instalación y uso de XSStrike

### Clonar el repositorio

```
git clone https://github.com/s0md3v/XSStrike.git
cd XSStrike
```

### Instalar dependencias

```
pip install -r requirements.txt
```

### Ejecutar la herramienta

```
python xsstrike.py
```

### Analizar un parámetro vulnerable

Utiliza `-u` para indicar la URL que quieres analizar:

```
python xsstrike.py -u "http://SERVER_IP:PORT/index.php?task=test"
```

En este ejemplo, la aplicación recibe el parámetro `task`.

XSStrike analiza el parámetro y prueba distintos payloads para comprobar si la entrada puede provocar XSS.

### Interpretar los resultados

Ejemplo de salida:

```
[~] Checking for DOM vulnerabilities
[+] WAF Status: Offline
[!] Testing parameter: task
[!] Reflections found: 1
[~] Analysing reflections
[~] Generating payloads
[!] Payloads generated: 3072
[+] Payload: <HtMl%09onPoIntERENTER+=+confirm()>
[!] Efficiency: 100
[!] Confidence: 10
```

|Resultado|Significado|
|---|---|
|`Checking for DOM vulnerabilities`|Comprueba posibles vulnerabilidades DOM.|
|`WAF Status: Offline`|No detecta un WAF activo según la comprobación de la herramienta.|
|`Testing parameter: task`|Está analizando el parámetro `task`.|
|`Reflections found: 1`|Ha encontrado una reflexión de la entrada.|
|`Payloads generated`|Cantidad de payloads generados para las pruebas.|
|`Payload`|Payload que la herramienta considera relevante para la prueba.|
|`Efficiency`|Indicador de eficiencia calculado por la herramienta.|
|`Confidence`|Indicador de confianza calculado por la herramienta.|

**Nota:** los indicadores de eficiencia y confianza son métricas propias de XSStrike; no deben interpretarse como una garantía de explotación exitosa.

## 🧪 3. Descubrimiento manual

El descubrimiento manual consiste en introducir payloads de prueba en las entradas de una aplicación y observar cómo se procesan.

### Procedimiento

1. Identificar campos y parámetros controlados por el usuario.
    
2. Introducir un valor de prueba.
    
3. Comprobar si la entrada aparece en la respuesta.
    
4. Probar un payload XSS apropiado para el contexto.
    
5. Observar si se ejecuta JavaScript.
    
6. Inspeccionar el código fuente y el DOM.
    
7. Determinar si la vulnerabilidad es Stored XSS, Reflected XSS o DOM XSS.
    

### Dónde buscar puntos de inyección

El XSS no se limita a los campos de los formularios HTML. También puede aparecer cuando la aplicación utiliza otros datos controlados por el usuario, como:

- Parámetros GET y POST.
    
- Campos de entrada.
    
- Cabeceras HTTP.
    
- Cookies.
    
- Cabecera `User-Agent`.
    

Por ejemplo, una aplicación podría mostrar en una página el valor de `User-Agent` recibido en una petición. Si lo inserta de forma insegura en el HTML, podría existir una vulnerabilidad XSS.

### Payloads XSS

Se pueden utilizar listas públicas de payloads para realizar pruebas:

- **PayloadsAllTheThings**
    
- **Payload-Box**
    

Sin embargo, no todos los payloads funcionan en todos los contextos.

Esto puede deberse a que:

- El payload está diseñado para una ubicación concreta dentro del HTML.
    
- Depende de una comilla simple o doble determinada.
    
- La aplicación aplica filtros o sanitización.
    
- El payload necesita un vector de inyección específico.
    
- El navegador no ejecuta el código en el contexto esperado.
    

Por tanto, no es eficiente copiar y pegar listas completas sin analizar primero cómo procesa la entrada la aplicación.

## 🔬 4. Revisión manual del código

La revisión manual del código es uno de los métodos más fiables para identificar vulnerabilidades XSS, especialmente cuando las herramientas automáticas no detectan el problema.

Debe analizarse cómo viajan los datos desde la entrada del usuario hasta el navegador.

### Revisión del frontend

En JavaScript, identifica:

- **Sources:** lugares de los que se obtienen datos controlados por el usuario.
    
- **Sinks:** funciones que utilizan esos datos para modificar el DOM.
    
- **Sanitización:** mecanismos que impiden que la entrada se interprete como código ejecutable.
    

Ejemplo de un posible flujo vulnerable:

```
var task = new URLSearchParams(window.location.search).get("task");

document.getElementById("todo").innerHTML = task;
```

En este ejemplo:

1. El parámetro `task` procede de la URL.
    
2. JavaScript obtiene su valor.
    
3. `innerHTML` lo inserta como HTML.
    
4. Si la entrada no se trata de forma segura, podría existir DOM XSS.
    

Este fragmento es un ejemplo ilustrativo del flujo fuente-sumidero, no código extraído del laboratorio.

### Revisión del backend

También es importante comprobar si el servidor:

- Devuelve entradas del usuario en sus respuestas.
    
- Incluye datos en mensajes de error o confirmación.
    
- Escapa correctamente los caracteres especiales.
    
- Aplica validaciones y sanitización apropiadas para el contexto.
    

La revisión del backend resulta especialmente relevante para identificar Stored XSS y Reflected XSS.

## ⚖️ 5. Comparación de métodos de detección

|Método|Ventajas|Limitaciones|
|---|---|---|
|Escáneres automatizados|Analizan muchas entradas rápidamente.|Pueden producir falsos positivos o no detectar vulnerabilidades complejas.|
|Herramientas especializadas como XSStrike|Generan y prueban payloads automáticamente.|Los resultados requieren verificación manual.|
|Pruebas manuales|Permiten estudiar el comportamiento real de la aplicación.|Pueden consumir mucho tiempo.|
|Revisión de código|Permite seguir el flujo de datos e identificar fuentes y sumideros inseguros.|Requiere acceso al código y conocimientos técnicos.|

## ⚡ 6. Flujo práctico de enumeración

1. **Enumerar las entradas:** formularios, parámetros URL, cookies y cabeceras.
    
2. **Probar una reflexión:** introducir un valor identificable y comprobar si aparece en la respuesta.
    
3. **Ejecutar un análisis automatizado:** utilizar XSStrike u otra herramienta disponible.
    
4. **Revisar los resultados:** identificar parámetros y payloads señalados.
    
5. **Verificar manualmente:** comprobar si el payload se ejecuta realmente.
    
6. **Inspeccionar el contexto:** analizar el HTML, el DOM y las solicitudes HTTP.
    
7. **Revisar el código cuando sea posible:** identificar Sources, Sinks y mecanismos de sanitización.
    
8. **Documentar la vulnerabilidad:** registrar el parámetro, el contexto, la prueba y el impacto observado.

- **Passive Scan:** analiza la aplicación sin enviar payloads de explotación.
    
- **Active Scan:** envía payloads para comprobar posibles vulnerabilidades.
    
- **XSStrike:** herramienta especializada en la detección y análisis de XSS.
    
- `**git clone**`**:** descarga el repositorio de la herramienta.
    
- `**pip install -r requirements.txt**`**:** instala las dependencias indicadas.
    
- `**python xsstrike.py -u "URL"**`**:** analiza una URL y sus parámetros.
    
- **Reflections found:** indica que se ha encontrado una reflexión de la entrada, no que la explotación esté confirmada.
    
- **Pruebas manuales:** permiten comprobar el comportamiento real del payload.
    
- **Puntos de inyección:** pueden incluir parámetros, formularios, cookies y cabeceras HTTP.
    
- **Revisión de código:** permite identificar el flujo desde la fuente hasta el sumidero y comprobar cómo se trata la entrada.
    
- **Regla fundamental:** un resultado automático es un indicio; hay que verificar manualmente si existe ejecución de JavaScript.
