
## 📌 Concepto

El **XSS reflejado** es una vulnerabilidad en la que una entrada controlada por el usuario llega al servidor backend y se devuelve en la respuesta HTTP sin filtrarse ni sanearse correctamente.

La entrada puede aparecer, por ejemplo, en:

- Mensajes de error.
    
- Mensajes de confirmación.
    
- Respuestas que muestran los datos enviados por el usuario.
    

A diferencia del **Stored XSS**, el payload no se almacena de forma persistente.

### Características principales

- **No persistente:** el payload no permanece almacenado para ejecutarse en futuras visitas.
    
- **Procesado por el servidor:** la entrada llega al backend y se incluye en la respuesta.
    
- **Requiere que la víctima envíe la entrada:** por ejemplo, visitando una URL manipulada.
    
- **Puede afectar a otros usuarios:** si visitan una URL preparada y vulnerable, el payload puede ejecutarse en su navegador.
    

## 🔎 Detección de Reflected XSS

### 1. Identificar una entrada reflejada

Introduce un valor de prueba en un formulario y observa cómo responde la aplicación.

Ejemplo de mensaje de error:

```
Task 'test' could not be added.
```

La aplicación ha incluido nuestra entrada `test` dentro del mensaje de error.

Esto puede indicar una posible vulnerabilidad, pero es necesario comprobar si la entrada se interpreta como código ejecutable.

### 2. Probar un payload XSS

```
<script>alert(window.origin)</script>
```

Si el navegador muestra una alerta con el origen de la página, significa que el JavaScript se ha ejecutado.

Un ejemplo de respuesta HTML vulnerable sería:

```
<div style="padding-left:25px">
    Task '<script>alert(window.origin)</script>' could not be added.
</div>
```

El payload aparece dentro del mensaje de error y el navegador interpreta la etiqueta `<script>` como código JavaScript.

### 3. Inspeccionar el código fuente

Pulsa `Ctrl + U` o utiliza las herramientas de desarrollador para comprobar cómo se refleja la entrada en el HTML.

Busca el payload y determina si el navegador lo está interpretando como código o mostrándolo como texto.

**Importante:** que una entrada aparezca en el HTML no demuestra por sí solo que exista XSS. Debe comprobarse si el contenido se ejecuta.

### 4. Comprobar que no es persistente

Vuelve a visitar la página o abandona la respuesta que contiene el mensaje de error.

Si el payload deja de ejecutarse porque el mensaje ya no aparece, el comportamiento es consistente con un **XSS reflejado**.

## 🌐 Identificar cómo se envía la entrada

Para saber cómo llega el payload al servidor, utiliza las herramientas de desarrollador de Firefox.

1. Pulsa `Ctrl + Shift + I`.
    
2. Abre la pestaña **Network**.
    
3. Envía de nuevo una entrada de prueba.
    
4. Selecciona la solicitud HTTP generada.
    
5. Comprueba el método HTTP y los parámetros enviados.
    

En el laboratorio, la entrada se envía mediante una solicitud **GET**.

Las solicitudes GET pueden incluir parámetros en la URL, lo que permite construir un enlace que contenga la entrada vulnerable.

Ejemplo del laboratorio:

```
GET /index.php?task=test HTTP/1.1
```

## 🎯 Explotación mediante una URL

Si el parámetro vulnerable es `task` y la aplicación lo refleja sin sanearlo, una URL de prueba sería:

```
http://SERVER_IP:PORT/index.php?task=<script>alert(window.origin)</script>
```

Para construirla correctamente:

1. Envía el payload desde el formulario.
    
2. Abre las herramientas de desarrollador y selecciona **Network**.
    
3. Identifica la solicitud GET.
    
4. Haz clic derecho sobre ella y selecciona **Copy → Copy URL**.
    
5. Utiliza la URL obtenida para comprobar la vulnerabilidad en el contexto del laboratorio.
    

Si otra persona visita un enlace preparado y la aplicación sigue siendo vulnerable, el JavaScript puede ejecutarse en el navegador de esa persona.

> En un entorno real, los caracteres especiales del payload pueden necesitar codificación URL para que el enlace se interprete correctamente.

## ⚖️ Diferencias entre Stored XSS y Reflected XSS

|Característica|Stored XSS|Reflected XSS|
|---|---|---|
|Persistencia|Sí, el payload queda almacenado.|No, el payload se refleja en una respuesta.|
|Ubicación habitual|Contenido almacenado en el backend.|Parámetros o entradas reflejadas por el servidor.|
|Forma de ejecución|Al visitar una página que muestra el contenido almacenado.|Al enviar una entrada vulnerable, por ejemplo, mediante una URL.|
|Víctimas potenciales|Usuarios que visiten la página con el contenido malicioso.|Usuarios que interactúen con la entrada vulnerable, por ejemplo, visitando un enlace.|
|Comprobación|Recargar la página para comprobar si persiste.|Comprobar si el payload se refleja y deja de ejecutarse cuando desaparece la respuesta correspondiente.|

## ⚡ Flujo práctico de enumeración

1. **Buscar entradas controladas por el usuario:** formularios, parámetros GET, mensajes de error o confirmaciones.
    
2. **Introducir un valor de prueba:** comprobar si aparece en la respuesta.
    
3. **Probar un payload inocuo:** utilizar `alert(window.origin)`.
    
4. **Inspeccionar la respuesta HTML:** comprobar cómo se incorpora la entrada.
    
5. **Revisar la solicitud HTTP:** identificar el método y los parámetros mediante la pestaña Network.
    
6. **Comprobar la persistencia:** determinar si el payload permanece después de abandonar o recargar la página.
    
7. **Analizar el vector de ataque:** si se utiliza GET, comprobar si puede reproducirse mediante una URL preparada.
    

## 🧠 Chuleta para el examen

- **Reflected XSS:** el servidor devuelve una entrada controlada por el usuario sin sanearla correctamente.
    
- **Non-Persistent XSS:** el payload no queda almacenado para futuras visitas.
    
- **Stored XSS:** el payload se almacena y puede ejecutarse en visitas posteriores.
    
- `**alert(window.origin)**`**:** payload básico para comprobar la ejecución de JavaScript.
    
- `**Ctrl + Shift + I**`**:** abre las herramientas de desarrollador de Firefox.
    
- **Network:** permite inspeccionar las solicitudes HTTP.
    
- **GET:** puede transportar parámetros dentro de la URL.
    
- **Copy → Copy URL:** permite copiar la URL de una solicitud desde Network.
    
- **Impacto:** una víctima puede ejecutar el payload al visitar una URL vulnerable preparada para ella.
