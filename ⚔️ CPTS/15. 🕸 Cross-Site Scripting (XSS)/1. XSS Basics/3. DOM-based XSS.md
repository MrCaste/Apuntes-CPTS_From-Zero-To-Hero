
## 📌 Concepto

El **DOM XSS** es una vulnerabilidad de XSS no persistente que se procesa completamente en el lado del cliente, mediante JavaScript, sin necesidad de que la entrada llegue al servidor backend.

Ocurre cuando JavaScript utiliza datos controlados por el usuario para modificar el **DOM (Document Object Model)** de la página y estos datos se insertan sin una sanitización adecuada.

### Características principales

- **Se procesa en el navegador:** la entrada se manipula mediante JavaScript.
    
- **No necesita llegar al backend:** la vulnerabilidad puede producirse completamente en el cliente.
    
- **No es persistente:** al recargar la página, la modificación del DOM puede desaparecer.
    
- **Puede explotarse mediante una URL:** si la aplicación obtiene los datos de ella, se puede preparar un enlace que active el payload.
    

## 🔎 Cómo identificar DOM XSS

### 1. Observar el comportamiento de la aplicación

Introduce un valor de prueba, por ejemplo:

```
test
```

Comprueba si la página muestra el valor introducido.

### 2. Inspeccionar las peticiones HTTP

1. Pulsa `Ctrl + Shift + I` para abrir las herramientas de desarrollador de Firefox.
    
2. Accede a la pestaña **Network**.
    
3. Introduce de nuevo el valor de prueba.
    
4. Comprueba si se genera alguna petición HTTP.
    

Si la entrada se procesa sin generar una petición al servidor, puede indicar que la operación se realiza en el cliente.

### 3. Revisar la URL

En el laboratorio, la URL utiliza el carácter `#`:

```
http://SERVER_IP:PORT/#task=test
```

El fragmento que aparece después de `#` se procesa en el navegador y no se envía al servidor como parte de la petición HTTP.

Esto es una pista de que JavaScript podría estar utilizando ese valor para modificar el DOM.

**Importante:** encontrar un fragmento `#` o no observar una petición HTTP no demuestra por sí solo que exista DOM XSS. Hay que analizar cómo se utiliza la entrada.

### 4. Inspeccionar el DOM renderizado

Pulsa `Ctrl + Shift + C` para abrir el inspector de elementos de Firefox.

A diferencia de `Ctrl + U`, que muestra el código fuente original de la página, el inspector permite examinar el DOM actual después de las modificaciones realizadas por JavaScript.

Por eso, una entrada añadida dinámicamente puede aparecer en el inspector aunque no figure en el código fuente original.

## 🔗 Source y Sink

Para detectar DOM XSS es fundamental identificar dos elementos: **Source (fuente)** y **Sink (sumidero)**.

### Source — Fuente

Es el origen de los datos controlados por el usuario que JavaScript lee.

Ejemplos:

- Parámetros de una URL.
    
- Campos de entrada.
    
- Datos que la aplicación procesa en el navegador.
    

En el laboratorio, la fuente obtiene el parámetro `task` de la URL:

```
var pos = document.URL.indexOf("task=");
var task = document.URL.substring(pos + 5, document.URL.length);
```

El código busca `task=` y extrae el contenido que aparece a continuación.

### Sink — Sumidero

Es la función que utiliza los datos para escribir contenido en el DOM.

Algunos ejemplos habituales:

|Función|Uso|
|---|---|
|`document.write()`|Escribe contenido en el documento.|
|`element.innerHTML`|Interpreta y establece contenido HTML dentro de un elemento.|
|`element.outerHTML`|Sustituye un elemento por contenido HTML.|
|jQuery `.add()`|Añade elementos a una colección jQuery; su comportamiento depende del uso.|
|jQuery `.after()`|Inserta contenido después de un elemento.|
|jQuery `.append()`|Añade contenido al final de un elemento.|

Un sink que recibe datos controlados por el usuario sin una validación o sanitización adecuada puede introducir una vulnerabilidad.

### Ejemplo del laboratorio

El código obtiene el parámetro `task` y después lo inserta en el elemento `todo`:

```
document.getElementById("todo").innerHTML =
    "<b>Next Task:</b> " + decodeURIComponent(task);
```

El flujo es el siguiente:

1. **Source:** se obtiene `task` de la URL.
    
2. **Procesamiento:** se aplica `decodeURIComponent(task)`.
    
3. **Sink:** se inserta el resultado mediante `innerHTML`.
    
4. **Problema:** la entrada se interpreta como HTML sin una sanitización adecuada.
    

La combinación de una fuente controlable y un sink peligroso permite identificar el posible DOM XSS.

## 💥 Explotación de DOM XSS

### ¿Por qué puede fallar `<script>`?

En este laboratorio, el siguiente payload no funciona como en los ejemplos anteriores:

```
<script>alert(window.origin)</script>
```

Esto se debe a que `innerHTML` no ejecuta las etiquetas `<script>` insertadas de esa manera.

Sin embargo, existen otros elementos HTML y atributos capaces de ejecutar JavaScript.

### Payload de prueba

```
<img src='' onerror=alert(window.origin)>
```

Este payload crea una imagen con un atributo `onerror`.

- `src=''`: utiliza una fuente de imagen vacía.
    
- `onerror`: ejecuta su manejador cuando se produce un error al cargar la imagen.
    
- `alert(window.origin)`: muestra el origen de la página como prueba de ejecución.
    

En el laboratorio, puede probarse mediante la URL:

```
http://SERVER_IP:PORT/#task=<img src='' onerror=alert(window.origin)>
```

Si el código JavaScript vulnerable obtiene el parámetro `task` y lo inserta mediante `innerHTML`, el navegador puede interpretar la etiqueta y ejecutar el manejador `onerror`.

> En otros entornos, puede ser necesario codificar los caracteres especiales de la URL. El resultado también depende de cómo la aplicación procese la entrada y de las restricciones del navegador.

## ⚡ Flujo práctico de enumeración

1. **Buscar entradas controlables:** parámetros URL, fragmentos `#` y campos de formularios.
    
2. **Comprobar el procesamiento:** observar si la entrada se maneja en el navegador.
    
3. **Inspeccionar Network:** comprobar las peticiones HTTP generadas.
    
4. **Examinar el DOM:** utilizar el inspector para ver las modificaciones dinámicas.
    
5. **Localizar la fuente:** identificar de dónde obtiene JavaScript los datos.
    
6. **Localizar el sumidero:** buscar funciones que insertan esos datos en el DOM.
    
7. **Analizar la sanitización:** comprobar si la entrada se inserta de forma segura.
    
8. **Probar un payload inocuo:** verificar si se ejecuta JavaScript.
    
9. **Comprobar la URL:** determinar si puede reproducirse el comportamiento visitando un enlace preparado.
    

## ⚖️ Diferencias entre los tres tipos de XSS

|Característica|Stored XSS|Reflected XSS|DOM XSS|
|---|---|---|---|
|Procesamiento|El contenido almacenado se devuelve y se interpreta en la página.|El servidor refleja la entrada en su respuesta.|JavaScript procesa la entrada en el navegador.|
|Persistencia|Sí.|No.|No, en el caso descrito en este módulo.|
|Intervención del backend|Habitualmente sí.|Sí.|No es necesaria para el procesamiento vulnerable.|
|Vector habitual|Contenido almacenado en la aplicación.|Entrada reflejada, como un parámetro GET.|Datos del cliente utilizados para modificar el DOM.|
|Elemento clave|Contenido persistente.|Entrada reflejada por el servidor.|Combinación de Source y Sink.|

## 🧠 Chuleta para el examen

- **DOM XSS:** JavaScript procesa la entrada y modifica el DOM de forma insegura.
    
- **Source:** lugar del que se obtienen los datos controlados por el usuario.
    
- **Sink:** función que utiliza esos datos para modificar el DOM.
    
- `**document.URL**`**:** permite acceder a la URL del documento.
    
- `**decodeURIComponent()**`**:** decodifica componentes de una URI.
    
- `**innerHTML**`**:** inserta contenido HTML y puede ser peligroso con entradas no confiables.
    
- `**Ctrl + Shift + I**`**:** abre las herramientas de desarrollador.
    
- `**Ctrl + Shift + C**`**:** permite inspeccionar elementos del DOM.
    
- `**Ctrl + U**`**:** muestra el código fuente original.
    
- `**<script>**` **dentro de** `**innerHTML**`**:** normalmente no se ejecuta al insertarse de esta forma.
    
- `**onerror**`**:** manejador de eventos que puede ejecutar JavaScript cuando falla la carga de un recurso.
    
- **Diferencia clave:** el DOM XSS se procesa en el cliente; el Reflected XSS devuelve la entrada desde el servidor; el Stored XSS utiliza contenido persistente.
