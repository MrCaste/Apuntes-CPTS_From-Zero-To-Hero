
## 1. Conceptos clave

Las aplicaciones web utilizan **cookies de sesión** para mantener autenticado a un usuario entre peticiones.

Si un atacante consigue una cookie de sesión válida, podría utilizarla para acceder a la sesión de la víctima sin conocer su contraseña. Este ataque se conoce como:

- **Session Hijacking:** secuestro de sesión.
    
- **Cookie Stealing:** robo de cookies.
    
- **Blind XSS:** vulnerabilidad XSS que se ejecuta en una página a la que el atacante no tiene acceso directo.
    

> El robo de una cookie no garantiza el acceso: depende de que sea válida, de los controles de seguridad y de las características de la sesión.

## 2. Detección de Blind XSS

En un XSS convencional, podemos observar directamente si el payload se ejecuta. En un **Blind XSS**, la entrada puede ser procesada posteriormente por un administrador u otro usuario al que no tenemos acceso.

### Lugares habituales donde buscar Blind XSS

- Formularios de contacto.
    
- Reseñas.
    
- Detalles de usuario.
    
- Tickets de soporte.
    
- Cabeceras HTTP, como `User-Agent`.
    

### Ejemplo del laboratorio

La aplicación se encuentra en:

```
http://SERVER_IP:PORT/hijacking/index.php
```

El formulario permite registrar usuarios, pero después de enviarlo aparece un mensaje indicando que un administrador revisará la solicitud.

Esto significa que no podemos observar directamente cómo se procesa nuestra entrada.

### Método de detección

1. Identificar los campos que aceptan datos controlados por el usuario.
    
2. Probar payloads compatibles con el contexto de inserción.
    
3. Utilizar un servidor de prueba para detectar solicitudes HTTP entrantes.
    
4. Comprobar si alguno de los payloads provoca una petición.
    
5. Relacionar la petición recibida con el campo que se estaba probando.
    

## 3. Carga de JavaScript remoto

Una página HTML puede cargar un archivo JavaScript externo mediante el atributo `src` de una etiqueta `<script>`.

Ejemplo conceptual:

```
<script src="http://LAB_IP/script.js"></script>
```

Si el navegador procesa esa etiqueta, intentará solicitar el archivo indicado.

Para identificar el origen de una solicitud durante una prueba autorizada, el laboratorio propone utilizar rutas diferenciadas:

```
http://LAB_IP/fullname
http://LAB_IP/username
```

Así, la ruta solicitada permite relacionar la petición con el campo que se estaba evaluando.

### Preparar un servidor de pruebas

```
mkdir -p /tmp/tmpserver
cd /tmp/tmpserver
sudo php -S 0.0.0.0:80
```

El servidor permite observar las peticiones HTTP que llegan a la máquina de laboratorio.

**Importante:** una petición recibida no demuestra por sí sola que exista una vulnerabilidad XSS. Hay que confirmar que procede de la ejecución del código de prueba y no de otro comportamiento de la aplicación.

### Reducir los campos que deben probarse

El módulo señala dos casos:

- **Correo electrónico:** puede estar sujeto a validaciones de formato tanto en el navegador como en el servidor.
    
- **Contraseña:** normalmente no se muestra en texto plano en los paneles de administración.
    

Estas observaciones ayudan a priorizar la investigación, pero no garantizan que esos campos sean seguros.

## 4. Robo de cookies: conceptos técnicos

JavaScript puede consultar las cookies accesibles mediante `document.cookie`.

Sin embargo, existen limitaciones importantes:

|Propiedad|Efecto|
|---|---|
|`HttpOnly`|Impide que JavaScript acceda a la cookie mediante `document.cookie`.|
|`Secure`|Restringe el envío de la cookie a conexiones HTTPS.|
|`SameSite`|Controla determinados escenarios de envío de cookies entre sitios.|
|Caducidad|Limita el tiempo durante el que la cookie puede utilizarse.|

Si una cookie está marcada como `HttpOnly`, una vulnerabilidad XSS puede seguir siendo peligrosa, pero el método directo de lectura de esa cookie mediante JavaScript no funcionará.

## 5. Análisis de solicitudes HTTP

El laboratorio utiliza solicitudes HTTP para observar los datos enviados a un servidor durante las pruebas.

Ejemplo de una petición con parámetros de consulta:

```
GET /?username=test&password=test HTTP/1.1
Host: LAB_IP
```

Los parámetros de una petición `GET` aparecen en la URL. Por ello, no conviene utilizar este método para transmitir contraseñas en aplicaciones reales.

### Inspeccionar solicitudes

Durante el análisis, comprueba:

- La ruta solicitada.
    
- Los parámetros de consulta.
    
- Las cabeceras HTTP.
    
- El origen de la petición.
    
- El código de respuesta.
    
- Si la petición está relacionada con el comportamiento que se está investigando.
    

## 6. Gestión de cookies en Firefox

Para inspeccionar las cookies de una aplicación durante una prueba autorizada:

1. Abrir la página del laboratorio.
    
2. Pulsar `F12` para abrir las herramientas de desarrollo.
    
3. Acceder a la pestaña **Almacenamiento (Storage)**.
    
4. Seleccionar las cookies del sitio.
    
5. Examinar el nombre, el valor, la ruta y los atributos de cada cookie.
    

El módulo también muestra cómo una cookie de sesión puede asociarse a una sesión autenticada. En una auditoría real, esta comprobación debe realizarse únicamente con cuentas y sesiones de prueba autorizadas.

## 7. Blind XSS frente a XSS convencional

|Característica|XSS convencional|Blind XSS|
|---|---|---|
|Acceso a la página afectada|Generalmente disponible|Puede no estar disponible|
|Visualización del resultado|Puede observarse directamente|Puede requerir una señal externa|
|Momento de ejecución|Al visitar la página vulnerable|Puede producirse posteriormente|
|Detección|Inspección directa y pruebas|Señales indirectas y correlación de peticiones|
|Contexto habitual|Página visitada por el atacante|Paneles administrativos, tickets o registros|

## 8. Resumen para el examen

- **Blind XSS:** la vulnerabilidad se ejecuta en una página que no podemos observar directamente.
    
- **Carga remota:** una etiqueta `<script src="...">` permite al navegador solicitar un archivo JavaScript externo.
    
- **Correlación:** las rutas diferenciadas ayudan a identificar qué entrada provocó una solicitud.
    
- `**document.cookie**`**:** permite consultar las cookies accesibles desde JavaScript, pero no las protegidas mediante `HttpOnly`.
    
- **Session Hijacking:** consiste en aprovechar una sesión válida ajena; no requiere necesariamente conocer la contraseña.
    
- **Cookies de sesión:** deben protegerse con atributos adecuados y controles de autenticación y autorización.
    
- **Prevención de XSS:** codificar correctamente la salida, evitar operaciones inseguras del DOM y aplicar una política CSP como defensa adicional.

