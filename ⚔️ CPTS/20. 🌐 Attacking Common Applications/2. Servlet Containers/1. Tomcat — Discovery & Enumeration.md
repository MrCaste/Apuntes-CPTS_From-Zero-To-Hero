
## 1. Identificar Tomcat

Apache Tomcat es un servidor que ejecuta aplicaciones Java, incluidos servlets y páginas JSP.

### Comprobar la versión mediante una respuesta HTTP

Podemos revisar una ruta inexistente para provocar un error 404 que revele el servidor y su versión.

```
curl -i http://TARGET:8080/invalid
```

Busca información similar a:

```
Apache Tomcat/9.0.30
```

Si hay un proxy inverso o páginas de error personalizadas, esta información podría estar oculta.

### Comprobar la página de documentación

```
curl -s http://TARGET:8080/docs/ | grep Tomcat
```

La documentación predeterminada puede mostrar el nombre y la versión de Tomcat.

## 2. Estructura de directorios

Es importante conocer estos directorios porque pueden contener configuraciones, credenciales o código de la aplicación.

|Directorio o archivo|Función|
|---|---|
|`bin/`|Scripts y ejecutables de Tomcat|
|`conf/`|Archivos de configuración|
|`conf/tomcat-users.xml`|Usuarios, contraseñas y roles configurados|
|`lib/`|Bibliotecas Java y archivos JAR|
|`logs/`|Registros del servidor|
|`temp/`|Archivos temporales|
|`webapps/`|Aplicaciones web desplegadas|
|`webapps/manager/`|Aplicación de administración|
|`work/`|Archivos generados durante la ejecución|

### Archivos importantes de una aplicación

Una aplicación típica puede tener esta estructura:

```
webapps/customapp/
├── index.jsp
├── META-INF/
│   └── context.xml
└── WEB-INF/
    ├── web.xml
    ├── classes/
    ├── lib/
    └── jsp/
```

`**WEB-INF/web.xml**` es especialmente importante porque define servlets, rutas y clases que gestionan las peticiones.

Por ejemplo:

```
<servlet>
    <servlet-name>AdminServlet</servlet-name>
    <servlet-class>com.inlanefreight.api.AdminServlet</servlet-class>
</servlet>

<servlet-mapping>
    <servlet-name>AdminServlet</servlet-name>
    <url-pattern>/admin</url-pattern>
</servlet-mapping>
```

Esto relaciona la ruta `/admin` con la clase `AdminServlet`.

Si una vulnerabilidad LFI permite leer archivos locales, `web.xml` puede revelar información útil sobre la aplicación.

## 3. Archivo tomcat-users.xml

Este archivo configura usuarios y roles que permiten acceder a las interfaces de administración.

### Roles principales

|Rol|Permisos|
|---|---|
|`manager-gui`|Interfaz gráfica de administración y páginas de estado|
|`manager-script`|API HTTP y páginas de estado|
|`manager-jmx`|Acceso al proxy JMX y páginas de estado|
|`manager-status`|Acceso únicamente a páginas de estado|

El archivo puede contener cuentas con contraseñas débiles, por ejemplo:

```
<role rolename="manager-gui" />
<user username="tomcat" password="tomcat" roles="manager-gui" />
```

Estas credenciales son un ejemplo del módulo, no credenciales válidas para cualquier servidor.

## 4. Enumerar rutas con Gobuster

Después de identificar Tomcat, debemos buscar las interfaces administrativas y otras rutas accesibles.

### Ejecutar Gobuster

```
gobuster dir \
-u http://TARGET:8080/ \
-w /usr/share/dirbuster/wordlists/directory-list-2.3-small.txt
```

El puerto puede ser diferente según la configuración del objetivo.

### Rutas importantes

|Ruta|Función|
|---|---|
|`/docs`|Documentación|
|`/examples`|Aplicaciones de ejemplo|
|`/manager`|Administración de aplicaciones|
|`/host-manager`|Administración de hosts virtuales|

También puedes comprobar las rutas directamente desde el navegador.

**Importante:** encontrar una ruta no significa que tengas acceso. Puede requerir autenticación o estar restringida.

---

## 5. Credenciales débiles

Una vez localizado el panel de administración, comprueba si las credenciales conocidas o habituales funcionan en el entorno autorizado.

Ejemplos mencionados en el módulo:

```
tomcat:tomcat
admin:admin
```

Si no funcionan, el módulo indica que puede considerarse un ataque de fuerza bruta contra el inicio de sesión, siempre dentro del alcance autorizado.

## 6. Ejecución remota de comandos (RCE)

Si conseguimos autenticarnos con una cuenta que tenga los permisos necesarios en el **Tomcat Manager**, puede ser posible desplegar una aplicación web maliciosa.

El procedimiento descrito en el módulo consiste en:

1. Identificar el panel `/manager`.
    
2. Obtener credenciales válidas.
    
3. Comprobar los permisos de la cuenta.
    
4. Desplegar un archivo WAR que contenga una web shell JSP.
    
5. Verificar si se consigue ejecutar código en el servidor.
    

Un archivo **WAR** (_Web Application Archive_) empaqueta una aplicación web Java.

---

## 7. Metodología para el examen

1. **Identificar Tomcat:** revisar las cabeceras HTTP y las páginas de error.
    
2. **Obtener la versión:** consultar `/docs/` si está disponible.
    
3. **Enumerar directorios:** utilizar Gobuster.
    
4. **Buscar paneles administrativos:** comprobar `/manager` y `/host-manager`.
    
5. **Investigar credenciales:** revisar las que aparezcan en el material obtenido y probar las débiles de forma autorizada.
    
6. **Comprobar los permisos:** una cuenta con acceso al Manager puede permitir desplegar aplicaciones.
    
7. **Evaluar la posibilidad de RCE:** comprobar si es posible desplegar un WAR.
    
8. **Documentar los hallazgos:** registrar la versión, las rutas, los accesos y los permisos identificados.
    

## Comandos esenciales

|Objetivo|Comando|
|---|---|
|Comprobar cabeceras y versión|`curl -i http://TARGET:8080/invalid`|
|Consultar documentación|`curl -s http://TARGET:8080/docs/ \| grep Tomcat`|
|Enumerar directorios|`gobuster dir -u http://TARGET:8080/ -w /usr/share/dirbuster/wordlists/directory-list-2.3-small.txt`|
|Panel de administración|`http://TARGET:8080/manager`|
|Administración de hosts|`http://TARGET:8080/host-manager`|

**Idea clave:** en Tomcat, céntrate en identificar la versión, encontrar `/manager` y `/host-manager`, y comprobar si existen credenciales débiles. Si consigues acceso al Manager con permisos suficientes, investiga la posibilidad de desplegar una aplicación WAR para obtener ejecución de código.
