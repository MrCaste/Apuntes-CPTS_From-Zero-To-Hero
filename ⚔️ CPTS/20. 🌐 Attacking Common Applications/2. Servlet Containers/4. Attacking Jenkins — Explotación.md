
## 1. Explotación mediante Script Console

Si tenemos acceso a Jenkins con permisos suficientes, podemos utilizar la consola de scripts para ejecutar comandos en el sistema operativo.

**Ruta:**

```
http://jenkins.inlanefreight.local:8000/script
```

### Ejecutar comandos en Linux

En la consola, podemos introducir un script Groovy que ejecute un comando y muestre su salida.

Ejemplo del módulo:

```
def cmd = 'id'
def sout = new StringBuffer(), serr = new StringBuffer()
def proc = cmd.execute()
proc.consumeProcessOutput(sout, serr)
proc.waitForOrKill(1000)
println sout
```

El resultado del laboratorio es:

```
uid=0(root) gid=0(root)
```

Esto confirma que el comando se ejecuta como `root`.

**Importante:** el usuario que ejecuta los comandos depende de la cuenta con la que se esté ejecutando Jenkins.

### Obtener una reverse shell en Linux

En el laboratorio se utiliza una reverse shell mediante Bash y `/dev/tcp`.

La idea es:

1. Preparar un listener en la máquina de pruebas.
    
2. Ejecutar el código Groovy desde Script Console.
    
3. Comprobar que se recibe una conexión.
    
4. Verificar los privilegios obtenidos.
    

Listener del ejemplo:

```
nc -lvnp 8443
```

La conexión recibida permite comprobar la identidad del usuario:

```
id
```

En el ejemplo, la shell se obtiene como `root`.

## 2. Ejecutar comandos en Windows

Si Jenkins se ejecuta en Windows, podemos utilizar Groovy para ejecutar comandos mediante `cmd.exe`.

Ejemplo del módulo:

```
def cmd = "cmd.exe /c dir".execute()
println("${cmd.text}")
```

El comando `dir` permite comprobar que podemos ejecutar comandos del sistema operativo y visualizar su salida.

### Posibles vías posteriores

El material menciona dos posibilidades:

- Agregar un usuario y utilizar RDP o WinRM, si el contexto y los permisos lo permiten.
    
- Utilizar un _PowerShell download cradle_ con `Invoke-PowerShellTcp.ps1` para obtener una shell inversa sin crear una cuenta nueva.
    

El resultado dependerá de los privilegios de Jenkins y de las restricciones del sistema.

## 3. Vulnerabilidades de Jenkins

El módulo presenta varias vulnerabilidades de ejecución remota de código (RCE).

### CVE-2018-1999002 y CVE-2019-1003000

El material describe una combinación de vulnerabilidades que puede permitir RCE sin autenticación mediante la evasión de las protecciones de la sandbox de scripts durante la compilación.

Se menciona un fallo en el enrutamiento dinámico de Jenkins que permite eludir la ACL `Overall / Read` y utilizar Groovy para descargar y ejecutar un archivo JAR malicioso.

**Versión indicada en el módulo:** Jenkins `2.137`.

Según el material, el ataque puede permitir que usuarios con permisos de lectura evadan las protecciones de la sandbox y ejecuten código en el servidor principal.

### Jenkins 2.150.2

El módulo también menciona una vulnerabilidad que permite ejecutar código en el sistema mediante Node.js.

Condiciones descritas:

- Jenkins `2.150.2`.
    
- Permisos para crear _jobs_ y ejecutar _builds_.
    
- La vulnerabilidad requiere autenticación, aunque el módulo señala que puede ser explotable mediante usuarios anónimos cuando tienen esos permisos por defecto.
    

### Comprobaciones durante la enumeración

Antes de intentar explotar una vulnerabilidad concreta:

1. Identificar la versión de Jenkins.
    
2. Comprobar los permisos disponibles.
    
3. Determinar si la instancia permite acceso anónimo.
    
4. Revisar si el usuario puede crear _jobs_ y ejecutar _builds_.
    
5. Contrastar la versión y las condiciones con la vulnerabilidad que se quiere validar.
    

**No basta con encontrar una versión mencionada:** deben cumplirse las condiciones necesarias para que la explotación sea viable.

## 4. Hardening y limpieza

El módulo destaca la importancia de reforzar la configuración de Jenkins.

Durante una evaluación, conviene comprobar:

- Si existen credenciales débiles.
    
- Si se permite el acceso anónimo.
    
- Qué usuarios pueden acceder a Script Console.
    
- Qué permisos tienen los usuarios para crear _jobs_ y ejecutar _builds_.
    
- Si la versión instalada está afectada por vulnerabilidades conocidas.
    

Después de las pruebas, hay que retirar los artefactos introducidos y documentar las acciones realizadas.

## 5. Checklist para HTB

- Identificar la versión de Jenkins.
    
- Comprobar si las credenciales permiten acceder al panel.
    
- Revisar el acceso a `/script`.
    
- Ejecutar un comando de prueba y analizar su salida.
    
- Identificar el usuario con el que se ejecuta Jenkins.
    
- Si el objetivo es Windows, comprobar la ejecución de comandos con `cmd.exe`.
    
- Contrastar la versión con las vulnerabilidades mencionadas.
    
- Revisar los permisos para crear _jobs_ y ejecutar _builds_.
    
- Comprobar si el acceso anónimo está habilitado.
    
- Documentar el impacto y limpiar los artefactos utilizados.
