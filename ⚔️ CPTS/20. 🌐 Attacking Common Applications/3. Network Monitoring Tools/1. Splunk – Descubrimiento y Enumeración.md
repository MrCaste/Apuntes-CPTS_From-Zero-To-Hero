
## 1. Descubrimiento del servicio

Splunk utiliza principalmente estos puertos:

|Puerto|Servicio|
|---|---|
|**8000/TCP**|Interfaz web de Splunk|
|**8089/TCP**|API REST y administración de Splunk|

Para identificar el servicio y obtener información de su versión:

```
sudo nmap -sV -p 8000,8089 10.129.201.50
```

En el laboratorio, Nmap detecta:

```
8000/tcp open ssl/http Splunkd httpd
8089/tcp open ssl/http Splunkd httpd
```

También podemos realizar un escaneo general:

```
sudo nmap -sV 10.129.201.50
```

**Importante:** el resultado del laboratorio identifica Splunk, pero no muestra su versión exacta.

---

## 2. Acceso a la interfaz web

La interfaz web se encuentra en:

```
https://10.129.201.50:8000
```

Una vez autenticados, podemos acceder a:

```
https://10.129.201.50:8000/en-US/app/launcher/home
```

Desde la interfaz podemos comprobar los permisos disponibles y si es posible instalar aplicaciones personalizadas.

### Credenciales por defecto

Las versiones antiguas de Splunk utilizaban:

```
admin:changeme
```

También podemos comprobar credenciales débiles habituales:

```
admin:admin
admin:Welcome
admin:Welcome1
admin:Password123
```

Las versiones más recientes establecen las credenciales durante la instalación.

---

## 3. Identificación de la versión

Es importante identificar la **versión exacta de Splunk** para comprobar si existen vulnerabilidades conocidas.

Podemos intentar obtener información desde:

- La interfaz web, si tenemos acceso.
    
- Los apartados de configuración e información del producto.
    
- Las cabeceras HTTP.
    
- Los recursos y archivos accesibles de la aplicación.
    

Para inspeccionar las cabeceras:

```
curl -k -I https://10.129.201.50:8000
```

Para consultar la respuesta HTTP del servicio de administración:

```
curl -k -i https://10.129.201.50:8089
```

Estos comandos permiten inspeccionar las respuestas, pero **no garantizan que se revele la versión**.

El material no proporciona una versión concreta de la instancia del laboratorio.

## 4. Splunk Free: acceso sin autenticación

Una de las configuraciones más interesantes durante una auditoría es **Splunk Free**.

Según el material de HTB:

1. Se instala Splunk Enterprise Trial.
    
2. Transcurren los 60 días de prueba.
    
3. La instalación pasa a Splunk Free.
    
4. La versión gratuita no dispone de autenticación.
    

Esto puede permitir acceder a Splunk sin conocer credenciales.

Una vez dentro, debemos comprobar si podemos:

- Consultar los datos y logs almacenados.
    
- Acceder a dashboards e informes.
    
- Instalar aplicaciones.
    
- Crear aplicaciones personalizadas.
    
- Configurar entradas programadas (_scripted inputs_).
    

**La posibilidad de instalar aplicaciones o configurar entradas programadas es especialmente importante para conseguir RCE.**

## 5. Enumeración de funcionalidades explotables

Splunk dispone de distintas funcionalidades que pueden permitir ejecutar código en el servidor.

|Funcionalidad|Posibilidad|
|---|---|
|Scripted Inputs|Ejecutar scripts que proporcionan datos a Splunk|
|Custom Applications|Instalar aplicaciones personalizadas|
|REST Endpoints|Ejecutar funcionalidades mediante endpoints REST|
|Alert Scripts|Ejecutar scripts asociados a alertas|
|Server-side Django Apps|Ejecutar código mediante aplicaciones del servidor|

### Scripted Inputs

Es una de las principales vías de explotación descritas por HTB.

Permite configurar scripts que Splunk ejecutará para obtener información de fuentes externas.

Dependiendo del sistema operativo, podemos utilizar:

```
Linux   → Bash
Windows → PowerShell
Windows → Batch
Ambos   → Python
```

Según el material, Splunk incluye Python en sus instalaciones, por lo que puede utilizarse para ejecutar scripts.

### Posible RCE

Si tenemos permisos suficientes para crear una entrada programada, el procedimiento descrito consiste en:

1. Crear una aplicación o entrada programada.
    
2. Incorporar un script de Python.
    
3. Configurar su ejecución mediante Splunk.
    
4. Utilizarlo para obtener ejecución de comandos o una reverse shell.
    

**HTB desarrolla la explotación mediante Scripted Inputs en la siguiente sección.**

## 6. Vulnerabilidades conocidas

El material menciona las siguientes vulnerabilidades:

|CVE|Descripción|
|---|---|
|**CVE-2018-11409**|Divulgación de información|
|**CVE-2011-4642**|Ejecución remota de código autenticada en versiones antiguas|

También menciona una vulnerabilidad SSRF documentada en Exploit-DB:

```
Exploit-DB: 40895
```

Esta SSRF podría utilizarse para obtener acceso no autorizado a la API REST de Splunk.

**Importante:** el material no especifica las versiones afectadas por cada vulnerabilidad.

Por tanto, antes de intentar explotarlas, debemos identificar la versión instalada y comprobar los requisitos del exploit.

---

## 7. Privilegios del servicio

Otro punto importante durante la enumeración es determinar con qué usuario se ejecuta Splunk.

El material indica que es habitual encontrar instalaciones ejecutándose como:

```
Linux   → root
Windows → NT AUTHORITY\SYSTEM
```

Esto significa que, si conseguimos RCE, podríamos obtener directamente privilegios elevados.

No obstante, **dependerá de la configuración concreta del servidor**.

---

## 8. Checklist de enumeración

1. Identificar Splunk mediante Nmap.
    
2. Comprobar los puertos `8000` y `8089`.
    
3. Acceder a la interfaz web.
    
4. Identificar la versión instalada.
    
5. Probar `admin:changeme` en instalaciones antiguas.
    
6. Comprobar credenciales débiles.
    
7. Verificar si la instancia permite acceso sin autenticación.
    
8. Determinar si utiliza Splunk Free.
    
9. Comprobar si podemos instalar aplicaciones personalizadas.
    
10. Comprobar si podemos configurar Scripted Inputs.
    
11. Identificar el sistema operativo del servidor.
    
12. Investigar las CVE aplicables a la versión detectada.
    
13. Si disponemos de permisos suficientes, evaluar la posibilidad de RCE mediante las funcionalidades integradas.
