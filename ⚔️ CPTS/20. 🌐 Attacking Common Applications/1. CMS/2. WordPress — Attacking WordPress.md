## 1. Fuerza bruta de contraseñas

WPScan permite probar contraseñas para usuarios identificados durante la enumeración.

```
wpscan --url http://TARGET \
  --password-attack xmlrpc \
  -t 20 \
  -U john \
  -P /usr/share/wordlists/rockyou.txt
```

**Parámetros:**

- `--url`: web objetivo.
    
- `--password-attack xmlrpc`: utiliza XML-RPC para los intentos de autenticación.
    
- `-t 20`: número de hilos.
    
- `-U`: usuario o lista de usuarios.
    
- `-P`: archivo de contraseñas.
    

WPScan también admite el método `wp-login`.

**Importante:** XML-RPC puede ser más rápido, pero su disponibilidad y comportamiento dependen de la configuración del sitio.

## 2. Ejecución de código mediante el editor de temas

Una cuenta con permisos administrativos puede tener acceso al editor PHP de los temas.

Ruta:

```
/wp-admin/theme-editor.php
```

Si el servidor permite modificar archivos PHP ejecutables, una modificación maliciosa del tema puede conducir a **Remote Code Execution (RCE)**.

En una auditoría, hay que comprobar los permisos de la cuenta y si la edición de archivos está habilitada. Esta vía no funciona necesariamente en todas las instalaciones.

## 3. Explotación de vulnerabilidades en plugins

Los plugins son una superficie de ataque importante. Hay que comprobar sus versiones y buscar vulnerabilidades conocidas.

### mail-masta — LFI y SQL Injection

El contenido muestra un ejemplo de código vulnerable:

```
include($_GET['pl']);
```

El parámetro `pl` se utiliza para incluir un archivo sin validar adecuadamente la entrada.

Esto puede provocar una vulnerabilidad **LFI (Local File Inclusion)**, que podría permitir acceder a archivos locales del servidor.

El contenido también identifica una posible SQL Injection relacionada con el parámetro `camp_id`.

### wpDiscuz 7.0.4 — RCE

El material describe una vulnerabilidad de subida de archivos que permite eludir determinadas comprobaciones del tipo de archivo.

En las versiones vulnerables y bajo las condiciones adecuadas, un atacante sin autenticar podría subir un archivo PHP y obtener ejecución remota de código.

Referencia del material: **CVE-2020-24186**.

## 4. Metasploit

El módulo que aparece en el laboratorio es:

```
exploit/unix/webapp/wp_admin_shell_upload
```

Este módulo utiliza credenciales de WordPress para subir un plugin y obtener una sesión de Meterpreter.

Antes de ejecutarlo, hay que revisar sus opciones, especialmente:

- `RHOSTS`: IP del objetivo.
    
- `RPORT`: puerto HTTP/HTTPS.
    
- `USERNAME` y `PASSWORD`: credenciales de WordPress.
    
- `VHOST`: nombre del host virtual, si corresponde.
    
- `LHOST` y `LPORT`: dirección y puerto del listener.
    

El módulo puede dejar archivos o plugins en el servidor. Es necesario comprobar los artefactos creados y documentarlos.

## 5. Después de conseguir acceso

En el laboratorio, la ejecución de comandos se obtiene como:

```
www-data
```

Esto representa la cuenta de servicio web de Linux, no una cuenta root.

Tras conseguir acceso, los siguientes pasos habituales de una auditoría son:

1. Identificar el usuario y los permisos actuales.
    
2. Enumerar el sistema y los archivos accesibles.
    
3. Buscar información sensible y posibles vías de escalada de privilegios.
    
4. Evaluar posibles rutas de movimiento lateral, si están dentro del alcance.
    
5. Documentar los cambios y artefactos creados.
    

## 6. Buenas prácticas de pentesting

- No des por válida una vulnerabilidad solo por conocer la versión: comprueba si afecta a la configuración examinada.
    
- Los plugins antiguos o abandonados pueden seguir siendo accesibles aunque ya no se utilicen.
    
- Las herramientas automáticas pueden fallar o no detectar todos los componentes.
    
- Registra los sistemas afectados, las cuentas comprometidas, el método de acceso y los archivos creados o modificados.
    
- Elimina los artefactos de prueba cuando esté autorizado y sea seguro hacerlo.
