
## 1. Descubrimiento del servicio

osTicket es una aplicación web desarrollada en PHP que utiliza MySQL y puede ejecutarse tanto en Windows como en Linux.

Durante el reconocimiento podemos identificarla mediante:

- El texto `powered by osTicket` en el pie de página.
    
- La frase `Support Ticket System`.
    
- La cookie de sesión `OSTSESSID`.
    
- Las páginas para crear tickets y consultar su estado.
    
- Capturas de herramientas como EyeWitness.
    

En el laboratorio, la aplicación se encuentra en:

```
http://support.inlanefreight.local/
```

### Identificación mediante curl

Podemos buscar referencias a osTicket en el HTML:

```
curl -s http://support.inlanefreight.local/ | grep -iE 'osticket|support ticket system|powered by'
```

También podemos comprobar las cookies:

```
curl -s -I http://support.inlanefreight.local/
```

Buscamos una cabecera similar a:

```
Set-Cookie: OSTSESSID=...
```

**Importante:** Nmap normalmente identifica el servidor web (Apache, IIS, etc.), pero no necesariamente osTicket.

## 5. Enumeración mediante creación de tickets

Una de las técnicas más interesantes consiste en aprovechar la funcionalidad de creación de tickets para obtener información sobre la infraestructura.

Accedemos a:

```
http://support.inlanefreight.local/open.php
```

Creamos un ticket utilizando el formulario.

En el ejemplo de HTB:

```
Help Topic: Feedback

Issue Summary: Your site is slow
```

Después de enviar el formulario, la aplicación devuelve un identificador:

```
Ticket ID: 940288
```

En la instalación modificada del laboratorio, también se proporciona una dirección de correo electrónico:

```
940288@inlanefreight.local
```

### ¿Por qué es interesante?

Algunos portales de soporte permiten recibir mensajes enviados a direcciones asociadas a los tickets.

Por ejemplo:

```
940288@inlanefreight.local
```

Si los correos enviados a esa dirección aparecen en la conversación del ticket, podríamos utilizarla como buzón para recibir mensajes de verificación.

**Importante:** esta funcionalidad depende de la configuración del portal. No todas las instalaciones de osTicket generan direcciones de correo asociadas a los tickets.

## 6. Abuso del correo asociado a tickets

Supongamos que encontramos otra aplicación corporativa que exige registrarse con un correo del dominio de la empresa.

Ejemplos mencionados por HTB:

```
GitLab
Slack
Mattermost
Rocket.Chat
Bitbucket
Wiki corporativa
```

Si el portal de soporte proporciona una dirección como:

```
940288@inlanefreight.local
```

Y permite consultar los mensajes recibidos, el procedimiento sería:

1. Crear un ticket.
    
2. Obtener la dirección de correo asociada.
    
3. Comprobar si podemos recibir mensajes.
    
4. Identificar una aplicación que permita el registro con ese dominio.
    
5. Utilizar la dirección del ticket durante el registro.
    
6. Consultar el ticket para recuperar el mensaje de verificación.
    
7. Completar el registro.
    

### Resultado potencial

Podríamos obtener una cuenta en una aplicación corporativa que normalmente requiere una dirección de correo de la organización.

Esta técnica se ilustra en la máquina **HTB Delivery**.

**La debilidad no está necesariamente en osTicket, sino en cómo se integran los sistemas de correo y los procesos de registro.**

## 10. Enumeración de tickets internos

Después de autenticarnos, accedemos al panel de un agente de soporte.

El usuario del ejemplo es:

```
Kevin Grimes
```

Aunque no tiene tickets abiertos, encontramos un ticket cerrado.

### Información descubierta

Un empleado llamado Charles Smithson informa de problemas para acceder a la VPN.

El agente de soporte restablece su contraseña.

Durante la conversación se revela que:

1. La empresa utiliza una contraseña estándar para empleados nuevos.
    
2. Esa misma contraseña se utiliza en determinados restablecimientos.
    
3. El agente comparte la contraseña directamente mediante el ticket.
    

Esto supone una exposición de información sensible.

### Posible impacto

La contraseña encontrada podría seguir siendo válida para el usuario afectado.

También podría haberse reutilizado para otros empleados.

El material plantea comprobar su validez en el portal VPN durante una evaluación autorizada.

**Importante:** el texto no revela el valor concreto de esa contraseña estándar.

## 11. Password Spraying a partir de información de osTicket

El material plantea un escenario en el que una contraseña estándar descubierta en un ticket podría utilizarse para comprobar si otros usuarios mantienen esa misma contraseña.

Para ello, menciona la herramienta:

```
linkedin2username
```

Su finalidad es generar posibles nombres de usuario a partir de información pública sobre empleados.

El flujo descrito sería:

```
Acceso a osTicket
        ↓
Lectura de tickets
        ↓
Descubrimiento de contraseña estándar
        ↓
Enumeración de empleados
        ↓
Generación de posibles usernames
        ↓
Evaluación de reutilización de contraseñas
```

El material menciona la posibilidad de realizar _password spraying_ contra el portal VPN.

**No proporciona un comando concreto para realizarlo ni indica que se haya ejecutado en el laboratorio.**

Otra funcionalidad interesante de los sistemas de tickets es su libreta de direcciones.

Puede contener:

- Nombres de empleados.
    
- Direcciones de correo corporativas.
    
- Nombres de usuario.
    
- Contactos internos.
    
- Información de departamentos.
    

Si conseguimos acceso a una cuenta de soporte con permisos suficientes, debemos revisar qué información puede consultarse o exportarse.

Estos datos pueden resultar útiles para enumerar cuentas y relacionar identidades con otros servicios.

## 13. Checklist de enumeración y explotación

1. Identificar osTicket mediante el HTML o EyeWitness.
    
2. Buscar la cookie `OSTSESSID`.
    
3. Localizar la página principal.
    
4. Identificar la versión de la aplicación.
    
5. Investigar vulnerabilidades aplicables a esa versión.
    
6. Comprobar la existencia de `/open.php`.
    
7. Crear un ticket de prueba.
    
8. Verificar si se genera una dirección de correo asociada.
    
9. Comprobar si el ticket permite recibir mensajes.
    
10. Identificar aplicaciones corporativas que requieren correo del dominio.
    
11. Localizar `/scp/login.php`.
    
12. Comprobar credenciales válidas obtenidas durante la auditoría.
    
13. Probar el formato de usuario y correo electrónico.
    
14. Si conseguimos acceso, revisar tickets abiertos y cerrados.
    
15. Buscar información sensible compartida en conversaciones.
    
16. Identificar posibles contraseñas estándar o reutilizadas.
    
17. Enumerar usuarios y direcciones de correo.
    
18. Revisar la libreta de direcciones.
    
19. Relacionar la información obtenida con otros servicios incluidos en el alcance.
