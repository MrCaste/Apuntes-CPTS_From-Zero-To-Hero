
## 1. Descubrimiento del servicio

GitLab puede identificarse accediendo a su interfaz web, que normalmente muestra el logotipo de la aplicación y un formulario de autenticación.

En el laboratorio, GitLab está disponible en:

```
http://gitlab.inlanefreight.local:8081
```

La página de inicio de sesión se encuentra en:

```
http://gitlab.inlanefreight.local:8081/users/sign_in
```

### Enumeración inicial con Nmap

Podemos identificar el servicio web:

```
sudo nmap -sV -p 8081 <IP>
```

También podemos inspeccionar las cabeceras HTTP:

```
curl -I http://gitlab.inlanefreight.local:8081
```

Y buscar referencias a GitLab en el HTML:

```
curl -s http://gitlab.inlanefreight.local:8081/users/sign_in | grep -i gitlab
```

**Importante:** estos comandos pueden ayudar a identificar GitLab, pero no garantizan que podamos obtener su versión.

## 2. Identificación de la versión

La versión de GitLab es especialmente importante para investigar vulnerabilidades conocidas.

Según el material de HTB, podemos identificarla accediendo a:

```
/help
```

Por ejemplo:

```
http://gitlab.inlanefreight.local:8081/help
```

**Requisito indicado en el material:** estar autenticados.

Si GitLab permite registrar usuarios, podemos:

1. Crear una cuenta.
    
2. Iniciar sesión.
    
3. Acceder a `/help`.
    
4. Identificar la versión instalada.
    
5. Buscar vulnerabilidades que afecten a esa versión.
    

### Versiones con vulnerabilidades conocidas

HTB menciona las siguientes versiones que han sufrido vulnerabilidades graves:

|Versión|Edición|
|---|---|
|`12.9.0`|GitLab|
|`11.4.7`|GitLab|
|`13.10.3`|GitLab Community Edition|
|`13.9.3`|GitLab Community Edition|
|`13.10.2`|GitLab Community Edition|

El material no especifica las CVE correspondientes a estas versiones.

**Tampoco proporciona la versión exacta de la instancia del laboratorio.**

### Si no podemos identificar la versión

HTB recomienda evitar lanzar múltiples exploits a ciegas.

En su lugar, debemos centrarnos en:

- Enumerar repositorios públicos.
    
- Buscar información sensible.
    
- Revisar commits.
    
- Identificar usuarios.
    
- Comprobar si podemos registrarnos.
    
- Buscar información que permita identificar la versión.

### ¿Qué debemos buscar?

Al revisar repositorios, debemos prestar especial atención a:

- Contraseñas almacenadas en código.
    
- Claves privadas SSH.
    
- API keys.
    
- Tokens de autenticación.
    
- Archivos de configuración.
    
- Credenciales de bases de datos.
    
- Información sobre servidores internos.
    
- Código fuente de aplicaciones corporativas.
    
- Funcionalidades ocultas o vulnerables.
    

### Archivos interesantes

Como ampliación práctica de la enumeración, algunos nombres de archivos que conviene buscar son:

```

docker-compose.yml
.gitlab-ci.yml
id_rsa
```

Estos archivos no aparecen necesariamente en el laboratorio; son ejemplos de archivos que pueden contener información sensible.

## 5. Enumeración del historial de commits

No debemos limitarnos a revisar los archivos actuales del repositorio.

También es importante examinar:

```
Commits
Branches
```

Un desarrollador podría haber subido accidentalmente una contraseña y eliminarla posteriormente.

Sin embargo, esa información podría seguir apareciendo en commits anteriores.

### Clonar un repositorio público

Si el repositorio permite clonación mediante HTTP:

```
git clone http://gitlab.inlanefreight.local:8081/root/inlanefreight-dev.git
```

Accedemos al directorio:

```
cd inlanefreight-dev
```

Consultamos el historial:

```
git log --oneline --all
```

Mostramos los cambios de un commit:

```
git show <COMMIT>
```

Buscamos referencias a posibles secretos en los archivos actuales:

```
grep -RniE 'password|passwd|secret|token|api.key|private.key' . --exclude-dir=.git
```

**Importante:** estos comandos son técnicas adicionales de enumeración. El material de HTB recomienda revisar los repositorios, pero no proporciona estos comandos concretos.

## 6. Tipos de repositorios y permisos

GitLab permite diferentes niveles de visibilidad.

|Tipo|Acceso|
|---|---|
|**Public**|Cualquier visitante|
|**Internal**|Usuarios autenticados|
|**Private**|Usuarios autorizados específicamente|

Esta diferencia es fundamental durante la enumeración.

### Sin autenticación

Podemos encontrar:

```
Public repositories
```

### Con una cuenta válida

Podríamos acceder adicionalmente a:

```
Internal repositories
```

### Con permisos específicos

Podríamos acceder a:

```
Private repositories
```

Por tanto, **conseguir una cuenta de GitLab puede ampliar considerablemente la información disponible**, incluso aunque no tenga privilegios administrativos.

## 7. Enumeración de usuarios mediante el registro

Una funcionalidad interesante de GitLab es el formulario de registro:

```
/users/sign_up
```

En determinadas versiones y configuraciones, permite comprobar si un nombre de usuario ya existe.

Por ejemplo, al intentar registrar:

```
root
```

La aplicación devuelve:

```
Username is already taken
```

Esto indica que el nombre de usuario está registrado.

### Enumeración de correos electrónicos

El material también muestra que podemos comprobar si una dirección de correo ya está registrada.

Cuando introducimos una dirección existente, GitLab devuelve:

```
1 error prohibited this user from being saved:
Email has already been taken
```

Esto puede permitir identificar direcciones de correo válidas.

### Punto importante

HTB indica que, en la instancia estudiada, la página:

```
/users/sign_up
```

Puede seguir siendo accesible aunque el registro de usuarios esté deshabilitado.

En ese caso:

- No podemos crear cuentas.
    
- Pero podríamos seguir enumerando usuarios.
    

**Este comportamiento depende de la versión y configuración de GitLab.**

## 8. Registro de una cuenta

En el laboratorio, GitLab permite registrar nuevos usuarios sin aprobación administrativa.

Accedemos a:

```
http://gitlab.inlanefreight.local:8081/users/sign_up
```

HTB utiliza las siguientes credenciales:

```
Username: hacker
Password: Welcome
```

Después del registro, podemos iniciar sesión.

### ¿Qué cambia?

Antes de autenticarnos, encontramos el proyecto público:

```
Inlanefreight dev
```

Después de iniciar sesión, encontramos otro proyecto:

```
Inlanefreight website
```

Este segundo proyecto tiene visibilidad interna.

El material indica que contiene:

```
22 commits
1 branch
```

### Resultado

```
Sin autenticación
       ↓
Repositorio público
       ↓
Registro de usuario
       ↓
Autenticación
       ↓
Acceso a repositorios internos
```

Esto demuestra que una cuenta sin privilegios elevados puede permitir acceder a información que no estaba disponible públicamente.

Durante una auditoría, debemos comprobar si:

- El registro está habilitado.
    
- Se requiere aprobación administrativa.
    
- Se permiten correos externos.
    
- Existen restricciones por dominio.

También se pueden configurar:

```

Two-factor authentication

```

**Importante:** no debemos asumir que todas las instalaciones de GitLab mantienen esas configuraciones.

## 10. Enumeración mediante credenciales filtradas

Otra posibilidad consiste en encontrar credenciales de usuarios mediante OSINT.

El material menciona herramientas como:

```
Dehashed
```

Si encontramos credenciales asociadas a empleados, podemos comprobar si siguen siendo válidas en la instancia de GitLab dentro del alcance autorizado.

Por ejemplo:

```
Email: empleado@inlanefreight.local
Password: contraseña_filtrada
```

Un acceso exitoso podría permitir consultar:

- Repositorios internos.
    
- Proyectos privados compartidos con ese usuario.
    
- Código fuente.
    
- Archivos de configuración.
    
- Información sobre la infraestructura.
    

**La sección no proporciona credenciales filtradas concretas para GitLab.**

## 11. Relación con osTicket

Esta sección está relacionada con la técnica estudiada anteriormente en osTicket.

En determinados escenarios, podemos combinar ambas aplicaciones:

```
osTicket
   ↓
Crear ticket
   ↓
Obtener dirección corporativa
   ↓
GitLab permite registro
   ↓
Recibir verificación en el ticket
   ↓
Crear cuenta
   ↓
Acceder a repositorios internos
```

Esta combinación depende de que:

1. osTicket permita recibir mensajes en una dirección asociada al ticket.
    
2. GitLab permita el registro.
    
3. La dirección sea aceptada.
    
4. No se requiera aprobación administrativa adicional.
    

No todas las instalaciones permiten realizar este procedimiento.

## 12. Checklist de enumeración

1. Identificar GitLab mediante la interfaz web.
    
2. Localizar `/users/sign_in`.
    
3. Acceder a `/explore`.
    
4. Enumerar proyectos públicos.
    
5. Revisar grupos y snippets.
    
6. Inspeccionar los archivos de los repositorios.
    
7. Buscar contraseñas, tokens y claves SSH.
    
8. Revisar el historial de commits.
    
9. Comprobar si `/users/sign_up` está disponible.
    
10. Evaluar si el registro permite enumerar usuarios.
    
11. Comprobar si permite enumerar correos electrónicos.
    
12. Verificar si podemos registrar una cuenta.
    
13. Si conseguimos acceso, visitar `/help` para identificar la versión.
    
14. Investigar vulnerabilidades aplicables a esa versión.
    
15. Volver a `/explore` después de autenticarnos.
    
16. Buscar repositorios internos.
    
17. Revisar el código y los archivos de configuración.
    
18. Comprobar si tenemos acceso a información sensible adicional.
