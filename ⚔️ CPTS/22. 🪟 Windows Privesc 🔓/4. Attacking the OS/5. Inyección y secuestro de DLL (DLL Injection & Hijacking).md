
## 1. DLL Injection

La **inyección de DLL** consiste en introducir una biblioteca DLL en un proceso que ya está en ejecución, haciendo que su código se ejecute dentro de ese proceso.

Puede utilizarse legítimamente para modificar aplicaciones en tiempo de ejecución, pero también para ejecutar código dentro de procesos de confianza.

### Método 1: `LoadLibrary`

`LoadLibrary` permite cargar una DLL en la memoria de un proceso.

Ejemplo de carga normal en C:

```
HMODULE hModule = LoadLibraryA("example.dll");

if (hModule == NULL) {
    printf("No se pudo cargar la DLL\n");
} else {
    printf("DLL cargada correctamente\n");
}
```

En este ejemplo, la DLL se carga en el proceso que ejecuta el código.

En una inyección remota, el objetivo es cargar la DLL dentro de **otro proceso**. El procedimiento descrito en el módulo es:

1. Abrir el proceso objetivo con `OpenProcess`.
    
2. Reservar memoria en ese proceso con `VirtualAllocEx`.
    
3. Escribir la ruta de la DLL en esa memoria mediante `WriteProcessMemory`.
    
4. Obtener la dirección de `LoadLibraryA`.
    
5. Crear un hilo remoto con `CreateRemoteThread` para ejecutar `LoadLibraryA` con la ruta de la DLL.
    

**Funciones importantes:**

|Función|Propósito|
|---|---|
|`OpenProcess`|Obtener acceso al proceso objetivo.|
|`VirtualAllocEx`|Reservar memoria dentro de otro proceso.|
|`WriteProcessMemory`|Escribir datos en la memoria del proceso objetivo.|
|`GetProcAddress`|Obtener la dirección de una función exportada.|
|`CreateRemoteThread`|Ejecutar una función mediante un hilo en otro proceso.|
|`LoadLibraryA`|Cargar una DLL desde una ruta.|

### Método 2: Manual Mapping

El **mapeo manual** carga una DLL en el proceso objetivo sin utilizar el mecanismo habitual de `LoadLibrary`.

Proceso simplificado:

1. Leer la DLL como datos.
    
2. Mapear sus secciones en la memoria del proceso objetivo.
    
3. Resolver las importaciones y las reubicaciones.
    
4. Ejecutar las callbacks TLS que correspondan.
    
5. Invocar el punto de entrada de la DLL.
    

Se utiliza para evitar parte de la actividad habitual de carga de bibliotecas, aunque **no garantiza que la técnica pase inadvertida**.

### Método 3: Reflective DLL Injection

En la **inyección reflexiva**, la propia DLL incorpora un cargador capaz de preparar la biblioteca desde la memoria.

A grandes rasgos:

1. La DLL se escribe en la memoria del proceso objetivo.
    
2. Se transfiere la ejecución a su función `ReflectiveLoader`.
    
3. El cargador localiza las funciones necesarias.
    
4. Reserva memoria y copia las cabeceras y secciones de la DLL.
    
5. Resuelve importaciones y reubicaciones.
    
6. Ejecuta `DllMain` con `DLL_PROCESS_ATTACH`.
    

**Diferencia clave:**

- **Manual Mapping:** el código externo realiza las operaciones necesarias para mapear la DLL.
    
- **Reflective DLL Injection:** la propia DLL incorpora la lógica para cargarse desde memoria.

## 2. DLL Hijacking

El **secuestro de DLL** aprovecha la forma en que una aplicación busca y carga sus bibliotecas.

Si una aplicación necesita `library.dll` y no especifica una ruta segura, podría cargar una DLL manipulada desde una ubicación que tenga prioridad en la búsqueda.

### Ejemplo sencillo

Una aplicación necesita:

```
C:\Aplicacion\library.dll
```

Si un atacante puede escribir en un directorio desde el que la aplicación busca esa biblioteca, podría colocar una DLL manipulada con el nombre esperado.

Cuando la aplicación cargue esa DLL, ejecutará el código que esta contenga, siempre que se cumplan las condiciones necesarias.

**Para que pueda convertirse en una vía de escalada de privilegios**, normalmente debe cumplirse lo siguiente:

- La aplicación o servicio se ejecuta con privilegios superiores a los del usuario.
    
- La DLL puede colocarse o sustituirse en una ubicación relevante.
    
- La aplicación carga la DLL manipulada.
    
- La DLL es compatible con la aplicación y satisface las funciones que esta necesita.
    

Encontrar una DLL susceptible de secuestro no implica automáticamente que se pueda obtener `SYSTEM`.

## 3. Orden de búsqueda de DLL en Windows

El orden de búsqueda depende de cómo cargue la aplicación la biblioteca, de las rutas especificadas y de la configuración de Windows.

Según el módulo, con **Safe DLL Search Mode** habilitado, el orden simplificado es:

1. Directorio desde el que se carga la aplicación.
    
2. Directorio del sistema.
    
3. Directorio del sistema de 16 bits.
    
4. Directorio de Windows.
    
5. Directorio actual.
    
6. Directorios incluidos en `PATH`.
    

Con **Safe DLL Search Mode** deshabilitado, el directorio actual pasa a buscarse antes que los directorios del sistema.

### Comprobar `SafeDllSearchMode`

Ruta del Registro:

```
HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Control\Session Manager
```

Valor:

```
SafeDllSearchMode
```

Consulta mediante PowerShell:

```
Get-ItemProperty `
  -Path "HKLM:\SYSTEM\CurrentControlSet\Control\Session Manager" `
  -Name SafeDllSearchMode
```

- `1`: modo de búsqueda segura habilitado.
    
- `0`: modo de búsqueda segura deshabilitado.
    
- Si el valor no existe, no debe asumirse automáticamente que está deshabilitado; hay que tener en cuenta el comportamiento predeterminado de Windows.
    

**Importante:** el orden anterior es una simplificación del módulo. El comportamiento real depende de factores como las rutas de búsqueda de la aplicación, las redirecciones, los directorios añadidos y las API utilizadas.

## 4. Enumerar DLL con Process Explorer y PE Explorer

### Process Explorer

Herramienta de Sysinternals que permite inspeccionar procesos en ejecución y las DLL que tienen cargadas.

Resulta útil para:

- Identificar las DLL cargadas por un proceso.
    
- Comprobar desde qué rutas se cargan.
    
- Investigar qué bibliotecas utiliza una aplicación.
    

### PE Explorer

Permite examinar ejecutables y DLL en formato PE.

Puede utilizarse para:

- Identificar las bibliotecas importadas por un ejecutable.
    
- Examinar funciones importadas y exportadas.
    
- Investigar las dependencias de una aplicación.
    

Estas herramientas ayudan a identificar bibliotecas relevantes, pero por sí solas no confirman que exista una vulnerabilidad explotable.

## 5. Analizar la carga de DLL con Process Monitor

**Process Monitor (**`**Procmon**`**)** permite observar las operaciones que realiza una aplicación al ejecutarse.

Es especialmente útil para investigar:

- Qué DLL intenta cargar.
    
- Desde qué directorios las busca.
    
- Qué archivos DLL encuentra.
    
- Qué rutas producen errores como `NAME NOT FOUND`.
    

### Procedimiento

1. Abrir Procmon.
    
2. Configurar un filtro para el proceso, por ejemplo:
    
    ```
    Process Name is main.exe
    ```
    
3. Añadir un filtro para las operaciones de carga:
    
    ```
    Operation is Load Image
    ```
    
4. Ejecutar `main.exe` mientras Procmon está capturando eventos.
    
5. Examinar las rutas de las DLL cargadas.
    

Si no aparecen eventos, hay que comprobar que la captura estaba activa cuando se ejecutó el programa.

### Interpretar los resultados

Ejemplo de una DLL cargada correctamente:

```
main.exe    Load Image    C:\Users\User\Desktop\Hijack\library.dll    SUCCESS
```

Esto indica que el proceso cargó la DLL desde esa ruta.

Ejemplo de una DLL que no se encuentra:

```
main.exe    CreateFile    C:\Users\User\Desktop\Hijack\x.dll    NAME NOT FOUND
```

Esto indica que la operación de búsqueda o apertura de `x.dll` en esa ruta no encontró el archivo.

**Punto clave:** `NAME NOT FOUND` puede revelar una dependencia ausente, pero hay que comprobar si la aplicación realmente necesita cargarla y si existe una ubicación donde pueda colocarse de forma controlada.

## 6. DLL Proxying

El **DLL Proxying** consiste en crear una DLL que expone las funciones que espera la aplicación y delega su funcionamiento en la DLL original.

Permite interceptar o modificar el comportamiento de una función sin tener que reimplementar toda la biblioteca original.

### Ejemplo del módulo: modificar una suma

La aplicación `main.exe` carga `library.dll` y utiliza su función exportada `Add`.

La función original suma dos números:

```
Add(1, 1) = 2
```

Una DLL proxy carga la biblioteca original, invoca su función `Add` y modifica el resultado añadiendo uno:

```
Resultado original: 2
Resultado modificado: 3
```

El módulo propone estos nombres para el ejemplo:

```
library.o.dll    -> DLL original renombrada
library.dll      -> DLL proxy
```

La aplicación continúa solicitando `library.dll`, pero carga la nueva biblioteca proxy.

El proxy obtiene la función original mediante `GetProcAddress` y llama a esta antes de modificar el resultado.

### Funciones relevantes

|Función|Propósito|
|---|---|
|`LoadLibraryA`|Cargar la biblioteca original.|
|`GetProcAddress`|Localizar la función `Add` exportada.|
|`FreeLibrary`|Liberar una biblioteca cargada cuando corresponda.|

**Diferencia importante:** el proxy del ejemplo modifica el resultado de una operación; no demuestra por sí mismo una escalada de privilegios. Para que exista escalada, el código debe ejecutarse en un contexto con más privilegios que el usuario.

## 7. Secuestro mediante una DLL ausente

Otra posibilidad es que la aplicación intente cargar una DLL que no encuentra.

En el ejemplo del módulo, `main.exe` busca:

```
x.dll
```

Procmon muestra que intenta abrirla desde el directorio de la aplicación y obtiene:

```
NAME NOT FOUND
```

Si se cumplen las condiciones adecuadas, una DLL compatible colocada en una ubicación de búsqueda relevante podría ser cargada por la aplicación.

El ejemplo utiliza una DLL cuya función `DllMain` imprime un mensaje cuando la biblioteca se carga:

```
#include <stdio.h>
#include <Windows.h>

BOOL APIENTRY DllMain(
    HMODULE hModule,
    DWORD ul_reason_for_call,
    LPVOID lpReserved
)
{
    switch (ul_reason_for_call)
    {
        case DLL_PROCESS_ATTACH:
            printf("Hijacked... Oops...\n");
            break;

        case DLL_PROCESS_DETACH:
            break;

        case DLL_THREAD_ATTACH:
            break;

        case DLL_THREAD_DETACH:
            break;
    }

    return TRUE;
}
```

En el ejemplo de HTB, la DLL se compila y se renombra a:

```
x.dll
```

Cuando `main.exe` la carga, aparece el mensaje:

```
Hijacked... Oops...
```

La aplicación puede continuar funcionando y realizar la suma normalmente.

**Qué demuestra:** que la DLL manipulada se ha cargado en el proceso. No demuestra automáticamente que se hayan obtenido privilegios elevados.

## 8. Diferencias entre las técnicas

|Técnica|Cómo funciona|Objetivo principal|
|---|---|---|
|DLL Injection con `LoadLibrary`|Carga una DLL en otro proceso utilizando una función de carga de Windows.|Ejecutar código dentro del proceso objetivo.|
|Manual Mapping|Mapea manualmente una DLL en memoria.|Cargar una DLL sin utilizar el mecanismo habitual de `LoadLibrary`.|
|Reflective DLL Injection|La DLL contiene su propio cargador en memoria.|Preparar y ejecutar la DLL desde memoria.|
|DLL Hijacking|Aprovecha la búsqueda o carga insegura de una DLL.|Hacer que una aplicación cargue una biblioteca manipulada.|
|DLL Proxying|Interpone una DLL que delega en la original.|Interceptar o modificar funciones esperadas por la aplicación.|

## 9. Checklist para HTB

Cuando investigues una posible vulnerabilidad de DLL:

1. **Identifica el proceso**
    
    - Nombre del ejecutable.
        
    - Usuario que lo ejecuta.
        
    - Privilegios del proceso.
        
2. **Identifica sus dependencias**
    
    - Usa PE Explorer para examinar las importaciones.
        
    - Usa Process Explorer para inspeccionar las DLL cargadas.
        
3. **Observa la búsqueda de bibliotecas**
    
    - Usa Procmon.
        
    - Filtra por el nombre del proceso.
        
    - Busca operaciones `Load Image`, `CreateFile` y resultados `NAME NOT FOUND`.
        
4. **Comprueba la ruta de carga**
    
    - Determina desde dónde intenta cargar la aplicación la DLL.
        
    - Comprueba si el usuario tiene permisos de escritura en alguna ubicación relevante.
        
5. **Valida la viabilidad**
    
    - Comprueba si la aplicación carga realmente la DLL.
        
    - Verifica que la biblioteca sea compatible y exporte las funciones necesarias.
        
    - Determina qué privilegios tiene el proceso.
        
6. **Distingue ejecución de escalada**
    
    - Que aparezca un mensaje de la DLL demuestra que se ha cargado.
        
    - Para demostrar escalada, hay que verificar que el código se ejecuta con privilegios superiores.
        

## Resumen rápido

- **DLL Injection:** introducir una DLL en un proceso en ejecución.
    
- **Manual Mapping:** mapear la DLL manualmente en memoria.
    
- **Reflective Injection:** la DLL incorpora su propio cargador.
    
- **DLL Hijacking:** aprovechar una búsqueda o carga insegura de bibliotecas.
    
- **DLL Proxying:** interceptar una función y delegar en la biblioteca original.
    
- **Procmon:** observar intentos de carga y rutas de DLL.
    
- `**Load Image**`**:** permite localizar DLL que se han cargado.
    
- `**NAME NOT FOUND**`**:** ayuda a identificar dependencias ausentes, pero no confirma por sí solo una vulnerabilidad.
    
- **Para escalar privilegios:** la DLL debe cargarse en un proceso que tenga privilegios superiores a los del usuario.
