
## 1. ¿Qué es Kerberoasting?

**Kerberoasting** es una técnica de movimiento lateral y escalada de privilegios en Active Directory que permite obtener tickets de servicio Kerberos (**TGS**) asociados a cuentas que tienen configurado un **Service Principal Name (SPN)** e intentar recuperar sus contraseñas mediante cracking offline.

### Conceptos clave

- **SPN (Service Principal Name):** identificador que Kerberos utiliza para asociar un servicio con la cuenta bajo la que se ejecuta.
    
- **TGS (Ticket Granting Service ticket):** ticket de servicio que podemos solicitar para una cuenta con SPN.
    
- **Cracking offline:** una vez obtenido el ticket, podemos intentar recuperar la contraseña sin realizar nuevos intentos de autenticación contra el dominio.
    
- **Impacket:** conjunto de herramientas que incluye `GetUserSPNs.py`, utilizada para enumerar SPN y solicitar tickets de servicio.
    

### ¿Por qué funciona?

1. Las cuentas de usuario del dominio pueden solicitar tickets TGS para servicios del dominio, siempre que se cumplan las condiciones de autenticación correspondientes.
    
2. El ticket de servicio contiene información cifrada que permite realizar ataques de contraseña offline.
    
3. El cifrado del ticket utiliza una clave derivada de las credenciales de la cuenta de servicio.
    
4. Si conseguimos crackear el ticket, podemos recuperar la contraseña de esa cuenta.
    
5. Si la cuenta tiene privilegios elevados, podremos utilizar las credenciales para intentar escalar privilegios o movernos lateralmente.
    

**Importante:** obtener un ticket TGS no significa que tengamos acceso a la cuenta. Primero debemos intentar crackearlo y después comprobar los privilegios de las credenciales recuperadas.

## 2. Requisitos previos

Para realizar Kerberoasting desde Linux, necesitamos:

- Credenciales válidas de un usuario del dominio, en texto plano o mediante un hash NTLM compatible con la herramienta.
    
- La dirección IP de un controlador de dominio (**Domain Controller, DC**).
    
- Conectividad con los servicios necesarios del controlador de dominio.
    

También es posible realizar el ataque desde otros contextos, como un equipo Windows unido al dominio, una sesión de usuario de dominio o determinadas situaciones en las que tenemos acceso como `SYSTEM`.

### Información que debemos identificar

|Dato|Ejemplo del laboratorio|
|---|---|
|Dominio|`INLANEFREIGHT.LOCAL`|
|Controlador de dominio|`172.16.5.5`|
|Usuario autenticado|`forend`|
|Cuenta de servicio objetivo|`sqldev`|
|SPN|`MSSQLSvc/DEV-PRE-SQL.inlanefreight.local:1433`|

Los valores anteriores pertenecen al laboratorio de HTB Academy.

## 3. Instalar y comprobar Impacket

Impacket proporciona herramientas para interactuar con distintos protocolos de red, incluido Kerberos.

### Instalación desde el repositorio clonado

```
cd /opt/impacket
sudo python3 -m pip install .
```

> En Kali, Impacket puede estar ya instalado. Comprueba primero si tienes disponible la herramienta para evitar instalaciones innecesarias.

### Consultar la ayuda

```
GetUserSPNs.py -h
```

En algunas instalaciones, el ejecutable puede tener un nombre o una ruta diferente. Comprueba su ubicación si el comando no se encuentra.

## 4. Enumerar cuentas con SPN

El primer paso consiste en identificar las cuentas que tienen servicios asociados.

```
GetUserSPNs.py -dc-ip 172.16.5.5 INLANEFREIGHT.LOCAL/forend
```

La herramienta solicitará la contraseña del usuario `forend` y consultará el dominio.

### Información relevante de la salida

|Campo|Significado|
|---|---|
|`ServicePrincipalName`|SPN asociado a la cuenta.|
|`Name`|Nombre de la cuenta de servicio.|
|`MemberOf`|Grupos a los que pertenece la cuenta.|
|`PasswordLastSet`|Fecha del último cambio de contraseña.|
|`LastLogon`|Último inicio de sesión registrado.|
|`Delegation`|Información relacionada con la delegación que muestra la herramienta.|

### ¿Qué debemos buscar?

Debemos prestar especial atención a las cuentas que:

- Pertenecen a `Domain Admins` o a otros grupos privilegiados.
    
- Ejecutan servicios importantes, como SQL Server.
    
- Tienen contraseñas antiguas que conviene investigar.
    
- Pueden permitirnos avanzar hacia otros sistemas si conseguimos recuperar sus credenciales.
    

**La presencia de un SPN no implica que la cuenta tenga privilegios elevados ni que su contraseña sea débil.** Hay que comprobar cada caso.

---

## 5. Solicitar todos los tickets TGS

Para solicitar los tickets de las cuentas con SPN enumeradas, utilizamos `-request`.

```
GetUserSPNs.py -dc-ip 172.16.5.5 INLANEFREIGHT.LOCAL/forend -request
```

La herramienta mostrará información sobre las cuentas y los tickets TGS obtenidos.

Los tickets se representan en un formato que puede utilizarse con herramientas de cracking como Hashcat.

Ejemplo del formato del ticket:

```
$krb5tgs$23$*usuario$DOMINIO$...
```

El contenido completo puede ser muy extenso.

### ¿Qué significa `$krb5tgs$23$`?

- `$krb5tgs$`: identifica un ticket de servicio Kerberos en el formato de hash utilizado por las herramientas.
    
- `23`: identifica el tipo de cifrado Kerberos RC4-HMAC, también conocido como `etype 23`.
    

En el laboratorio, Hashcat utiliza el modo `13100` para este formato.

**Nota:** no todos los tickets Kerberos utilizan el mismo tipo de cifrado. El modo de Hashcat debe corresponder al formato del ticket obtenido.

---

## 6. Solicitar el ticket de una cuenta concreta

No es necesario solicitar todos los tickets. Podemos seleccionar una cuenta específica con `-request-user`.

Por ejemplo, para solicitar el ticket de `sqldev`:

```
GetUserSPNs.py -dc-ip 172.16.5.5 INLANEFREIGHT.LOCAL/forend -request-user sqldev
```

En el laboratorio, la salida muestra que `sqldev` pertenece al grupo `Domain Admins`.

Esto hace que la cuenta sea especialmente interesante, ya que recuperar su contraseña podría proporcionar acceso privilegiado.

### Flujo de trabajo

1. Enumerar las cuentas con SPN.
    
2. Revisar la pertenencia a grupos de cada cuenta.
    
3. Seleccionar las cuentas más interesantes.
    
4. Solicitar sus tickets TGS.
    
5. Guardar los tickets para intentar crackearlos offline.
    
6. Comprobar los privilegios de las credenciales recuperadas.
    

---

## 7. Guardar el ticket TGS en un archivo

Para facilitar el cracking, podemos guardar el ticket en un archivo mediante `-outputfile`.

```
GetUserSPNs.py -dc-ip 172.16.5.5 INLANEFREIGHT.LOCAL/forend -request-user sqldev -outputfile sqldev_tgs
```

Esto guarda el material obtenido en el archivo `sqldev_tgs`, que podremos utilizar como entrada para Hashcat.

Comprueba que el archivo existe y contiene el ticket antes de continuar:

```
ls -lh sqldev_tgs
```

---

## 8. Crackear el ticket con Hashcat

Una vez guardado el ticket, podemos intentar recuperar la contraseña mediante un ataque de diccionario.

En el ejemplo de HTB Academy se utiliza `rockyou.txt` y el modo `13100`.

```
hashcat -m 13100 sqldev_tgs /usr/share/wordlists/rockyou.txt
```

### Parámetros

|Parámetro|Función|
|---|---|
|`-m 13100`|Selecciona el modo Kerberos 5, etype 23, TGS-REP.|
|`sqldev_tgs`|Archivo que contiene el ticket.|
|`rockyou.txt`|Diccionario de contraseñas.|

Si Hashcat recupera la contraseña, puede mostrar un resultado con esta estructura:

```
$krb5tgs$23$*sqldev$...:contraseña_recuperada
```

En el ejemplo del módulo, la contraseña recuperada es:

```
database!
```

Esta contraseña es un resultado específico del laboratorio, no un valor que debamos asumir en otros objetivos.

### Si Hashcat no encuentra la contraseña

Un resultado sin contraseña recuperada no significa necesariamente que el ticket sea incorrecto.

Puede deberse a que:

- La contraseña no está presente en el diccionario.
    
- La contraseña es larga y robusta.
    
- El diccionario no contiene una variante adecuada.
    
- El modo de Hashcat no corresponde al tipo de ticket.
    

Podemos probar otros diccionarios o estrategias de cracking autorizadas, pero no existe garantía de éxito.

---

## 9. Validar las credenciales recuperadas

Después de recuperar una contraseña, debemos comprobar si las credenciales son válidas y qué acceso proporcionan.

En el laboratorio se utiliza:

```
sudo crackmapexec smb 172.16.5.5 -u sqldev -p 'database!'
```

En instalaciones actuales puede utilizarse NetExec, sucesor de CrackMapExec:

```
nxc smb 172.16.5.5 -u sqldev -p 'database!'
```

### ¿Qué debemos comprobar?

- Si las credenciales se aceptan.
    
- Si la autenticación funciona contra el controlador de dominio.
    
- Qué permisos tiene la cuenta.
    
- Si dispone de privilegios administrativos o pertenece a grupos privilegiados.
    

Una autenticación correcta no implica automáticamente privilegios de administrador. Hay que interpretar la salida de la herramienta y verificar los permisos de la cuenta.

> En el ejemplo del módulo, `sqldev` pertenece a `Domain Admins`. Por tanto, si la contraseña recuperada es válida, el resultado supone un compromiso de alto impacto.

## 10. Importancia de los privilegios de las cuentas

No todas las cuentas con SPN tienen el mismo valor desde el punto de vista de una evaluación de seguridad.

|Resultado|Impacto potencial|
|---|---|
|Ticket obtenido, pero no crackeado|No se han recuperado credenciales.|
|Contraseña recuperada de una cuenta de bajo privilegio|Puede facilitar nuevos accesos o movimientos laterales.|
|Contraseña recuperada de una cuenta con acceso administrativo a servidores|Puede permitir comprometer esos sistemas.|
|Contraseña recuperada de una cuenta perteneciente a `Domain Admins`|Puede suponer un compromiso del dominio si las credenciales son válidas y los privilegios son efectivos.|

El riesgo real depende de los privilegios de la cuenta, de los sistemas a los que puede acceder y de las medidas de seguridad del entorno.

Una contraseña débil o reutilizada aumenta las posibilidades de éxito. Una contraseña robusta puede hacer que el cracking resulte inviable en la práctica.

---

## 11. Posible movimiento lateral mediante servicios

Aunque la cuenta recuperada no pertenezca a un grupo privilegiado, podría tener acceso a servicios importantes.

Por ejemplo, un SPN como:

```
MSSQLSvc/SRV01
```

indica una asociación con un servicio SQL Server.

Si recuperamos las credenciales de la cuenta correspondiente, podemos investigar si estas permiten autenticarnos en el servicio y qué permisos tenemos allí.

En determinadas configuraciones de SQL Server, una cuenta con permisos suficientes podría tener capacidades administrativas sobre la instancia o habilitar funcionalidades que permitan ejecutar comandos en el servidor.

**Importante:** disponer de credenciales de una cuenta con SPN no concede automáticamente permisos `sysadmin` en SQL Server ni acceso al sistema operativo. Es necesario comprobar los permisos reales del servicio.

---

## 12. Consideraciones para el informe de seguridad

El resultado del ataque debe evaluarse según el impacto real:

- **Riesgo alto:** se recuperan credenciales de una cuenta privilegiada que permiten comprometer sistemas críticos o el dominio.
    
- **Riesgo medio:** se demuestra que una cuenta de servicio tiene una contraseña susceptible de recuperación, pero no se consigue un acceso privilegiado significativo.
    
- **Sin compromiso demostrado:** se obtienen tickets, pero no se recuperan contraseñas ni se demuestra un impacto adicional. El riesgo debe justificarse en función de las evidencias y del contexto.
    

No debe asignarse automáticamente un riesgo alto a cualquier cuenta con SPN. La evidencia obtenida y el impacto potencial deben respaldar la clasificación.

### Enumerar cuentas con SPN

```
GetUserSPNs.py -dc-ip <IP_DC> <DOMINIO>/<USUARIO>
```

```
GetUserSPNs.py -dc-ip <IP_DC> <DOMINIO>/<USUARIO> -request
```

### Solicitar el ticket de una cuenta concreta

```
GetUserSPNs.py -dc-ip <IP_DC> <DOMINIO>/<USUARIO> -request-user <CUENTA>
```

### Guardar el ticket en un archivo

```
GetUserSPNs.py -dc-ip <IP_DC> <DOMINIO>/<USUARIO> -request-user <CUENTA> -outputfile <ARCHIVO>
```

### Crackear un ticket etype 23 con Hashcat

```
hashcat -m 13100 <ARCHIVO_TGS> <DICCIONARIO>
```

### Validar credenciales mediante SMB

```
nxc smb <IP_OBJETIVO> -u <USUARIO> -p '<CONTRASEÑA>'
```

## 15. Puntos clave para el examen

- Kerberoasting se dirige a cuentas que tienen configurado un SPN.
    
- Un usuario del dominio puede solicitar tickets TGS para servicios, sujeto a las condiciones de autenticación del entorno.
    
- La obtención del ticket no requiere conocer previamente la contraseña de la cuenta de servicio.
    
- El ticket obtenido se utiliza para realizar cracking offline.
    
- `GetUserSPNs.py` permite enumerar SPN y solicitar tickets TGS.
    
- `-request` solicita los tickets de las cuentas encontradas.
    
- `-request-user` permite seleccionar una cuenta concreta.
    
- `-outputfile` guarda los tickets obtenidos.
    
- Hashcat utiliza `-m 13100` para Kerberos 5 TGS-REP con etype 23.
    
- Crackear una contraseña no implica automáticamente que las credenciales sean válidas o que la cuenta tenga privilegios elevados.
    
- Debemos comprobar los grupos, los permisos y los accesos efectivos de la cuenta.
    
- Las contraseñas débiles o reutilizadas aumentan la probabilidad de éxito.
    
- El impacto depende de los privilegios de la cuenta y de los recursos a los que tenga acceso.
    

**Idea fundamental:** Kerberoasting permite obtener tickets de servicio y atacarlos offline para intentar recuperar contraseñas. El verdadero valor del hallazgo depende de si conseguimos recuperar una contraseña y de los privilegios que tenga la cuenta comprometida.
