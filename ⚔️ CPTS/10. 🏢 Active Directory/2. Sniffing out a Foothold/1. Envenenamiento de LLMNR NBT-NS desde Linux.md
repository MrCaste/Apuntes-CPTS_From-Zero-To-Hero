
## 1. Objetivo

Conseguir credenciales válidas de un usuario del dominio mediante el envenenamiento de solicitudes de resolución de nombres.

El proceso consiste en:

1. Identificar solicitudes LLMNR/NBT-NS en la red.
    
2. Ejecutar **Responder** para responder a solicitudes de resolución de nombres.
    
3. Capturar hashes NetNTLMv1/NetNTLMv2 cuando un equipo víctima intenta autenticarse contra nuestro sistema.
    
4. Intentar descifrar los hashes offline mediante Hashcat o John.
    
5. Utilizar las credenciales obtenidas para continuar la enumeración del dominio.
    

> **Importante:** los hashes NetNTLMv2 capturados mediante Responder no se pueden utilizar directamente en un ataque Pass-the-Hash. Primero debemos intentar recuperar la contraseña en texto plano o evaluar otras técnicas compatibles con las condiciones del entorno.

---

## 2. LLMNR y NBT-NS

Son mecanismos de resolución de nombres utilizados por Windows cuando no consigue resolver un nombre mediante DNS.

|Protocolo|Descripción|Puerto|
|---|---|---|
|LLMNR|Resolución de nombres dentro del enlace local cuando falla DNS.|UDP 5355|
|NBT-NS|Resolución de nombres NetBIOS en la red local.|UDP 137|

### Funcionamiento del ataque

1. Un equipo intenta conectarse a un recurso de red, por ejemplo, `\\printer01.inlanefreight.local`.
    
2. La resolución DNS falla porque el nombre no existe o está mal escrito.
    
3. El equipo realiza una solicitud LLMNR o NBT-NS.
    
4. El atacante responde a la solicitud utilizando Responder y afirma conocer la ubicación del recurso.
    
5. Si la víctima confía en la respuesta e intenta autenticarse contra el atacante, este puede capturar un desafío-respuesta NetNTLM.
    
6. El material capturado puede someterse a cracking offline o, si se cumplen las condiciones necesarias, evaluarse para un ataque de retransmisión.
    

### ¿Por qué funciona?

En estos protocolos, otros equipos de la red local pueden responder a las solicitudes de resolución de nombres. Un atacante situado en el segmento de red adecuado puede aprovechar esta característica para suplantar la respuesta legítima.

La combinación de envenenamiento de nombres, autenticación NTLM y una configuración SMB insegura puede facilitar ataques de retransmisión.

## 4. Responder

### 4.1. Consultar las opciones

```
responder -h
```

Opciones importantes:

|Parámetro|Función|
|---|---|
|`-I <interfaz>`|Selecciona la interfaz de red.|
|`-A`|Activa el modo de análisis pasivo.|
|`-f`|Intenta identificar el sistema operativo y la versión del host remoto.|
|`-w`|Activa el servidor WPAD integrado.|
|`-F`|Fuerza la autenticación al recuperar `wpad.dat`; puede provocar solicitudes de inicio de sesión.|
|`-P`|Fuerza la autenticación del proxy.|
|`-v`|Aumenta la verbosidad.|
|`-r`|Habilita respuestas a determinadas consultas NetBIOS `wredir`.|
|`-d`|Habilita respuestas a determinadas consultas NetBIOS de sufijo de dominio.|
|`-b`|Utiliza autenticación HTTP Basic en lugar de NTLM.|

**Precaución:** las opciones `-r`, `-d`, `-F` y `-P` pueden alterar el comportamiento de la red o provocar solicitudes de autenticación. Deben utilizarse únicamente cuando sean necesarias y estén autorizadas.

### 4.2. Modo de análisis pasivo

Durante la enumeración inicial se puede utilizar Responder para observar las solicitudes sin envenenarlas:

```
sudo responder -I ens224 -A
```

Este modo permite identificar solicitudes LLMNR y NBT-NS sin responder a ellas.

Es útil para comprobar si existe actividad susceptible de ser aprovechada antes de iniciar el envenenamiento.

### 4.3. Ejecutar Responder

En un laboratorio autorizado, para iniciar Responder con su configuración predeterminada:

```
sudo responder -I ens224
```

Sustituye `ens224` por la interfaz de red que corresponda a tu entorno.

Responder escuchará las solicitudes y responderá a aquellas que pueda gestionar mediante los servicios habilitados en su configuración.

Se recomienda dejarlo ejecutándose mientras se realizan otras tareas de enumeración, siempre dentro del entorno autorizado.

### 4.4. Puertos y servicios

Responder utiliza distintos servicios y protocolos, entre ellos SMB, HTTP, DNS, LDAP y otros mecanismos de autenticación.

El módulo indica que, para aprovechar todas sus funciones, deben estar disponibles los puertos necesarios para los servicios habilitados. Entre los puertos y protocolos mencionados se encuentran:

- UDP 137 y 138: NetBIOS.
    
- UDP 53: DNS.
    
- UDP 5355: LLMNR.
    
- UDP 5353: mDNS.
    
- TCP 80: HTTP.
    
- TCP 135: RPC.
    
- TCP 139 y 445: NetBIOS/SMB.
    
- TCP/UDP 389: LDAP.
    
- TCP 1433 y UDP 1434: MSSQL.
    
- Otros puertos asociados a servicios de autenticación y proxy.
    

Los servicios individuales pueden deshabilitarse mediante el archivo de configuración `Responder.conf`.

## 5. Localizar los hashes capturados

Responder muestra las autenticaciones capturadas en la consola y, normalmente, almacena los registros en:

```
/usr/share/responder/logs/
```

Para consultar los archivos generados:

```
ls /usr/share/responder/logs/
```

Ejemplos de nombres de archivos:

```
SMB-NTLMv2-SSP-172.16.5.25.txt
SMB-NTLMv2-SSP-172.16.5.50.txt
HTTP-NTLMv2-172.16.5.200.txt
Proxy-Auth-NTLMv2-172.16.5.200.txt
```

### Interpretación del nombre

Por ejemplo:

```
SMB-NTLMv2-SSP-172.16.5.25.txt
```

- `SMB`: protocolo implicado.
    
- `NTLMv2-SSP`: tipo de autenticación capturada.
    
- `172.16.5.25`: dirección IP del cliente.
    

Los hashes también pueden almacenarse en una base de datos SQLite, cuya configuración depende del archivo `Responder.conf`.

**Nota:** las rutas pueden variar si Responder se instaló desde otra fuente o se ejecuta desde un repositorio clonado.

## 6. Cracking de hashes NetNTLMv2 con Hashcat

Una vez capturado el material de autenticación, podemos intentar recuperar la contraseña mediante cracking offline.

### 6.1. Identificar el modo de hash

El módulo utiliza el modo:

```
5600 — NetNTLMv2
```

### 6.2. Ejecutar Hashcat

Ejemplo del módulo:

```
hashcat -m 5600 forend_ntlmv2 /usr/share/wordlists/rockyou.txt
```

Donde:

- `-m 5600`: selecciona el modo NetNTLMv2.
    
- `forend_ntlmv2`: archivo que contiene el material de autenticación capturado.
    
- `/usr/share/wordlists/rockyou.txt`: diccionario utilizado para probar contraseñas.
    

El archivo debe contener el hash en el formato esperado por Hashcat. No basta con copiar cualquier línea de la salida de Responder sin comprobar que su formato sea válido.

### 6.3. Interpretar los resultados

Si el cracking tiene éxito, Hashcat puede mostrar información similar a:

```
Status...........: Cracked
Hash.Name........: NetNTLMv2
Recovered........: 1/1 (100.00%)
```

En el ejemplo de HTB Academy, el usuario `FOREND` tiene la contraseña recuperada:

```
Klmcargo2
```

Estas credenciales pertenecen al entorno de laboratorio del ejemplo; no deben asumirse válidas en otros objetivos.

### 6.4. ¿Qué ocurre si no se recupera la contraseña?

El cracking puede fallar si:

- La contraseña no aparece en el diccionario utilizado.
    
- La contraseña es larga o compleja.
    
- El formato del hash no es correcto.
    
- Se ha seleccionado un modo de Hashcat incorrecto.
    
- El tiempo o los recursos disponibles son insuficientes.
    

Una contraseña que no aparece en `rockyou.txt` no significa que el hash sea incorrecto: puede requerir otro diccionario o una estrategia distinta.

## 7. Diferencia entre capturar un hash y obtener una contraseña

Capturar un hash NetNTLMv2 **no equivale a conocer la contraseña**.

|Resultado|Qué permite|
|---|---|
|Captura de material NetNTLMv2|Intentar recuperar la contraseña offline.|
|Contraseña recuperada|Probar la autenticación con esa cuenta, si las condiciones del entorno lo permiten.|
|Hash NetNTLMv2 sin descifrar|No permite utilizarlo directamente como un hash NT para Pass-the-Hash.|
|Autenticación retransmitida|Puede permitir autenticarse contra otro servicio si se cumplen las condiciones específicas de la retransmisión.|

El objetivo de esta fase es obtener credenciales que permitan continuar la enumeración desde una perspectiva autenticada.

## 8. Estrategia durante la evaluación

No todos los hashes tienen el mismo valor. Conviene recopilar la información necesaria para determinar qué cuentas pueden ayudar a avanzar hacia el objetivo.

Flujo de trabajo:

1. Enumerar la red y los servicios.
    
2. Identificar solicitudes de resolución de nombres.
    
3. Analizar el tráfico con Responder en modo pasivo.
    
4. En el laboratorio autorizado, ejecutar Responder para observar las autenticaciones que se produzcan.
    
5. Revisar los registros generados.
    
6. Identificar el tipo y el formato del hash.
    
7. Intentar el cracking offline con el modo adecuado de Hashcat o John.
    
8. Validar las credenciales recuperadas dentro del alcance autorizado.
    
9. Utilizar el acceso obtenido para continuar la enumeración del dominio.
    

No conviene invertir todo el tiempo disponible en descifrar hashes de cuentas que no aporten una vía útil hacia el objetivo.

## 10. Ideas clave para el examen

- **LLMNR utiliza UDP 5355.**
    
- **NBT-NS utiliza UDP 137.**
    
- Ambos mecanismos pueden utilizarse cuando falla la resolución DNS.
    
- Responder puede observar solicitudes en modo pasivo con `-A`.
    
- Al ejecutarse sin `-A`, Responder puede responder a solicitudes mediante los servicios habilitados.
    
- Una autenticación capturada puede proporcionar material NetNTLMv1 o NetNTLMv2.
    
- **Hashcat utiliza el modo** `**5600**` **para NetNTLMv2.**
    
- Los registros de Responder suelen encontrarse en `/usr/share/responder/logs/`.
    
- Los hashes NetNTLMv2 deben tratarse como material de desafío-respuesta, no como hashes NT utilizables directamente mediante Pass-the-Hash.
    
- El objetivo es conseguir credenciales válidas para ampliar la enumeración y obtener un punto de apoyo inicial en el dominio.
    
- Inveigh permite estudiar técnicas similares desde un host Windows; esa es la siguiente parte del módulo.
