
## 1. ¿Qué es el problema del Double Hop?

El **Double Hop** ocurre cuando nos conectamos a un equipo mediante WinRM y, desde esa sesión remota, intentamos acceder a otro recurso del dominio, como un controlador de dominio (DC), un servidor SMB o Active Directory.

**Ejemplo de movimiento lateral:**

```
Máquina de ataque → DEV01 → DC01
     1.er salto     2.º salto
```

Podemos autenticarnos correctamente en `DEV01`, pero no necesariamente podremos utilizar esa sesión para autenticarnos contra `DC01`.

### ¿Por qué ocurre?

Con la autenticación Kerberos mediante WinRM:

- La sesión remota dispone de un ticket de servicio (**TGS**) para acceder al servicio del equipo de destino.
    
- El **TGT** del usuario no se delega automáticamente a la sesión remota.
    
- Las credenciales del usuario no quedan disponibles como una contraseña o un hash NTLM reutilizable.
    
- Al intentar acceder a otro recurso del dominio, la autenticación puede fallar porque no disponemos de las credenciales delegadas necesarias.
    

Esto puede provocar errores al ejecutar comandos de PowerView que necesitan consultar Active Directory.

**Importante:** el problema no significa que el usuario carezca de permisos. Puede tenerlos, pero la sesión no dispone de la autenticación necesaria para utilizarlos en el segundo salto.

## 2. Identificar el problema

### Conectarse mediante WinRM

Desde una sesión de PowerShell:

```
$Password = ConvertTo-SecureString 'PASSWORD' -AsPlainText -Force
$Cred = New-Object System.Management.Automation.PSCredential('INLANEFREIGHT\backupadm', $Password)

Enter-PSSession -ComputerName DEV01 -Credential $Cred
```

### Comprobar los tickets Kerberos

```
klist
```

Si únicamente aparece un ticket para el servicio del equipo remoto, puede que no dispongamos de los tickets necesarios para acceder a otros recursos del dominio.

### Comprobar el acceso a Active Directory

```
Import-Module .\PowerView.ps1

Get-DomainUser -SPN | Select-Object samaccountname
```

Si aparece un error como:

```
DirectoryServicesCOMException
An operations error occurred.
```

puede deberse al problema del Double Hop.

### Diferencia entre una sesión WinRM y una sesión RDP

|Característica|WinRM con Double Hop|RDP con tickets disponibles|
|---|---|---|
|Acceso al primer equipo|Sí|Sí|
|Acceso a otros recursos|Puede fallar|Puede funcionar|
|TGT disponible en la sesión|No necesariamente|Puede estar disponible|
|Consultas a Active Directory|Pueden fallar|Pueden funcionar|

El resultado depende del tipo de inicio de sesión, de los tickets disponibles y de la configuración del entorno.

## 3. Solución 1: utilizar un objeto PSCredential

Esta alternativa resulta útil cuando trabajamos desde una sesión de **Evil-WinRM**.

La idea consiste en proporcionar explícitamente las credenciales en cada comando que necesite autenticarse contra otro recurso.

### Paso 1. Crear el objeto PSCredential

```
$SecPassword = ConvertTo-SecureString 'PASSWORD' -AsPlainText -Force

$Cred = New-Object System.Management.Automation.PSCredential(
    'INLANEFREIGHT\backupadm',
    $SecPassword
)
```

Sustituye `PASSWORD` por la contraseña válida de la cuenta.

### Paso 2. Ejecutar el comando indicando las credenciales

```
Get-DomainUser -SPN -Credential $Cred |
    Select-Object samaccountname
```

Al proporcionar `-Credential $Cred`, PowerView utiliza las credenciales indicadas para realizar la consulta al dominio.

### Paso 3. Comparar el resultado

Sin proporcionar las credenciales:

```
Get-DomainUser -SPN | Select-Object samaccountname
```

La consulta puede volver a fallar debido al Double Hop.

**Ventaja:** permite realizar consultas autenticadas sin depender de que las credenciales se hayan delegado automáticamente a la sesión remota.

**Limitación:** solo funciona con comandos que admiten un parámetro de credenciales. No todos los cmdlets o herramientas lo permiten.

## 4. Solución 2: registrar una configuración de PSSession

Este método permite configurar una sesión remota de PowerShell para ejecutarse utilizando unas credenciales determinadas.

**Requisitos importantes:**

- Acceso a una consola de PowerShell de Windows adecuada.
    
- Privilegios elevados en el equipo donde se registra la configuración.
    
- Una cuenta válida que pueda utilizarse como `RunAsCredential`.
    

Según el material de HTB, este método no resulta apropiado para una sesión de Evil-WinRM ni para PowerShell en Linux en el escenario descrito.

### Paso 1. Registrar la configuración

Desde PowerShell elevado:

```
Register-PSSessionConfiguration `
    -Name backupadmsess `
    -RunAsCredential 'INLANEFREIGHT\backupadm'
```

El sistema puede solicitar las credenciales de la cuenta.

> **Advertencia de seguridad:** una configuración `RunAs` puede debilitar el aislamiento entre sesiones si no se restringen correctamente los permisos y comandos disponibles.

### Paso 2. Reiniciar WinRM

```
Restart-Service WinRM
```

El reinicio puede desconectar las sesiones remotas existentes.

### Paso 3. Conectarse utilizando la configuración registrada

```
Enter-PSSession `
    -ComputerName DEV01 `
    -Credential 'INLANEFREIGHT\backupadm' `
    -ConfigurationName backupadmsess
```

### Paso 4. Comprobar los tickets

```
klist
```

En el escenario del laboratorio, ahora aparece un TGT para la cuenta utilizada.

### Paso 5. Volver a ejecutar la consulta

```
Get-DomainUser -SPN | Select-Object samaccountname
```

La consulta puede realizarse sin especificar `-Credential` en cada comando, porque la sesión está configurada para ejecutarse en el contexto de la cuenta indicada.

**Diferencia fundamental:** el primer método pasa credenciales explícitamente en cada operación; el segundo configura el contexto de ejecución de la sesión remota.

## 5. Delegación Kerberos

La delegación Kerberos permite que un servicio actúe en nombre de un usuario para acceder a otros servicios, siempre que se cumplan las condiciones de configuración y autorización correspondientes.

En el escenario descrito por HTB, la **delegación no restringida (Unconstrained Delegation)** puede evitar el Double Hop porque el servidor puede recibir y conservar el TGT del usuario para solicitar tickets de servicio posteriores.

Sin embargo, no debe asumirse que cualquier sesión WinRM dispone de delegación.

### Comprobación de tickets

```
klist
```

Este comando permite inspeccionar los tickets de la sesión actual.

---

## 6. Otras alternativas

El material menciona otros métodos para resolver o evitar el problema:

- **CredSSP:** permite delegar credenciales a un equipo remoto cuando está configurado correctamente.
    
- **Port forwarding:** redirige conexiones a través de otro equipo.
    
- **Inyección en procesos:** permite utilizar el contexto de seguridad de otro proceso, si se dispone de los permisos necesarios.
    

Estos métodos no se desarrollan en detalle en esta sección.

## 7. Flujo de resolución para el laboratorio

Cuando WinRM funciona, pero los comandos de Active Directory fallan:

1. Comprueba que la cuenta tiene permisos para acceder al recurso.
    
2. Comprueba los tickets disponibles:
    
    ```
    klist
    ```
    
3. Prueba una consulta de Active Directory:
    
    ```
    Get-DomainUser -SPN
    ```
    
4. Si falla por un problema de autenticación, utiliza un objeto `PSCredential`:
    
    ```
    $SecPassword = ConvertTo-SecureString 'PASSWORD' -AsPlainText -Force
    $Cred = New-Object System.Management.Automation.PSCredential('INLANEFREIGHT\backupadm', $SecPassword)
    
    Get-DomainUser -SPN -Credential $Cred
    ```
    
5. Si trabajas desde una consola de PowerShell de Windows con los privilegios necesarios, considera registrar una configuración `PSSession` con `RunAsCredential`.
    
6. Comprueba de nuevo los tickets y repite la consulta.

## 8. Chuleta rápida

|Situación|Qué comprobar o utilizar|
|---|---|
|WinRM funciona, pero PowerView no consulta el dominio|Double Hop y tickets Kerberos|
|Ver tickets de la sesión|`klist`|
|Consultar usuarios con SPN|`Get-DomainUser -SPN`|
|Pasar credenciales explícitamente|`Get-DomainUser -SPN -Credential $Cred`|
|Crear credenciales reutilizables|`ConvertTo-SecureString` + `PSCredential`|
|Configurar una sesión remota con otro contexto|`Register-PSSessionConfiguration`|
|Conectarse usando una configuración registrada|`Enter-PSSession -ConfigurationName`|
|Investigar la delegación Kerberos|Revisar la configuración y los tickets disponibles|

### Lo que debes recordar para el examen

- **Double Hop:** autenticarse en un primer equipo no implica que la autenticación se pueda reutilizar automáticamente en un segundo recurso.
    
- **TGT:** permite solicitar tickets de servicio; su ausencia en la sesión puede impedir la autenticación posterior.
    
- **TGS:** permite acceder al servicio para el que se ha emitido.
    
- **PSCredential:** permite pasar credenciales explícitamente a los comandos compatibles.
    
- **PSSessionConfiguration:** permite configurar el contexto de ejecución de una sesión remota, pero requiere privilegios y una configuración segura.
    
- **Unconstrained Delegation:** puede permitir que un servicio utilice el TGT recibido para acceder a otros servicios en nombre del usuario.
    
- **Error de PowerView:** si falla una consulta al dominio desde WinRM, no asumas inmediatamente que faltan permisos; comprueba primero el contexto de autenticación.
