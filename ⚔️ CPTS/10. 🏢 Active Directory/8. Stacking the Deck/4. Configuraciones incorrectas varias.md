
## 1. Pertenencia a grupos relacionados con Exchange

Las instalaciones de Microsoft Exchange en Active Directory pueden introducir vías de escalada de privilegios debido a los permisos elevados que reciben determinados grupos.

### Exchange Windows Permissions

- No es un grupo protegido, pero sus miembros pueden disponer de permisos `WriteDacl` sobre el objeto del dominio.
    
- `WriteDacl` permite modificar la DACL del objeto y puede aprovecharse para conceder privilegios adicionales.
    
- Una posible consecuencia es obtener permisos **DCSync**, que permiten recuperar hashes de contraseñas de Active Directory.
    
- Se pueden encontrar usuarios y equipos dentro del grupo debido a configuraciones incorrectas o a la asignación de permisos para tareas de soporte.
    

### Organization Management

- Es un grupo extremadamente privilegiado dentro de Exchange.
    
- Puede acceder a los buzones de correo de los usuarios del dominio.
    
- Tiene control sobre la OU `Microsoft Exchange Security Groups`, que contiene `Exchange Windows Permissions`.
    
- Comprometer un servidor Exchange puede facilitar la escalada hasta `Domain Admin`.
    
- El volcado de credenciales en memoria de un servidor Exchange puede revelar numerosas credenciales en texto plano o hashes NTLM, entre otras cosas, debido a las credenciales almacenadas en memoria tras los inicios de sesión en OWA.
    

**Qué comprobar durante una auditoría:**

- Miembros de `Exchange Windows Permissions`.
    
- Miembros de `Organization Management`.
    
- Permisos ACL sobre el dominio y las OUs relacionadas con Exchange.
    
- Posibles permisos `WriteDacl` y vías para conseguir privilegios DCSync.

## 2. PrivExchange

**PrivExchange** aprovecha un fallo en la característica `PushSubscription` de Exchange Server.

### Funcionamiento

1. Un usuario del dominio con buzón puede provocar que Exchange se autentique contra un host controlado por el atacante mediante HTTP.
    
2. El servicio de Exchange se ejecuta como `SYSTEM` y, en versiones vulnerables, disponía de privilegios excesivos.
    
3. La autenticación capturada puede retransmitirse hacia LDAP.
    
4. Según la versión y los permisos disponibles, esto puede permitir modificar permisos del dominio, obtener privilegios DCSync y recuperar la base de datos `NTDS`.
    

Si no es posible retransmitir la autenticación hacia LDAP, puede estudiarse la posibilidad de retransmitirla hacia otros servicios o equipos.

> **Punto clave:** PrivExchange puede convertir una cuenta de dominio con buzón en el punto de partida para una escalada de privilegios importante cuando el servidor y el entorno son vulnerables.

La vulnerabilidad descrita depende de la versión de Exchange y de las actualizaciones de seguridad instaladas.

## 3. Printer Bug (MS-RPRN)

El **Printer Bug** aprovecha el protocolo `MS-RPRN`, utilizado para la comunicación con el servicio de impresión de Windows.

### Funcionamiento

1. Un usuario del dominio puede conectarse al servicio de cola de impresión (`spooler`) de un servidor.
    
2. Mediante llamadas RPC específicas, puede provocar que el servidor se autentique contra un host controlado por el atacante a través de SMB.
    
3. La autenticación puede retransmitirse hacia LDAP u otros servicios.
    
4. Dependiendo de los permisos y la configuración del entorno, puede permitir:
    
    - Obtener privilegios DCSync.
        
    - Modificar permisos de delegación.
        
    - Configurar Resource-Based Constrained Delegation (RBCD).
        
    - Atacar otros equipos o dominios en determinados escenarios de confianza.
        

El servicio `spooler` se ejecuta como `SYSTEM` y suele estar instalado en servidores Windows con Desktop Experience.

### Enumerar el Printer Bug con PowerShell

```
Import-Module .\SecurityAssessment.ps1

Get-SpoolStatus -ComputerName ACADEMY-EA-DC01.INLANEFREIGHT.LOCAL
```

Una salida con `Status: True` indica que el host responde afirmativamente a la comprobación de la herramienta.

**Importante:** que un servidor responda a esta comprobación no demuestra por sí solo que una cadena completa de explotación vaya a funcionar. El resultado depende también de LDAP, la retransmisión, las protecciones instaladas y los permisos disponibles.

## 4. MS14-068

MS14-068 fue una vulnerabilidad de Kerberos que podía permitir a un usuario de dominio estándar elevar sus privilegios hasta `Domain Admin`.

### Conceptos importantes

- Los tickets de Kerberos incluyen información del usuario y de sus grupos.
    
- El **PAC (Privilege Attribute Certificate)** contiene información de autorización, incluida la pertenencia a grupos.
    
- El KDC firma el PAC para validar su integridad.
    
- La vulnerabilidad permitía que un PAC manipulado se aceptara como legítimo.
    

Un atacante podía construir un PAC falso que presentara al usuario como miembro de un grupo privilegiado.

### Herramientas mencionadas

- Python Kerberos Exploitation Kit (`PyKEK`).
    
- Impacket.
    

**Defensa:** aplicar las actualizaciones de seguridad correspondientes. La vulnerabilidad se considera histórica y su explotación depende de que el entorno siga siendo vulnerable.

## 5. Captura de credenciales LDAP

Las aplicaciones, impresoras y otros dispositivos pueden almacenar credenciales LDAP para autenticarse contra Active Directory.

### Posibles escenarios

- Credenciales visibles en texto plano en la consola de administración.
    
- Contraseñas débiles o predeterminadas.
    
- Funciones de prueba de conexión que permiten configurar una dirección LDAP arbitraria.
    
- Dispositivos que envían credenciales al probar una conexión contra un servidor controlado por el evaluador.
    

### Procedimiento conceptual

1. Revisar la configuración LDAP del dispositivo.
    
2. Comprobar si las credenciales están expuestas en la interfaz.
    
3. Evaluar, dentro del alcance autorizado, si la función de prueba de conexión puede dirigir la autenticación hacia un servidor de prueba.
    
4. Analizar las credenciales recibidas y determinar sus permisos en el dominio.
    

El material menciona el puerto LDAP `389` como ejemplo de puerto para recibir la conexión.

**Por qué es interesante:** las cuentas de servicio LDAP pueden tener privilegios elevados. Incluso si son cuentas de bajo privilegio, las credenciales pueden proporcionar un punto de apoyo inicial.

## 6. Enumeración de registros DNS con `adidnsdump`

Los registros DNS almacenados en Active Directory pueden revelar nombres de equipos y servicios que no resultan evidentes durante otras enumeraciones.

### ¿Para qué sirve?

`adidnsdump` permite enumerar registros DNS de un dominio mediante una cuenta de usuario de dominio válida.

Puede ayudar a identificar:

- Servidores con nombres descriptivos.
    
- Servicios interesantes, como Jenkins.
    
- Equipos cuya función no resulta evidente por su nombre.
    
- Registros que no aparecen directamente en consultas LDAP convencionales.
    

### Enumeración inicial

```
adidnsdump -u inlanefreight\\forend ldap://172.16.5.5
```

La herramienta solicita la contraseña y guarda los resultados en `records.csv`.

Consultar los primeros registros:

```
head records.csv
```

Ejemplo:

```
type,name,value
?,LOGISTICS,?
AAAA,ForestDnsZones,dead:beef::7442:c49d:e1d7:2691
A,ForestDnsZones,10.129.202.29
A,ForestDnsZones,172.16.5.240
```

Los registros que aparecen con tipo y valor desconocidos pueden requerir una resolución adicional.

### Resolver registros desconocidos

```
adidnsdump -u inlanefreight\\forend ldap://172.16.5.5 -r
```

Después, revisar de nuevo el archivo:

```
head records.csv
```

La opción `-r` intenta resolver los registros desconocidos mediante consultas DNS de tipo A.

**Idea clave:** no limitarse a los nombres de equipos obtenidos con BloodHound. La enumeración DNS puede descubrir nombres alternativos que revelen servicios relevantes.

## 8. Indicador `PASSWD_NOTREQD`

El atributo `userAccountControl` puede incluir el indicador `PASSWD_NOTREQD`.

Esto significa que la cuenta no está sujeta al requisito habitual de longitud de contraseña de la política actual. **No significa necesariamente que la cuenta no tenga contraseña.**

Puede deberse a:

- Configuraciones heredadas.
    
- Productos de terceros.
    
- Errores durante cambios de contraseña.
    
- Decisiones administrativas.
    

### Enumerar cuentas afectadas

```
Get-DomainUser -UACFilter PASSWD_NOTREQD |
    Select-Object samaccountname,useraccountcontrol
```

El resultado puede incluir cuentas deshabilitadas y cuentas activas.

### Qué hacer con los resultados

1. Identificar las cuentas afectadas.
    
2. Comprobar su estado y contexto.
    
3. Verificar, de forma autorizada, si pueden autenticarse sin contraseña.
    
4. Documentar el indicador como una posible configuración incorrecta.
    

**Punto clave:** `PASSWD_NOTREQD` es una señal para investigar, no una prueba de que la contraseña esté vacía.

## 9. Credenciales en recursos SMB y scripts de SYSVOL

El recurso compartido `SYSVOL` suele ser legible por los usuarios autenticados del dominio y puede contener scripts administrativos.

### Rutas de interés

```
\\ACADEMY-EA-DC01\SYSVOL\INLANEFREIGHT.LOCAL\scripts
```

Enumerar el directorio:

```
ls \\academy-ea-dc01\SYSVOL\INLANEFREIGHT.LOCAL\scripts
```

Buscar scripts de:

- PowerShell (`.ps1`).
    
- Batch (`.bat`, `.cmd`).
    
- VBScript (`.vbs`).
    
- Configuración de servicios.
    
- Restablecimiento de contraseñas.
    
- Automatización de tareas administrativas.
    

### Revisar un script

```
cat \\academy-ea-dc01\SYSVOL\INLANEFREIGHT.LOCAL\scripts\reset_local_admin_pass.vbs
```

El ejemplo de la lección muestra un script con una contraseña incrustada para la cuenta de administrador local.

### Después de encontrar una contraseña

1. Determinar si sigue siendo válida.
    
2. Identificar si corresponde a una cuenta local o de dominio.
    
3. Comprobar, dentro del alcance autorizado, si se reutiliza en otros equipos.
    
4. Evaluar los privilegios que proporciona.
    
5. Registrar el hallazgo y recomendar la eliminación de credenciales de los scripts.
    

> Las contraseñas antiguas también pueden ser útiles si se han reutilizado en otros sistemas.

## 10. Contraseñas de Group Policy Preferences (GPP)

Las **Group Policy Preferences (GPP)** permiten distribuir configuraciones a usuarios y equipos mediante directivas de grupo.

Históricamente, algunos archivos XML de GPP podían almacenar contraseñas mediante el atributo `cpassword`.

### Archivos que conviene revisar

|Archivo|Posible contenido|
|---|---|
|`Groups.xml`|Creación o modificación de usuarios y grupos locales|
|`Services.xml`|Configuración de servicios|
|`ScheduledTasks.xml`|Tareas programadas|
|`Drives.xml`|Unidades de red|
|`Printers.xml`|Configuración de impresoras|
|`Registry.xml`|Configuración del Registro, incluida la configuración de inicio de sesión automático|

### ¿Por qué podían recuperarse las contraseñas?

- El atributo `cpassword` se cifraba con AES de 256 bits.
    
- Microsoft publicó la clave necesaria para descifrar esos valores.
    
- Los usuarios autenticados del dominio suelen tener acceso de lectura a `SYSVOL`.
    

Microsoft corrigió esta vulnerabilidad mediante **MS14-025** en 2014, impidiendo el uso de GPP para establecer contraseñas de determinadas formas.

Sin embargo, el parche no eliminó automáticamente todos los archivos XML antiguos que ya contenían contraseñas.

### Descifrar un `cpassword`

Si se ha recuperado un valor `cpassword`, la herramienta `gpp-decrypt` permite intentar descifrarlo:

```
gpp-decrypt 'VALOR_CPASSWORD'
```

Ejemplo de la lección:

```
gpp-decrypt VPe/o9YRyz2cksnYRbNeQj35w9KxQ5ttbvtRaAVqxaE
```

La contraseña resultante debe verificarse y tratarse como información sensible.

### Buscar contraseñas GPP con CrackMapExec

Listar los módulos relacionados:

```
crackmapexec smb -L | grep gpp
```

La lección identifica estos módulos:

- `gpp_password`: busca contraseñas distribuidas mediante Group Policy Preferences.
    
- `gpp_autologin`: busca información de inicio de sesión automático en `Registry.xml`.

## 11. Credenciales de inicio de sesión automático en `Registry.xml`

El inicio de sesión automático puede configurarse mediante una GPO para que un equipo inicie sesión con una cuenta determinada al arrancar.

Si la configuración se distribuye mediante GPP, las credenciales pueden quedar almacenadas en `Registry.xml` dentro de `SYSVOL`.

Según el material, este problema es distinto del almacenamiento de contraseñas GPP mediante `cpassword`, ya que las credenciales de inicio de sesión automático pueden quedar en texto plano.

### Enumeración con CrackMapExec

```
crackmapexec smb 172.16.5.5 \
    -u forend \
    -p 'Klmcargo2' \
    -M gpp_autologin
```

La salida puede mostrar:

- La ruta del archivo `Registry.xml`.
    
- Los nombres de usuario encontrados.
    
- Los dominios asociados.
    
- Las contraseñas almacenadas.
    

### Qué comprobar

1. Si la cuenta existe y está habilitada.
    
2. Si las credenciales siguen siendo válidas.
    
3. Si corresponden a una cuenta local o de dominio.
    
4. Si la contraseña se reutiliza en otros sistemas.
    
5. Si la cuenta posee privilegios relevantes.
    

**Recomendación:** eliminar las credenciales almacenadas, rotar las contraseñas expuestas y evitar el inicio de sesión automático con cuentas privilegiadas.

## 12. Reutilización de contraseñas

La reutilización de contraseñas es una línea de investigación importante durante una evaluación de Active Directory.

Cada vez que se obtengan credenciales, conviene comprobar si permiten acceder a otros recursos autorizados.

### Checklist

- Verificar si la cuenta existe y está habilitada.
    
- Determinar si es una cuenta local, de dominio o de servicio.
    
- Comprobar los permisos y grupos de la cuenta.
    
- Revisar ACL interesantes.
    
- Comprobar el acceso a recursos SMB.
    
- Investigar si la contraseña se reutiliza en otros hosts.
    
- Evaluar, cuando esté autorizado, un password spraying controlado.
    
- Registrar los sistemas y privilegios afectados.
    

Una contraseña de una cuenta antigua o deshabilitada también puede ser útil si se reutiliza en otra cuenta.

## 13. ASREPRoasting

**ASREPRoasting** permite obtener material de autenticación Kerberos de cuentas que tienen deshabilitada la preautenticación.

### Concepto

En una autenticación Kerberos convencional:

1. El usuario proporciona información de autenticación.
    
2. El KDC valida la preautenticación.
    
3. Si la validación es correcta, el KDC emite un TGT.
    

Cuando una cuenta tiene habilitada la opción `Do not require Kerberos pre-authentication`, es posible solicitar una respuesta AS-REP sin realizar la preautenticación habitual.

Parte de esa respuesta está cifrada utilizando material derivado de la contraseña de la cuenta, lo que permite intentar recuperar la contraseña mediante cracking sin conexión.

### Diferencias respecto a Kerberoasting

|Característica|ASREPRoasting|Kerberoasting|
|---|---|---|
|Material obtenido|AS-REP|TGS-REP|
|Condición principal|Preautenticación deshabilitada|Cuenta asociada a un SPN|
|Requiere SPN|No|Sí|
|Cracking|Sin conexión|Sin conexión|
|Éxito|Depende, entre otros factores, de la fortaleza de la contraseña|Depende, entre otros factores, de la fortaleza de la contraseña|

### Enumerar cuentas con PowerView

```
Get-DomainUser -PreauthNotRequired |
    Select-Object samaccountname,userprincipalname,useraccountcontrol |
    Format-List
```

Buscar el indicador:

```
DONT_REQ_PREAUTH
```

Ejemplo:

```
samaccountname     : mmorgan
userprincipalname  : mmorgan@inlanefreight.local
useraccountcontrol : NORMAL_ACCOUNT, DONT_EXPIRE_PASSWORD, DONT_REQ_PREAUTH
```

### Obtener la AS-REP con Rubeus

```
.\Rubeus.exe asreproast /user:mmorgan /nowrap /format:hashcat
```

- `/user:mmorgan`: especifica la cuenta objetivo.
    
- `/nowrap`: evita que el hash se divida en varias líneas.
    
- `/format:hashcat`: solicita el formato compatible con Hashcat.
    

El resultado incluye un hash que puede guardarse para intentar recuperarlo sin conexión.

### Crackear el hash con Hashcat

Para el formato Kerberos 5 AS-REP con etype 23, el modo indicado en la lección es `18200`.

```
hashcat -m 18200 ilfreight_asrep /usr/share/wordlists/rockyou.txt
```

Donde:

- `-m 18200`: selecciona el modo AS-REP de Kerberos 5, etype 23.
    
- `ilfreight_asrep`: archivo que contiene el hash.
    
- `rockyou.txt`: diccionario de contraseñas.
    

El cracking solo tendrá éxito si la contraseña se encuentra en el diccionario o puede descubrirse mediante la estrategia utilizada.

### Enumerar usuarios y recuperar AS-REP con Kerbrute

```
kerbrute userenum \
    -d inlanefreight.local \
    --dc 172.16.5.5 \
    /opt/jsmith.txt
```

Durante la enumeración, Kerbrute puede identificar cuentas válidas y detectar usuarios que no requieren preautenticación. Cuando encuentra una cuenta vulnerable, puede mostrar el material AS-REP correspondiente para cracking sin conexión.

### Buscar cuentas con Impacket

Si se dispone de una lista de usuarios válidos:

```
GetNPUsers.py INLANEFREIGHT.LOCAL/ \
    -dc-ip 172.16.5.5 \
    -no-pass \
    -usersfile valid_ad_users
```

La herramienta busca usuarios que tengan activado `UF_DONT_REQUIRE_PREAUTH` y puede devolver hashes AS-REP para las cuentas afectadas.

Los mensajes que indican que un usuario no tiene establecido `UF_DONT_REQUIRE_PREAUTH` significan que esa cuenta no cumple la condición para este ataque.

### Abuso de permisos sobre una cuenta

Si tenemos permisos `GenericWrite` o `GenericAll` sobre una cuenta, la lección indica que podría ser posible habilitar temporalmente el atributo de preautenticación deshabilitada, obtener su AS-REP y después restaurar la configuración.

Esto requiere que los permisos y las condiciones del entorno permitan modificar el atributo.

### Puntos importantes para el examen

- No se necesita un SPN para ASREPRoasting.
    
- No es necesario disponer de una sesión en un equipo unido al dominio.
    
- La cuenta debe permitir solicitudes AS-REP sin la preautenticación habitual.
    
- El hash se ataca sin conexión.
    
- Si la contraseña es fuerte, el cracking puede fallar.
    
- Aunque no se recupere la contraseña, la configuración puede documentarse como hallazgo de seguridad.

## 14. Abuso de objetos de directiva de grupo (GPO)

Las **Group Policy Objects (GPO)** permiten aplicar configuraciones a usuarios y equipos de Active Directory.

Una mala configuración de permisos sobre un GPO puede permitir modificar las políticas que se aplican a los objetos afectados.

### Posibles abusos

Un GPO modificable puede permitir, dependiendo de los permisos y del contexto:

- Añadir usuarios a grupos de administradores locales.
    
- Conceder privilegios como `SeDebugPrivilege`, `SeTakeOwnershipPrivilege` o `SeImpersonatePrivilege`.
    
- Crear tareas programadas.
    
- Ejecutar scripts de inicio de equipo.
    
- Facilitar el movimiento lateral.
    
- Escalar privilegios.
    
- Establecer mecanismos de persistencia.
    

### Enumerar GPO con PowerView

```
Get-DomainGPO | Select-Object displayname
```

### Enumerar GPO con los cmdlets integrados

Si están instaladas las herramientas de administración de directivas de grupo:

```
Get-GPO -All | Select-Object DisplayName
```

La lista puede revelar políticas relacionadas con:

- Inicio de sesión automático.
    
- Restricciones de CMD o del Panel de control.
    
- Políticas de contraseñas.
    
- Servicios de certificados.
    
- Configuración de equipos.
    

### Comprobar permisos de Domain Users

Primero, obtener el SID del grupo:

```
$sid = Convert-NameToSid "Domain Users"
```

Después, revisar los permisos de los objetos GPO:

```
Get-DomainGPO |
    Get-ObjectAcl |
    Where-Object {$_.SecurityIdentifier -eq $sid}
```

Buscar permisos relevantes como:

- `WriteProperty`
    
- `WriteDacl`
    
- `WriteOwner`
    
- `GenericWrite`
    
- `GenericAll`
    

Estos permisos no significan exactamente lo mismo, pero algunos pueden permitir modificar la configuración o los permisos del objeto GPO.

### Convertir el GUID del GPO en su nombre

```
Get-GPO -Guid 7CA9C789-14CE-46E3-A722-83F4097AF532
```

Esto permite identificar el GPO, consultar su nombre y revisar sus propiedades.

### Análisis con BloodHound

BloodHound permite comprobar:

1. Qué usuarios o grupos tienen permisos sobre el GPO.
    
2. Qué relaciones de control aparecen en el grafo.
    
3. A qué OU está vinculado.
    
4. Qué equipos y usuarios se ven afectados.
    

La pestaña `Node Info`, en `Affected Objects`, permite examinar los objetos afectados por el GPO.

### SharpGPOAbuse

SharpGPOAbuse es una herramienta mencionada en la lección para aprovechar permisos insuficientemente restringidos sobre GPO.

Entre las acciones descritas están:

- Añadir un usuario controlado al grupo de administradores locales.
    
- Crear tareas programadas.
    
- Configurar scripts de inicio de equipo.
    

**Precaución importante:** un GPO puede aplicarse a muchos equipos. Antes de modificarlo, hay que identificar su alcance y limitar las acciones a los objetivos autorizados. Un cambio indiscriminado podría afectar a cientos o miles de sistemas.

La sección recomienda profundizar en:

# Checklist de enumeración para una evaluación AD

- Revisar miembros y permisos de los grupos relacionados con Exchange.
    
- Comprobar posibles problemas de autenticación forzada y retransmisión.
    
- Enumerar registros DNS con `adidnsdump`.
    
- Revisar atributos `Description` y `Notes` de los usuarios.
    
- Identificar cuentas con `PASSWD_NOTREQD`.
    
- Buscar credenciales en scripts y recursos compartidos SMB.
    
- Revisar archivos XML de GPP y credenciales de autologon.
    
- Probar de forma controlada la reutilización de las credenciales recuperadas.
    
- Buscar usuarios con `DONT_REQ_PREAUTH`.
    
- Obtener y analizar hashes AS-REP cuando proceda.
    
- Enumerar GPO y sus ACL.
    
- Revisar en BloodHound qué objetos están afectados por los GPO modificables.
    
- Documentar las configuraciones incorrectas aunque no se consiga explotarlas.
    

**Idea central de la sección:** no limitar la evaluación a los ataques más conocidos. Los grupos de Exchange, los registros DNS, las credenciales olvidadas, los scripts de SYSVOL, la preautenticación Kerberos y los permisos sobre GPO pueden revelar rutas adicionales hacia un mayor acceso en Active Directory.
