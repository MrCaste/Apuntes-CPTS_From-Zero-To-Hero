

## 1. Kerberoasting entre bosques (Cross-Forest Kerberoasting)

Permite solicitar tickets TGS de cuentas con SPN en otro dominio accesible mediante una confianza. Si conseguimos crackear el hash de una cuenta privilegiada del dominio objetivo, podemos obtener acceso administrativo.

### 1.1. Enumerar usuarios con SPN en el dominio objetivo

Con PowerView:

```
Get-DomainUser -SPN -Domain FREIGHTLOGISTICS.LOCAL | Select-Object SamAccountName
```

El resultado muestra las cuentas que tienen SPN y que pueden ser candidatas a Kerberoasting.

### 1.2. Comprobar los privilegios de la cuenta

```
Get-DomainUser -Domain FREIGHTLOGISTICS.LOCAL -Identity mssqlsvc |
    Select-Object SamAccountName, MemberOf
```

Si pertenece a `Domain Admins`, comprometer su contraseña podría proporcionar privilegios administrativos en el dominio objetivo.

### 1.3. Ejecutar Cross-Forest Kerberoasting con Rubeus

```
.\Rubeus.exe kerberoast /domain:FREIGHTLOGISTICS.LOCAL /user:mssqlsvc /nowrap
```

**Parámetros importantes:**

- `/domain:`: dominio objetivo en el que buscar la cuenta.
    
- `/user:`: cuenta específica que se quiere atacar.
    
- `/nowrap`: evita que el hash se divida en varias líneas.
    

Rubeus devuelve el hash TGS de la cuenta. Podemos guardarlo en un archivo y probar a crackearlo fuera de línea con Hashcat.

```
hashcat -m 13100 hash.txt /ruta/a/wordlist.txt
```

El modo `13100` corresponde a Kerberos 5 TGS-REP etype 23 (RC4). Hay que utilizar el modo que corresponda al formato de hash obtenido.

**Objetivo:** conseguir la contraseña de una cuenta privilegiada del dominio de confianza sin necesidad de escalar privilegios primero en nuestro dominio actual.

## 2. Reutilización de contraseñas entre dominios

Cuando existe una confianza bidireccional entre bosques, conviene comprobar si las cuentas privilegiadas reutilizan contraseñas.

### Procedimiento

1. Obtener una contraseña en texto claro o un hash NT de una cuenta privilegiada del dominio comprometido.
    
2. Identificar cuentas privilegiadas del otro dominio.
    
3. Comprobar si existe reutilización de contraseñas o credenciales.
    
4. Validar el acceso utilizando los mecanismos de autenticación permitidos en el laboratorio.
    

Presta especial atención a:

- La cuenta `Administrator`.
    
- Miembros de `Domain Admins`.
    
- Miembros de `Enterprise Admins`.
    
- Cuentas administrativas con nombres diferentes entre dominios.
    

**Idea clave:** una cuenta con un nombre diferente puede reutilizar la misma contraseña. No hay que limitar la comprobación a cuentas que tengan exactamente el mismo nombre.

## 3. Enumerar miembros de grupos externos

Un dominio puede incluir una cuenta de otro dominio o bosque como miembro de uno de sus grupos.

Los **Domain Local Groups** permiten incluir entidades de seguridad externas dentro de sus miembros, por lo que pueden existir relaciones de pertenencia que proporcionen acceso a recursos del dominio objetivo.

### 3.1. Enumerar miembros externos con PowerView

```
Get-DomainForeignGroupMember -Domain FREIGHTLOGISTICS.LOCAL
```

Ejemplo de salida:

```
GroupDomain             : FREIGHTLOGISTICS.LOCAL
GroupName               : Administrators
MemberName              : S-1-5-21-...-500
```

El SID representa una entidad de seguridad externa incluida en el grupo.

### 3.2. Resolver el SID a un nombre

```
Convert-SidToName S-1-5-21-3842939050-3880317879-2865463114-500
```

Ejemplo de resultado:

```
INLANEFREIGHT\administrator
```

En este caso, el grupo `Administrators` del dominio `FREIGHTLOGISTICS.LOCAL` incluye a la cuenta `administrator` de `INLANEFREIGHT.LOCAL`.

### 3.3. Validar el acceso mediante WinRM

Si las credenciales y los permisos permiten la conexión, podemos probar una sesión remota:

```
Enter-PSSession -ComputerName ACADEMY-EA-DC03.FREIGHTLOGISTICS.LOCAL `
    -Credential INLANEFREIGHT\administrator
```

Dentro de la sesión:

```
whoami
```

Para comprobar la identidad utilizada:

```
whoami /all
```

**Importante:** la pertenencia al grupo solo será aprovechable si la confianza, la autenticación y los permisos efectivos permiten acceder al recurso. La enumeración por sí sola no garantiza acceso remoto.

## 4. Abuso del historial de SID entre bosques

El atributo `SIDHistory` permite conservar SID anteriores cuando una cuenta se migra entre dominios.

Si una cuenta migrada conserva un SID privilegiado de otro dominio y el filtrado de SID no impide que se utilice a través de la confianza, ese SID puede conceder acceso a recursos del dominio de origen.

### Escenario

- `INLANEFREIGHT.LOCAL`: dominio de origen.
    
- `CORP.LOCAL`: dominio de destino.
    
- Un usuario se migra de `INLANEFREIGHT.LOCAL` a `CORP.LOCAL`.
    
- La cuenta conserva un SID anterior con privilegios en el dominio de origen.
    
- La confianza y la configuración del filtrado de SID permiten que ese SID sea aceptado.
    

En ese escenario, la cuenta migrada podría conservar acceso a recursos del dominio anterior.

### Qué comprobar

1. Si existe una confianza entre los bosques.
    
2. La dirección y el tipo de confianza.
    
3. Si las cuentas migradas conservan valores de `SIDHistory`.
    
4. Si el SID conservado pertenece a un grupo privilegiado o tiene permisos relevantes.
    
5. Si el filtrado de SID impide que se utilice ese SID a través de la confianza.
    

**Nota:** esta sección presenta el concepto y el escenario de abuso, pero no incluye comandos para ejecutar el ataque. El módulo indica que se desarrollará en profundidad más adelante.

## 5. Flujo de enumeración recomendado

Ante una confianza entre bosques, sigue este orden:

1. **Enumerar las cuentas con SPN** en el dominio objetivo.
    
2. **Comprobar los grupos** a los que pertenecen las cuentas candidatas.
    
3. **Probar Cross-Forest Kerberoasting** con Rubeus.
    
4. **Analizar los hashes obtenidos** con Hashcat, utilizando el modo correcto.
    
5. **Buscar miembros de grupos externos** con `Get-DomainForeignGroupMember`.
    
6. **Resolver los SID** encontrados con `Convert-SidToName`.
    
7. **Comprobar la reutilización de contraseñas** de cuentas privilegiadas.
    
8. **Revisar** `**SIDHistory**` **y el filtrado de SID** cuando existan migraciones entre bosques.
    
9. **Validar el acceso efectivo** a los recursos del dominio objetivo.

## Conceptos clave

- **Cross-Forest Kerberoasting:** solicitar tickets TGS de cuentas con SPN de otro dominio y crackear sus hashes fuera de línea.
    
- **Reutilización de contraseñas:** una contraseña obtenida en un dominio puede permitir el acceso a una cuenta privilegiada de otro.
    
- **Foreign Group Membership:** una cuenta externa puede formar parte de un grupo del dominio objetivo y obtener sus permisos efectivos.
    
- **SIDHistory:** puede conservar privilegios del dominio de origen tras una migración, si la configuración de confianza permite aprovecharlos.
    
- **Confianza bidireccional:** puede permitir autenticación en ambas direcciones, pero no concede automáticamente privilegios administrativos.
