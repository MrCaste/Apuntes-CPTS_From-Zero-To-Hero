
## 1. Introducción a SQL Injection

La **SQL Injection (SQLi)** es una vulnerabilidad que permite modificar una consulta SQL mediante la introducción de datos manipulados en una aplicación web.

En esta sección, aprenderemos a utilizar el operador `OR` para alterar la lógica de una consulta y comprender cómo puede producirse una elusión de autenticación.

## 2. Elusión de autenticación

Consideremos un formulario de inicio de sesión que solicita un nombre de usuario y una contraseña.

La aplicación ejecuta una consulta similar a esta:

```
SELECT * FROM logins
WHERE username = 'admin' AND password = 'p@ssw0rd';
```

La consulta busca un registro que cumpla ambas condiciones:

- El nombre de usuario debe ser `admin`.
    
- La contraseña debe ser `p@ssw0rd`.
    

Como se utiliza `AND`, ambas condiciones deben ser verdaderas para obtener un registro coincidente.

Si las credenciales son incorrectas, la consulta no devuelve el registro esperado y el inicio de sesión falla.

## 3. Detectar una posible SQL Injection

Antes de intentar modificar la lógica de una consulta, debemos comprobar si la aplicación puede ser vulnerable a SQLi.

Una primera prueba consiste en introducir caracteres que puedan alterar la sintaxis de SQL y observar la respuesta de la aplicación.

|Carácter|Codificación URL|
|---|---|
|`'`|`%27`|
|`"`|`%22`|
|`#`|`%23`|
|`;`|`%3B`|
|`)`|`%29`|

La codificación URL puede ser necesaria cuando los caracteres se introducen directamente en una URL, por ejemplo, en una petición HTTP GET.

### Ejemplo: comilla simple

Si introducimos una comilla simple en el campo del usuario, la consulta podría quedar así:

```
SELECT * FROM logins
WHERE username = ''' AND password = 'something';
```

La comilla adicional puede provocar un error de sintaxis SQL.

Si la aplicación muestra un error de la base de datos en lugar del mensaje habitual de inicio de sesión fallido, puede ser un indicio de que la entrada está afectando a la consulta.

**Importante:** un error SQL es un indicio, pero no demuestra por sí solo que exista una vulnerabilidad explotable.

## 4. Utilizar `OR` para modificar la lógica

El operador `OR` devuelve `TRUE` cuando al menos una de las condiciones es verdadera.

Por ejemplo:

```
'1' = '1'
```

Esta comparación siempre es verdadera, porque ambos valores son iguales.

En el laboratorio de HTB Academy se estudia cómo utilizar una condición de este tipo para alterar la consulta de autenticación.

### Ejemplo del laboratorio

La consulta original es:

```
SELECT * FROM logins
WHERE username = 'admin' AND password = 'something';
```

El contenido introducido en el formulario puede modificar la consulta resultante:

```
SELECT * FROM logins
WHERE username = 'admin' OR '1' = '1' AND password = 'something';
```

Para comprender el resultado, es necesario tener en cuenta la precedencia de los operadores.

`**AND**` **tiene mayor precedencia que** `**OR**`**.**

Por tanto, la expresión se interpreta de la siguiente manera:

```
username = 'admin'
OR
(
    '1' = '1'
    AND password = 'something'
)
```

La condición `'1' = '1'` es verdadera, pero eso no hace que toda la consulta sea necesariamente verdadera: el resultado de la expresión entre paréntesis también depende de la contraseña.

Si la contraseña no coincide, esa parte será falsa. Si existe un registro con el nombre de usuario `admin`, la primera condición será verdadera y el resultado global será verdadero.

**Conclusión:** el resultado depende de cómo se combinen las condiciones y de la precedencia de los operadores.

## 5. La importancia de conocer un usuario válido

En el ejemplo anterior, la consulta puede devolver el registro de `admin` porque el nombre de usuario existe.

Si se utiliza un nombre inexistente, como `notAdmin`, la primera condición será falsa:

```
username = 'notAdmin'
```

Si la segunda parte también es falsa, la consulta no devolverá ningún registro y el inicio de sesión fallará.

Esto demuestra que **una condición que contiene** `**OR**` **no garantiza por sí sola que toda la consulta sea verdadera**.

## 6. Modificación de la condición de contraseña

El material de HTB Academy también explica que modificar la condición de contraseña puede cambiar el resultado global de la consulta.

La consulta resultante del ejemplo es:

```
SELECT * FROM logins
WHERE username = 'notAdmin'
OR '1' = '1' AND password = 'something'
OR '1' = '1';
```

Debido a la precedencia de `AND` y `OR`, la expresión se interpreta así:

```
username = 'notAdmin'
OR
(
    '1' = '1'
    AND password = 'something'
)
OR
'1' = '1'
```

La última condición es verdadera, por lo que toda la expresión de `WHERE` resulta verdadera para los registros de la tabla.

En el laboratorio, esto permite observar cómo una consulta alterada puede devolver registros sin que las credenciales originales sean válidas.

Cuando una consulta devuelve varios registros, el comportamiento final de la aplicación depende de cómo su código gestione esos resultados.

## 7. Conceptos clave

|Concepto|Descripción|
|---|---|
|SQL Injection|Introducir datos que alteran la estructura o lógica de una consulta SQL.|
|`AND`|Devuelve verdadero únicamente si ambas condiciones son verdaderas.|
|`OR`|Devuelve verdadero si al menos una condición es verdadera.|
|Precedencia|Determina el orden en que se evalúan los operadores.|
|Error SQL|Puede indicar que una entrada está afectando a la sintaxis de la consulta.|
|Elusión de autenticación|Conseguir que una aplicación acepte un inicio de sesión sin validar correctamente las credenciales.|

## 8. Chuleta rápida

```
-- Consulta original de autenticación
SELECT * FROM logins
WHERE username = 'admin' AND password = 'p@ssw0rd';

-- Condición siempre verdadera
SELECT '1' = '1';

-- Condición verdadera combinada con AND
SELECT '1' = '1' AND 'test' = 'abc';

-- AND se evalúa antes que OR
SELECT FALSE OR TRUE AND FALSE;
```

Resultados esperados:

- `'1' = '1'` → verdadero.
    
- `TRUE AND FALSE` → falso.
    
- `FALSE OR (TRUE AND FALSE)` → falso.
    

## 9. Aplicación práctica en HTB

Al analizar una posible SQL Injection en un formulario de autenticación:

1. Identificar los campos que podrían incorporarse a una consulta SQL.
    
2. Observar cómo responde la aplicación ante entradas inesperadas.
    
3. Comprobar si aparecen errores SQL o cambios de comportamiento.
    
4. Reconstruir la consulta original cuando la aplicación permita observarla.
    
5. Analizar cómo interactúan `AND`, `OR` y las condiciones de autenticación.
    
6. Tener en cuenta la precedencia de operadores antes de sacar conclusiones.
    
7. Recordar que el comportamiento final depende también de cómo la aplicación gestione los registros devueltos.
    

**Idea fundamental:** para comprender una SQL Injection, no basta con identificar una condición verdadera. Hay que analizar la consulta completa, la precedencia de los operadores y la forma en que la aplicación procesa los resultados.
