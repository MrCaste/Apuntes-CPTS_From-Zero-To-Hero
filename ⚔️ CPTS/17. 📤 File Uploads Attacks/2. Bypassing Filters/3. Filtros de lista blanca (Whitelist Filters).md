
## 1. Concepto

Una **whitelist** es una lista de extensiones permitidas por el servidor. En general, es más segura que una blacklist porque solo acepta los tipos expresamente autorizados.

|Tipo de filtro|Funcionamiento|Debilidad principal|
|---|---|---|
|**Blacklist**|Bloquea extensiones concretas.|Puede dejar extensiones alternativas sin bloquear.|
|**Whitelist**|Permite únicamente extensiones autorizadas.|Puede implementarse incorrectamente mediante expresiones regulares o configuraciones inseguras del servidor.|

Ambos filtros pueden combinarse con comprobaciones del tipo y contenido del archivo.

## 2. Identificar una whitelist

Si intentamos subir un archivo `.phtml` y obtenemos:

```
Only images are allowed
```

podría existir una whitelist de imágenes.

Sin embargo, **el mensaje de error no confirma qué método de validación se utiliza**. Podemos comprobarlo mediante fuzzing de extensiones con Burp Intruder.

- Si todas las extensiones PHP son rechazadas, pero otras se aceptan, debemos investigar qué está comprobando realmente la aplicación.
    
- Que una extensión sea aceptada no significa que el archivo vaya a ejecutarse como código PHP.

## 3. Evasión mediante extensiones dobles

### ¿En qué consiste?

Algunas aplicaciones utilizan una expresión regular que comprueba si el nombre del archivo contiene una extensión permitida, pero no verifican que sea la extensión final.

Ejemplo vulnerable en PHP:

```
$fileName = basename($_FILES["uploadFile"]["name"]);

if (!preg_match('^.*\.(jpg|jpeg|png|gif)', $fileName)) {
    echo "Only images are allowed";
    die();
}
```

La expresión regular no está anclada al final del nombre. Por ello, un archivo que contenga `.jpg` antes de `.php` podría superar la validación.

### Ejemplo

Nombre del archivo:

```
shell.jpg.php
```

La aplicación encuentra `.jpg` y puede aceptar el archivo, aunque termine en `.php`.

Si el servidor interpreta la extensión final como PHP, el archivo podría ejecutarse.

### Comprobación en el laboratorio

1. Interceptar una petición de subida con Burp Suite.
    
2. Modificar el nombre para probar una extensión doble.
    
3. Enviar la petición y comprobar la respuesta.
    
4. Si se acepta, acceder a la ruta donde se guarda el archivo.
    
5. Verificar si el servidor lo interpreta como PHP.
    

### Expresión regular más estricta

Una validación que comprueba el final del nombre podría ser:

```
if (!preg_match('/^.*\.(jpg|jpeg|png|gif)$/', $fileName)) {
    // Rechazar archivo
}
```

Los símbolos importantes son:

- `^`: inicio de la cadena.
    
- `.*`: cualquier secuencia de caracteres.
    
- `\.`: un punto literal.
    
- `$`: final de la cadena.
    

Esta expresión exige que el nombre termine con una de las extensiones indicadas, por lo que `shell.jpg.php` no debería superarla.

## 4. Evasión mediante extensión doble inversa

En ocasiones, la validación de la aplicación es estricta, pero el servidor web tiene una configuración insegura que permite ejecutar archivos cuya extensión final no es PHP.

### Ejemplo de configuración de Apache

```
<FilesMatch ".+\.ph(ar|p|tml)">
    SetHandler application/x-httpd-php
</FilesMatch>
```

Esta configuración asigna el intérprete PHP a los archivos cuyos nombres coinciden con el patrón.

El problema es que el patrón no termina con `$`. Por tanto, puede coincidir con un nombre que contenga `.php`, `.phar` o `.phtml` aunque después aparezcan otros caracteres.

### Ejemplo conceptual

```
shell.php.jpg
```

Podría darse esta combinación:

1. La aplicación acepta el archivo porque termina en `.jpg`.
    
2. Apache lo interpreta como PHP porque el nombre contiene `.php`.
    
3. El código PHP se ejecuta cuando se solicita el archivo.
    

**Diferencia importante:**

- **Extensión doble:** se aprovecha una validación de la aplicación que acepta una extensión permitida en una posición incorrecta.
    
- **Extensión doble inversa:** se aprovecha una configuración del servidor que puede interpretar como PHP un nombre que termina en otra extensión.
    

Este segundo caso depende de la configuración real del servidor. No todas las instalaciones de Apache ejecutan PHP de esta manera.

## 5. Inyección de caracteres

Otra técnica consiste en introducir caracteres especiales en el nombre del archivo para provocar que la aplicación y el servidor lo interpreten de manera diferente.

Caracteres mencionados en el módulo:

|Carácter o secuencia|Posible efecto|
|---|---|
|`%20`|Espacio codificado.|
|`%0a`|Salto de línea codificado.|
|`%00`|Byte nulo; puede truncar nombres en sistemas antiguos.|
|`%0d0a`|Secuencia de retorno de carro y salto de línea.|
|`/`|Separador de ruta.|
|`.\`|Secuencia que puede tener efectos específicos según el entorno.|
|`.`|Punto adicional en el nombre.|
|`…`|Secuencia de puntos que puede interactuar con implementaciones particulares.|
|`:`|Puede tener efectos especiales en determinados sistemas Windows.|

### Ejemplo histórico: byte nulo

En versiones antiguas de PHP, como PHP 5.x o anteriores, un byte nulo podía hacer que parte del procesamiento interpretara el nombre hasta ese punto.

Por ejemplo, el módulo menciona:

```
shell.php%00.jpg
```

La validación podría interpretar `.jpg`, mientras que un componente vulnerable podría tratar el nombre efectivo como `shell.php`.

**Importante:** esta técnica depende de implementaciones antiguas o vulnerables y no debe considerarse un método universal en sistemas actuales.

### Generar una wordlist con Bash

El siguiente script genera distintas combinaciones de nombres para utilizarlas en un laboratorio autorizado:

```
for char in '%20' '%0a' '%00' '%0d0a' '/' '.\\' '.' '…' ':'; do
    for ext in '.php' '.phps'; do
        echo "shell$char$ext.jpg" >> wordlist.txt
        echo "shell$ext$char.jpg" >> wordlist.txt
        echo "shell.jpg$char$ext" >> wordlist.txt
        echo "shell.jpg$ext$char" >> wordlist.txt
    done
done
```

El archivo `wordlist.txt` contendrá las distintas permutaciones.

Puedes ampliar el conjunto de extensiones y probar los nombres con Burp Intruder. Después, comprueba por separado cuáles se aceptan y cuáles llegan a ejecutarse.

## 6. Metodología para el laboratorio

1. Intentar subir un archivo con una extensión PHP alternativa.
    
2. Observar el mensaje de error y realizar fuzzing para identificar las extensiones permitidas.
    
3. Examinar cómo se valida el nombre del archivo.
    
4. Comprobar si la expresión regular verifica la extensión final o solo busca una extensión permitida en cualquier posición.
    
5. Si la validación de la aplicación es estricta, investigar si el comportamiento del servidor web permite una interpretación diferente.
    
6. En entornos vulnerables, probar las técnicas de inyección de caracteres descritas en el módulo.
    
7. Verificar siempre dos resultados distintos: **archivo aceptado** y **código ejecutado**.
    

## 🎯 Chuleta para el examen

- **Whitelist:** permite extensiones expresamente autorizadas.
    
- **Regex sin** `**$**`**:** puede aceptar nombres que contengan una extensión permitida sin terminar en ella.
    
- **Extensión doble:** ejemplo `shell.jpg.php`; la validación puede encontrar `.jpg`, mientras que el servidor puede ejecutar PHP por la extensión final.
    
- **Extensión doble inversa:** ejemplo `shell.php.jpg`; puede funcionar si la aplicación acepta `.jpg` y el servidor tiene una configuración de ejecución demasiado permisiva.
    
- `**^**`**:** inicio de la cadena.
    
- `**$**`**:** final de la cadena.
    
- `**<FilesMatch>**` **de Apache:** puede determinar qué nombres reciben un manejador PHP.
    
- **Inyección de caracteres:** intenta aprovechar diferencias en el tratamiento del nombre entre la aplicación, el sistema operativo y el servidor web.
    
- **Byte nulo (**`**%00**`**):** técnica histórica dependiente de implementaciones antiguas.
    
- **Burp Intruder:** automatiza las pruebas de extensiones y nombres de archivo.
    
- **Regla fundamental:** que un archivo supere la whitelist no demuestra que pueda ejecutarse; hay que verificar también el comportamiento del servidor.
