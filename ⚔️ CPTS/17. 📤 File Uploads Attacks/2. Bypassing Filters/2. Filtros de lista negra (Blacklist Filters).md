
## 1. Concepto

Una **blacklist** es una lista de extensiones que el servidor rechaza para impedir la subida de determinados archivos, como scripts PHP.

Ejemplo de validación en PHP:

```
$fileName = basename($_FILES["uploadFile"]["name"]);
$extension = pathinfo($fileName, PATHINFO_EXTENSION);
$blacklist = array('php', 'php7', 'phps');

if (in_array($extension, $blacklist)) {
    echo "File type not allowed";
    die();
}
```

El servidor extrae la extensión del nombre del archivo y comprueba si aparece en la lista negra.

**Problema:** la lista puede estar incompleta. Si una extensión capaz de ejecutar PHP no está incluida, es posible que podamos eludir el filtro.

Además, si la comparación distingue entre mayúsculas y minúsculas (_case-sensitive_), puede aceptar extensiones como `pHp`. Su efectividad dependerá del sistema operativo y de la configuración del servidor web.

## 2. Fuzzing de extensiones

El objetivo es probar diferentes extensiones para identificar cuáles acepta el servidor.

### Paso 1. Interceptar una petición válida

Sube una imagen y captura la petición a `/upload.php` con Burp Suite.

Después, modifica el nombre del archivo para utilizar una extensión PHP:

```
Content-Disposition: form-data; name="uploadFile"; filename="HTB.php"
```

Si el servidor responde:

```
Extension not allowed
```

sabemos que la extensión está bloqueada.

### Paso 2. Enviar la petición a Intruder

En Burp Suite:

1. Abre **Proxy → HTTP history**.
    
2. Selecciona la petición a `/upload.php`.
    
3. Haz clic derecho y selecciona **Send to Intruder**.
    
4. En **Positions**, pulsa `Clear`.
    
5. Selecciona únicamente la extensión `php` del nombre del archivo.
    
6. Pulsa `Add` para establecer la posición de fuzzing.
    

La petición tendrá una posición similar a esta:

```
Content-Disposition: form-data; name="uploadFile"; filename="HTB§.php§"
```

Los símbolos `§` representan la posición de prueba de Intruder.

### Paso 3. Cargar la lista de extensiones

En **Payloads**:

- Selecciona el tipo de ataque `Sniper`.
    
- Carga una lista de extensiones PHP, por ejemplo, de PayloadsAllTheThings o SecLists.
    
- Desactiva `URL Encoding` si es necesario para evitar que se codifique el punto de la extensión.
    
- Inicia el ataque con **Start Attack**.
    

Durante el fuzzing, mantén el contenido del archivo sin modificar: el objetivo es comprobar qué extensiones acepta el servidor.

### Paso 4. Analizar las respuestas

Busca diferencias entre las respuestas del servidor.

|Respuesta|Interpretación|
|---|---|
|`Extension not allowed`|La extensión ha sido rechazada por el filtro.|
|`File successfully uploaded`|La extensión ha superado la validación observada.|
|Respuesta diferente o longitud distinta|Puede indicar un comportamiento diferente que conviene investigar.|

En el ejemplo del módulo, las respuestas con una longitud de `193` correspondían a archivos aceptados.

**Importante:** una extensión aceptada no implica necesariamente que el servidor vaya a ejecutar el archivo como PHP.

## 3. Extensiones alternativas

Una blacklist puede bloquear extensiones comunes, pero dejar otras sin filtrar.

Entre las extensiones que conviene investigar en un laboratorio PHP se encuentran:

|Extensión|Observación|
|---|---|
|`.php`|Extensión PHP habitual; puede estar bloqueada.|
|`.php7`|Puede estar bloqueada explícitamente por la blacklist.|
|`.phps`|Puede estar bloqueada explícitamente por la blacklist.|
|`.phtml`|Puede ser interpretada como PHP según la configuración del servidor.|
|Variantes con mayúsculas|Pueden eludir comparaciones sensibles a mayúsculas y minúsculas, dependiendo del entorno.|

No existe una extensión alternativa que funcione en todas las configuraciones. Hay que comprobar tanto la aceptación del archivo como su interpretación por el servidor.

## 4. Explotación con `.phtml`

Si el fuzzing identifica `.phtml` como una extensión aceptada, podemos comprobar si el servidor también ejecuta PHP con ella.

### Paso 1. Modificar la petición

Envía la petición identificada a **Repeater** y modifica el nombre del archivo:

```
Content-Disposition: form-data; name="uploadFile"; filename="shell.phtml"
```

Para comprobar la ejecución en un laboratorio autorizado, utiliza una prueba PHP sencilla:

```
<?php echo "PHP ejecutado correctamente"; ?>
```

Envía la petición y comprueba si la aplicación confirma la subida.

### Paso 2. Acceder al archivo

Si el archivo se almacena en `profile_images`, prueba la ruta:

```
http://TARGET/profile_images/shell.phtml
```

Si aparece el texto `PHP ejecutado correctamente`, el servidor está interpretando el archivo como PHP.

En el laboratorio del módulo también se utiliza una web shell para comprobar la ejecución de comandos:

```
http://TARGET/profile_images/shell.phtml?cmd=id
```

Una respuesta que muestre el usuario del servidor, como `www-data`, confirma que el parámetro está llegando a una función que ejecuta comandos.

## 5. Flujo de trabajo para el laboratorio

1. Intentar subir un archivo PHP y observar la respuesta.
    
2. Si aparece `Extension not allowed`, sospechar de un filtro en el back-end.
    
3. Capturar la petición con Burp Suite.
    
4. Utilizar Intruder para probar extensiones alternativas.
    
5. Identificar las respuestas que indican que una extensión ha sido aceptada.
    
6. Comprobar si alguna extensión aceptada permite ejecutar PHP.
    
7. Verificar el resultado accediendo al archivo subido.
    

## 🎯 Chuleta para el examen

- **Blacklist:** bloquea extensiones incluidas en una lista; puede ser incompleta.
    
- **Whitelist:** permite únicamente extensiones expresamente autorizadas.
    
- **Fuzzing:** prueba múltiples extensiones para identificar cuáles acepta el servidor.
    
- **Burp Intruder:** automatiza las pruebas de extensiones.
    
- `**PATHINFO_EXTENSION**`**:** extrae la extensión del nombre del archivo en PHP.
    
- `**in_array()**`**:** comprueba si un valor aparece en un array PHP.
    
- `**.phtml**`**:** extensión que puede ejecutar PHP si el servidor está configurado para interpretarla.
    
- **Archivo aceptado ≠ código ejecutado:** hay que comprobar por separado la subida y la ejecución.
    
- **La validación del back-end es fundamental:** las restricciones del front-end se pueden manipular y una blacklist mal diseñada puede eludirse.
