
## 1. Concepto

Aunque una aplicación web tenga filtros seguros que impidan subir archivos arbitrarios o ejecutar PHP, algunos formatos permitidos pueden explotarse para introducir otras vulnerabilidades.

**Objetivo:** identificar las extensiones permitidas y comprobar qué ataques pueden realizarse mediante archivos manipulados.

|Formato|Posibles ataques|
|---|---|
|HTML|XSS almacenado y CSRF|
|SVG|XSS, XXE y SSRF mediante XXE|
|XML|XXE y SSRF mediante XXE|
|PDF, Word, PowerPoint|XXE si el visor procesa XML de forma vulnerable|
|JPG, PNG|XSS mediante metadatos o DoS|
|ZIP|Bomba de descompresión|
|Cualquier archivo permitido|DoS por tamaño excesivo, según las validaciones|

## 2. XSS mediante archivos subidos

El **XSS almacenado (Stored XSS)** permite ejecutar JavaScript en el navegador de una víctima cuando la aplicación muestra contenido malicioso previamente almacenado.

### 2.1. Archivos HTML

Si la aplicación permite subir archivos HTML, podemos incluir JavaScript en ellos.

```
<!DOCTYPE html>
<html>
<body>
    <script>
        alert(window.origin);
    </script>
</body>
</html>
```

**Procedimiento:**

1. Crear un archivo HTML con el código JavaScript.
    
2. Subirlo a la aplicación.
    
3. Acceder al archivo mediante su URL.
    
4. Comprobar si se ejecuta el JavaScript.
    

Aunque HTML no permita ejecutar PHP en el servidor, puede ejecutar JavaScript en el navegador de quien visite el archivo.

### 2.2. XSS mediante metadatos de imágenes

Algunas aplicaciones muestran los metadatos de las imágenes después de subirlas. Si los muestran sin escapar correctamente, pueden permitir XSS.

Podemos modificar el campo `Comment` utilizando `exiftool`:

```
exiftool -Comment=' "><img src=1 onerror=alert(window.origin)>' HTB.jpg
```

Comprobar los metadatos:

```
exiftool HTB.jpg
```

Buscar el campo `Comment` y verificar que contiene el payload.

**Condición:** la aplicación debe procesar o mostrar el contenido de forma vulnerable para que se ejecute el JavaScript.

Otra posibilidad es modificar el tipo MIME a `text/html`. Algunas aplicaciones podrían interpretar el archivo como HTML en lugar de como una imagen, aunque esto depende de cómo gestionen y sirvan el contenido.

### 2.3. XSS mediante imágenes SVG

Los archivos SVG están basados en XML y pueden incluir código JavaScript.

Crear `HTB.svg`:

```
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE svg PUBLIC "-//W3C//DTD SVG 1.1//EN" "http://www.w3.org/Graphics/SVG/1.1/DTD/svg11.dtd">
<svg xmlns="http://www.w3.org/2000/svg" version="1.1" width="1" height="1">
    <rect x="1" y="1" width="1" height="1" fill="green" stroke="black" />
    <script type="text/javascript">alert(window.origin);</script>
</svg>
```

Subir el archivo y acceder a él o visualizarlo en la aplicación.

**Importante:** el JavaScript no se ejecuta necesariamente en todos los contextos en los que se muestra una imagen SVG. Depende de cómo el navegador y la aplicación procesen el archivo.

## 3. XXE mediante SVG y XML

**XXE (XML External Entity)** es una vulnerabilidad que aparece cuando un procesador XML interpreta entidades externas definidas por el usuario de forma insegura.

Puede permitir leer archivos locales del servidor y, dependiendo del contexto, obtener código fuente de la aplicación.

### 3.1. Leer `/etc/passwd`

Crear un SVG con una entidad XML externa:

```
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE svg [
    <!ENTITY xxe SYSTEM "file:///etc/passwd">
]>
<svg>&xxe;</svg>
```

**Procedimiento:**

1. Guardar el contenido en un archivo SVG.
    
2. Subirlo a la aplicación.
    
3. Provocar que el servidor procese o muestre el XML.
    
4. Comprobar si el contenido de `/etc/passwd` aparece en la respuesta o en el código fuente de la página.
    

Esto solo funcionará si el procesador XML permite la resolución de entidades externas y la aplicación expone el resultado.

### 3.2. Leer el código fuente PHP mediante `php://filter`

También podemos intentar obtener el código fuente de un archivo PHP codificado en Base64.

```
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE svg [
    <!ENTITY xxe SYSTEM "php://filter/convert.base64-encode/resource=index.php">
]>
<svg>&xxe;</svg>
```

Si la aplicación procesa el payload de forma vulnerable, la respuesta podría contener el código fuente de `index.php` codificado en Base64.

Decodificar el resultado:

```
echo 'BASE64_OBTENIDO' | base64 -d
```

**¿Por qué es útil?**

El código fuente puede revelar:

- El directorio donde se almacenan los archivos subidos.
    
- Las extensiones permitidas.
    
- El mecanismo de validación de archivos.
    
- El sistema utilizado para nombrar los archivos.
    
- Otras vulnerabilidades explotables.
    

### 3.3. XXE en otros documentos

Los archivos PDF, Word y PowerPoint pueden contener estructuras XML internas.

Si una aplicación utiliza un visor de documentos vulnerable que procesa esas estructuras, un documento manipulado podría permitir un ataque XXE, incluso de tipo _blind XXE_ cuando los resultados no se muestran directamente.

### 3.4. Relación entre XXE y SSRF

XXE también puede utilizarse para intentar acceder a servicios internos del servidor.

Dependiendo de las restricciones del procesador XML y de la red, esto podría permitir:

- Enumerar servicios internos.
    
- Consultar recursos accesibles únicamente desde el servidor.
    
- Interactuar con APIs privadas.
    

Este comportamiento puede derivar en una vulnerabilidad **SSRF (Server-Side Request Forgery)**.

## 4. Denegación de servicio (DoS)

Una subida de archivos vulnerable puede provocar un consumo excesivo de recursos y afectar a la disponibilidad del servidor.

### 4.1. Bomba de descompresión

Una bomba de descompresión utiliza archivos comprimidos que generan una cantidad de datos descomprimidos desproporcionadamente grande.

Ejemplo: un archivo ZIP que contiene otros ZIP anidados.

Si la aplicación descomprime automáticamente el archivo sin límites adecuados, puede provocar:

- Consumo excesivo de memoria.
    
- Agotamiento del almacenamiento.
    
- Sobrecarga de CPU.
    
- Caída del servicio.
    

### 4.2. Pixel Flood

Algunas imágenes comprimidas pueden declarar dimensiones extremadamente grandes en sus cabeceras.

Si una aplicación procesa una imagen con dimensiones manipuladas, puede intentar reservar demasiada memoria para decodificarla o representarla.

**Posibles consecuencias:**

- Consumo excesivo de memoria.
    
- Agotamiento de recursos.
    
- Caída del proceso que procesa la imagen.
    

### 4.3. Archivos excesivamente grandes

Si la aplicación no limita adecuadamente el tamaño de los archivos, subir un archivo enorme puede llenar el disco del servidor o ralentizar el servicio.

Hay que comprobar si existen límites de tamaño tanto en el cliente como en el servidor. La validación del lado del cliente, por sí sola, no es suficiente.

### 4.4. Directory Traversal durante la subida

Si la aplicación permite controlar la ruta de destino sin validarla correctamente, un atacante podría intentar escribir archivos fuera del directorio previsto.

Ejemplo conceptual de una ruta manipulada:

```
../../../ruta/destino
```

Las consecuencias dependen de los permisos del proceso web y del destino de escritura. Una escritura fuera del directorio de subida podría sobrescribir archivos o afectar al funcionamiento del sistema.

## 5. Metodología de enumeración

Cuando no sea posible subir un archivo ejecutable, no debemos dar por terminada la evaluación.

1. **Enumerar las extensiones permitidas.** Probar de forma controlada los formatos aceptados por la aplicación.
    
2. **Identificar cómo se procesa cada formato.** Comprobar si el archivo se muestra directamente, si se procesan sus metadatos o si se utiliza un visor.
    
3. **Evaluar XSS.** Revisar HTML, SVG y metadatos de imágenes.
    
4. **Evaluar XXE.** Comprobar si los archivos XML o documentos que contienen XML se procesan mediante un parser vulnerable.
    
5. **Valorar SSRF.** Si existe XXE, determinar si puede utilizarse para acceder a recursos internos.
    
6. **Revisar riesgos de DoS.** Comprobar límites de tamaño, descompresión y procesamiento de imágenes.
    
7. **Analizar las rutas de almacenamiento.** Revisar si es posible manipular el nombre o la ubicación del archivo.
    

Realizar las pruebas únicamente en laboratorios o sistemas para los que se tenga autorización.

## 🎯 Chuleta para el examen

|Técnica|Requisito principal|Resultado posible|
|---|---|---|
|XSS mediante HTML|La aplicación permite subir HTML y una víctima lo visita|Ejecución de JavaScript|
|XSS mediante metadatos|Los metadatos se muestran sin escapar correctamente|XSS almacenado|
|XSS mediante SVG|El SVG se procesa en un contexto que permite ejecutar su JavaScript|Ejecución de JavaScript|
|XXE mediante SVG/XML|Parser XML vulnerable a entidades externas|Lectura de archivos locales|
|XXE con `php://filter`|XXE explotable y acceso al wrapper desde el contexto vulnerable|Código fuente PHP en Base64|
|SSRF mediante XXE|XXE explotable y acceso a recursos internos|Consultas a servicios internos|
|Bomba de descompresión|Descompresión sin límites suficientes|Agotamiento de recursos|
|Pixel Flood|Procesamiento de imágenes con dimensiones manipuladas|Consumo excesivo de memoria|
|Archivo excesivamente grande|Límites de tamaño insuficientes|Agotamiento del almacenamiento|
|Directory Traversal|Ruta de destino manipulable y escritura fuera del directorio permitido|Sobrescritura de archivos o daños al servicio|

**Idea clave:** una lista blanca de extensiones puede impedir la subida de archivos ejecutables, pero no garantiza que los archivos permitidos sean seguros. Hay que analizar también cómo se interpretan, procesan y muestran.
