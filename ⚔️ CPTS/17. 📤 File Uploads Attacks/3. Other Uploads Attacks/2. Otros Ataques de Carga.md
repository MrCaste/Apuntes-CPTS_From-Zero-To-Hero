
## 1. Inyecciones en el nombre del archivo

El nombre de un archivo subido puede convertirse en un vector de ataque si la aplicación lo utiliza de forma insegura.

### 1.1. Command Injection

Si la aplicación utiliza el nombre del archivo dentro de un comando del sistema operativo sin sanearlo correctamente, podría permitir la ejecución de comandos.

Ejemplos de nombres maliciosos:

```
file$(whoami).jpg
file`whoami`.jpg
file.jpg||whoami
```

Por ejemplo, si el servidor utiliza el nombre del archivo dentro de un comando como `mv`, una concatenación insegura podría permitir inyectar comandos.

**Condición:** la aplicación debe procesar el nombre mediante un comando vulnerable. Que el nombre contenga caracteres especiales no implica, por sí solo, que exista una vulnerabilidad.

### 1.2. XSS mediante el nombre del archivo

Si el nombre del archivo se muestra en una página web sin escapar correctamente los caracteres HTML, podría ejecutarse JavaScript.

Payload de ejemplo:

```
<script>alert(window.origin);</script>
```

**Condición:** el nombre debe reflejarse en un contexto HTML vulnerable.

### 1.3. SQL Injection mediante el nombre del archivo

Si el nombre del archivo se incorpora de forma insegura a una consulta SQL, podría producirse una inyección SQL.

Ejemplo de nombre:

```
file';select+sleep(5);--.jpg
```

**Condición:** el nombre debe incorporarse a una consulta vulnerable sin utilizar consultas parametrizadas ni una validación adecuada.

## 2. Divulgación del directorio de carga

En ocasiones, la aplicación permite subir archivos, pero no muestra su URL ni revela dónde los almacena.

Conocer el directorio de subida puede ayudar a localizar archivos, comprender cómo se nombran y preparar una explotación posterior.

### 2.1. Fuzzing de directorios

Se pueden utilizar herramientas de enumeración para descubrir posibles directorios de subida.

Ejemplo con `ffuf`:

```
ffuf -w /ruta/a/wordlist.txt -u http://TARGET/FUZZ
```

Hay que analizar las respuestas y comprobar si los directorios encontrados corresponden realmente al almacenamiento de archivos subidos.

### 2.2. Aprovechar otras vulnerabilidades

Otras vulnerabilidades pueden revelar la ubicación de los archivos:

- **LFI:** puede permitir leer archivos locales y, en determinadas condiciones, el código fuente de la aplicación.
    
- **XXE:** puede permitir leer archivos locales si el procesador XML es vulnerable.
    
- **IDOR:** puede ayudar a descubrir cómo se accede a archivos de otros usuarios o cómo se identifican los recursos.
    

El código fuente puede revelar el directorio de subida, las extensiones permitidas y el esquema de nomenclatura.

### 2.3. Provocar errores

Los mensajes de error pueden revelar rutas internas e información útil para la enumeración.

Pruebas descritas en el módulo:

- Subir un archivo cuyo nombre ya exista.
    
- Enviar dos solicitudes idénticas simultáneamente.
    
- Probar nombres de archivo excesivamente largos, por ejemplo, de 5.000 caracteres.
    

Si la aplicación maneja incorrectamente estos casos, puede mostrar errores que revelen el directorio de almacenamiento.

**Importante:** estas técnicas no garantizan que se revele la ruta; depende de cómo la aplicación gestione los errores.

## 3. Ataques específicos de Windows

### 3.1. Caracteres reservados

Windows reserva determinados caracteres para usos especiales, entre ellos:

```
| < > * ?
```

Si la aplicación no sanea correctamente los nombres de archivo, estos caracteres pueden provocar errores durante su procesamiento o almacenamiento.

Los errores podrían revelar rutas internas u otra información sobre el servidor.

### 3.2. Nombres reservados de Windows

Algunos nombres están reservados por el sistema operativo y no se pueden utilizar normalmente como nombres de archivo.

Ejemplos:

```
CON
COM1
LPT1
NUL
```

Intentar utilizar estos nombres en una subida puede provocar errores si la aplicación no los gestiona correctamente.

### 3.3. Convención de nombres 8.3

Windows puede admitir nombres cortos compatibles con la convención **8.3**, utilizada históricamente para representar nombres largos mediante una versión abreviada.

Ejemplos mencionados en el módulo:

```
HAC~1.TXT
HAC~2.TXT
WEB~1.CON
```

El número después de `~` puede representar el orden de los nombres coincidentes.

En determinadas condiciones, esta convención puede utilizarse para referirse a archivos existentes mediante nombres abreviados. Si una aplicación vulnerable permite escribir en ubicaciones o archivos no previstos, esto puede contribuir a:

- Divulgación de información.
    
- Sobrescritura de archivos.
    
- Denegación de servicio.
    
- Acceso no autorizado a archivos.
    

**Precaución:** la existencia de nombres cortos no garantiza que sea posible sobrescribir un archivo. Depende de la configuración del sistema, de los nombres existentes y de los permisos de escritura.

## 4. Ataques avanzados de carga de archivos

Los archivos subidos suelen procesarse automáticamente. Estas operaciones también pueden introducir vulnerabilidades.

Ejemplos de procesamiento:

- Codificación de vídeos.
    
- Compresión de archivos.
    
- Conversión entre formatos.
    
- Extracción de archivos.
    
- Modificación de imágenes.
    
- Renombrado y almacenamiento.
    

Si el procesamiento se realiza mediante bibliotecas vulnerables o código personalizado inseguro, la subida puede convertirse en el punto de entrada de otros ataques.

### Ejemplo: FFmpeg y archivos AVI

El módulo menciona vulnerabilidades relacionadas con archivos AVI que pueden provocar XXE en determinadas versiones o configuraciones de FFmpeg.

La idea principal es que **un archivo puede ser aceptado correctamente por el formulario y, aun así, explotar una vulnerabilidad en el componente que lo procesa después**.

Para investigar estos casos, conviene identificar:

1. El formato aceptado.
    
2. El procesamiento automático aplicado al archivo.
    
3. Las bibliotecas o herramientas utilizadas.
    
4. Las versiones y vulnerabilidades conocidas.
    
5. Los errores que aparecen durante el procesamiento.
    

Las vulnerabilidades avanzadas pueden requerir analizar el código fuente, el funcionamiento de las bibliotecas y los informes públicos de bug bounty.

## 🎯 Chuleta para el examen

|Técnica|Qué comprobar|Posible impacto|
|---|---|---|
|Command Injection|Si el nombre se utiliza en comandos del sistema operativo|Ejecución de comandos|
|XSS en el nombre|Si el nombre se refleja sin escapar en HTML|Ejecución de JavaScript|
|SQL Injection en el nombre|Si se concatena en consultas SQL|Inyección SQL|
|Fuzzing de directorios|Si existen rutas públicas de almacenamiento|Descubrimiento del directorio de subida|
|Errores de subida|Nombres duplicados, solicitudes simultáneas y nombres largos|Divulgación de rutas e información interna|
|Caracteres reservados de Windows|Si el nombre provoca errores o un procesamiento inesperado|Divulgación de información|
|Nombres reservados|`CON`, `COM1`, `LPT1`, `NUL`|Errores y posible filtración de información|
|Nombres 8.3|Si el sistema admite nombres cortos y cómo los resuelve|Referencia a archivos existentes y posibles ataques posteriores|
|Procesamiento automático|Conversión, compresión, extracción o manipulación de archivos|Explotación de bibliotecas o código vulnerable|

### Idea clave

No hay que limitarse a comprobar si se puede subir un archivo ejecutable. También hay que analizar **cómo se procesa el nombre, dónde se almacena el archivo y qué componentes lo manipulan después de la subida**.
