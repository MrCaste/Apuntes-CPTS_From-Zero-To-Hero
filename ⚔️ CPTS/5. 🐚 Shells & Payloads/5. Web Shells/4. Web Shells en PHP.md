
## 1. ¿Qué es PHP?

**PHP (Hypertext Preprocessor)** es un lenguaje de programación que se ejecuta en el lado del servidor y se utiliza habitualmente en aplicaciones web.

Cuando un servidor web utiliza PHP, los archivos `.php` pueden procesar solicitudes y ejecutar código en el servidor.

Desde el punto de vista del pentesting, si encontramos una vulnerabilidad que permita subir y ejecutar un archivo PHP, podríamos conseguir una **Web Shell** para ejecutar comandos en el sistema operativo subyacente.

### Ejemplo: rConfig

En las secciones anteriores vimos que rConfig utiliza PHP. Esto nos permite investigar si existe alguna funcionalidad vulnerable que permita subir un archivo PHP y ejecutarlo en el servidor.

---

## 2. PHP Web Shell

Una Web Shell PHP es un archivo PHP que permite ejecutar comandos en el servidor y devolver sus resultados a través del navegador.

En este ejercicio, HTB utiliza una Web Shell de **WhiteWinterWolf** para demostrar cómo una vulnerabilidad de subida de archivos puede proporcionar acceso al sistema.

El objetivo del laboratorio es aprovechar una vulnerabilidad de rConfig 3.9.6 para subir un archivo PHP e interactuar con el servidor Linux.

---

## 3. Identificar la funcionalidad vulnerable

En el laboratorio, el procedimiento inicial consiste en:

1. Acceder a rConfig.
    
2. Iniciar sesión con las credenciales indicadas en el ejercicio (`admin:admin`).
    
3. Navegar hasta `Devices > Vendors`.
    
4. Seleccionar `Add Vendor`.
    
5. Localizar el campo para subir el logotipo del proveedor.
    

La funcionalidad permite asociar una imagen a un proveedor, pero inicialmente restringe los tipos de archivo que se pueden subir.

El objetivo es comprobar si esa validación puede eludirse y si el archivo subido termina en una ubicación desde la que el servidor pueda ejecutarlo.

---

## 4. Interceptar la petición con Burp Suite

**Burp Suite** permite interceptar y modificar las peticiones HTTP que intercambian el navegador y el servidor.

Para utilizarlo en el laboratorio, configura el proxy del navegador con los siguientes valores:

|Parámetro|Valor|
|---|---|
|Dirección del proxy|`127.0.0.1`|
|Puerto|`8080`|

Con el proxy configurado:

1. Inicia la interceptación en Burp.
    
2. Selecciona el archivo que quieres subir desde el formulario.
    
3. Envía la solicitud.
    
4. Localiza la petición HTTP `POST` que contiene el archivo.
    
5. Examina las cabeceras y los datos de la petición.
    

### Cabecera `Content-Type`

El encabezado `Content-Type` indica el tipo de contenido declarado en una petición HTTP.

En el ejercicio, la aplicación espera archivos de imagen, pero se intenta subir un archivo PHP.

El material muestra una modificación de:

```
Content-Type: application/x-php
```

a:

```
Content-Type: image/gif
```

Esta modificación pretende que el archivo sea presentado como una imagen ante la validación de la aplicación.

**Importante:** cambiar `Content-Type` no convierte un archivo PHP en una imagen ni garantiza que se pueda eludir la validación. El resultado depende de cómo el servidor compruebe el archivo y de cómo gestione su almacenamiento y ejecución.

---

## 5. Comprobar si la subida ha funcionado

Después de enviar la petición, debemos comprobar la respuesta de la aplicación.

En el laboratorio, aparece el mensaje:

```
Added new vendor NetVen to Database
```

Esto indica que se ha añadido el proveedor `NetVen`.

El logotipo aparece como una imagen rota porque la aplicación no reconoce el archivo PHP como una imagen válida.

Sin embargo, que el proveedor se haya añadido correctamente no demuestra por sí solo que el archivo sea ejecutable.

Para verificar el resultado, debemos comprobar dónde se ha almacenado el archivo y si el servidor permite acceder a él y ejecutarlo.

---

## 6. Acceder a la Web Shell

En la demostración, el archivo se guarda en el directorio:

```
/images/vendor/
```

La ruta indicada en el material es:

```
/images/vendor/connect.php
```

Si el servidor permite ejecutar el archivo PHP en esa ubicación, acceder a él puede abrir la interfaz de la Web Shell en el navegador.

La shell permite enviar comandos al sistema operativo Linux y recibir sus resultados.

El acceso inicial dependerá de los permisos del proceso web y de las restricciones aplicadas por el servidor.

---

## 7. Limitaciones de las Web Shells

Las Web Shells pueden ser útiles para obtener acceso inicial, pero presentan varias limitaciones.

### Archivos eliminados automáticamente

Algunas aplicaciones eliminan los archivos subidos después de un periodo determinado.

Esto puede provocar que la Web Shell deje de funcionar.

### Interactividad limitada

Una Web Shell basada en navegador no proporciona necesariamente una terminal interactiva completa.

Entre sus limitaciones pueden encontrarse:

- Navegación limitada por el sistema de archivos.
    
- Dificultades para subir y descargar archivos.
    
- Problemas al encadenar comandos.
    
- Falta de funcionalidades propias de una terminal.
    
- Inestabilidad durante la enumeración.
    

Por ejemplo, una operación que intente ejecutar varios comandos encadenados puede no comportarse igual que en una shell interactiva.

### Evidencias en el sistema

La subida y ejecución de archivos puede dejar rastros en el servidor, como:

- Archivos nuevos.
    
- Registros de peticiones HTTP.
    
- Entradas en bases de datos.
    
- Registros de errores o ejecución.
    

Durante un pentest autorizado, debemos documentar las acciones realizadas y sus resultados.

## 8. Web Shell y Reverse Shell

Una Web Shell puede servir como punto de entrada inicial para investigar el sistema.

Sin embargo, la interacción desde el navegador puede resultar limitada.

|Característica|Web Shell|Reverse Shell|
|---|---|---|
|Interfaz|Navegador web|Sesión de terminal|
|Ejecución de comandos|A través de la aplicación web|Mediante una conexión de shell|
|Interactividad|Generalmente limitada|Puede ser más completa|
|Dependencia del archivo web|Normalmente sí|No necesariamente después de establecer la sesión|
|Limitaciones|Aplicación, archivo y permisos|Conectividad, permisos y tipo de shell|

En determinados escenarios de laboratorio, puede ser conveniente obtener una shell más interactiva para facilitar la enumeración del sistema.

## 9. Documentación durante el pentest

Durante una evaluación autorizada, conviene registrar los resultados para poder reproducirlos y documentarlos correctamente.

Podemos anotar:

- La vulnerabilidad identificada.
    
- La funcionalidad afectada.
    
- El nombre del archivo utilizado.
    
- La ubicación donde se almacenó.
    
- El resultado de las pruebas.
    
- Los permisos de la cuenta que ejecuta los comandos.
    
- Las evidencias relevantes para el informe.
    

También pueden utilizarse hashes, como SHA-256, para identificar los archivos empleados durante las pruebas.

Ejemplo:

```
sha256sum <archivo>
```

Esto permite registrar una huella del archivo utilizado.

## 10. Metodología práctica

1. **Enumerar la aplicación:** identificar la tecnología y su versión.
    
2. **Investigar la vulnerabilidad:** comprobar si existe una funcionalidad de subida de archivos vulnerable.
    
3. **Identificar las validaciones:** determinar qué tipos de archivo permite la aplicación.
    
4. **Analizar la petición:** utilizar Burp Suite para examinar la solicitud HTTP.
    
5. **Comprobar la subida:** verificar la respuesta de la aplicación y la ubicación del archivo.
    
6. **Verificar la ejecución:** comprobar si el servidor interpreta el archivo PHP.
    
7. **Enumerar el sistema:** identificar el usuario y los permisos disponibles.
    
8. **Evaluar las limitaciones:** determinar si la Web Shell es suficiente para las pruebas.
    
9. **Documentar los resultados:** registrar los archivos, rutas y evidencias relevantes.
    

---

## 11. Ideas clave para el examen

- PHP es un lenguaje de programación del lado del servidor.
    
- Una Web Shell PHP puede permitir ejecutar comandos a través del navegador.
    
- Las funcionalidades de subida de archivos pueden representar un punto de entrada.
    
- Burp Suite permite interceptar y analizar peticiones HTTP.
    
- `Content-Type` declara el tipo de contenido de una petición, pero no garantiza que el archivo sea realmente de ese tipo.
    
- La subida correcta de un archivo no demuestra que el servidor permita ejecutarlo.
    
- La ruta de almacenamiento y la configuración del servidor determinan si el archivo puede ejecutarse.
    
- Una Web Shell puede tener limitaciones de interactividad y estabilidad.
    
- Durante un pentest autorizado, debemos documentar las acciones y evidencias.
    
- El acceso obtenido utiliza los permisos del proceso web; conseguir una Web Shell no implica obtener privilegios de `root`.
